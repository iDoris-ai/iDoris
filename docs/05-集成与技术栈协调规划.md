## 0. 一句话结论（先给答案）

> **集成契约 = REST（OpenAI-compat HTTP）+ 进程边界。** iDoris 是一个"编排进程"，把每个能力组件当作**独立进程**、用 **HTTP/REST** 调；内部组件用什么语言（Python/Go/Node/Rust）不重要，**只要它在进程边界上说 OpenAI-compat（或 Nostr/HTTP）**。组件以**二进制/CLI/容器**形态引入、**不 vendor 源码**——与 Agent24 既定的 `进程边界=授权边界`（SPEC-001 §10 / G3）完全一致。这条一旦定死，整个生态天然兼容、可换、可升级、许可清晰。

---

## 1. 为什么是 REST + 进程边界（而非 import / 同语言）

### 1.1 现状：生态本就是多语言（polyglot）
| 仓库 | 语言/栈 | 对外接口 |
|---|---|---|
| **Agent24** | Rust 内核（agent24d）+ TS（node-daemon / bridges / Electron）+ pnpm | HTTP v1 (OpenAI-compat)、WS 事件、CLI |
| **agent-speaker** | **Go** CLI（Nostr + nak submodule）| CLI + Nostr（NIP-44）|
| **auraai-packages** | **TS** / pnpm（@auraaihq/idoris 网关契约、sdk、core、memory）| npm import + Adapter/Bridge 契约 |
| **iDoris-SDK** | **TS**（平台桥接 WeChat/Telegram…）| Agent interface + 各平台协议 |
| 拟引入组件 | LiteLLM(Py+Rust)、ClawRouter/OmniRoute(TS)、llama-swap(Go)、onecli(Rust)、Flower(Py)、MLX(Py/C++) | **全部 OpenAI-compat HTTP / CLI** |

**结论**：强求"同一语言 / 直接 import"不可能也没必要。生态早已在**进程边界上用 HTTP/Nostr/CLI 说话**——iDoris 顺着这条既有事实做统一即可。

### 1.2 为什么进程边界是对的（不只是权宜）
- **稳定**：组件崩溃/升级不波及 iDoris；健康检查+重启+fallback 已是 Agent24 `ModelRouter` 标配。
- **许可干净**：包二进制不复制源码 → 可合法集成 GPL/非商用上游（Agent24 SPEC-001 §10 已论证）。
- **可换**：ClawRouter↔LiteLLM↔OmniRoute、llama.cpp↔MLX↔vLLM 都在 OpenAI-compat 契约后可互换。
- **可取消/可审批**：跨进程调用天然可 kill、可经 Agent24 审批门（C4/D3）。
- **语言自由**：内部临时方案随便用 Python/Go/Node，验证后可按需内化进 Rust——不锁死。

## 2. LLM 组件：exe 还是源码？—— 分发形态治理

| 组件类型 | 推荐形态 | 理由 | 例 |
|---|---|---|---|
| **推理引擎** | **二进制 / 预编译**（brew/release/GGUF+llama.cpp、MLX pip、Ollama app）| 不 vendor，版本可 pin，升级解耦 | llama.cpp、mlx-lm、Ollama |
| **模型权重** | **内容寻址下载**到统一目录（`~/.omlx/models/`），签名校验 | 与 Agent24 oMLX 一致；registry 治理（文档 04 I2）| Ornith GGUF、Agents-A1 |
| **路由/网关** | **独立进程 + HTTP**（npx/单二进制/容器）| OpenAI-compat 后可换 | ClawRouter(npx)、OmniRoute、LiteLLM |
| **凭证网关** | **独立进程 + MITM/HTTP**（Rust）| 密钥不进 agent 上下文 | onecli 模式 |
| **联邦训练** | **Python 进程 + gRPC/HTTP**，按需拉起 | 训练是离线批处理，不常驻 | Flower + PEFT + mlx-lm |
| **订阅中转** | **subprocess 驱动 CLI**（claude/codex）封 HTTP | 进程边界=授权边界（G3）| agent-cli-to-api 模式 |

**硬规则**：
1. **不 vendor 第三方源码**（除非需 patch 的协议层用 submodule 固定 commit，如 agent-speaker 的 nak）。
2. **一切经 pin 的版本**（二进制版本号 / 容器 tag / commit / 模型指纹），杜绝"悄悄升级破坏兼容"。
3. **每个组件在进程边界只暴露 OpenAI-compat HTTP 或既有协议（Nostr/CLI）**，不暴露语言特定 SDK 作为跨仓库契约。

## 3. iDoris 目标集成架构（进程拓扑）

```
                         ┌─────────────── 对外：统一本地 URL (OpenAI-compat) ───────────────┐
   Agent24 / 渠道 / 业务 │  http://127.0.0.1:PORT/v1   (Mac mini + Tailscale 可远程同址)     │
   (Rust+TS / Go / …) ──▶└───────────────────────────────┬─────────────────────────────────┘
                                          ┌──────────────▼───────────────┐
                                          │      iDoris Router (进程)      │  ← 我们自研的薄编排层
                                          │  意图路由/隐私标签/订阅门禁/    │    (可先 TS/Go 起，后内化 Rust)
                                          │  业务能力组合/用量/审批接线      │
                                          └──┬──────────────┬───────────┬──┘
                     ┌───────── REST ────────┘      REST    │    REST   └──── subprocess+REST ──┐
                     ▼                               ▼       ▼                                   ▼
        ┌────────────────────────┐   ┌──────────────────────────┐   ┌────────────────────────────┐
        │ 能力② 外部API 路由/网关 │   │ 能力③ 本地模型编排         │   │ 能力① 订阅中转              │
        │ ClawRouter / OmniRoute  │   │ llama-swap (TTL 常驻/临时) │   │ agent-cli-to-api 模式:       │
        │ / LiteLLM (择一/组合)   │   │  → MLX / llama.cpp / vLLM │   │ 驱动本地 claude/codex CLI    │
        │ (OpenAI-compat :端口)   │   │ (OpenAI-compat :端口)     │   │ (loopback+单用户)            │
        └────────────┬───────────┘   └──────────────────────────┘   └────────────────────────────┘
                     │ 出站凭证注入(可选)
              ┌──────▼──────┐        ┌──────────────────────────────┐
              │ onecli 模式  │        │ 联邦训练进程(离线,按需拉起)    │
              │ Rust 凭证网关│        │ Flower + PEFT + mlx-lm (Python)│
              └─────────────┘        └──────────────────────────────┘
```

**级联事实（已被业界实证）**：`业务 → 路由(ClawRouter/OmniRoute/LiteLLM) → llama-swap → {MLX/llama.cpp}`，全链 OpenAI-compat，iDoris Router 只在最上层加"意图+隐私+订阅门禁+业务组合"。

## 4. 组件选型建议（优先参考你 blog 收录的项目）

> 你的 blog 已为特定方向收录了成熟项目，以下选型**先采你收录的**，通用方案作备选。

> **优先级（U0 后定稿，local-first）**：`③ 本地模型(核心) > ① 订阅中转(可选) > ② 外部API(罕用逃生口)`。

| 能力 | 首选 | 备选 | 判据 |
|---|---|---|---|
| ③本地模型（核心）| **按平台选**（LoadPolicy 契约后可换）：macOS→**oMLX**(U0实测通过)；Win/Linux→**vLLM/llama.cpp/Ollama** | 同契约任一后端 | ⚠️ **不写死 oMLX**——它仅 Apple Silicon；Agent24 要分发 Win/Linux/Mac，按 OS/硬件探测选后端（见 [06 §10.3 跨平台约束](./06-组件接口契约与互换标准.md)）|
| ①订阅中转（可选）| agent-cli-to-api 模式（`claude -p`/`codex exec`，**U0 实测通过**）| CLIProxyAPI | best-effort，不作核心必需 fallback（S3）|
| ②外部 API（可选/罕用）| 需要时再引 **OmniRoute/ClawRouter/LiteLLM** 之一 | — | local-first；只做 OpenAI-compat 冒烟，Anthropic/Gemini 保真度等真实消费者再做 |
| 凭证安全 | **onecli 模式**(Rust MITM) 或 CredentialProvider 抽象 | env/vault | 出站外部 API 的 key 保护 |
| 联邦 | Flower + PEFT + mlx-lm | OpenFedLLM | 文档 03/04 |

> **决策变更（U0 实测）**：原计划用 llama-swap 做"常驻/临时"，实测发现 **oMLX 原生已具备**（多模型+LRU+memory-guard，KV 估算与 07 公式一致），故 **capability③ = oMLX，不装 llama-swap**（详见 [spike/u0/U0-LOG.md](../spike/u0/U0-LOG.md)）。llama-swap 仅保留为"将来混非-MLX 引擎"的备选，且在 [06 §10.3 LoadPolicy](./06-组件接口契约与互换标准.md) 抽象后可换。
> **能力② 不再是 Spike 关键路径**（local-first + 无 Anthropic/Gemini key）；等真实需求出现再对比 OmniRoute/ClawRouter/LiteLLM。

## 5. 核心模型选定（Mac mini M4 24GB）

**你看好的"横向扩展 / 以小打大"路线成立且有现成开源模型**——正是 blog 收录的两个：

| 模型 | 路线 | 战绩 | Mac 实测 | 适配 iDoris |
|---|---|---|---|---|
| **Ornith-1.0**（deepreinforce-ai, MIT）| 自改进脚手架 RL（同时优化"路径"和"答案")| **9B 打 Qwen3.5-35B；35B MoE 打 397B**；256K 上下文 | **16GB Mac mini 60 t/s**（9B GGUF）| coding/agent 强；Mac 亲和 |
| **Agents-A1**（上海AI Lab, 开源）| Horizon Scaling（KAG+自博弈，非堆参数）| **35B MoE 追平 Kimi-K2.6/GPT-5.5 等万亿模型** | 35B MoE 4bit ≈18GB（24GB 偏紧但 MoE 激活少）| 通用长程 agent 强 |

**M4 24GB 落地决策（经 [07 内存评估](./07-模型量化内存评估与动态推荐.md) 算账后修正）**：
- **常驻核心 = Ornith-1.0-9B @ Q6_K（32K, Q8 KV）**：~9.8GB，近无损(~99.5%)、60 t/s 量级、推理/脚手架强；24GB 上舒适且能同时挂一个临时小模型。**推理为核心能力**（对齐你的定义），可换。
- **临时（可与 9B 共存）** = Qwen2.5-VL-3B（视觉/banner）/ whisper-turbo（ASR）/ Kokoro-82M（TTS），均 ≤2GB。
- **重 coding 临时** ≈ Qwen2.5-Coder-14B @ Q4（~8GB，与 9B 临界共存）。
- **⚠️ 35B MoE 修正**：**24GB 撑不住**——FP16=70GB，Q4≈19GB 吃满内存、需驱逐常驻 9B + 激进 wired + 短上下文，不实用；Q3 放得下但推理退化。**35B 标注"32GB+ 推荐"，24GB 不作默认**（详细算账见 07 §4）。
- **可换机制**：`IDORIS_CORE_MODEL` 配置项 + **动态推荐模块**（07 §5）按硬件自动选：16GB→Ornith-9B(Q4/Q5)；24GB→Ornith-9B(Q6_K)；32GB+→可上 35B MoE。

> 记账修正：24GB 实用天花板 = **9B 常驻 + ≤14B 临时**；同时常驻两个大模型不现实——llama-swap TTL 负责按需换入换出。

## 6. 跨仓库协调（谁调谁、在哪对齐）

| 关系 | 集成方式 | 对齐点 |
|---|---|---|
| **Agent24 → iDoris** | Agent24 `ModelRouter` 把 iDoris 统一 URL 作为一个 provider（`IDORIS_URL`，纯加法）| OpenAI-compat HTTP；隐私标签 `TaskProfile` 复用 |
| **iDoris → agent-speaker** | 需要 Nostr 通信（节点发现/联邦握手）时，subprocess 驱动 agent-speaker(Go) CLI | 复用 Agent24 nostr-bridge 已验证的 subprocess 模式 |
| **iDoris ↔ @auraaihq/idoris** | TS 侧消费者用网关 Adapter/Bridge 契约；Rust 侧走 REST | provider 家族枚举（idoris/claude/openai/local）统一 |
| **iDoris → 渠道(微信/Nostr)** | 渠道 bridge 调 iDoris 统一 URL（同 Agent24 wechat/nostr-bridge 现状）| Agent interface / OpenAI-compat |
| **身份/签名** | 联邦/社区互认用 AirAccount DID + Agent24 M5 模块签名 | Mycelium 信任根 |

**统一 lingua franca**：**OpenAI-compat HTTP**（模型调用）+ **Nostr**（去中心通信/发现）+ **DID**（身份）。三者是整个生态的"普通话"，任何新组件只要会说其一即可接入。

## 7. 合规立场更新（能力①订阅中转，采纳你的判断）

**采纳你的论证**：个人把**自己的** Claude Code / Codex 订阅转成本地 API 供**自己**使用，是**用户对自有资产的正当使用**——开源、非商业、不干预服务方、不转售。这**合理**；ToS 层面属未明确禁止的灰区（"不一定合法但也没说不允许"）。

**据此的设计立场**（不再用"红线"框定，改为"边界"）：
- 能力① **默认 loopback + 单用户本地自用**——这是尊重 ToS 灰区的**保守默认**，也保护用户自己。
- **社区端 / 城市端绝不转发个人订阅**：不是合规洁癖，而是"个人订阅是个人资产，多租户转发既超出自用范畴、也会触碰服务方明确红线"。社区/城市端用自己的 API（能力②）或自己的本地模型（能力③）。
- 提供开关：用户可自行决定是否放开到局域网（Tailscale 自用多设备属"个人自用"延伸，合理）。

## 8. ✅ Spike 前确认清单（请你拍板）

在动手做技术验证前，请确认以下 5 条集成基线；确认后我按文档 01 §6 的 U0 Spike 开工：

1. **集成契约 = REST(OpenAI-compat HTTP) + 进程边界**，组件二进制/CLI/容器引入、不 vendor 源码，版本 pin。 —— 同意？
2. **能力② Spike 对比 OmniRoute / ClawRouter / LiteLLM** 三者（保真度+订阅层+Web3 结算），再定主力。 —— 同意，还是你已倾向某一个？
3. **核心模型 = Ornith-1.0-9B(Q6_K) 常驻 + ≤14B 临时**（M4 24GB；35B 需 32GB+，24GB 不作默认，见 07 §4 算账），由**动态推荐模块**按硬件选，`IDORIS_CORE_MODEL` 可 override。 —— 同意？（此条已按 codex-rescue G1 修正：不再拿 35B 当 24GB 的 spike 目标）
4. **iDoris Router 先用 TS/Go 快速起（复用生态），验证后按需内化进 Agent24 Rust 内核**。 —— 同意语言路线？
5. **凭证安全采用 onecli 式 MITM 注入**（出站外部 API key 不进 agent 上下文）。 —— 纳入 Spike？

> 确认后，U0 Spike 首批验证项：①三路由保真度矩阵 ②llama-swap 跑通"Ornith-9B(Q6_K) 常驻 + ≤14B 临时"（**非** 35B，修 G1）③订阅中转 subprocess 最小封装（**能力①标为可选/best-effort，绝不作为核心正确性的必需 fallback**，修 S3）④iDoris 统一 URL 级联连通性 + 性能基线（TTFT/吞吐）+ 控制面 header 透传（修 S4）。
