## 1. 一句话

```
Agent24  做事      iDoris  准入      Hyphae  传话      agentEar  听与说
```

四者**不是四层，是四种权限域**。它们各自持有一条别人不能替它执行的规则，组装起来才是「个人 / 组织的智能大脑」。

## 3. 逐个组件：只负责什么 / 明确不负责什么

| 组件 | 只负责 | 明确**不**负责 | 独占的不可破规则 |
|:---|:---|:---|:---|
| **Agent24** | Skill / agent 执行、会话生命周期、工具调用、插件与 OS 配置定义业务场景 | 部署全栈、保存所有密钥、语音流、租户账本 | **危险动作必须过审批门** |
| **iDoris** | 推理资源**准入**：租户身份→策略、预算/配额、provider 凭证、隐私策略判定、用量账本、远程请求出口 | agent 工作流、原始音频、长期记忆、DID 私钥、业务语义 | **LocalOnly 绝不出设备** · **预算是拒绝不是降级** · **租户预算/用量硬隔离** |
| **Hyphae** | Nostr 传输、节点发现、加密信封、投递确认 | 协作工作流、任务仲裁、重试/超时/补偿、业务状态机 | **agent 间消息端到端加密（NIP-44）** |
| **AgentEar**（外部组件，非 iDoris 子模块）| **输入法组件**：收音、VAD、唤醒词、分段、打断；**「说话器官」**：可插入任意 agent 的语音出口；本地 ASR/TTS 运行时；知识库投递与标签路由 | 通用文本路由、组织预算、跨租户策略 | **原始录音不出机器** |
| **AirAccount** | DID、身份绑定、签名、授权根 | provider key、模型路由 | **私钥不离持有方** |
| **MemPalace** | 跨会话 / 跨 agent 的长期记忆及其生命周期（命名空间、来源、保留、删除、导出） | agent 执行、推理准入 | **记忆不跨租户/跨 subject 串线** |
| **模型制品层** | 权重下载、哈希与签名校验、许可证、版本固定、缓存配额、回滚 | 推理策略、租户计费 | **未验签的权重不得载入** |
| **brain-dist** | 安装、配置 schema 与启动前校验、版本兼容矩阵、升级/回滚、健康检查 | 任何运行期业务决策 | **只布线密钥引用，不读明文** |

## 4. 三条关键边界（最容易打架的地方）

### 4.1 iDoris 的边界不是「智能」，是**权限**

原表述「iDoris 负责所有智能处理」不可执行——隐私分类、文档解析、提示构造、记忆检索、工具选择、ASR、TTS、Embedding 都能叫「智能处理」。照它走，每加一种模态 iDoris 就要长一个后端，最终它同时是策略中心 + 密钥库 + 推理代理 + 租户数据库 + 审计系统，**一个进程挂掉，文本、语音、外部 API 全瘫**。

改成按权限定义：

> **iDoris 决定「哪个租户，在什么预算与隐私策略下，可以访问哪些推理资源」。它不天然拥有每一种模型运行时。**

**因此被保护的不变式也要改**。原来想守的是「所有模型请求都过 iDoris」，实际该守的是：

> **所有远程的、计费的、或受组织策略约束的模型访问，必须经 iDoris 准入；**
> **隐私敏感的纯本地推理可以在可信边缘直接执行，但必须先取得策略授权，并回传不含原始内容的用量与审计凭据。**

前者是组织纪律（谁都可能绕过），后者靠拓扑与沙箱（绕不过）。

### 4.2 语音：控制面与数据面分离（推翻了我的初始倾向）

我原本主张 agentEar 只做 I/O、ASR/TTS 推理回落 iDoris，理由是保住「所有请求过 iDoris」。**这个主张被否掉了，理由比我的更强**：

- 实时音频多一次进程跳转与序列化；流式、取消、背压、采样率协商会全部污染 iDoris 的接口。
- iDoris 是**持有租户凭证和外网出口权限**的进程。把原始录音送进去，**扩大**了泄露面而不是缩小——恰好与「录音不出机器」的承诺相反。
- VAD / partial ASR / 端点检测 / TTS 打断构成一个**反馈环**，不是两个干净的 HTTP 请求。

所以：**agentEar 拥有语音模型的完整生命周期**；iDoris 只签发短期 capability、记录用量、并禁止远程路径。原始音频走 unix socket / loopback，用出站网络限制落实「不出机器」。

> 副作用（好的）：iDoris **不需要**为 M1 引入非-MLX 后端。`06 §10.3` 给 llama-swap 留的那个口子暂时不必打开。

### 4.3 「双 harness 嵌套」必须二选一

下游泰国业务的产品形态是「**Python Harness 托管 Skill**」，而 Agent24 的定位也是「**agent harness**」。两边会自然争夺同一批职责：Skill 加载与版本、输入输出校验、重试与超时、工具权限、审批、会话状态、错误恢复。

**长期保持两个 harness 嵌套，一次请求就会有两套生命周期和两套错误语义。** 必须选一条：

- **(A) Python Harness 只是产品适配层**，真正执行委托给 Agent24；
- **(B) Python Harness 就是产品 runtime**，Agent24 只提供路由 / 审批 / 工具执行等独立服务。

**这条待拍板**，且比 agentEar 的边界更迫近——下游已经在跑 (B) 的形态了。

## 5. 必须立刻处理的两个漏洞

### 5.1 🔴 订阅中转会绕过 Agent24 的审批门

能力① 是 spawn `claude -p` / `codex exec`。**这两个不是纯模型 provider，是具备工具与工作区能力的 agent 程序。** 如果 iDoris 把它们当成「一个 provider」放进推理路径，调用方就获得了一条**绕过 Agent24 审批门执行工具**的通道——审批门管的是 Agent24 自己的动作，管不到 iDoris 里 spawn 出来的 CLI。

**结论**：该适配器必须运行在**无工具、无工作区写权限、无任意子进程能力**的沙箱里；做不到就**不得**放进可信推理路径。这条要写成 T1.4.x 的验收，不是注意事项。

### 5.2 🔴 多租户不会因为「归 iDoris」就自动成立

iDoris 能隔离的只有**预算、用量、provider 凭证**。真正的租户隔离必须由**每个有状态组件各自执行**：

| 组件 | 它必须自己隔离的东西 |
|:---|:---|
| Agent24 | 会话、工具凭证、审批记录 |
| Hyphae | 收件箱、路由元数据、消息保留 |
| agentEar | 录音缓冲、转写缓存、设备权限 |
| MemPalace | 记忆命名空间、删除与导出 |
| 模型制品层 | 租户专属 LoRA、授权权重 |
| iDoris | 预算、用量、provider credential |

> **iDoris 可以是租户身份与策略的权威来源，但不能替其他组件完成隔离。**
> 否则所谓「多租户底座」只隔离了账单，没有隔离数据。这一条要写进对外契约。

## 5.3 事实更正：AgentEar 已存在，且是四者中做得最深的

我在初稿里写过「agentEar 不存在任何仓库」——**那是错的，我的核查范围漏了 `~/Dev/tools/`**。实际是 [`iDoris-ai/AgentEar`](https://github.com/iDoris-ai/AgentEar)，Rust，**M1 + M2 已完成**（v0.4.2），有发布版 `.app`。详见 [`voice-v0-findings.md`](voice-v0-findings.md)。

**定位（2026-09-07 jason 拍板）**：**AgentEar 是外部输入法组件，未来还包括独立的、可插入到任意 agent 的「说话器官」。** 即它既是**入口**（听）也是**出口**（说），且「说话器官」是可被任意 agent 插入的独立件——不是 iDoris 或 Agent24 的子模块。**iDoris 是它的消费者与被消费者，不是它的拥有者**：iDoris 不改它、只提需求；它接 iDoris 拿文本推理。

**这个事实反过来验证了 §4.2 的结论**：AgentEar 已经自己拥有完整的语音运行时（SenseVoiceSmall + FunASR llamacpp + fsmn-vad，泰语另走 whisper.cpp 引擎），且「录音不出机器」本来就是它的设计约束。如果按我最初的倾向 (a) 把 ASR 推理挪进 iDoris，等于**要求重写一个已经跑通并发版的系统**——那不只是过度设计，是破坏。

**更要紧的是它已经是 iDoris 的第二个消费者，而且几乎零成本**：
`src/correct.rs` 与 `src/label.rs` 默认连 `http://127.0.0.1:8793`，发 `POST /v1/chat/completions`，用的模型是 **Ornith——正是 iDoris 选定的常驻核心**。它现在要求用户「自己备一个本地 LLM」；接上 iDoris 只需改一个 URL，并顺带获得隐私路由、预算与审计。

> **规划含义**：iDoris 的 M1 纵切多了一个几乎免费的验收场景。文本推理跑通那一刻，AgentEar 就能指过来——比等泰国业务改完薄客户端更快拿到真实流量。

## 6. 评审采纳与驳回

**采纳**（本稿据此改写）：
1. iDoris 按权限定义而非按「智能」定义 —— §4.1
2. 语音走控制面/数据面分离，推翻我的初始倾向 —— §4.2
3. Hyphae 是传输不是协作编排 —— §3
4. 装配不归 Agent24，另立无常驻服务的发行层 —— §3（理由：负责启动所有进程的组件通常也能读所有配置与凭证，这直接破坏「进程边界=授权边界」）
5. 密钥按权限域拆分，不整体归 iDoris —— §3（「统一管理」与「统一爆炸半径」只差一步）
6. 补齐 MemPalace / AirAccount / 模型制品层 / 全链路审计四处缺失职责
7. 订阅中转绕过审批门 —— §5.1
8. 多租户需各组件各自隔离 —— §5.2
9. M1 做极薄纵切而非一次建完整底座 —— 见 [`roadmap.md`](roadmap.md)

**驳回**：
- **「把 Agent24 的 ModelRouter 拆成独立进程 `agent24-routerd`」** —— 驳回。这是对 Agent24 内核的改造，而 [`../09-对Agent24的需求.md`](../09-对Agent24的需求.md) 的非需求里明确写了「不要求 Agent24 做的事」，iDoris 只提需求不改其内核。**采纳其关切、换一种解法**：Agent24 的 `ModelRouter` **保持不动**，iDoris 作为它的一个 provider 接入（R1，纯加法零回归）；**策略权威归 iDoris，Agent24 侧不新增策略**。两者的重叠靠「只有一个地方长新策略」收敛，而不是靠一次高风险迁移。
- **「不能让零代码项目先获得逻辑所有权」** —— 措辞驳回，实质采纳。设计权归属与实现进度是两件事；但底下那句警告是对的：**不要重写一份 Agent24 已经有的路由**。已写进上一条。

## 7. 已拍板（2026-09-07 jason）

### B1 — 双 harness：**兼容，但不是「合并」**

用户问「Agent24 能不能兼容 Python 环境？二者可以合并、兼容」。查 Agent24 `docs/ADR-026-rust-core-polyglot.md`（状态 ✅ 已采纳并落地），答案分两半：

**✅ 能兼容，路径是现成的。** ADR-026 决议 5：非 Rust 模块经 **Node Host（JSON-RPC / MCP）**接入内核，不由 Rust 直接加载。**MCP 是语言无关的**——TS 能这么接，Python 同样能。所以泰国的 Python Harness 可以作为 MCP server 挂进 Agent24，不需要改写成 Rust，也不需要 Agent24 内嵌 Python 解释器。

**⚠️ 但「合并」这个词要收窄，否则会撞既定架构。** ADR-026 决议 6 明写：

> **Python 仅用于 ML Worker**（MLX 加载、Embedding、Whisper、图像生成、LoRA 训练），**不承担会话状态 / 权限 / 任务持久化 / CLI / 审计**。

而泰国 Python Harness 承担的恰恰是**权限与审计**（审批队列、出网闸门、审计留痕）。所以「把 Python Harness 并进 Agent24 作为它的一部分」与决议 6 直接冲突。

**⚠️ 还有一个现实事实必须摆上桌**：ADR-026 自己的现状盘点写着——

> Agent Loop、任务分解/状态机、调度器、分层记忆、上下文压缩、**权限审批**、工作流引擎、多 Agent、自进化 —— **全部 planned（尚不存在）**。
> 「Agent24 目前有『容器』，没有『agent』。」

**即 Agent24 的审批门还没写，而泰国那套已经建成并有 16 条变异测试守着。** 谈「谁并入谁」之前，得先承认现在只有一边有实现。

### 结论：不合并，**分层承接**

| 层 | 谁 | 管什么 | 状态 |
|:---|:---|:---|:---|
| **通用 agent 能力** | Agent24 Rust 内核 | Agent Loop、记忆、调度、**通用权限审批**（「这个动作要不要人点头」）| 待建 |
| **领域校验** | Python Harness（经 MCP 接入） | **领域不可破规则**（「这份输出合不合规」：出处、字数、数字对账、敬语一致）| 已建，113 条变异 |
| **推理准入** | iDoris | 租户、预算、隐私、凭证、用量 | 待建 |

> **🔧 修正（codex 对抗式评审）**：本节早先版本把分界线写成「Agent24 管**动作**、Python 管**输出**」，并称「不重叠」。**那条线不可判定，已推翻。**
>
> **反例**：经 LINE 发一张催款 Flex Message ——「您尚欠 ฿12,480，点击按钮确认自动扣款」，含客户姓名、金额、群聊收件人、以及一个 `postback` 扣款按钮。这**一个对象**同时是：远程发送 / 产生费用 / 向第三方披露信息的**动作**；需要数字对账、隐私检查、敬语检查的**输出**；而按钮 payload 还是**下一次金融动作的授权入口**。
> Rust 门不能只看 `line.send`——准不准发取决于收件人、金额、正文与按钮语义；Python 也不能只看文字合不合规——同一句话发给客户本人和发到客户群，结论不同。
> **两种故障都会发生**：两边都管 → 用户连点两次批准；两边都不管 → Rust 信任 `output_valid=true`、Python 认为远程动作已由 Rust 批准，错误收件人或恶意 postback 从夹缝通过。

### 可判定的分界线：**授权者 vs 校验器**（不是动作 vs 输出）

| | 谁 | 职责 | 关键约束 |
|:---|:---|:---|:---|
| **唯一最终授权点** | Agent24 Rust 权限门 | 对「**动作 + 目标 + 内容摘要/分类 + 校验凭据**」**整体**做最终决定 | 只有它持有审批状态机与否决权 |
| **校验器** | Python Harness | 产出**带证据的校验结果**（出处、字数、数字对账、敬语一致），交给授权者 | **不持有否决权、不持有审批状态** |

否则 Python 事实上仍拥有否决权和审批状态，它就不是校验器，双门问题原样存在。

### 迁移：**这是有状态安全组件的替换，不是加法**

早先版本称「加法迁移、不推翻」——**不成立**。审批队列含有无法靠「多接一道 MCP」自然迁移的状态：待审/已批/已拒/已超时的请求、审批人与租户身份、幂等键与执行次数、**批准时看到的内容版本**、超时与故障时的默认行为、审计记录与实际执行结果的关联。

上线期必然出现的窗口：**双门在线**（两次批准；或第一道批准后内容变了、第二道批准的是另一个版本）· **单门窗口**（路由已切 Rust 但旧 worker 只认 Python 凭据；或 Python 已停拦而 Rust 客户端尚未强制带票据）· **重放窗口**（旧凭据被新内核接受，但新内核不知道它是否已执行）· **队列分裂**（切换时 Python 里的 pending 请求没有归属）。

**安全迁移的最低要求**：Rust 单一权威 · Python shadow 判定 · **版本化授权票据** · **请求内容哈希** · 共享幂等键 · 旧队列排空 · 按租户切流 · 全链路 fail-closed。**最后移除 Python 动作门那一步明确是减法**，不能叫纯加法。

### Python 动作审批即刻**冻结为遗留实现**

ADR-026 决议10 禁「临时 TS 版内核能力」的**理由与语言无关**：避免第二套状态机与权限语义、避免下游依赖临时实现、避免 Rust 重写时背行为兼容、避免安全规则在迁移中漂移。**这些放到 Python 一样成立。**

它不该立刻删除（是**已投产的安全控制**，贸然拿掉更危险），但从现在起：
- ✅ 只允许**安全修复**；
- ❌ **不再新增**通用动作类型、审批工作流、权限模型；
- 📅 明确 **sunset 条件**（Rust 权限门达到什么状态即开始切流）；
- 🔄 **113 条变异测试逐步转为 Rust 权限门的契约测试** —— 让语义归属内核，而不是让 Python 永久持有它。

> 否则决议10 就只是在禁 TS，没有禁重复建设，技术原则失去一致性。
> 领域校验（出处/字数/数字对账/敬语）**不受此冻结约束**——那本就是 Python Harness 该长的地方。

### B2 — MemPalace：**作为 Agent24 的模块**
不独立成组件。评审曾建议独立（理由是跨 agent 复用与租户隔离层次），**驳回**：iDoris.ai PROFILE 的 Phase 2 本就把 MemPalace 列为 Agent24 的记忆模块，独立会凭空多一个进程边界与一套契约。
租户隔离与命名空间**由 Agent24 在其模块内执行**（见 §5.2——iDoris 不替它做），记忆数据**不进 iDoris**。

> **⚠️ 但成立需要一个当前还没有的协议（codex 评审）**：「记忆**数据**不进 iDoris」没问题（数据面归属）；「记忆的**租户定义**不进 iDoris」才有问题——那会制造**第二套 tenant 真相**。
> Agent24 **不能**从请求参数、目录名或 MCP payload 自行相信 `tenant_id`，否则每个 Node Host / Python Worker / 客户端都能各自定义租户边界。需要一份**不可伪造的能力凭据**，至少绑定：`tenant_id` · 用户/Agent/服务身份 · `deploy_mode` · 可访问的 memory namespace · 权限范围 · 策略版本与有效期 · 请求或会话绑定。Agent24 只验证凭据并把记忆读写**强制映射到凭据里的 namespace**；**调用方自带的 tenant 字段必须被忽略，或要求与凭据严格相等**。缓存与离线模式还要规定撤权延迟。
>
> **⚠️ 这与已冻结的 [`contract-tenancy.md`](contract-tenancy.md) §3 有张力**：契约现在写的是「Router 不做租户鉴权与签发……只消费已验明的 `tenant_id`」。两句要调和：
> **认证**归 AirAccount / 组织侧（iDoris 不做，契约这半对）；**授权凭据的签发**归 iDoris（作为租户策略的权威来源）——这一半契约还没写。
> **处置**：不动已冻结的 v1.3（下游正照着实现，且他们是单一可信部署，header 自述 tenant 在那个场景下够用）；把「跨组件 tenant 传播需要签名凭据」记为 **B7 待设计**，等真的有第二个组件消费 tenant 身份时再定契约 v2。

### B3 — AgentEar：**外部输入法组件 + 可插入任意 agent 的「说话器官」**
定位见 §5.3。**M3（TTS）优先级与「理解层何时从自备 LLM 切到 iDoris」= 需要设计，不着急** —— 不进 M1，记为设计项。
> 附一条本轮核到的事实：TTS 的 ADR-0005 状态是「**草稿，不可据此拍板**」，卡在一件**只有 jason 能做**的事上（`~/Desktop/agentear-tts-samples/` 里 `nan_tw_000.wav` 是闽南语还是普通话腔调念的闽南语汉字，需要人耳）。**所以这条线的阻塞不是技术，是一次听音判断。** 载体已通（OmniVoice 经 mlx-audio 在 M1 Max 热启动 3–4 秒一句，峰值 RSS 1.8GB）。

### B4 — 模型制品层：**先设计，不实现**
产出设计文档（下载来源、哈希与签名校验、许可、版本固定、LoRA 归属、磁盘配额、灰度回滚、多运行时共享缓存、离线安装），**不进 M1 实现**。
> 设计时带上本轮学到的门禁形状：**把待核项挂在具体动作前面，而不是挂在待办列表里**——AgentEar 的 `plan-i18n-thai.md` §4 立的是「在确认再分发义务之前不要开始托管」，不是「记得核一下许可」。列表不产生阻力，动作前置的门禁才产生阻力。

### B5 — AgentEar TTS 方言判定：**腔调不对（2026-09-07 jason 听音）**

`nan_tw_000.wav` **不是台湾闽南语**。ADR-0005 因此落到**情形 B**：OmniVoice 声称的「646+ 语言」**不覆盖台湾闽南语**，它不能作为方言方案的单一候选。

**后果**（ADR-0005 §3 情形 B 已预写）：
- 要么换模型：先验证 `MERaLiON-OmniVoice-Hokkien` 与 `mlx-community/OmniVoice-bf16` **是否同源**（都叫 OmniVoice、都有 `audio_tokenizer` 子目录，架构上很可能同基座）。若同源，那份闽南语微调权重可转 MLX 再用 mlx-audio 跑 —— **和泰语 whisper 那次是同一套路数**（转换 + 量化 + 校验指纹）。
- ⚠️ **但那是新加坡闽南语，不是台湾话。** 台湾话对口的是 `BreezyVoice-Taigi`，**能否在 Apple Silicon 上跑完全没测**。
- 要么按 ADR §4 的三条走向之一推迟方言（jason 自己说过「先完成普通话或先完成英语都可以」）。

> **顺带**：OmniVoice 那个候选还有一处独立的硬伤 —— `mlx-community/OmniVoice-bf16` **无模型卡、无许可标注**，而我们要随包分发或按需下载。就算腔调对了，许可这关也得先过。

### B3 补充 — 「理解层切 iDoris」不是「不着急」，它是 M3 的前置

原判「需要设计，不着急，不进 M1」。**但资源账把它变成了 M3 的依赖**：

`milestones.md` M3 的原文写着 —— TTS 1.8 GB + M2 常驻 LLM 7.3 GB ≈ **9.1 GB，已贴着 ADR-0002 的 ≤9 GiB 上限**，并注明「两者能否同时常驻是个独立于选型的问题」。

**而理解层切到 iDoris，正是解掉这笔账的办法**：那 7.3 GB 从 AgentEar 的进程预算里**移出去**，交给 iDoris 的 oMLX（它本来就在做多模型 + LRU + memory-guard 的内存编排，U0 已实测）。于是：

| | AgentEar 自身进程预算 | 结果 |
|:---|:---|:---|
| 现状（自备 LLM）| TTS 1.8 + LLM 7.3 = **9.1 GB** | 贴着 9 GiB 预算上限，TTS 与理解层能否共存存疑 |
| 切到 iDoris 后 | TTS 1.8 GB（+ ASR）| **AgentEar 的预算腾出 7.3 GB** |

> ⚠️ ADR-0002 §2.2 的 ≤9 GiB 是 **AgentEar 自己的进程预算**（三项：Ornith 6bit 7.65 GiB + KV cache 64K ~1 GiB + SenseVoice ~0.4 GiB），**不是整机上限**（那台 M1 Max 有 64 GB）。同机部署下不凭空多出物理内存，收益是「AgentEar 预算腾空」+「那部分交给 oMLX 后变成可驱逐的」；异机部署（Mac mini + Tailscale）才真正腾出物理内存。详见 [`voice-duplex-assessment.md`](voice-duplex-assessment.md) §4。

**所以 B3 的两件事有先后**：「理解层切 iDoris」应排在「TTS 选型落地」**之前**，否则 M3 会在一个本可以避免的内存约束下做选型（可能因此排除掉更大更好的 TTS 模型）。
