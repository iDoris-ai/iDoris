# 双工语音接口 · 可行性评估

> 回答一个设想：**AgentEar 作为双工语音接口 —— 说话、收音、智能处理、内容输出、语音输出（可配置方言/英语/日语），插拔式。**
> 结论先行：**三件事里两件能做、一件要先纠正前提，而最难的那件不是「插拔」。**
> 记录日期：2026-09-07 ｜ 关联：[`ecosystem-boundaries.md`](ecosystem-boundaries.md) §4.2 · AgentEar `docs/asr-selection.md` §0/§4 · `docs/milestones.md` M3 · ADR-0005

## 0. 设想的链路

```
   人说话
     │
     ▼
 ┌────────────────── AgentEar（外部组件，双工语音接口）──────────────────┐
 │  收音 → VAD → 流式 ASR ──┐                    ┌── 流式 TTS → 播放     │
 │         ▲                │                    │        │             │
 │         │  回声消除(AEC)  │                    │        ▼             │
 │         └────────────────┼────────────────────┼──  打断检测          │
 └──────────────────────────┼────────────────────┼──────────────────────┘
                            │ 文本                │ 文本
                            ▼                    │
                  ┌─────────────────────────────┴──┐
                  │   iDoris（智能处理）             │
                  │   路由·隐私·预算·审计 → 本地模型  │
                  └────────────────────────────────┘
```

**好消息先说**：这条链路与已定架构**自洽**。[`ecosystem-boundaries.md`](ecosystem-boundaries.md) §4.2 定的是「语音运行时归 AgentEar，iDoris 只管文本推理与准入」——设想里的「智能处理」正好落在 iDoris，「说话/收音/内容输出」全在 AgentEar。**不需要改架构。**

## 1. ⚠️ 「双工」这个词要先纠正前提

**AgentEar 自己已经分析过，而且结论比设想更严格。** `docs/asr-selection.md` **§0 结论先行**（`:25`，其自身注明「详见第 4 节」）原文：

> 你想要的「他一边听我说一边理解、可以互相打断」**不是 ASR 模型能提供的能力**，那是 **speech-to-speech 全双工模型（Moshi 那一类）**的能力，而它们是 **7B 级别、常驻远超 2 GB**。**在 2 GB 预算内做不到真全双工。**

所以要分清两个东西：

| | 是什么 | 代价 | 现状 |
|:---|:---|:---|:---|
| **真·全双工** | 一边听一边想，双方可随时插话（speech-to-speech 端到端） | **7B 级模型常驻**，远超现有 2 GB ASR 预算；且整条链路要换成 s2s 架构，文本层消失 —— **iDoris 的「智能处理」将被绕过** | 不可行（预算 + 架构双重冲突）|
| **打断式半双工** | 「说完才轮到我」，但**我可以随时打断它说话** | 流式 ASR + VAD 掐断 TTS + **AEC** | M3 的既定目标 |

同节（`:27`）还有一句提醒：**「注意这不等于全双工，也不要说成『体感接近』」** —— 它解决「说完才轮到我」，不解决「一边听一边想」。

> **一条容易被忽略的架构后果**：真·全双工的 s2s 模型是**音频进、音频出**，中间没有文本。那意味着**隐私过滤、预算、审计、路由全都没有了作用点** —— iDoris 在那条链路上无处插入。所以「追求真全双工」和「所有受策略约束的推理必须过 iDoris 准入」是**冲突的**，不只是贵。

**建议**：目标定为**打断式半双工**，并且在对外措辞上就叫它「可打断」，不叫「双工」。

## 2. 三件事的真实难度排序（难点不在插拔）

### 🔴 最难：AEC（回声消除）—— 双工的真正前提

没有 AEC，机器会**把自己说的话当成用户在说话**，于是自己打断自己。M3 的验收表已经写死了阈值：

> **AEC 自触发率 = 0** · 打断响应 **< 300 ms** · 误打断 **< 1 次 / 10 分钟** · 打断后恢复行为一致

`milestones.md` 说得很直白：M3「**是 AEC 和流式 raw 语义真正登场的地方**，也是 M1–M2 之外**工程量最大的一块**」。

### 🟡 次难：流式 ASR —— 现有主链路做不到

`asr-selection.md` 的候选表里 **SenseVoice-Small 的「流式」一栏是 ❌ 分块离线**。现在的交互是「按右 Command 开始、再按停止、然后转写」，这个形态**天然不需要流式**；改成可打断就必须换或加一条流式路径。
表里 `Paraformer` 有流式版但 CER 更差（10.18% vs 7.81%）；`mlx-audio` 里的 Qwen3-ASR 被列为 v2 观察对象。**这是一次选型，不是加个开关。**

### 🟢 最容易：插拔式本身

**这一层反而是三件里最简单的**，因为它就是一份契约 + 一个注册表，而且我们已经有同构的现成设计：iDoris 的 `LoadPolicy` / `ProviderDescriptor`（[`spec.md`](spec.md)）。语音侧的等价物大致是：

```yaml
speech_backend:
  id: omnivoice-mlx
  kind: tts | asr
  languages: [zh-CN, en, ja, th, yue, nan-TW]   # 声称覆盖
  verified_languages: [zh-CN, en]               # ★ 实听验证过的，与上面分开
  runtime: mlx-audio | llamacpp | whisper-cpp
  form: sidecar_process                          # 见下方 §3 的硬约束
  license: <必须白纸黑字>
  memory_gb: 1.8
  streaming: true | false
```

**关键是 `languages` 与 `verified_languages` 必须分开两栏** —— 本轮 B5 正是栽在这里：OmniVoice **声称** 646+ 语言，实听下来台湾话腔调不对。**「声称覆盖」不是「验证覆盖」**，插拔式的注册表若只有前者，就是把一个未经证实的声明当成能力对外承诺。

## 3. 插拔式的真正障碍：不是抽象层，是被抽象的东西还不存在

ADR-0005 已经查清四条，每一条都在插拔层之外：

| 需求 | 现实 |
|:---|:---|
| 台湾闽南语 | OmniVoice 腔调不对（**本轮已证**）；MERaLiON 是**新加坡**闽南语；`BreezyVoice-Taigi` 对口但 **Apple Silicon 能否跑完全没测** |
| 粤语 / 香港话 | 仅 CosyVoice 2 声称覆盖（`tts-survey.md`，**不在 ADR-0005 那张四行候选表里**），原文自注「粤语待核实」；本地可跑与许可均 ❓ 待查 |
| 英语 / 普通话 | ✅ 有方案（Qwen3-TTS，Apache-2.0） |
| 日语 | 仅 CosyVoice 2 声称覆盖（`tts-survey.md` 同一行写「中英日韩粤等」），**与粤语是同一条未核实的声明**；本地可跑与许可均 ❓ 待查 |
| 泰语 TTS | 未调研（泰语目前只有 **ASR** 侧方案）|
| 全部候选 | **都是 PyTorch/CUDA 取向，没有单二进制** → TTS 只能走 ADR-0002 允许的**独立进程边车**，是新增一整套运行时 |

**所以「可配置不同方言」在今天的现实里不是一个开关，是「每种方言 = 一个独立模型 + 一份独立许可 + 可能一套独立运行时」。** 插拔契约能把这件事管起来（这正是它的价值），但它**变不出还不存在的权重**。

> 这也正好命中 **B4 模型制品层**：多方言 = 多权重 = 下载来源、签名校验、许可、版本固定、磁盘配额全都要有主。B4「先设计」的优先级，会被「要做多方言」直接抬高。

## 4. 结论与建议顺序

**能做到，但要拆成四件独立的事，且顺序不能乱：**

1. **先把理解层切到 iDoris** —— 不是为了少维护一个 LLM，是为了**解掉 M3 的资源账**：现在 TTS 1.8 GB + 常驻 LLM 7.3 GB ≈ 9.1 GB 已贴着 ≤9 GiB。**在这之前做 TTS 选型，会在一个本可避免的约束下排除掉更好的模型。**

   > ⚠️ **前提必须写明，因为整个优先级变更都压在这一格上。** ADR-0002 §2.2 的 ≤9 GiB 是 **AgentEar 自己的进程预算**（**三项**：常驻 Ornith 6bit 7.65 GiB **+ KV cache 64K 上下文 ~1 GiB** + 按需的 SenseVoice 子进程 ~0.4 GiB ≈ 9 GiB 峰值），**不是整机上限**——那台 M1 Max 有 64 GB。所以「切到 iDoris」在**同机部署**下并不凭空多出 7.3 GB 物理内存，收益来自两处：
   > ① **AgentEar 自己的预算真的腾空了**，TTS 选型不再被这条自设约束卡住；
   > ② 那部分内存交给 oMLX 后**变成可驱逐的**（LRU + memory-guard，U0 已实测），而 AgentEar 自己常驻的 LLM 边车做不到——TTS 要内存时它不会让路。
   > **异机部署**（iDoris 跑 Mac mini + Tailscale，见 [`architecture.md`](architecture.md) 运行形态）下才是真正腾出物理内存。两种部署收益不同，但**都足以解除 M3 的选型约束**。
2. **定义 `speech_backend` 插拔契约**（`languages` / `verified_languages` 两栏分开），与 iDoris 的 `LoadPolicy` 同构。**这一步现在就能做，且不依赖任何模型到位。**
3. **按语言逐个落实**，每个都要过「实听验证 + 许可白纸黑字」两道门。**先做已有方案的（普通话/英语），方言按可得性排队**，不要为了凑齐清单去等一个还不存在的模型。
4. **最后做可打断**（AEC + 流式 ASR）—— 工程量最大，且它与「说哪种语言」正交，不该互相阻塞。

**措辞建议**：对外说「**可打断的语音接口 + 可插拔的语音后端**」，不要说「双工」。真全双工需要 7B 级 s2s 模型，且**会把 iDoris 从链路里挤出去**，那与隐私/预算/审计必须有作用点的约束直接冲突。
