# 安装 iDoris v0.3.0 并完成首次本地调用

本指南对应正式 tag `v0.3.0`，解引用提交 `03c079c70611331a8c85a1666e32a75df6359d09`。Rust 是生产实现。先完成具体模型调用，再检查 Agent24 的角色接入条件。

## 确认安装的是什么

正式 [v0.3.0 发布页](https://github.com/iDoris-ai/iDoris/releases/tag/v0.3.0) 提供 Apple Silicon macOS 的 `.tar.gz` 二进制包及 `.sha256`。包内只有 `idoris` 和四份运行配置；没有模型权重、oMLX、桌面安装器或后台服务安装步骤。GitHub 的 Source code 下载项是源码快照，需要 Rust 工具链编译，并自行布置配置目录。

本版没有 iDoris DMG、Windows EXE、Intel Mac 或 Linux 预编译包。源码中存在跨平台代码及其他运行时适配器，不等于这些平台已有经过本次归档验证的安装路径。默认后端卡针对 oMLX 0.6.4；该版本上游说明要求 Apple Silicon、macOS 15+，源码安装需要 Python 3.11–3.13。iDoris 二进制自身的 Mach-O 最低系统声明不等于完整推理栈的支持范围。

下面的命令使用 shell、curl、tar、shasum、openssl 和 Python 3。所有路径在当前用户下，默认仅绑定本机。准备模型属于独立下载步骤，本指南的自动验证不会执行下载或付费调用。

## 下载、校验并保留目录布局

在一个新目录执行：

```sh
mkdir -p "$HOME/Applications/iDoris-v0.3.0"
cd "$HOME/Applications/iDoris-v0.3.0"
curl -fLO https://github.com/iDoris-ai/iDoris/releases/download/v0.3.0/idoris-v0.3.0-aarch64-apple-darwin.tar.gz
curl -fLO https://github.com/iDoris-ai/iDoris/releases/download/v0.3.0/idoris-v0.3.0-aarch64-apple-darwin.tar.gz.sha256
shasum -a 256 -c idoris-v0.3.0-aarch64-apple-darwin.tar.gz.sha256
tar xzf idoris-v0.3.0-aarch64-apple-darwin.tar.gz
```

校验应显示 `OK`。本次审计下载的正式包 SHA256 为 `ce54063f78b2d092c0ba820be4729635a5fe1df2ec91debeec10ef5dd582dfad`。不要使用其他开发包遗留的同名校验文件。

保留 `idoris` 旁边的 `config/`；默认路径相对二进制，而非终端当前目录。如果确认来源可信且 macOS 因隔离属性拒绝执行，可对该二进制执行 `xattr -d com.apple.quarantine ./idoris` 后重试。

## 初始化独立数据库并签发推理 key

没有 `idoris init`、`model pull` 或交互式配置向导。签发 key 和首次启动都会按需创建 SQLite 表。签发与服务必须使用同一个数据库绝对路径。

以下数据库须是独立的 Personal 数据库，不要复用 Tenant 历史数据库；模式切换见[迁移说明](releases/v0.3.0.md#从-tenant-切换到-personal)。

以下是个人本机的具体模型调试 key：它只有 `local_only` 权限。具体模型名无法证明属于哪个角色，当前实现要求 key 拥有全部角色，包含 `auto`；这不代表可以调用远程或付费模型。

```sh
umask 077
mkdir -p "$HOME/.local/share/idoris-personal"
export IDORIS_DEPLOY_MODE=personal
export IDORIS_DB_PATH="$HOME/.local/share/idoris-personal/state.sqlite3"
./idoris key issue --spec-stdin > "$HOME/.local/share/idoris-personal/key.json" <<'JSON'
{"owner":"personal-local","allowed_privacy":["local_only"],"allowed_roles":["fast","daily","deep","vision","embed","rerank","decide","auto"]}
JSON
export IDORIS_API_KEY="$(python3 -c 'import json,os; print(json.load(open(os.path.expanduser("~/.local/share/idoris-personal/key.json")))["secret"])')"
```

成功时输出文件含 `key_id` 和一次明文 `secret`，服务端库保存验证哈希。不要把 key 文件提交到仓库。`fast` 在这里是模型角色枚举，不是计费服务模式。`IDORIS_API_KEY` 是本指南及消费方使用的 shell 变量；iDoris 服务端通过数据库验证请求的 Bearer key，不会读取此变量来配置认证。

## 准备后端与模型

iDoris 默认连接 `http://127.0.0.1:8000` 的 oMLX，不负责安装引擎或下载权重。遵循 [oMLX v0.6.4 安装说明](https://github.com/jundot/omlx/blob/v0.6.4/README.md#install) 安装引擎。上游提供自己的 DMG、Homebrew 和源码路径；oMLX 的 DMG 不是 iDoris 安装包。Homebrew 当前配方可能已更新，不能把今天的 `brew install` 结果当作 0.6.4 兼容性验证。

在 oMLX 的模型下载界面选择适合实际内存、许可和用途的 **MLX 格式**权重，或使用已有的本地 MLX 模型目录。确认文件已下载完整，再启动引擎；例如已有 `~/models/` 下的模型子目录时，上游文档支持：

```sh
omlx serve --model-dir "$HOME/models"
```

不要因模型名出现在 iDoris `config/catalog.yaml` 就认为它已经下载或能被该引擎运行。catalog 是推荐元数据，可能含实验条目及其他量化格式；模型实际 ID 以引擎发现结果为准。选择时先核实权重大小、KV/context 预算和引擎支持，避免用整机空闲内存直接当模型占用。

若 oMLX 启用了推理认证，在启动 iDoris 前设置 `IDORIS_OMLX_API_KEY` 为 oMLX 配置的 key；它与 iDoris 的 virtual key 是两把独立凭证。iDoris 不自动读取 `OMLX_API_KEY` 或 oMLX 设置文件。若更换引擎端口，在启动 iDoris 前编辑 `config/components/omlx.yaml` 的 endpoint。**先确认 oMLX 已启动并可访问，再启动 iDoris。** v0.3.0 会锁存启动时的后端错误（`startup_error`）；若先启动了 iDoris、后来才启动或恢复后端，即使 `/v1/models` 已返回 200，聊天仍可能持续 503，必须重启自己启动的 iDoris 实例。补充上游 key 或修改 endpoint 后也须重启。

其他可选运行时的手工配置见 [multi-backend 示例](../config/examples/multibackend/README.md)。示例需要真实的本地执行文件、模型路径及可靠的占用值，不是开箱自动探测安装。

## 启动服务并打开只读控制台

在刚才同一终端启动，保留数据库变量。生成一个已知的 Admin token，通过 stdin 交给进程：

```sh
IDORIS_ADMIN_TOKEN="$(openssl rand -hex 32)"
printf '%s\n' "$IDORIS_ADMIN_TOKEN" | ./idoris serve --admin-token-stdin &
IDORIS_PID=$!
python3 - "$IDORIS_PID" <<'PYREADY'
import json, os, sys, time, urllib.request
pid = int(sys.argv[1])
client = urllib.request.build_opener(urllib.request.ProxyHandler({}))
deadline = time.monotonic() + 15
while time.monotonic() < deadline:
    os.kill(pid, 0)  # 新进程退出时失败，不接受旧服务的健康结果。
    try:
        with client.open('http://127.0.0.1:8740/health', timeout=1) as response:
            health = json.load(response)
        if health.get('status') == 'ok' and health.get('version') == '0.3.0':
            print(health)
            break
    except OSError:
        pass
    time.sleep(0.1)
else:
    raise SystemExit('iDoris 启动超时；检查服务日志、端口和配置')
PYREADY
printf '%s\n' "$IDORIS_ADMIN_TOKEN" | ./idoris admin status --token-stdin
```

预期 `/health` 中 `status` 为 `ok`，`version` 为 `0.3.0`。它只证明路由服务启动，不能证明已安装或加载模型。数据端口默认 `8740`；Admin 端口默认 `8741`，两者均须空闲。修改时分别设置 `IDORIS_PORT`、`IDORIS_ADMIN_PORT`，并同步修改客户端 URL。

打开 `http://127.0.0.1:8741/admin/`。在同一终端运行 `printf '%s' "$IDORIS_ADMIN_TOKEN" | pbcopy`，把剪贴板内容粘贴到页面的 Session token，再点 Refresh。页面显示 status、backends、models、roles、runtimes 的 JSON 快照。刷新会清空输入框；下次需重新粘贴。

Admin token 与推理 key 不互通。Admin token 仅供本次服务会话使用，不会出现在 URL 或服务日志中。直接运行 `./idoris` 也能启动，但其自动生成的 token 没有向用户交付的入口；需要已知 token 时停止该实例，以 `--admin-token-stdin` 重启。控制台当前只读，不能安装/切换模型、管理 key 或配置后端。`idoris admin models --token-stdin` 也是读取，不是加载命令。正常停止服务可在对应终端使用 shell 作业控制；前台启动则用 Ctrl-C。

若 iDoris 已先于后端启动，在同一终端停止并等待上面记录的自有进程，然后重新执行本节启动及就绪检查命令（不要停止其他实例）：

```sh
kill "$IDORIS_PID"
wait "$IDORIS_PID"
```

## 发现并调用一个具体模型

保持前面终端中的 `IDORIS_API_KEY`。以下写法从 stdin 传递 curl 配置，避免把 Bearer key 作为 curl 的命令行参数：

```sh
printf 'header = "Authorization: Bearer %s"\n' "$IDORIS_API_KEY" |
  curl -fsS --config - http://127.0.0.1:8740/v1/models
```

预期为 `{"object":"list","data":[...]}`。`data` 为空说明没有可发现模型；认证失败应先区分本地 key 和上游 oMLX key。模型发现成功还不证明内存足够加载。

服务就绪后也可读取 `/capabilities` 查看推荐与准入事实；该端点需要 virtual key，沿用 stdin Bearer 写法：

```sh
printf 'header = "Authorization: Bearer %s"\n' "$IDORIS_API_KEY" |
  curl -fsS --config - http://127.0.0.1:8740/capabilities
```

它不执行安装、不保证下一次调用成功，也没有完成角色到实际模型的绑定。

把下面 JSON 的 `MODEL_ID_FROM_LIST` 替换为刚才返回的准确 ID：

```sh
cat > /tmp/idoris-first-chat.json <<'JSON'
{"model":"MODEL_ID_FROM_LIST","messages":[{"role":"user","content":"请只回复：你好"}],"stream":false}
JSON
printf 'header = "Authorization: Bearer %s"\n' "$IDORIS_API_KEY" |
  curl -sS -i --config - http://127.0.0.1:8740/v1/chat/completions \
    -H 'Content-Type: application/json' \
    -H 'X-iDoris-Privacy: local_only' \
    --data-binary @/tmp/idoris-first-chat.json
```

默认 Supervisor 路径当前拒绝 `max_tokens` 等尚未支持的采样字段（400 `unsupported_field`）；首次调用仅传上面的最小请求。

成功应有 HTTP 200、`choices` 和 `X-iDoris-Served-Locality: loopback`、`X-iDoris-Record-Id`。失败请读取状态码和 `error.type`/`reason_code`：401/403 常见于凭证或角色权限；503 可能是后端不可用、模型 ID 不存在、加载状态未确认或容量准入失败。`local_only` 不会因本地不可用而调用远程订阅。

默认 oMLX on-demand 路径会在推理前获取模型占用、执行 Supervisor 加载/状态核对。若遇到 `load.pending` 围栏，按 [README 的已知限制](../README.md) 恢复，不能仅凭重启或空快照删围栏。不要把组件卡改成 `resident` 来绕过生命周期：resident 走独立 HTTP 代理；付费 buffered 请求仍须预算预留与结算，付费 streaming 当前拒绝。它不能代替受 Supervisor 管理的模型生命周期。

## 检查 Agent24 接入条件

Agent24 是独立应用；此仓库发布包不含 Agent24，也不能证明 Agent24 当前版本已经实现 provider 注册。接口真源见 [边界与接口规范](interfaces/iDoris-Agent24-边界与接口规范.md)，不要用已废弃的 `agent/handoff-agent24.md` 作为当前安装手册。

在**实际支持该契约的 Agent24 版本**中，配置数据根 URL `IDORIS_URL=http://127.0.0.1:8740` 与 iDoris virtual key；URL 以消费方实现为准，不把 Admin 8741 端口当模型服务。通用 OpenAI SDK 若要求 `base_url`，常见形式则为 `http://127.0.0.1:8740/v1`，不要重复拼接 `/v1`。

契约要求挂载时检查 `/health` 服务身份，传递 `model=idoris/<role>`、Privacy、Complexity、Request-Id；个人模式不发送 Tenant。`idoris-local` 必须验证响应 locality 为 `loopback`，缺失、lan、remote 都不向模块返回结果，并记录 Record-Id。不要在配置 iDoris 后又让 Agent24 直连同一 oMLX，绕过生命周期与审计。

**v0.3.0 的角色选模还存在阻塞。** 当前 `dispatch::candidate` 把所有目录角色赋给所有卡，尚未使用 catalog 建立真正的角色绑定；默认生命周期路径把 `idoris/daily` 解析为组件 provider ID `omlx`，引擎只有真实模型名时会返回 503。通用 resident 路径则把 `idoris/daily` 原样转发给上游。它不等于“根据机器与用途自动选中了模型”。不要在 Agent24 验收中靠放宽权限、伪造 ID、取消 locality 校验或改卡模式掩盖这一缺口。

联调与缺口跟踪：[iDoris #506](https://github.com/iDoris-ai/iDoris/issues/506)、[Agent24 #974](https://github.com/iDoris-ai/Agent24/issues/974)。契约已接受不等于消费方 launcher 已交付。独立使用 iDoris 的具体模型路径不依赖 Agent24；协作验收需检查两边真实实现。

因此，先用具体模型证明 iDoris 的安装和推理链路；Agent24 的角色路由验收需等待明确角色绑定修复，并在真实 Agent24 进程完成测试。签发仅允许 `daily` 的 Agent24 key 可以验证权限边界，但该 key 当前会拒绝具体模型名调用，这是预期的 fail-closed 权限行为。

## 复现无需模型的归档验证

本仓新增脚本使用 Python 标准库、临时数据库、临时端口与本机 HTTP 夹具，直接运行解压出的正式 Rust 二进制。先切换到 **iDoris 源码仓库检出根目录**（含 `scripts/`），不要在二进制解压目录执行；发布包不含测试脚本：

```sh
python3 scripts/test_onboarding_smoke.py "$HOME/Applications/iDoris-v0.3.0/idoris"
```

测试覆盖启动、key 落库及重启、未认证拒绝、模型发现、Admin 页面/认证/CLI、具体模型调用及响应头、受限角色拒绝、oMLX 形状的加载流程。它还明确断言默认 `daily` 别名解析为 `omlx` 后失败、resident 别名原样透传，以及后端晚启动时模型发现 200 但聊天持续 503、自有 iDoris 重启后聊天 200。可在上述命令末尾加 `--late-backend-only` 单独复现晚启动用例。此脚本刻意固定 v0.3.0 行为，暂不接入 CI；验证 v0.3.1 前须先更新角色绑定等预期。夹具回复 `fixture-ok`，不是模型质量或真实 Agent24 的测试。原 `scripts/smoke-agent24.mjs` 使用 TS 参考实现，不能替代此归档验证。
