## 0. 先说结论

**1. 不该"选一个模型"，该选"一组角色"。** 同一个模型无法同时满足"常驻 24h 不占内存"和"复杂任务够聪明"。正确形态是四角色分层，由 Router 自动调度，用户只看到 `Local → Local Deep → Private Cloud`：

```
Fast Brain（常驻小脑）  → 意图/隐私分流、简单问答、工具选择     1–3B
Daily Brain（日常主力） → 邮件/TODO/写作/项目/知识库           7–12B
Deep Brain（本地深度）  → 复杂推理、长文档、私有难题           20–35B，按需
External Expert（外部） → 脱敏后交给 Claude Code / Codex / API 兜底
```

**2. 硬件决定"能放什么"，场景决定"该放什么"。** 两者是正交的：同样 32GB，写作者和开发者该拿到不同组合。这正是 `07 §5.3` 现有算法缺的一维（它只按 `reasoning × quality` 排序）。

**3. 对 64GB M1 Max：**「不超过 30GB」这个约束**不需要任何 sysctl 改动就成立**（macOS 默认 GPU wired 上限 ≈ RAM×66–75%，64GB 即 ~42–48GB）。真正该管的不是"单个模型多大"，而是"**同时常驻几个**"——那是 `LoadPolicy` + oMLX memory-guard 的职责，不是一个模型体积上限。

**4. 本次核验推翻了原始对话里的 4 条事实**（`lfm1.0` 许可陷阱、Qwen3.5-4B 基准来源、Ling-3.0 的 FP8/Ollama 状态、Qwen3.8-27B 量化体积），并**补上 5 个对话漏掉的候选**（Ornith 家族、Nanbeige4.2-3B、Muse-Glimmer-30B、Qwen3.6-35B-A3B、MiniCPM5-1B）。详见 §1。

**5. 本文件同时修正了仓库自身的 3 处数据错误**（`07 §3` 预算公式两端失效、`07 §5.2` catalog 的 ornith arch 写错、"35B Q4≈18–19GB"低估）与 1 处事实混淆（`docs/05` 把 35B 的 60 t/s 记成了 9B 的成绩）。详见 §3.1、§10.1。

**6. 一个被原始对话**（以及仓库 `07 §1`「KV 可量化」那句）**完全漏掉的硬约束：**

> ⚠️ **本节初稿写的是"MLX 的 KV 量化未合并"—— 经核实这是错的，已更正。**
> **准确的说法是：KV 量化已合并（PR #1832，2026-09-09）且已发布在 `mlx-lm` v0.31.3 里；但它 `--kv-bits` 会禁用连续批处理，且滑窗/rotating cache 无法量化。**
>
> **这意味着 MLX 今天无法同时服务 3–5 个带量化 KV 的长上下文模型。** 所以不是"没有这个能力"，而是"**这个能力与批处理互斥**"——**结论方向不变（长上下文仍走 GGUF），但理由完全不同**，且更难绕开。

**后果**：若某条路径只能用 fp16 KV，本文档所有"合计"要**大幅上调**——9B 的 32K KV 从 2.15GB 涨到 4.29GB，**27B 的从 4.29GB 涨到 8.59GB**。这条直接决定 §7 的三套配置是否成立，故单列 §3.3。详见 §3.3。

**7. 最重要的一条：核验推翻了本文档初稿自己的推荐——不要把 Ornith 作默认主力。**

> 独立受控 A/B 显示，Ornith 的**厂商基准跨 harness 不迁移**（换 harness 后 5/12 vs 其底座 7/12，**严格子集**），且 **Ornith-1.5-9B 有 12.6% 的 think 链在 greedy 下永不终止**——对 24h 常驻 agent 是生产级缺陷。
> **默认主力改为 `Qwen3.5-9B`**（7 项基准全核验、无此问题）；**Ornith 降为待 A/B 的实验项**。详见 §1.4 与 §7.3。

### 1.3 我不同意原始对话的三处判断（独立分析）

**① 「小模型负责隐私分类」——方向错了。**
对话把 `MiniCPM5-2B` 定位成 "privacy classification" 的执行者。这是把**授权**和**建议**混为一谈。2B 模型在隐私判定上的假阴性率不可接受（漏一条就是数据出设备），而 iDoris 的架构早就给了正确答案：`TaskProfile.privacy` **缺省即 `local_only`**（`spec.md`「保守默认」）。也就是说——

> **升障（local → remote）必须是显式 opt-in，不能是模型的判断结果。**
> 模型可以**建议**"这条看起来可脱敏"，但**授权者是确定性规则 + 用户显式声明**。

这反而**支持**用小模型：既然路由器不承担授权责任，它就不需要很聪明。但绝不能把它当防火墙。这条与 `architecture.md`「不可动摇的边界」第 1 条同源。

**② 「7B 级」对 64GB 机器不是最优目标。**
对话在 64GB 上仍以 dense 9B / 27B 为主轴。但在 ~22GB 这个体积档上，**30B-A3B MoE 严格优于 dense 27B**：内存相同（Ornith-1.5-35B-A3B Q4_K_M **21.71GB** 权重，合计 ≈24.1GB vs Qwen3.8-27B Q4_K_M **16.46GB** 权重 + KV 4.29GB + 开销 ≈ **21.8GB**），但激活参数只有 3B → **交互式生成的 tok/s 高一个档**。dense 27B 只在批处理/深度推理上赢。对"日常助理"这个交互场景，MoE 是更好的默认。

**③ 分层只按"模型大小"组织，缺"场景权重"。**
对话的四层（Fast/Daily/Deep/External）是对的，但选型逻辑仍是"越大越好，看放得下哪个"。同一台 32GB 机器，**写作者**要的是长上下文 + 中文质量，**开发者**要的是 tool-calling + SWE。`07 §5.3` 的算法只按 `capability.reasoning × quant.quality` 排序，无法表达这个差别。本文 §4–§6 补上这一维。

### 1.4 ⚠️ 核验中发现的最大问题：Ornith 的厂商基准经不起跨 harness 复现

这条**既不在原始对话里，也不在仓库任何文档里**，但它直接推翻了本文档 §7.3 的初稿推荐，必须单列。

**仓库现选的核心模型（`docs/05 §5`）是 Ornith-1.0-9B。** 核验到的第三方证据：

| 证据 | 来源 | 内容 |
|:---|:---|:---|
| ❌ **scaffold 不可迁移**（最致命） | 受控 RTX-5090 A/B | Ornith-1.0-35B 的"自写脚手架"**换 harness 后不成立**：同一批题它 **5/12** vs 其底座 Qwen3.5-35B-A3B **7/12**，且是**严格子集**。败因是 tool-call JSON 脆弱（多行 bash 触发严格 parser 500）。**合成 agentic 分（98.06）高于底座（97.5），真实 bug 却倒退** |
| ❌ **think 链不终止** | 同上 | **Ornith-1.5-9B：greedy 解码下 12.6% 的 think-on 链永不终止（25/198）**——连厂商自己的 BF16 GGUF 都复现 |
| ⚠️ **"就是 Qwen3.5-8B 档的正常水平"** | Classmethod DevelopersIO（非厂商） | JCQ 93.0 不错，但 BFCL v4 `live_simple` 74.42 / `live_parallel` 68.75。结论原话：**"standard for a Qwen3.5-8B-class model, not outstanding for an agentic-specialised one"**。BFCL 官方目录里**没有** Ornith，评测者只能借用 `Qwen/Qwen3-8B` 的 handler |
| ⚠️ **社区工具调用不靠谱** | osaurus#2327、metaharness 探测 2/15 | "Tool calling not reliable"；独立探测通过率 **13.3%** |
| ⚠️ **`<think>` 无法关闭** | 模型卡 | 始终 ON，无文档化 off 开关——对常驻低延迟场景是硬伤 |
| ⚠️ **谱系未声明 / 卡上宣称的兄弟仓不存在** | HF `cardData` | `base_model` 字段**为空**，自动化血缘工具**解不出 Ornith → Qwen**；卡上宣称的 **31B-Dense 仓不存在** |
| ⚠️ **"Opus 4.7 等价"是 397B 的成绩** | 多来源 | 该宣传只对 397B 旗舰、且只在 TB2.1/SWE-V 两项成立（同表 SWE-bench Pro 62.2 vs 64.3、ClawEval 77.1 vs 78.2 是**输的**）。**与 9B 无关** |

**结论（直接改变选型）：**

> **不要把 Ornith 系作为默认主力。** 它的 MIT 许可与 agentic-coding 定位是真实的，但：(a) 厂商基准**跨 harness 不可迁移**；(b) **12.6% 的 think 链不终止是生产级缺陷**（常驻 agent 会挂死）；(c) `<think>` 关不掉。
> **改用 `Qwen3.5-9B` 作日常主力默认**（7 项基准全部经核验、无上述问题、生态更稳），**把 `Ornith-1.5-9B` 降级为待 A/B 的实验项**。§7.3 已按此改写。

> 这正印证 `tasks.md` FU-8 那条纪律——「**绿灯不代表你以为的那件事成立**」。厂商卡上的绿灯，和一个换了 harness 还能亮的绿灯，不是同一盏。

## 2. 分析框架：四个正交维度

```
              ① 角色 Role            ② 硬件 Hardware
         Fast/Daily/Deep/External   8→128GB 可用预算
                    ╲                  ╱
                     ╲                ╱
                      选型 = 交集
                     ╱                ╲
                    ╱                  ╲
              ③ 场景 Scenario      ④ 隐私等级 Privacy
     通用/写作/开发/隐私/组织/语音    local_only ⇒ 硬约束
```

**维度间的依赖方向（关键）：**

| 维度 | 作用 | 不作用 |
|:---|:---|:---|
| ② 硬件 | **筛除**放不下的候选（硬门槛） | 不决定"该选哪个" |
| ④ 隐私 | **收窄**候选集到 `tier ∈ {local, lora}`（硬约束） | 不参与打分 |
| ③ 场景 | 决定能力**权重**（加权排序） | 不改变门槛 |
| ① 角色 | 决定**量化档**与 `LoadPolicy`（常驻/按需） | — |

> 即 `候选 = 硬件筛(全目录) → 隐私筛 → 场景加权打分 → 按角色分配量化与装载策略`。
> 这是对 `07 §5.3` 伪代码的**扩展**，不是替换——原有 `min_ram_gb` / `quality_threshold` 门槛全部保留。

## 3. 硬件档位与可用预算

### 3.1 ⚠️ 先修正 `07 §3` 的公式（本文件发现）

`07 §3` 给的三档是：

```
conservative = RAM × 0.66
moderate     = RAM − 6
aggressive   = RAM − 4
```

**实测复算，这个公式在两端都失效：**

| RAM | cons(0.66R) | mod(R−6) | agg(R−4) | 问题 |
|---:|---:|---:|---:|:---|
| 8GB | 5.3 | **2.0** | 4.0 | ❌ 排序倒置：moderate < conservative，且 aggressive < conservative |
| 16GB | **10.6** | 10.0 | 12.0 | ❌ 排序倒置：moderate < conservative |
| 24GB | 15.8 | 18.0 | 20.0 | ✅ |
| 64GB | 42.2 | **58.0** | 60.0 | ❌ `RAM−6` = **91% of RAM**，远超 Apple「≤70% 且留 8–16GB」的建议 |
| 128GB | 84.5 | **122.0** | 124.0 | ❌ 95% of RAM |

**根因**：两条曲线在 `RAM = 17.65GB` 处交叉（`0.34R = 6`），而 `RAM−6` 在大内存端不再构成任何约束。

**修正建议**（提请修订 `07 §3`，并同步 `T2.1.1` 的验收基线）：

```python
reserve(RAM)      = clamp(RAM × 0.30, 3, 16)    # 给系统的绝对保留，随 RAM 缩放，上下限兜底
usable(RAM, tier) = min(RAM × pct, RAM − reserve(RAM))
pct ∈ { conservative: 0.66, moderate: 0.70, aggressive: 0.75 }
```

| RAM | reserve | conservative | moderate | aggressive | 常见机型 |
|---:|---:|---:|---:|---:|:---|
| 8GB | 3.0 | 5.0 | 5.0 | 5.0 | MacBook Air M1/M2/M3 基础款 |
| 16GB | 4.8 | 10.6 | 11.2 | 11.2 | MacBook Air / Pro 基础款 |
| 18GB | 5.4 | 11.9 | 12.6 | 12.6 | M3 Pro 基础 |
| **24GB** | 7.2 | **15.8** | 16.8 | 16.8 | **Mac mini M4（部署目标）** |
| 32GB | 9.6 | 21.1 | 22.4 | 22.4 | M1 Max / M4 高配 |
| 36GB | 10.8 | 23.8 | 25.2 | 25.2 | M3/M4 Max 基础 |
| 48GB | 14.4 | 31.7 | 33.6 | 33.6 | M4 Pro 高配 |
| **64GB** | 16.0 | **42.2** | 44.8 | 48.0 | **M1/M2 Max（你的机器）** |
| 96GB | 16.0 | 63.4 | 67.2 | 72.0 | M2 Max 高配 |
| 128GB | 16.0 | 84.5 | 89.6 | 96.0 | M3/M4 Max 高配 |

> 8GB 上三档收敛到同一个数（~5GB）——这是**诚实的结果**，不是公式缺陷：8GB 机器上给系统的保留是硬的，改策略拿不到更多。

### 3.2 64GB 上的「30GB」约束怎么读

你的原始要求是「占用不超过一半，最好十几 G」。**这个直觉是对的，但机制该换：**

| 你的表述 | 实际含义 | 正确机制 |
|:---|:---|:---|
| "不能超过 30GB" | 怕机器被吃满 / 卡顿 / OOM | `oMLX --memory-guard balanced --memory-guard-gb 30`（**运行时闸门**，不是模型体积上限） |
| "最好是十几 G" | 常驻主力别太重 | 常驻 **9B Q6 ≈ 10.5GB**，符合 |
| — | 没说的第三件事 | **同时常驻几个**才是内存的真正变量（KV 随上下文线性涨） |

**关键事实**：64GB 的 conservative 预算就是 **42.2GB**，你的 30GB 目标**落在其中，且不需要碰任何 sysctl**。U0 已在 64GB 机上用 `--memory-guard-gb 16` 模拟过 24GB 预算并通过（`U0-LOG`），同一机制直接可用于 30GB。

> ⚠️ **oMLX 版本的注意事项**（本次核验）：U0 测的是 **v0.4.3**，当前稳定版已是 **v0.6.4**（2026-08-29，[jundot/omlx](https://github.com/jundot/omlx)，Apache-2.0，21.9k star）。
> - `--memory-guard` 的取值是 **`{safe | balanced | aggressive}`**（`07 §5.2` 写对了，本文档 §7.1 已按此写）。
> - `ProcessMemoryEnforcer` 的上限**默认 = 系统 RAM − 8GB**（64GB 机即 56GB）——**必须显式用 `--memory-guard-gb` 收紧**，否则默认值远超我们的 30GB 目标。
> - **[issue #2290](https://github.com/jundot/omlx/issues/2290)：模型换入依赖 Memory Guard——不开启时第二个模型载入会让 server 无响应。** 即 memory-guard 在实践中**不是可选项**。
> - 新 CLI 还多了 `--paged-ssd-cache-dir`（冷 KV 落盘）、`--hot-cache-max-size`（热缓存占比）。

### 3.3 ⚠️ 被漏掉的隐藏约束：MLX 的 KV 量化**与批处理互斥**（决定预算能否成立）

`07 §1` 断言「**KV 可量化**：Q8 KV 减半、Q4 KV 减到 1/4。长上下文必须量化 KV」。**方向正确，但在我们选定的 MLX 后端上不是白拿的**：

| 路径 | KV 量化状态 | 可用方式 |
|:---|:---|:---|

> **决定性约束（改写后的选型含义）**：
> `--kv-bits` 禁用批处理 + 滑窗 KV 无法量化 ⇒ **MLX 今天无法同时服务 3–5 个带量化 KV 的长上下文模型。**
>

>

### 7.3 为什么默认主力是 Qwen3.5-9B（而不是 Ornith-1.5-9B）

两者**同架构**（`qwen3_5`，32L/4kv/256d/hidden 4096）、体积几乎相同，所以初稿把它列为"Ornith 升级"。**核验后这个判断被推翻**（§1.4）：

| 维度 | Qwen3.5-9B | Ornith-1.5-9B | 结论 |
|:---|:---|:---|:---|
| 许可 | Apache-2.0 | MIT | 平（都可用于托管） |
| 基准可信度 | **7 项全部经 HF 卡核验 ✅** | 仅厂商自报 ⚠️ | **Qwen 胜** |
| 跨 harness 复现 | 无负面证据 | ❌ **5/12 vs 底座 7/12，严格子集** | **Qwen 胜** |
| 长任务稳定性 | 无已知问题 | ❌ **12.6% think 链不终止** | **Qwen 胜（决定性）** |
| reasoning 开关 | 可控 | ❌ `<think>` 强制 ON，关不掉 | **Qwen 胜** |
| 通用知识 / 中文 | MMLU-Pro 82.5 · 201 语言 | 未报告 · ❓ | **Qwen 胜** |
| 多模态 | ✅ 视觉 + 视频 | 有 mmproj（视觉） | 平 |
| 生态血缘 | 官方 base 仓 `Qwen3.5-9B-Base` 存在 | `base_model` 元数据**缺失**，血缘工具解不出 | **Qwen 胜（联邦对齐要靠它）** |
| agentic coding | 未专精 | 定位专精（但未证实） | **Ornith 名义领先，实测未兑现** |

> **判据**：你的场景是"管理日常工作 + 处理隐私 + 复杂任务转外部"。这是**长期常驻**的 agent——**"12.6% 的 think 链不终止"直接否定它作为默认主力**（会挂死且无人值守）。故：
> - **默认 = `Qwen3.5-9B`**（MLX-4bit 起步，需要质量时切 MLX-8bit）
> - **`Ornith-1.5-9B` 降为实验项**：若你是重度 agentic coding 用户，值得花一天做 A/B（同 harness、同题集），**以你自己的实测为准**——这正是 §1.4 的教训。
> - 若 A/B 后 Ornith 确实更好，再改 `IDORIS_CORE_MODEL` 即可，**契约不变**。

### 7.4 同机型实测参考（⚠️ 社区自报，非受控基准）

oMLX 的社区基准库里有**与你完全同机型**的一条记录，正好是本文档推荐的深度模型：

| Mac | 模型 | 峰值进程内存 | 生成速度 |
|:---|:---|:---|:---|
| **M1 Max 64GB** | **Qwen3.6-35B-A3B-MLX-4bit** | 19.4GB @1k → **21.4GB @4k** | 67.2 → **64.8 tok/s**（batch 4× = 229.5 tok/s） |
| M4 Pro 24GB | Qwen3.5-9B-MLX-4bit | 5.8GB @1k → 6.3GB @4k | 31.5 → 30.0 tok/s |
| M4 32GB | Qwen3.5-35B-A3B-oQ3 (3-bit) | 17.1 → 19.9GB @64k | 91.2 @1k → **9.5 @32k** ⚠️ |
| M1 16GB | Qwen2.5-7B-Instruct-MLX-4bit | 4.8 @8k → 5.3GB @16k | 13.5 → 11.1 tok/s |

**三个可用的结论：**

1. **§7.1 配置 B/C 的深度模型在你的机器上确实跑得动、且跑得好**：21.4GB @4k、65 tok/s，比稠密 27B 的交互体验好得多（这正是 §1.3 ② 的理由）。MLX 4-bit 比 GGUF Q4_K_M 小 5–10%，所以 §5.3 的 22.13GB(GGUF) 对应 MLX 约 20–21GB。
2. **⚠️ 长上下文会击穿 MoE 的速度优势**：同族 3-bit 在 32GB 上从 91 tok/s（1k）**崩到 9.5 tok/s（32k）**。这正是「内存按 total 算、速度按 active 算」之外的第三个变量——**上下文长度同时吃内存和吃速度**。§7.1 的 guard 值按 **32K 上下文**设，不要按 128K 想。
3. **量化权重不覆盖实际占用**：本次核验的独立结论是「**按 权重 + 3–6GB 预留**」。§5 用的 `+1GB overhead` **偏乐观**，这是附录 B-4 要回归校准的原因。

> 该基准库是**社区自报、无提交管控**（462k 行，可见重复），故只作量级参考，不作验收依据。

## 8. 隐私升障设计（硬门，不可省）

原始对话说"绝对不要让 LLM 自己成为唯一的隐私防火墙"——**这条我完全同意，并把它落成可实现的顺序**：

```
请求进入
  │
  ├─ ① 确定性规则层（必跑，先于任何模型）
  │    路径/密钥/API key/密码/邮箱/手机号/身份证/银行卡/客户名/私有 repo
  │    → 命中即标记 PRIVATE，禁止出网
  │
  ├─ ② TaskProfile.privacy 解析
  │    显式 header 优先；【未声明 ⇒ local_only】（spec.md 保守默认）
  │
  ├─ ③ 小脑模型（可选，只做"建议"）
  │    MiniCPM5-2B 输出 {suggested_class, reason, entities[]}
  │    ⚠️ 它只能"建议升障"，不能"授权降障"
  │
  ├─ ④ 授权判定（确定性）
  │    local_only ⇒ tier ∈ {local, lora}，无候选 ⇒ 503 local_only_unavailable（终态）
  │    any + 用户显式声明 ⇒ 允许远程，但须过 ①②再复核（不信任 policy，二次校验）
  │
  └─ ⑤ 脱敏 → 外部 → 本地回填
       Alice → PERSON_001；返回后本地还原（映射表不出设备）
```

**三条不可协商：**

1. **升障是显式 opt-in**，缺省 `local_only`。小模型**没有**"决定可以上云"的权力。
2. **确定性规则先于模型**。模型漏判的代价是数据出设备，规则漏判的代价是一条误报——**代价不对称，顺序就不能反**。
3. **`fail_closed` 是终态**，不降级（`spec.md` 状态机 `REJECTED_LOCAL_ONLY`）。这与 `architecture.md`「不可动摇的边界」第 1 条完全一致——本文档不新增机制，只是把"小模型做隐私分类"这个误读**纠正回**既有架构。

### 9.1 角色 → `LoadPolicy` 映射

| 角色 | 建议配置项 | `LoadPolicy.mode` | 组件卡映射（oMLX） |
|:---|:---|:---|:---|
| Fast Brain | `IDORIS_FAST_MODEL` | `resident` | `model_settings.is_pinned = true` |
| Daily Brain | `IDORIS_CORE_MODEL` | `resident`（默认）或 `on_demand` | `is_pinned = true` / unpinned |
| Deep Brain | `IDORIS_DEEP_MODEL` | `on_demand` / `evict_to_load` | unpinned + ProcessMemoryEnforcer |

### 9.2 对 `T2.1.2` 推荐算法的修正建议

`07 §5.3` 现有伪代码：

```
score[m] = m.capability.reasoning × q.quality
resident = argmax(score)
```

**建议扩展为场景加权**（保留全部原有门槛）：

```python
usable = usable(ram_gb, wired_mode)                       # §3.1 修正公式

cands = [m for m in catalog if ram_gb >= m.min_ram_gb]    # ① 硬件硬门槛
if task.privacy == 'local_only':                          # ② 隐私硬约束
    cands = [m for m in cands if m.tier in ('local', 'lora')]
if deploy_mode == 'tenant':                               # ②' 许可/合规红线
    cands = [m for m in cands if m.license not in REDLINE_LICENSES]

def score(m, q, scenario):                                # ③ 场景加权
    return sum(scenario.weight[cap] * m.capability[cap] for cap in scenario.weight) * q.quality

resident = argmax(score(m, best_quant(m), scenario) for m in cands)
# 其余角色：按 scenario 的次要权重依次 admission，放不下则标 requires_eviction
```

> 与 `07 §5.3` 的差异只有两处：**① 打分从 `reasoning × quality` 换成场景加权**；**② 增加许可红线过滤**（§5.5）。原有 `min_ram_gb` / `quality_threshold` / `footprint ≤ budget` 门槛全部保留。

配套给 `catalog.yaml` **新增三个字段**：`roles: [fast|core|deep]`、`scenarios: {s1: .., s2: ..}`、`license: <spdx>`（用于 §5.5 红线过滤）。

### 9.3 与三能力的关系（不越界）

| 角色 | 对应能力 | 越界风险 |
|:---|:---|:---|
| Fast / Daily / Deep | 能力③ 本地模型 | 无 |
| External Expert | 能力② 外部 API | 须过隐私门；`budget_exceeded` 是**拒绝不是降级**（`T1.5.2`） |
| （订阅中转） | 能力① | **`deploy_mode=tenant` 下拒绝注册**；**必须沙箱化**（`ecosystem-boundaries.md §5.1`：`claude`/`codex` 是带工具能力的 agent 程序，不沙箱 = 绕过 Agent24 审批门） |

> ⚠️ 原始对话建议"复杂问题交给 Claude Code / Codex"。**在 iDoris 架构里这条有前提**：能力①的 CLI 必须跑在无工具、无工作区写权限的沙箱里，否则它给调用方开了一条绕过审批门的通道。这条已写进 `T1.4.1` 的验收命令。
