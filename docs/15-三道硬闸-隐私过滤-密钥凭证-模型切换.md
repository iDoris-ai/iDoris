## 0. 为什么叫「闸」不叫「功能」

三道闸有一个共同点，也是它们值得单独成文的原因：

> **它们都是结构性保证（structural guarantee），不是"尽力而为"（best effort）。**

| | 功能（best effort） | 闸（structural） |
|:---|:---|:---|
| 隐私 | "我们检测并脱敏敏感信息" | **默认不出网；只有规则证明可出网才出网** |
| 密钥 | "我们不把密钥写进 prompt" | **密钥从构造上不进上下文——模型只见到 handle** |
| 模型 | "我们支持切换模型" | **调用方只依赖角色名；具体模型可换而不改调用方** |

**贯穿三道闸的设计原则：让失败的方向指向可用性损失，而不是安全事故。**

这条不是修辞。它把"机械规则不可能完备"——一个无法回避的事实——从**致命缺陷**变成**可接受的成本**。详见 §1.1。

## 1. 闸一 · 程序级机械隐私过滤

### 1.1 ⚠️ 必须先纠正的前提（这条决定闸一能否成立）

原始需求是「即便模型漏网了，所有隐私我们也会通过代码和机械规则留在本地」。**方向对，但表述必须改一个字**，否则无法实现：

| 说法 | 能否实现 | 原因 |
|:---|:---|:---|
| ❌ "扫到隐私 → 拦住" | **不能保证** | 机械规则必然不完备：未枚举的实体类型、编码变形、上下文依赖的标识符，都会漏。漏一次就是数据出设备 |
| ✅ "**默认不出网 → 规则证明安全才放行**" | **能保证** | 漏检的后果退化为"本可出网的请求没出网"——**可用性损失，不是安全事故** |

**所以闸一不是一道"过滤网"，是一道"放行闸"：**

```
              ┌──────────────────────────────────────────────┐
   请求内容 ──▶│  默认：local_only（spec.md 已有的保守默认）    │
              │                                              │
              │  闸一 = 把 local_only 提升为 any 的            │
              │        【唯一合法通道】                        │
              │                                              │
              │  证明失败（含扫描器报错/超时）⇒ 维持 local_only │
              └──────────────────────────────────────────────┘
```

**三个直接推论：**

1. **闸一是唯一的升障通道。** `X-iDoris-Privacy: any` 这个 header **不再是授权**，只是"请求评估"；真正的授权由闸一输出。
2. **扫描器失败必须是 fail-closed**：抛异常、超时、OOM、规则库加载失败 —— **一律维持 `local_only`**，不是"跳过检查继续"。这与 `architecture.md`「出网控制是启动断言」同源。
3. **保证的准确表述**（对外只能用这个）：
   > "**所有命中我们规则的内容不会离开设备。**"
   > 不能说："所有隐私都不会离开设备。"
   >
   > 前者是可验证的工程承诺；后者是无法兑现的营销话术。**两者差一次事故。**

### 1.1b ⚠️ 必须补上的要件：「没扫到」不能当证明

上面把闸一定义为"放行闸"，但**放行的依据是什么**？这里有致命陷阱，调研数据正好把它照出来：

| 调研发现 | 含义 |
|:---|:---|
| 规则法在**高敏类别**召回仅 **0.07**（REDACT, arXiv:2606.19881）| **"L0 没命中"是极弱的证据** |
| 替换策略（redact / faker / hybrid）泄漏率**完全相同，都是 0.249**（arXiv:2605.13538）| **隐私上限由检测召回率（≈0.627）决定，与怎么替换无关** |
| 在 `[PERSON]` 脱敏语料上训练的 NER 得 **F1 = 0.000** | 占位符会摧毁下游可用性 |
| 1-bit 小模型在固定 few-shot 下，对"杨娟""山田太郎"**照样吐出 demo 里的 "Alice Johnson"** | 模型回显占位符是真实故障，不是理论风险 |

> **结论（改写闸一的实现）：`ALLOW` / `REDACT` 的正当性不能来自"扫描没发现东西"，必须来自"出网的内容是被构造出来的"。**
> 即 **absence of evidence ≠ evidence of absence**——`tasks.md` FU-8 那句"绿灯不代表你以为的那件事成立"在隐私上的化身。

**放行只允许三种"承重"依据：**

| # | 依据 | 为什么承重 | 适用 |
|:---|:---|:---|:---|
| **P-1** | **内容是被构造的，不是被转发的**——出网的是本地模型**生成的派生文本**（摘要/分类/草稿），不是原文 | 原文根本没进过出网通道，与扫描召回率无关 | ⭐ 主路径 |
| **P-2** | **用户显式声明 + 内容类型白名单**（如"这是公开文档"）| 责任明确；类型受限使风险有界 | 辅路径 |
| **P-3** | **L0 零命中 且 结构校验全过 且 输入未超限** | 三重条件**同时**成立才构成弱证明——**单独"零命中"不算** | 加分层 |

**且：L0 的低召回在这里不再致命。** 因为默认"不出网"，低召回 = **能证明的更少** = 更多请求留本地 = **失败方向指向可用性**（§1.1）。**这就是 fail-closed 重构的价值。**
> ⚠️ 反之：**若有人把默认改成"扫到才拦"，上面全部推理立刻失效**，低召回会直接变成漏放。**两者不能混用。**

### 1.1c 三条来自实测的实现红线

| # | 红线 | 依据 |
|:---|:---|:---|
| **X-1** | **超大输入必须"截断并拒绝"，绝不能"扫一部分就放行"** | 规则引擎在高敏类别召回 0.07，分块又丢上下文。**扫前缀再放行是经典 fail-open** |
| **X-2** | **校验和失败 ⇒ 降级，不是硬拒** | Faker 的 `zh_CN` 身份证 provider **校验和有效**（实测确认）；15 位老身份证**无校验位**；OCR/手误常失败。硬拒造成大量误伤 |
| **X-3** | **必须两套独立规则集** | Gitleaks 8.21.2 有**硬编码终结符允许列表缺陷**，导致**多数凭证类型完全漏检**（召回 **0.9976 → 0.5233**）。单一规则源 = 单点失效 |

### 1.2 分层设计

```
┌─ L0 机械规则（纯代码，零模型依赖）────────────────────────┐
│  · 正则 + 校验和（身份证 Luhn/加权、银行卡 Luhn）           │
│  · 高熵串检测（API key / 私钥 / token）                    │
│  · 已知密钥前缀白名单（sk- / AKIA / ghp_ / -----BEGIN …）   │
│  · 路径与文件名（~/.ssh, .env, *.pem, keychain）           │
│  · 附件与上下文元数据（来源、收件人、租户）                  │
│  ⚠️ 这一层是硬保证所在。它必须能独立运行、无网络、可单测。   │
└───────────────────────────────────────────────────────────┘
                          │  只能"提升"隐私等级
                          ▼
┌─ L1 语义增强（可选，模型参与）─────────────────────────────┐
│  · NER / 小模型判定中文姓名、机构、地址、项目代号            │
│  ⚠️ 单向阀：L1 只能把 any 降回 local_only，              │
│     永远不能把 local_only 提升为 any。                     │
│  ⚠️ L1 不可用时，系统仍然正确（只是更保守）。               │
└───────────────────────────────────────────────────────────┘
                          │
                          ▼
┌─ L2 策略判定（确定性，无模型）────────────────────────────┐
│  输入：L0 命中集 + L1 建议 + 用户显式声明 + 租户策略        │
│  输出：BLOCK | REDACT | ALLOW + 非空 reason                │
│  规则是数据（YAML），不是代码分支                          │
└───────────────────────────────────────────────────────────┘
```

**单向阀是这套设计的关键**：模型可以让我们**更保守**，但不能让我们**更冒险**。这样 L1 的假阴性不构成安全风险——只是少了一层额外保护。

#### 1.2b 调研回填：选库（结论是"自建"）

> **核心发现：没有任何库同时提供"生产级中文"和"Rust/Node 原生路径"。**
> Presidio、scrubadub、piiranha、OpenAI 的 Privacy Filter **全部不含中文**（Presidio recognizer 只有 `[en]`，仓库 `zh|chinese|china` 路径数 = **0**）。**所以 L0 自建，只买英文/密钥那一半。**

| 层 | 选型 | 依据 |
|:---|:---|:---|
| **L0 多模式匹配** | Rust **`vectorscan`/`hyperscan`** + Aho-Corasick（RE2 式线性时间、**无回溯**；`StreamingDatabase` 跨块保状态，处理流式切分） | noseyparker 实测 **1.11 GiB/s** |
| **L0 密钥规则** | 种子取 **gitleaks（MIT）**；**必须补第二套**（X-3）。备选 **`betterleaks`**（gitleaks 作者新作）、**Titus**（唯一 Go **库**形态：`ScanString`、默认离线、487 规则；noseyparker 已归档） | gitleaks 已声明"功能完成，仅安全补丁" |
| **L0 中文实体** | 自建：正则 + **结构校验** + 校验和（§1.7）| 无可用库 |
| **L1 语义（可选）** | ONNX 跑英文 PERSON/ADDRESS；**中文 NER 仅供参考** | 中文 PII 模型全部 ≤~60 下载量，未检验 |
| **不要用** | `trufflehog`（**AGPL-3.0**，且其"验证"会**把你要拦的密钥发去 provider**）；`ggshield`（需 GitGuardian 云 API）；`piiranha`（**CC-BY-NC-ND-4.0**，禁商用）；`detect-secrets`（2024-05 停更）；`presidio` / `scrubadub` 直接用于中文 | 见各项 |

**性能（决定 L1 能不能上热路径）：**

| 层 | 1–4 KB | 100 KB+ | 结论 |
|:---|:---|:---|:---|
| **L0 规则** | **≲1 ms** | 低个位数 ms | ✅ **可每请求跑** |
| **L1 NER（CPU）** | **~1–1.7 s / 512 tokens** | 完整替代管线 **41.2 s/文档** | ❌ **绝不能放热路径**——异步，或只在已标记片段上跑 |

> ⚠️ 所以 **L1 实质只能是"事后加严"或"仅对 L0 命中片段做语义扩边"**。这与 §1.1b 的 P-1 呼应：**真正的保证不来自扫描覆盖面，来自构造方式。**

### 1.3 三种动作，各自的语义

| 动作 | 含义 | 何时用 | 失败模式 |
|:---|:---|:---|:---|
| **BLOCK** | 请求不出设备，返回 `local_only_unavailable` 或本地模型处理 | L0 硬命中（密钥、私钥、证件号） | 无——这是最安全的分支 |
| **REDACT** | 占位符替换 → 出网 → 本地回填 | 可枚举、可逆的实体（姓名/公司/号码），且用户显式同意 | **见 §1.4，这条最容易出事** |
| **ALLOW** | 原样出网 | L0 零命中 且 用户显式 `any` 且 租户策略允许 | 漏检 → 但此时"默认不出网"已经兜住了大部分 |

> **默认动作是 BLOCK，不是 ALLOW。** 新增规则类型时，未覆盖的实体落在 BLOCK 侧。

### 1.4 ⚠️ 可逆脱敏（REDACT）的失败模式 —— 最容易出事的一环

替换-回填看起来简单，实际有四个已记录的失败点：

| # | 失败模式 | 后果 | 防御 |
|:---|:---|:---|:---|
| R-1 | 模型**改写或吞掉**占位符（`PERSON_001` → `PERSON 001` / `某人`） | 回填失败，输出残缺 | 回填前做占位符集合比对；**数量或类型不匹配 ⇒ 拒绝回填并告警**，不猜 |
| R-2 | 模型**幻觉出**不存在的占位符 | 回填把无关内容替换成隐私 | 只回填**本地映射表里存在**的占位符；未知占位符原样保留并告警 |
| R-3 | 模型**复述**占位符到不该出现的地方 | 占位符污染用户可见文本 | 输出后扫描残留占位符，有残留 ⇒ 标记并提示 |
| R-4 | 映射表**泄漏或落盘** | 脱敏等于没做 | 映射表只在进程内存、**绝不落盘、绝不进审计**、随请求结束销毁；审计只记 `{entity_type, count}` |

**硬规则**：R-1 与 R-2 必须**拒绝服务而不是尽力修复**。理由同 `T1.5.2`——"悄悄降级"比"明确报错"危险得多。

### 1.5 状态机位置（对 `spec.md` 的修订建议）

`spec.md` 现有：

```
RECEIVED ─▶ PROFILED ─▶ POLICY_MATCHED ─▶ BUDGET_CHECK ─▶ CANDIDATES ─▶ ADMITTED ─▶ DISPATCHED ─▶ DONE
```

**建议插入 `INSPECTED` 阶段**（内容级扫描必须在任何路由决策之前，因为它决定 `privacy`）：

```
RECEIVED ─▶ INSPECTED ─▶ PROFILED ─▶ POLICY_MATCHED ─▶ BUDGET_CHECK ─▶ CANDIDATES ─▶ ADMITTED ─▶ DISPATCHED ─▶ DONE
              │                                                                          │
              └─ 扫描器异常 ⇒ 强制 privacy=local_only，带 reason=inspect_failed          └─ 见闸三
```

**顺序即语义**（沿用 `spec.md` 已有纪律）：`INSPECTED` 必须在 `PROFILED` 之前，因为 `PROFILED` 会读 `X-iDoris-Privacy`——而闸一有权**否决**这个 header。反过来写就等于让调用方自己授权。

### 1.6 测试策略（这是闸一能否被称为"硬"的唯一依据）

沿用 `tasks.md` FU-8 的纪律——**"绿灯不代表你以为的那件事成立"**，故闸一的测试必须包含三类，缺一不可：

| 类别 | 作用 | 具体做法 |
|:---|:---|:---|
| **哨兵串（sentinel）** | 证明"命中的确实没出网" | 注入唯一随机串，断言它**不出现在**任何出站载荷、日志、审计中 |
| **负对照（negative control）** | 证明"探针真的能抓到" | 造一条**刻意违规**的用例，断言它**必须**被拦。**拦不住 ⇒ 判闸一未完成**（探针不承重，它的"零泄漏"什么都不证明） |
| **变异测试（mutation）** | 证明"检查在承重" | 逐条删掉 L0 规则，断言对应用例**变红**。全绿说明那条规则根本没被用到 |

外加**逃逸用例集**（L0 必须扛住的变形）：

```
编码类：base64 / hex / URL-encode / unicode escape
隐形类：零宽字符插入 / 同形字（homoglyph）/ 全角半角混用
切分类：分段成多行、拆进不同字段、跨消息分片
结构类：藏在文件路径、文件名、Excel 单元格、图片 OCR 文本、代码注释
上下文类：单个"张伟"难判，但"张伟 + 身份证 + 住址"必须命中
```

> **向量维度要对得上错误方向**（FU-8）：闸一要抓的错误是"**漏放**"，所以判据必须是"**该拦的拦住了几条**"，而不是"拦住了多少条"。断言写成"至少有 N 条被拦"是**测不出漏放**的——那正是 FU-8 说的量纲不匹配。

### 1.7 中文实体规则集（调研核到标准原文，可直接实现）

| 标识符 | 标准 | 格式 | 校验和 |
|:---|:---|:---|:---|
| **身份证号** | **GB 11643-1999** ✅ | 6 位行政区划（**GB/T 2260**）+ YYYYMMDD + 3 位顺序（奇=男）+ 1 位校验；**15 位老号无校验位** | **ISO 7064 MOD 11-2**；权重 `7,9,10,5,8,4,2,1,6,3,7,9,10,5,8,4,2`；校验码表 `10X98765432`（已复现标准示例 ✅）|
| **手机号** | MIIT | `1[3-9]\d{9}` **在 2026 仍正确** ✅；**140–144 是 13 位物联网号** ⚠️ | 无 ✅ |
| **银行卡号** | ISO/IEC 7812-1 | 16–19 位；银联 BIN **62**/81 ✅ | **Luhn** ✅ |
| **统一社会信用代码** | **GB 32100-2015** ✅ | 1 登记部门 + 1 机构类别 + 6 区划 + 9 主体标识 + 1 校验；**排除 I、O、Z、S、V** ✅ | **MOD 31-3**；权重 `1,3,9,27,19,26,16,17,20,29,25,13,8,24,10,30,28`（已复现示例 ✅）|
| **车牌号** | **GA 36-2018** ✅ | 省份简称 + 字母 + 5 位；**新能源 +6**：D/A/B/C/E 纯电，F–K 非纯电 | 无 |
| **护照号** | 国家移民管理局 ✅ | `E`+8；**2017-04 起 `E`+字母+7**（排除 I、O）；`G`+8 为旧式 | 无 ✅ |
| **港澳台** | — | **HKID** 权重 `9,8,7,6,5,4,3,2`、空格=36、`(11−sum%11)%11` ✅ 数值验证；**回乡证 `H`+8 / `M`+8**；**台胞证 8 位**；18 位形式是台湾居民居住证（`830000`）| 澳门 ❓、台湾 ❓ |

**⚠️ 最重要的工程结论：结构校验压倒校验和。**

| 手段 | 随机数字的假阳性降幅 |
|:---|:---|
| Luhn | 10× |
| MOD 11-2（身份证）| 11× |
| MOD 31-3（统一社会信用代码）| 31× |
| **再加 GB/T 2260 区划有效 + 日历有效日期** | **≈ 1.4×10⁻⁷** |

> **校验和只降一个数量级，结构校验降六个。** 所以实现顺序是「**区划 → 日历 → 校验和**」，不是"正则+校验位"就完事。
> 且它**抓不住**"格式对但人不对"，也**抓不住合成数据**——**Faker 的 `zh_CN` 身份证 provider 是校验和有效的**（实测）。这正是 X-2 说"校验和失败要降级不要硬拒"的另一面。

**中文姓名**：规则法（姓氏表 + 1–2 字名 + 边界规则）**精确率可达 97%，但召回仅约 68.8%**（1998 bakeoff）；角色标注/HMM 可达 **F1 95.40%**（张华平 & 刘群 2004）。在自由文本中会误伤——`刘庄`、`吕梁` 是"姓+字"但为地名。
> **定性：姓名规则是"增强器"，不是"检测器"**——它可以提升已有命中的置信度，不能作为独立的拦截依据。

## 2. 闸二 · 本地密钥与凭证代理

### 2.1 结构性保证（不是"我们很小心"）

> **密钥从构造上就不进入模型上下文。模型只见到 handle，见不到值。**

这不是靠"记得不要把密钥放进 prompt"，而是靠**接口形状**：模型能看到的唯一东西是一个不透明引用（如 `secret://openai/default`），真实值只在**闸二进程的内存里**，在**出网那一瞬间**被注入。

| 层 | 能看到密钥值？ |
|:---|:---|
| 模型（本地或远程） | ❌ 永远不能 |
| Agent / 调用方 | ❌ 不能 |
| iDoris Router 的**策略层** | ❌ 不能（只处理 handle） |
| iDoris Router 的**注入点**（最小面积） | ✅ 能，且仅此一处 |
| 审计日志 | ❌ 不能（只记 `secret_id` 与用途） |

**关键设计**：注入点应当是**代码里面积最小的一块**——理想上只有一个函数、一处解引用。面积越小，可审计性越高。

### 2.1b ⚠️ 但"同进程内存隔离"在 macOS 上**不是安全边界**（调研发现，必须修正上表）

上表的最后一道防线（"密钥只在注入点进程的内存里"）**在 macOS 上被一个有记录的漏洞否证**：

> **CVE-2025-24204**：Apple 在 macOS 15.0 给 `/usr/bin/gcore` 授予了 `com.apple.system-task-ports.read` entitlement，使其能**在 SIP 开启的情况下 dump 任意进程的内存**。研究者（FFRI, Koh M. Nakagawa）据此从 `securityd` 的内存转储中**还原出登录钥匙串的主密钥**。macOS 15.3 修复，但**它证明的规律不会随补丁消失**：同机上任何一个持有合适 entitlement 的二进制，都能读到你 broker 进程里的明文。

**因此设计要求提高一档：**

| | ❌ 不够 | ✅ 应当 |
|:---|:---|:---|
| 隔离手段 | 同进程内的模块边界 / 类型封装 | **独立 UID 的独立进程**（`launchd` 托管的服务账户） |
| 密钥可读范围 | "只有注入点函数能读" | **只有该 UID 能读**；Router 主体即使被攻陷也读不到 |
| 传递方式 | 进程内函数调用 | **Unix domain socket + 文件权限 0600**，每次请求临时授权 |

**这修正了本文件 §2.1 的一句话**：结构性保证依然成立（**模型与调用方**永远看不到密钥值），但"**本机同用户下的其他进程也看不到**"这个更强的宣称**不成立**，必须删掉。

> 与 §13/§2.5 的威胁模型合并：闸二把"密钥泄漏"从**默认可能**变成**需要攻破本机**——而**独立 UID** 把这个门槛再抬高一层（从"攻陷主进程"变成"拿到另一个 UID 的权限"）。**这是可做的最强隔离，不是绝对隔离。**

### 2.2 存储（调研确定）

#### 2.2a ⚠️ 一条决定架构的 Apple 约束：必须是 **LaunchAgent，不是 LaunchDaemon**

> ✅ **Apple TN3137 原文**：「Programs that run outside of a user context, like a `launchd` daemon, **must target the file-based keychain**. The **data protection keychain is only available to programs running in a user context**.」

**这一条同时否掉三样**：生物识别（`kSecAccessControlBiometryCurrentSet`）、Secure Enclave 密钥保护、keychain access group —— **全都要 data protection keychain**，因而**全与系统级 LaunchDaemon 互斥**。

| 结论 | 说明 |
|:---|:---|
| ✅ **形态 = LaunchAgent（用户登录上下文）** | 不是 root LaunchDaemon |
| ✅ **存储 = data protection keychain，由 Secure Enclave 的 P-256 不可导出密钥包裹**，**不设 `userPresence`** | ⇒ 启动**无提示**解封，**磁盘上无主密钥** |
| ⚠️ **生物识别与无人值守互斥——必须二选一** | 无头调用方须设 `LAContext.interactionNotAllowed = true`，否则弹窗；随后以 `errSecInteractionNotAllowed` 失败 |
| ⚠️ access group 还需**代码签名 entitlement + Apple team 前缀 + provisioning profile**，对 CLI 形态很别扭 | 尽量不用 |

> **取舍建议：选「无提示」**（不设 `userPresence`）。iDoris 是 24h 常驻服务，弹窗解锁等于不可用。**代价要写明**：等于"以该用户身份登录的任何进程都能解封"——隔离靠 §2.1b 的独立 UID，不靠生物识别。

#### 2.2b 库（✅ 版本已核）

| 生态 | 选型 | 状态 |
|:---|:---|:---|
| **Rust**（若 D-1 选 Rust）| **`security-framework` 3.7.0** —— 薄 FFI，暴露 `SecItem*` / `SecAccessControl` / `Token::SecureEnclave`。**这是 broker 该用的层级** | ✅ |
| | `keyring` **4.2.0**（2026-08-29）—— v4 重写：API 拆 `keyring-core`，后端拆各 store crate（`apple-native-keyring-store` 1.0.2 提供 `keychain`=legacy / `protected`=data protection）| ✅ |
| **Node**（若 D-1 选 TS）| **`keytar` 7.9.0 已是 Public archive（2022 停更）—— 死路** | ❌ |
| | 替代 `@napi-rs/keyring` **2.1.0**（2026-09-13） | ⚠️ 较新 |
| **外部 vault CLI** | **1Password `op` 2.39.0** 与 **Bitwarden `bws` 2026.9.0** 是**唯一重启后真正非交互**的两个 | ✅ |
| **不要选** | `age`/`sops` 是**文件加密不是 broker**（sops **无 macOS Keychain 后端**）；Vault `-dev` 内存态、官方明说不用于生产；`gopass`/`pass`（**gpg-agent 缓存重启后为空**）；**`aws-vault` 已官方弃用** | ❌ |

### 2.3 两种代理方式（调研后修正了排序）

| 方式 | 机制 | 优点 | 代价 | 建议 |
|:---|:---|:---|:---|:---|
| **A · 显式 brokering API** | 调用方请求 iDoris 代为发起出网调用，带 `credential_ref`；iDoris 注入后转发 | 无需 TLS 中间人、无需装证书、路径清晰可审计、易测 | 调用方要改一处 | ✅ **先做（仍然推荐第一步）** |
| **B · MITM 证书注入** | 透明代理，对调用方无感 | 调用方零改动 | 需信任自签根证书、TLS 拦截复杂度高 | ✅ **但调研改变了它的可行性判断，见下** |

**调研的关键发现：`onecli` 是真实存在的，且几乎就是目标架构。**

> [`onecli`](https://onecli.sh/docs/how-it-works)：**Rust** 网关 · MITM HTTPS 拦截 · **per-agent 凭证授权（grant）** · **策略在解密之前求值**（被拒的请求根本不接触密钥）· AES-256-GCM 密钥库按 **host + path** 匹配 · 支持注入为 header 或 query 参数。

这条**同时改变了三件事**：
1. **"MITM 方案很复杂"这个判断要下调**——已有 Rust 实现可**作为组件引入**（符合 `architecture.md`「不 vendor 源码，二进制/CLI/容器引入，版本 pin」）。
2. **"策略先于解密"是本设计该抄的关键次序**——与闸一"默认不出网"同构：**先判定，后接触密钥**。
3. **但它仍是第 2 步，不是第 1 步**：引入一个 MITM 组件意味着把 TLS 信任链交给它，且 `architecture.md` 要求版本 pin + 不 vendor；先用 A 把契约和测试做出来，再评估是否引入 B。

**⚠️ 一个必须避开的具体实现陷阱（调研发现）：**

> `Envoy` 的 `credential_injector` 中 `overwrite` **默认为 `false`** —— 意味着**攻击者自带的 `Authorization` 头会「赢」**，注入的凭证被绕过。必须显式设为覆盖。

这条对**任何**注入实现都成立：**注入点必须强制覆盖调用方提供的同名头**，而不是"仅在缺失时填充"。否则闸二的整个保证被一个请求头绕过。**这条要写成闸二的验收断言。**

> 另一处前提更正：**`mitmproxy` 没有官方凭证注入插件**（其约 30 个官方 addon 示例中没有任何一个做"占位符换真值"）。网络上流传的"mitmproxy 可以注入凭证"指的是自行编写 addon，不是开箱能力。**不要按"装上即有"来排期。**

**A 的形状**（示意，非最终契约）：

```
POST /v1/broker/http
{
  "credential_ref": "secret://openai/default",   # 只是引用
  "destination": "https://api.openai.com",
  "method": "POST",
  "path": "/v1/chat/completions",
  "body_ref": "req_abc123"                        # body 另存，避免进日志
}
```

**为什么先做 A**：A 的每一分复杂度都换来**可测性**；B 的复杂度（TLS 信任链、自签根证书、可能破坏 pinning）换来的是**不可测性**——中间人代理出错时表现为"网络问题"，最难定位。
> 调研补充：`onecli`（Rust，MITM + 解密前策略求值）的存在**降低了 B 的实现成本**，但不改变排序——**先有 A 建立的契约与测试基线，再评估引入 B 是否值得**。若引入，按 `architecture.md`「不 vendor 源码、二进制/CLI 引入、版本 pin」办理。

**闸二的三条硬性验收断言**（来自调研发现的真实漏洞模式）：

| # | 断言 | 依据 |
|:---|:---|:---|
| C-1 | **注入必须强制覆盖**调用方提供的同名头（如 `Authorization`），而非"仅在缺失时填充" | `Envoy` `credential_injector` 的 `overwrite` **默认 false** ⇒ 攻击者自带的头会赢 |
| C-2 | **策略在解密之前求值**——被拒的请求**根本不接触密钥** | `onecli` 的次序设计；与闸一"默认不出网"同构 |
| C-3 | 出站**响应**也必须过闸一（防上游回显凭证） | 已记录的泄漏路径（上游回显 `Authorization`） |

### 2.4 与闸一的关系：纵深防御，不是重复

| | 闸二（凭证代理） | 闸一（机械过滤） |
|:---|:---|:---|
| 拦什么 | 密钥**进入**上下文 | 密钥/隐私**离开**设备 |
| 机制 | 接口形状（结构性） | 内容扫描（检测性） |
| 若失效 | 密钥出现在上下文里 | 内容出网 |
| 失效后果 | **仍不出事**（闸一兜住） | 事故 |

**两道闸不是二选一，是串联**：闸二让密钥极难进入，闸一让已进入的也极难出去。**同时失效才出事**——这是把单点故障变成双点故障，而不是把同一件事做两遍。

### 2.5 威胁模型（诚实版）

**保护：**
- ✅ 模型（本地或远程）通过 prompt / 输出 / 幻觉泄漏密钥
- ✅ Prompt injection 诱导 agent 把密钥发到外部
- ✅ 密钥进入日志、审计记录、崩溃报告、错误信息
- ✅ 密钥被写入模型上下文缓存、KV cache、会话历史
- ✅ 调用方代码里硬编码密钥（改为只写 handle）

**不保护（必须说清楚）：**
- ❌ **本机同用户的其它进程** —— 这是最反直觉的一条：**CVE-2025-24204 证明持有合适 entitlement 的二进制可在 SIP 开启时 dump 任意进程内存**（§2.1b）。**这正是要求独立 UID 的原因**，也是"同进程隔离不算边界"的证据
- ❌ 攻击者已获得本机 root / 内核权限
- ❌ 调试器附加、core dump、休眠镜像、冷启动攻击
- ❌ 用户在**非 iDoris 路径**上自己把密钥粘进某个模型 —— 闸二管不到
- ❌ 注入点进程被完全攻陷 —— 它能以同样的权限使用密钥（**独立 UID 把这个门槛从"攻陷主进程"提高到"拿到另一个 UID"**）
- ❌ 恶意上游服务（密钥给出去后被对方滥用）—— 这是信任问题不是机制问题
- ❌ **上游把 `Authorization` 头回显给调用方** —— 一条被明确记录的泄漏路径：若注入的凭证被上游原样回显，agent 就拿到了真值。缓解：出站响应也要过**闸一**（纵深防御的又一次体现）

> 结论：闸二把"密钥泄漏"从**默认可能**变成**需要攻破本机**；**独立 UID** 再抬高一层。**不宣称后者不可能。**

### 2.6 审计（只记用途，不记值）

```
{ request_id, secret_id, purpose, destination_host, method, ts_utc, outcome }
```

**绝不记录**：值、值的任何前缀/后缀、hash（可被爆破）、长度（可缩小搜索空间）。
**必须记录**：谁（tenant/agent）、何时、用哪个 secret、发往哪个 host、结果如何。

沿用 `spec.md`「审计只存元数据」的既有纪律：字段名黑名单命中即**抛错拒写**，不是静默丢弃。

## 3. 闸三 · 动态模型切换

> 内存公式、量化与体积账见 [`13`](./13-本地模型候选-硬件与场景匹配.md) §3/§5；`LoadPolicy` 契约与 oMLX 映射见 [`agent/spec.md`](./agent/spec.md) 与 [`07`](./07-模型量化内存评估与动态推荐.md) §5。本节只讲**切换这件事本身**。

### 3.1 核心：调用方依赖「角色名」，不依赖「模型名」

**这是闸三能成立的前提。** 若调用方写死 `qwen3.5-9b`，则换模型 = 改调用方，闸三就没意义了。

```
调用方看到的 model 字段：        iDoris 内部映射：
  idoris-fast        ──▶  MiniCPM5-2B (resident, pinned)
  idoris-daily       ──▶  Qwen3.5-9B  (resident, pinned)      ← 可换成 Ornith / 其它，调用方无感
  idoris-deep        ──▶  Qwen3.6-35B-A3B (on_demand)
  idoris-vision      ──▶  Qwen2.5-VL-3B  (on_demand, temp slot)
  <具体模型名>        ──▶  直通（给高级用户 / 复现用）
```

- `/v1/models` 同时暴露**角色名**与**具体模型名**，并标注哪个是稳定契约。
- `IDORIS_FAST_MODEL` / `IDORIS_CORE_MODEL` / `IDORIS_DEEP_MODEL` 是**映射表**，不是模型名硬编码。
- 与 `T2.1.2` 的 `IDORIS_CORE_MODEL` override 兼容，但语义收窄为"改映射"，而非"指定唯一模型"。

### 3.2 六个触发条件（"动态"的具体含义）

| # | 触发 | 动作 | 需要重启？ |
|:---|:---|:---|:---|
| T-1 | 首次启动硬件探测 | 按 §3 的预算表产出推荐组合 | 否 |
| T-2 | 硬件/内存策略变更（`iogpu.wired_limit_mb`、guard 值） | 重算推荐，可能触发驱逐 | 否 |
| T-3 | 模型目录更新（我们上新候选） | 重算；已载模型不动，下次请求生效 | 否 |
| T-4 | 用户 override | 覆盖映射并**输出警告** | 否 |
| T-5 | 运行时内存压力（oMLX `ok→soft→hard→ceiling`） | 按 LRU 驱逐 unpinned；**pinned 不动** | 否 |
| T-6 | **场景信号**（如检测到超长文档 / 代码仓库 / 图片） | 路由到对应角色，按需载入 | 否 |

> T-6 是把 [`13`](./13-本地模型候选-硬件与场景匹配.md) §4 的场景画像真正用起来的地方——**场景不只用于选型，也用于运行时路由**。

### 3.3 切换不能破坏在途请求（三条硬规则）

| # | 规则 | 理由 |
|:---|:---|:---|
| S-1 | **驱逐必须先确认目标模型无在途请求**（引用计数），否则等待或拒绝 | 已吐 token 的流被中途换模型 = 输出污染 |
| S-2 | **`evict_to_load` 全程持 per-backend 互斥锁**，等待超时 10s ⇒ 返回 `oom` 而非无限等待 | 防两个请求互相驱逐的活锁（`T1.3.5`） |
| S-3 | **流式请求已开始吐 token 后，任何切换/重试都不可发生**，只能以 SSE error 终止 | 重试会造成重复 token（`T1.3.4` 既有纪律） |

### 3.4 载入失败必须显式，不许悄悄降级

沿用 `spec.md` 的错误分类与 `architecture.md` 的边界：

```
idoris-deep 载入失败（OOM / 模型损坏 / guard 拒绝）
  ├─ fallback_policy = fail_closed   ⇒ 503 + reason=model_load_failed   ← 默认
  └─ fallback_policy = next_in_chain ⇒ 降级到 idoris-daily，但必须在响应头回传
                                        X-iDoris-Degraded: idoris-deep→idoris-daily
                                        且审计 reason=degraded（非空、可区分）
```

**"悄悄用主力模型回答了深度问题"是最坏的失败模式**——用户以为拿到了深度推理，实际没有，且没有任何信号。

### 3.5 可观测（否则"动态"等于黑箱）

| 出口 | 内容 |
|:---|:---|
| `GET /v1/models` | 角色名 → 当前映射 + pinned 状态 |
| `GET /capabilities` | 每个角色的 `admission_status`（`ready`/`requires_eviction`/`blocked`）+ 估算内存 + 队列深度 |
| 响应头 | `X-iDoris-Role`、`X-iDoris-Model`（实际用的）、`X-iDoris-Degraded`（若降级） |
| 审计 `reason` | 区分 `intent_match` / `degraded` / `privacy_enforced` / `budget`（`spec.md` 四类） |
| 日志 | 每次 load / evict / pin / unpin 一行，含触发条件（T-1…T-6） |

## 4. 三闸的合成视图

```
                        请求
                         │
                         ▼
        ┌──────── 闸一 · INSPECTED（默认不出网）────────┐
        │  L0 机械规则 → L1 语义(单向阀) → L2 策略        │
        │  输出：BLOCK │ REDACT │ ALLOW + reason         │
        └───────────────────┬───────────────────────────┘
                            │ ALLOW / REDACT
                            ▼
                    PROFILED → POLICY → BUDGET → CANDIDATES
                            │
                            ▼
        ┌──────── 闸三 · 角色映射 + 载入策略 ────────────┐
        │  idoris-daily → Qwen3.5-9B；pinned / on_demand │
        │  载入失败 ⇒ 显式降级 + 响应头回传（不静默）      │
        └───────────────────┬───────────────────────────┘
                            │ DISPATCH
                            ▼
        ┌──────── 闸二 · 凭证注入点（面积最小）──────────┐
        │  模型只提供 secret:// 引用；真值仅在此处解引用   │
        └───────────────────┬───────────────────────────┘
                            │
                            ▼
                      出网 / 本地执行
                            │
                    返回 → 回填（R-1/R-2 校验）→ 用户
```

**三闸的失效叠加关系：**

| 同时失效 | 后果 |
|:---|:---|
| 仅闸一失效 | 隐私可能出网（**这是最严重的单点**） |
| 仅闸二失效 | 密钥可能进上下文，但**闸一仍拦得住出网** |
| 仅闸三失效 | 降级不透明 / 载入失败被静默吞掉 |
| 闸一 + 闸二同时失效 | 密钥出网（真正的红线） |

> 因此**闸一的优先级高于闸二**：它是唯一的最后一道。这决定了投入顺序与测试严格度——`T1.3.3` / `T1.3.6` 的阻断级定位与此一致。

## 6. 调研回填（✅/⚠️/❓）

> 两路调研已回：**确定性隐私过滤** · **本地密钥与凭证代理**。以下为抓取/实测值。

### Q-1/Q-2/Q-3 闸一（→ §1）

- **Q-1 规则库**：❌ **无库可买**——Presidio（MIT，10,944★，2.2.364）recognizer 只有 `[en]`；scrubadub（2023-09 停更）；piiranha（**CC-BY-NC-ND-4.0，禁商用**）；OpenAI `privacy-filter`（2,706★，**"Primarily English"**，1.5B MoE）。实测：OPF 在合成 PII 上 **0.855 vs Presidio 0.431**，但**在 CJK 上崩到 0.138**、阿拉伯 0.038、西里尔 0.027，person 仅 **0.40**。→ **L0 自建**（Rust `vectorscan`/`hyperscan` + Aho-Corasick）。
- **Q-2 中文校验和**：✅ 标准原文已核并复现示例，见 §1.7。**关键结论：结构校验（区划+日历）降 6 个数量级，校验和只降 1 个。**
- **Q-3 L1 语义**：⚠️ 中文 NER 只能"参考"——`OpenMed-PII-Chinese` micro-F1 **0.7407**、≤512 token、**下载量 ~33**；`stanza` zh NER F1 **79.2**（Apache-2.0 ✅，但需 torch）；spaCy `zh_core_web_trf` **74.08** 且**无 PII 类型**。**L1 放热路径不可行**（~1–1.7 s/512 token）。

**密钥扫描器实测定性（✅ 两个独立来源，都反营销）**：
- gitleaks **P 46% / R 88%**；trufflehog **R 52%**（arXiv:2307.00714）
- **gitleaks 8.21.2 的终结符缺陷使召回 0.9976 → 0.5233**（arXiv:2609.02983）⇒ 必须双规则集（X-3）
- **FP 排序在合成语料与真实语料间会反转** ⇒ 测试必须**两个语料都跑**（§1.6）
- **scanner 之间的召回差异不显著** ⇒ 不要指望换工具解决召回问题

### Q-4 闸二存储（→ §2.2）

✅ 已定：**LaunchAgent（用户上下文）+ data protection keychain + Secure Enclave P-256 包裹、无 `userPresence`**。依据是 Apple **TN3137** 的硬约束（数据保护钥匙串**只对用户上下文进程可用**）。Rust 走 `security-framework` 3.7.0 + `keyring` 4.2.0；Node 的 `keytar` **已归档**，只能 `@napi-rs/keyring` 2.1.0。

### Q-5 闸二注入点（→ §2.3）

✅ 已定三条断言（C-1/C-2/C-3）。补充两条可抄的实现经验（来自 `keys-on-the-wire`）：
- **G5 按"不作为"执行**：非许可目的地拿到的是**原样占位符**，而**不是错误**——返回 5xx 会把代理变成一个**探测预言机**
- **G6 审计先 fsync，再让改写的字节上上游 socket**——顺序反了就会出现"用了密钥但没记录"的窗口

### Q-6 闸三双后端（→ §3.2）

→ 见 [`14`](./14-常驻服务技术栈选型-语言与推理后端.md) §7.4：**按角色拆舰队**（常驻/工具调用走 oMLX；长上下文/RAG 走高并发必须走 llama.cpp，因为 **MLX 的 `--kv-bits` 会禁用连续批处理**）。

### 补充：审计不得泄漏（✅ Vault 的模型 + 三个真实 CVE）

- ✅ **Vault 的模型**：*"By default, Vault only writes a keyed hash (HMAC-SHA256) of most string values."*
- **日志层绝不能先拿到值再脱敏**（不要 log-then-redact）。记录：`{ts, request_id, secret_id, HMAC(value), caller_uid, dest_host, method, path, decision}`
- ✅ **审计不可写 ⇒ 拒绝服务**（Vault 也拒绝它无法审计的请求）
- 三个真实教训：Vault **CVE-2025-4166**（错误路径记下 KV v2 值）、**CVE-2024-8365**（header HMAC 被移除）、**CVE-2024-0831**（`log_raw=true` 全局泄漏）
- ⚠️ **macOS 特有陷阱**：`os_log` 默认对动态字符串脱敏，**但 Apple 的 Device Management schema 暴露 `SystemLogging.System → Enable-Private-Data`，可"为整个系统开启私有数据日志"** ⇒ **绝不要把密钥写进 `os_log`，哪怕标成 `private`**。Apple 自己的安全模式是 `OSLogPrivacy.Mask.hash`——这正是对 HMAC 做法的官方背书

## 7. 调研已确认的残余风险（诚实版）

| # | 风险 | 状态 |
|:---|:---|:---|
| R-1 | **broker 是全量沦陷的单一故障点**；macOS 没有 Linux 那种 systemd 式沙箱可依赖 | ⚠️ 独立 UID 把门槛从"攻陷进程"抬到"拿到另一个 UID"，**不是绝对隔离** |
