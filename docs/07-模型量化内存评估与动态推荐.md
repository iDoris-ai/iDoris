## 1. 内存评估公式（标准）

一个模型实际占用 = **权重 + KV 缓存 + 运行时开销**：

```
footprint(GB) = P × bpp(quant)              # 权重：参数量 × 每参数字节
              + KV(ctx)                      # KV 缓存：随上下文长度线性增长
              + overhead(~0.5–1.5GB)         # 运行时/激活/碎片
```

- **P** = 参数总量（十亿）。⚠️ **MoE 按总参数算内存**（所有专家都要在内存里），激活参数只影响**速度**不影响**内存**——这是 35B MoE 的关键陷阱。
- **bpp(quant)** = 每参数字节（见 §2）。
- **KV(ctx)** = `2 × n_layers × n_kv_heads × head_dim × ctx × kv_bytes / 1e9`（GQA 下 n_kv_heads 很小）。

### KV 缓存的量级（常被忽略，但很大）
以 9B 级模型（约 36 层、GQA 8 kv-heads、head_dim 128）估：
- 每 token ≈ `2×36×8×128×2B ≈ 0.147 MB`（fp16 KV）
- **8K 上下文 ≈ 1.2GB；32K ≈ 4.8GB；128K ≈ 19GB(!)**
- **KV 可量化**：Q8 KV 减半、Q4 KV 减到 1/4。长上下文必须量化 KV，否则 KV 比权重还大。

> 结论：**上下文长度是内存的一等变量**。同一个模型，8K vs 128K 上下文的内存差出好几个 GB。推荐模块必须把 `ctx` 当输入。

## 2. 量化标准（bytes/参数 + 质量，实测数据）

| 量化 | bytes/参数 | 质量保留(困惑度) | 判断 |
|---|---|---|---|
| FP16 | 2.0 | 100% | 基准，本地几乎不用 |
| **Q8_0** | **1.0** | **~99.8%**（≈无损）| 质量敏感/常驻核心首选 |
| **Q6_K** | **~0.82** | **~99.5%** | 质量与体积极佳平衡 |
| **Q5_K_M** | **0.69** | **~99%** | 长链推理/计算类推荐下限 |
| **Q4_K_M** | **0.55** | **~98%**（困惑度 +1–3%）| **生产甜点**，通用首选 |
| Q3_K | ~0.43 | 明显下降 | 仅"塞不下才用"，**推理类不推荐** |
| Q2 | ~0.30 | 严重下降 | 不用 |

**标准**：`quality_threshold` 默认 **≥98%（即 ≥Q4_K_M）**；对"以推理为核心"的常驻模型，倾向 **Q6_K/Q8**（把大模型量化到 Q3 去换容量，等于把它最值钱的推理能力砍掉——得不偿失）。

来源：GGUF 量化实测（Q4_K_M ~98%、Q6_K ~99.5%、Q8_0 ~99.8%；bpp Q8=1.0/Q5_K_M=0.69/Q4_K_M=0.55）。

## 3. Apple Silicon 可用内存标准

macOS 不把全部 RAM 给 GPU：
- **默认** GPU wired 上限 ≈ RAM × **66–75%**（系统保留 ~25–33%）。
- 可 `sudo sysctl iogpu.wired_limit_mb=<MB>` 提高，但 **Apple 建议 ≤70%**，且留 **8–16GB 给系统**，过高会不稳。

**可用预算三档标准**：
```
conservative(默认,不改)   usable = RAM × 0.66
moderate(适度调, 留6GB)   usable = RAM − 6
aggressive(激进, 留4GB)   usable = RAM − 4     ← 有不稳风险, 仅短时重任务
```

## 4. 把账算清：M4 24GB 实例（有理有据）

**可用预算**：conservative ≈ **15.8GB**；moderate ≈ **18GB**；aggressive ≈ **20GB**。

### 4.1 Ornith-9B 作常驻核心 —— ✅ 舒适
| 量化 | 权重 | +KV@32K(Q8) | 合计 | 24GB 判断 |
|---|---|---|---|---|
| Q4_K_M | 5.0GB | +2.4 | ~7.4GB | 极宽裕，留 8GB 给临时槽 |
| **Q6_K** | 7.4GB | +2.4 | **~9.8GB** | **推荐**：近无损 + 留 ~6GB 临时槽 |
| Q8_0 | 9.0GB | +2.4 | ~11.4GB | 无损，临时槽余量小 |

→ **9B 常驻用 Q6_K@32K 最优**：质量 ~99.5%，合计 ~10GB，24GB 上舒适且能同时挂一个临时小模型（VL-3B/whisper/kokoro）。

### 4.2 35B MoE 作临时 —— ⚠️ 24GB 基本撑不住（修正我上轮的乐观）
你问得对——**35B FP16 = 70GB**。量化后：
| 量化 | 权重(35B总参) | +KV@8K | 合计 | 24GB 判断 |
|---|---|---|---|---|
| Q8 | 35GB | — | — | ❌ 远超 |
| Q6_K | 28.7GB | — | — | ❌ 超 |
| Q5_K_M | 24.2GB | — | — | ❌ ≈全部 RAM |
| **Q4_K_M** | **19.3GB** | +~2.5 | **~22GB** | ⚠️ 需激进 wired(留2GB给系统, 不安全) + **驱逐常驻9B** + 短上下文 |
| Q3_K | 15GB | +~2.5 | ~17.5GB | 勉强放下, 但**推理质量明显掉**——砍掉它最值钱的能力 |

**判断**：在 24GB 上，35B MoE 要么 Q4（~19GB 吃满内存、必须驱逐 9B、只能短上下文、需激进 wired、有不稳风险），要么 Q3（放得下但推理退化，违背用它的初衷）。**两条路都不好。** → **35B MoE 在 24GB 上不是一个实用的常规工作马；推荐 32GB+ 再上 35B。**

### 4.3 M4 24GB 的诚实结论
- **常驻核心 = Ornith-1.0-9B @ Q6_K（32K, Q8 KV）**，~10GB，推理强、Mac 亲和、60 t/s 量级。✅
- **重任务临时槽（可与 9B 共存）的舒适上限 ≈ 14B dense @ Q4（~8GB）**（如 Qwen2.5-Coder-14B）或直接用 9B。
- **35B MoE**：24GB 上仅"驱逐式短上下文"勉强可试（Q4，激进 wired），**不作默认**；标注"32GB+ 推荐"。
- **多模态/ASR/TTS 临时**：Qwen2.5-VL-3B（~2GB Q4）/ whisper-turbo（~1GB）/ Kokoro-82M（<0.5GB）——都能与 9B 共存。

> 这就是"有理有据"：不是"35B 临时"一句话，而是**按公式+量化+Apple 预算算出——24GB 的实用天花板是 9B 常驻 + ≤14B 临时；35B 要 32GB+**。

## 5. 动态推荐模块设计（HardwareAwareModelRecommender）

把上面的评估**自动化**：输入硬件 + 候选目录，输出最佳组合。这正是你要的"动态推荐模块"。

### 5.1 输入
```yaml
hardware:            # 自动探测 (system_profiler / sysctl / os.cpus)
  ram_gb: 24
  chip: "M4"         # 决定速度档 (TTFT/吞吐参考)
  gpu_cores: 10
policy:
  wired_mode: moderate       # conservative|moderate|aggressive
  context_target: 32768      # 目标上下文 → 影响 KV
  kv_quant: q8               # KV 量化
  temp_slots: 1              # 想同时挂几个临时模型
  quality_threshold: 0.98    # 质量下限
```

### 5.2 模型目录（每个候选一条，来自我们筛选的推荐集）
```yaml
- id: ornith-1.0-9b
  family: ornith
  params_total_b: 9
  params_active_b: 9          # dense
  arch: {n_layers: 36, n_kv_heads: 8, head_dim: 128}
  modality: [text]
  capability: {reasoning: 0.85, coding: 0.90}
  quant_options: [{label: q4_k_m, bpp: 0.55, quality: 0.98},
                  {label: q6_k,   bpp: 0.82, quality: 0.995},
                  {label: q8_0,   bpp: 1.0,  quality: 0.998}]
  min_ram_gb: 12
- id: agents-a1-35b
  params_total_b: 35
  params_active_b: 3          # MoE：内存按 35 算，速度按 3 算
  ...
  min_ram_gb: 32              # ←我们据 §4 标注的门槛
```

### 5.3 算法（伪代码）
```
usable = budget(ram_gb, wired_mode)                     # §3 三档
resident_budget = usable − Σ temp_reserve − headroom

# 选常驻核心：capability=reasoning 的候选里，
# 取"能放下的最高质量量化"后按 (能力分 × 质量) 排序
for m in catalog where m.capability.reasoning:
    q = highest quant of m s.t.
        footprint(m, q, ctx) ≤ resident_budget and q.quality ≥ threshold
        and ram_gb ≥ m.min_ram_gb
    if q exists: score[m] = m.capability.reasoning × q.quality
resident = argmax(score)   ; footprint_r = footprint(resident, q*, ctx)

# 选临时模型（按业务能力: vision/asr/tts/coding/heavy）
for cap in needed_caps:
    pick model that fits in (usable − footprint_r) when swapped in
    if none fits alongside resident:
        mark requires_eviction=true (llama-swap 卸常驻再载, 短上下文)

emit {
  resident: {id, quant, footprint, ctx},
  temp: [...],
  warnings: [ "35B 需 32GB+ / 需驱逐 / 需激进 wired" ... ],
  recommended_sysctl: iogpu.wired_limit_mb = usable×1024,
  tradeoffs: "..."   # 解释为什么这么选（可读理由）
}
```

### 5.4 输出（M4 24GB 实跑示例）
```
resident: ornith-1.0-9b @ q6_k, 32K ctx, ~9.8GB
temp slots (与常驻共存):
  - qwen2.5-vl-3b @ q4 (~2GB)   [vision/banner]
  - whisper-large-v3-turbo (~1GB) [asr]
  - kokoro-82m (~0.4GB)          [tts]
heavy (需驱逐常驻, 短上下文):
  - qwen2.5-coder-14b @ q4 (~8GB) [重 coding]  ← 可与9B共存(临界)
  - agents-a1-35b @ q4: BLOCKED on 24GB (需32GB+); 或激进模式短上下文试
recommended_sysctl: iogpu.wired_limit_mb=18432 (moderate, 留6GB)
tradeoff: "9B Q6_K 近无损且留足临时槽; 35B 在24GB非实用, 升级32GB或用14B替代"
```

### 5.5 落地位置与"动态"
- **形态**：先做成配置驱动的 util（目录 YAML + 打分器，TS/Python 皆可，快速起）；验证后**内化进 Agent24 Rust `ModelRouter`**——它已有 tier/health 概念，加一个 `HardwareProfile` + `catalog` + `recommend()` 即可（对齐 06 的"接口不变，实现可换"）。
- **动态触发**：①首次启动探测硬件出推荐；②硬件/内存策略变化重算；③模型目录更新（我们上新候选）重算；④用户可 override（`IDORIS_CORE_MODEL` 强制）。
- **组件卡对接**：推荐结果直接生成 llama-swap 的 model 配置（常驻=长 TTL，临时=短 TTL），落成 06 的组件卡。

## 6. 小结（回应你的三点要求）

1. **有过程有标准**：内存=权重(P×bpp)+KV(ctx)+开销；量化按 bpp×质量表；Apple 预算按 RAM×0.66~(RAM−6) 三档。全部公式化，可复核。
2. **35B/24GB 的账算清了**：FP16=70GB；Q4≈19GB 吃满 24GB、需驱逐+激进+短上下文，不实用；**24GB 实用天花板 = 9B 常驻(Q6_K) + ≤14B 临时；35B 要 32GB+**。这是有依据的判断，不是拍脑袋。
3. **动态推荐模块**：`HardwareAwareModelRecommender`——输入硬件+目录，按上述标准自动算出常驻/临时最佳组合 + 警告 + sysctl 建议 + 可读理由；先 util 后内化进 Rust ModelRouter，随硬件/目录变化动态重算。
