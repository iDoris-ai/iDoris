## 0. 一句话结论

**倾向 Rust 是对的，但"Rust"和"MLX"是两个独立的决策，不该捆在一起。**

推荐形态：

```
┌─────────────────────────────────────────────┐
│  iDoris Router —— Rust 常驻单二进制           │
│  axum + tokio + serde + regex               │
│  策略/隐私门/凭证代理/角色映射/审计            │
└───────────────┬─────────────────────────────┘
                │  HTTP（OpenAI-compat + Anthropic-compat）
    ┌───────────┼───────────┬──────────────┐
    ▼           ▼           ▼              ▼
 oMLX(MLX)  llama-server  Claude/Codex   外部 API
 macOS 默认   GGUF 跨平台   订阅中转       能力②
    └─ 进程外，可替换，LoadPolicy 统一抽象 ─┘
```

**两个决策分开：**
- **编排层语言 = Rust**（理由见 §3，与你的倾向一致）
- **推理后端 = 进程外、按平台探测**（MLX 是 macOS 默认，**不是**唯一实现）

## 1. 先拆一个被混在一起的问题

你把「Rust」和「MLX」放在一句话里，但它们其实是**三个独立决策**：

| # | 决策 | 选项 | 与另外两个的耦合度 |
|:---|:---|:---|:---|
| **D1** | 编排层用什么语言 | Rust / TypeScript / 混合 | **低** |
| **D2** | 推理在哪跑（进程内 / 进程外） | 内嵌 / 外部服务 | **高**（决定 D1 的候选集） |
| **D3** | 用什么推理引擎 | MLX / GGUF-llama.cpp / 都要 | **中**（决定 D2 的可行性） |

**关键：进程边界让 D1 与 D3 解耦。** 这正是 `architecture.md` 核心判断 1 已经定下的东西——

> 「集成契约 = REST(OpenAI-compat HTTP) + 进程边界，不是 import、不是同语言。」

一旦推理走进程外 HTTP，那么：
- **Rust 服务根本不需要 MLX 绑定** —— 它只需要一个 HTTP 客户端
- **MLX 是什么语言写的变得无关** —— oMLX 是 Python/MLX，服务侧看不见
- **换推理引擎不改编排层** —— 这就是 `LoadPolicy` 抽象的意义

> 所以「Rust + MLX」这个组合**唯一需要 MlX Rust 绑定的场景，是 D2 选「内嵌」**。
> 若 D2 选「进程外」（推荐），则 Rust 与 MLX 之间**没有直接依赖**——两件事同时成立，但互不牵连。

**这个拆分很重要**：它意味着你不需要为了用 Rust 而放弃 MLX，也不需要为了用 MLX 而接受 Python/TS 编排。

## 2. 与仓库既有决策的冲突（必须明说）

变更语言不是"选个新库"，是**推翻一条已记录、有理由的决策**。原始理由原文（`architecture.md` 核心判断 6）：

> 「**Router 第一版 TypeScript / pnpm**（2026-09-07 拍板）。与 auraai-packages / iDoris-SDK 同栈，oMLX 与 CLI 中转都是 HTTP/subprocess，TS 起最快。验证后按 06 契约内化进 Agent24 Rust `ModelRouter`——**契约不变，实现可换**这条对我们自己也成立。」

**这条决策的三层理由，逐条检验：**

| 原始理由 | 今天是否还成立 | 说明 |
|:---|:---|:---|
| ① 与 auraai-packages / iDoris-SDK 同栈 | ⚠️ **部分失效** | 同栈的价值在"共享类型"；若契约改为语言中立（§6），这个价值就转移到契约层，不再依赖同语言 |
| ② oMLX 与 CLI 中转都是 HTTP/subprocess | ✅ 成立 | 但这条恰恰**同时支持** Rust —— HTTP/subprocess 是 Rust 的强项 |
| ③ TS 起最快 | ⚠️ **成立但有代价** | 快在"写策略"；慢在"后期内化进 Rust"要**重写一遍** |

**原始决策里最关键的一句是**「验证后内化进 Agent24 Rust」——也就是说**终态本来就是 Rust**。那么问题变成：

> 是「TS 写一版 → 验证 → 用 Rust 重写」，
> 还是「直接用 Rust 写一版」？

**若契约先行（`T1.1.1`/`T1.1.2` 正是干这个），第二种更省。** 原始决策选第一种的理由是"策略会churn，TS 迭代快"——这是个真实成本，见 §3。

### 2.1 一处已存在的自相矛盾（本文件顺带指出）

| 位置 | 说了什么 |
|:---|:---|
| `06-组件接口契约与互换标准.md:184` | 「让整个 Mycelium **多语言生态（Rust/Go/TS/Python）** 在 REST+Nostr+DID 上自然互通」 |
| `agent/spec.md:17, 193` | 五份契约 = 「**TS 类型 + zod schema** + 校验器」 |
| `agent/tasks.md` T1.1.2 | 「五份契约的 **TS 类型 + zod schema**」 |

**zod 是 TS 专属的。** 把契约的实现锁在 zod 上，等于**用实现细节拆掉了自己宣称的语言中立性**。这不是语言选型问题，是**契约层设计问题**——但它直接决定"换语言贵不贵"。

**修正建议见 §6。**

## 3. 这个服务到底在做什么（这才是选语言的依据）

把 `tasks.md` 的 M1/M2 任务按**工作性质**归类，而不是按编号：

| 工作性质 | 涉及任务 | 计算特征 | 语言敏感度 |
|:---|:---|:---|:---|
| HTTP 服务 + 路由 | T1.3.1 | I/O 密集 | 低 |
| Header 解析 + 策略引擎 | T1.3.2 | 纯逻辑、无计算 | **高**（churn 最多） |
| 契约校验（schema） | T1.1.2 / T1.1.3 | 纯逻辑 | **高** |
| SSE 流式代理 | T1.3.4 | **热路径**、字节搬运 | 中 |
| **闸一 正则/熵扫描** | 本文件 §15-§1 | **热路径、每请求都跑** | **高** |
| 子进程 spawn/kill/沙箱 | T1.4.1 | 系统调用、**必须无孤儿** | **高** |
| 租户隔离 / 审计写入 | T1.5.x / T2.2.3 | I/O + 正确性 | 中 |
| 内存公式 / 推荐 | T2.1.x | 算术 | 低 |
| 凭证注入 | 本文件 §15-§2 | **安全敏感、面积要最小** | **高** |

**三个结论：**

1. **没有任何重计算。** 全部是 HTTP / JSON / 策略 / 子进程 / 本地存储。**没有任何一处需要 Rust 的性能。**
2. **但有三处需要 Rust 的"正确性"**：
   - **闸一的正则扫描**——每请求都跑，且**出错的代价是隐私**（`Switch` 穷尽性、无 panic 路径有价值）
   - **子进程管理**——`T1.4.1` 明确要求"不留孤儿进程"，RAII + `Drop` 在这里是**结构性正确**而非风格偏好
   - **凭证注入点**——要求"面积最小、可审计"，Rust 的类型系统能把"密钥值"封成不可打印、不可序列化的类型（newtype + 不实现 `Display`/`Serialize`），**编译期就防止它进日志**
3. **唯一的反方向力量是 churn。** 策略引擎与契约是改得最多的地方，Rust 的编译期约束会让每次改动更慢。

### 3.1 决定性的那个论点

> **凭证注入点需要一个"不可能被打印出来"的密钥类型。**
> 在 Rust 里这是**一条 newtype + 不实现两个 trait**，编译器替你保证；
> 在 TS 里这是**代码评审纪律**，靠人记着。
>
> 对一个承诺"密钥永不出现在日志/审计/上下文"的系统，**前者的保证等级更高一个量级**。

这条与 §15 的闸二直接挂钩：闸二宣称的是**结构性保证**，而结构性保证最好由**类型系统**承载，而不是由约定承载。

## 4. 三个候选架构

| | **A · Rust 编排 + 进程外推理**（推荐） | **B · Rust 编排 + 内嵌 Rust 推理** | **C · TS 编排 + 进程外推理**（现状决策） |
|:---|:---|:---|:---|
| 编排层 | Rust (axum/tokio) | Rust | TypeScript (node/pnpm) |
| 推理 | 外部 oMLX / llama-server | `mistral.rs` / `candle` 内嵌 | 外部 oMLX / llama-server |
| MLX 权重 | ✅ 可用（oMLX 读） | ❌ 需 GGUF/safetensors | ✅ 可用 |
| 跨平台 | ✅（换后端即可） | ⚠️ 绑定 Rust 推理生态 | ✅ |
| 闸一性能 | ✅ 原生 | ✅ 原生 | ⚠️ 正则/扫描在 JS 里；可下沉 native addon |
| 密钥类型安全 | ✅ **编译期** | ✅ 编译期 | ❌ 运行期约定 |
| 子进程无孤儿 | ✅ RAII | ✅ RAII | ⚠️ 需显式清理逻辑 |
| 分发 | ✅ 单二进制 + 签名 | ✅ 单二进制 | ⚠️ 需打包 Node runtime 或用 pkg/bun |
| 常驻 RSS | 低 | 低 | 中（Node runtime 基线） |
| 迭代速度 | 中 | 中 | ✅ **最快** |
| 与 Agent24 终态 | ✅ **一致，无需重写** | ✅ 一致 | ❌ 需重写 |
| 生态共享（TS 包） | ⚠️ 靠契约层（§6） | ⚠️ 同 | ✅ 原生 |

**D · 混合（Rust 核心 + TS 壳体）** 需要单独说明：**不推荐做第一版**。理由：它把"两套契约同步"的成本前置到项目最早期，而契约层本来就已经是共享点（§6）。真要混合，也应该在**契约稳定之后**，而不是之前。此外 `architecture.md` 明确已有过一次"拆 Agent24 ModelRouter 成独立进程"的**驳回记录**（ecosystem-boundaries §6），说明这个团队已经拒绝过类似的双核方案。

## 5. MLX 的现实约束（决定它能不能是"唯一"后端）

| 约束 | 影响 | 出处 |
|:---|:---|:---|
| **MLX 仅 Apple Silicon** | 无法覆盖 Windows/Linux；而 `architecture.md` 要求按平台探测、Agent24 要分发三平台 | `architecture.md` 核心判断 3 |
| **上游 `mlx-lm` 无 KV 量化** | 长上下文内存预算落空；27B 的 32K KV 从 4.29GB 涨到 **8.59GB** | [`13`](./13-本地模型候选-硬件与场景匹配.md) §3.3 |
| **Rust↔MLX 绑定成熟度** | 见 §9（调研回填）——决定架构 B 是否可行 | 调研 |
| **oMLX 是独立应用、手动升级** | 升级=换 .app，用户操作；`architecture.md` 要求"不写死后端，`omlx` 字样只出现在 `adapters/omlx/`" | U0-LOG · `architecture.md` 边界 |

**结论：MLX 应当被定为「macOS 的默认实现」，而不是「iDoris 的后端」。** 这不是降级——它正是 `architecture.md` 核心判断 3 已经写下的东西：

> 「oMLX 仅 Apple Silicon，而 Agent24 要分发 Windows/Linux/macOS。故 capability③ 的实现**按平台探测选择**，全部在 `LoadPolicy` 抽象之后。oMLX 是『macOS 的默认实现』，不是 iDoris 的固定依赖。」

**所以：你倾向 MLX 是合理的（在你自己的 Mac 上它确实是最优解），但"我们基于 MLX"这个表述要收窄成"我们在 macOS 上默认用 MLX"。** 两者的工程后果差别很大——前者会让 Windows/Linux 支持变成重构，后者只是加一个适配器。

## 6. 契约的语言中立化（让这个决策可反悔的关键）

**这是本文件最重要的一条工程建议，与选 Rust 还是 TS 无关。**

现状（`spec.md:17`）：契约 = TS 类型 + zod schema。

**问题**：契约是"核心资产"（`06:184`），但它的**唯一真源是一个 TS 库**。于是：
- 选 TS → 无障碍
- 选 Rust → 要么用 `serde` 重写一遍并**人工保持同步**，要么引入代码生成
- 加第三个语言（Go/Python）→ 同样的问题再来一遍

**建议：把真源上移一层到 JSON Schema，由它生成两侧。**

```
        contracts/*.schema.json          ← 唯一真源（语言中立、可 diff、可评审）
                 │
        ┌────────┴────────┐
        ▼                 ▼
   TS 类型 + zod      Rust 类型 + serde
   (供 Agent24 TS /    (供 Router 核心)
    iDoris-SDK /
    auraai-packages)
```

**收益：**
1. **语言决策变得可反悔** —— 契约不动，实现可换（这正是 `architecture.md` 反复强调的「契约不变，实现可换」对**我们自己**的适用）
2. **`06` 的 L2「完整 I/O schema」有了明确落点** —— 契约成熟度分级终于有了载体
3. **组件卡的强制字段校验（T1.1.3）可以在两边一致执行** —— 不会出现"TS 校验器放行、Rust 校验器拒绝"
4. **`T1.1.2` 的交付物要改**：从「TS 类型 + zod」变成「JSON Schema + 两侧生成产物 + 一致性测试」

**成本**：引入一次性的代码生成配置；`zod` 变成产物而非真源（写自定义校验逻辑时会有些别扭，可用 `superRefine` 的替代方案规避）。

> 若不做这一步，选 Rust 的隐含成本就是"永久的人工契约同步"——**那是本决策最大的一项隐性负债**，而且它会随语言数量线性增长。

### 7.2 ⚠️ 分歧：调研推荐 TypeScript，我仍推荐 Rust

调研结论是「**TS + 进程外推理**」。我逐条核对后判断：**分歧不在事实，在权重。**

| 调研的论据 | 我的核对 |
|:---|:---|
| ①「Rust 无生产级 MLX 路径 → 该要求不再区分语言」 | ✅ 事实成立，但它是**移除一条挺 Rust 的理由**，不是**新增一条挺 TS 的理由**。我们本就把推理放进程外，MLX 与语言**从不应绑定**（§1）|
| ②「网关是 JSON/策略形状的活，TS 最强」 | ⚠️ **判断而非事实**。Rust `serde` 在 JSON 上同属第一梯队；真实成本是**编译期约束拖慢 churn**，不是"做不了" |
| ③「Agent24 ADR 让非 Rust 模块走 Node Host」 | ⚠️ 那讲的是**集成方式**，不是**归属**。`architecture.md` 核心判断 6 明写「验证后**内化进 Agent24 Rust**」——**终态是 Rust** |
| ④「进程边界是行业常态（Ollama 也 spawn runner）」 | ✅ 成立，**但这条同时支持 Rust**——spawn/kill 恰是 Rust 更强处 |
| ⑤「跨语言边界是翻车处 → 选一个语言」 | ✅ 成立，**但它反对的是"混合架构 D"，不是反对 Rust** |
| ⑥「契约同步无双向工具 → 必须以 JSON Schema 为轴」 | ✅ **完全成立，已采纳**（§6） |

**决定权重的三项，全部落在仓库已有的硬要求上：**

| # | 硬要求（仓库原文） | Rust | Node/TS |
|:---|:---|:---|:---|
| 1 | `T1.4.1`「**不留孤儿进程**」是**硬性验收项**（"孤儿进程会吃满机器"）| ✅ `tokio::process` 的 `process_group()` + `kill_on_drop`；`command-group`（5.0.1）专为杀子进程组而生 | ❌ **Node 无进程组 kill 助手**；`shell:true` + args 已被 **DEP0190** 弃用（shell 注入风险）|
| 2 | `15 §2`「密钥**永不进日志/审计/上下文**」的结构性保证 | ✅ `newtype` + 不实现 `Display`/`Serialize` ⇒ **编译期**阻止 | ❌ 只能靠评审纪律。而调研查到的真实 CVE 正是**日志层泄漏**：Vault CVE-2025-4166、CVE-2024-8365 |
| 3 | `architecture.md` 核心判断 6「验证后内化进 Agent24 **Rust**」 | ✅ 一步到位 | ❌ 需**重写一遍** |

**另有两条偏向 Rust 的实测：** 常驻 RSS **8.5MB vs 82.5MB**、冷启动 **19ms vs 274ms**；公证方面 Node 需 `allow-jit` entitlement 而 Rust 不需要（Node SEA 仍是 **Stability 1.1** 且**仅 arm64**）。
**Node 侧硬伤（调研自查）：** `keytar` 已成 **Public archive（2022 停更）**；SSE 增长有记录（2,000 连接时 RSS 26→86→178MB）。

> **因此建议仍是 Rust。但决定性的不是技术，是团队：**
> **Rust 熟练（Agent24 已是 Rust，看起来是）⇒ 选 Rust，省掉一次重写。**
> **Rust 不熟且"最快跑到第一个真实消费者"优先 ⇒ 选 TS，前提是先把 D-3 做掉。**
> 调研里那句「Prisma 离开 Rust 的第一原因是**贡献者技能**而非速度」值得记住——**语言选型的失败模式通常是人的，不是机器的。**

### 7.3 架构 B 已死（调研确证，两条独立理由）

| 选项 | 调研结论 | 后果 |
|:---|:---|:---|
| `mlx-rs` | ✅ 0.32.0（2026-09-12）、373★，**能**加载 safetensors/GGUF 并生成 token——**但非生产级**：`Compiled` 是 `!Send`，流与编译闭包**线程亲和、不能跨线程**（研究原话："hostile to a multi-threaded gateway"）；自报**并行测试 data race**；autodiff 闭包可 **segfault**；**docs.rs 每个已发布版本都构建失败**；**27 个反向依赖全钉在 `^0.25`**；**未找到生产用户** ❓ | ❌ 不能作为 24/7 网关基础 |
| `mistral.rs` | ✅ v0.9.3（2026-09-07，7,704★）确有 OpenAI 兼容 + 连续批处理 + Metal + 预编译 Apple Silicon 单二进制——**但完全不支持 MLX 权重**（文档无 "MLX" 字样）；crates.io 最高仅 **0.8.1**（2026-04-02） | ❌ 选它 = **放弃 MLX 权重与优化** |

> **结论：D2 = 进程外，不是权衡结果，是唯一选项。** §4 表格中架构 B 应标为「当前不可行」。

### 7.4 D3 的决定性约束（改变的是架构，不只是选型）

调研最有价值的一句判断：

> **`--kv-bits` 会禁用连续批处理，且滑窗 KV 无法量化 ⇒ MLX 今天无法同时服务 3–5 个带量化 KV 的长上下文模型。**

**所以不是"oMLX 好还是 llama.cpp 好"，是"按角色拆舰队"：**

| 角色 | 后端 | 决定性理由 |
|:---|:---|:---|
| 常驻聊天 + 工具调用（2–3 个）| **oMLX** | ✅ **唯一**原生具备 pin + per-model TTL + LRU **且同时给 OpenAI 与 Anthropic `/v1/messages`** 的 MLX 服务器 |
| 长上下文 / RAG / 高并发 | **llama.cpp（GGUF）** | **唯一**同时具备"K/V 独立可选类型"与"批处理"的路径 |
| 小模型 / VLM 按需 | oMLX 同一池 | 共用驱逐 + 统一内存池 + 前缀/SSD 缓存 |
| Embedding / rerank | oMLX | `/v1/embeddings`、`/v1/rerank` 已在池内 |

> ⚠️ **不要建在 `mlx_lm.server` 上**——它自述「**not recommended for production as it only implements basic security checks**」，且**没有模型池**（一次只装一个模型来回换）。这反过来确认 oMLX 的选择是对的。
