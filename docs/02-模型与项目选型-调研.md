## 一、能力① 本地订阅中转 —— 项目 landscape

| 项目 | Star/活跃 | 能力 | 与 iDoris 的关系 | 采用建议 |
|---|---|---|---|---|
| **[agent-cli-to-api](https://github.com/leeguooooo/agent-cli-to-api)** | 活跃 | Codex/Cursor/Claude Code/Gemini CLI → OpenAI `/v1`，前缀选后端 | **最贴合**能力① | **首选参考/直接借鉴其 subprocess 封装** |
| [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) | 活跃 | OpenAI/Gemini/Claude/Codex 兼容，OAuth | 订阅态接入范式 | 借鉴 OAuth 流 |
| [claude-code-proxy](https://github.com/fuergaosi233/claude-code-proxy) | 活跃 | Claude Code ↔ OpenAI 双向翻译 | 协议翻译参考 | 借鉴 Anthropic↔OpenAI 映射 |
| [claudecodex](https://github.com/karem505/claudecodex) | 新 | ChatGPT 订阅经本地 Codex proxy 驱动 Claude Code | 订阅复用 | 参考 |
| claude-max-api-proxy / clovapi | 新 | 订阅→localhost OpenAI 端点 | 极简本地桥 | 参考极简实现 |

**结论**：能力① 无需自研协议栈，`agent-cli-to-api` 的"多 CLI→统一 /v1 + 前缀路由"就是目标形态；我们加 loopback+单用户门禁（合规）即可。

## 二、能力② 外部 API 统一 —— 项目 landscape

| 项目 | 规模 | 语言/许可 | 亮点 | 采用建议 |
|---|---|---|---|---|
| **[LiteLLM](https://github.com/BerriAI/litellm)** | **140+ provider / 1892 模型** | Rust core+Py SDK / MIT | 统一 OpenAI 格式；SDK+Proxy 双形态；**已内置 Anthropic Messages / Gemini 原生翻译**；cost/fallback/LB/guardrails；支持 `native` 透传 | **首选采用**（外部 API 层地基）|
| [one-api](https://github.com/songquanpeng/one-api) / new-api | 20+ provider | Go / MIT | 单二进制、易部署、中文生态 | 轻量部署备选 |
| OpenRouter | 云聚合 | 商业 | 一个 key 打多家 | 当"外部的外部"上游 |
| [LLM Gateway](https://llmgateway.io/) | 云/自建 | 商业+OSS | OpenAI-compat 迁移友好 | 参考产品形态 |

**非 OpenAI-compat 的两大异类（Spike 重点）**：
- **Anthropic Messages API**（`/v1/messages`）：system 独立、content 块数组、tool_use/tool_result、thinking 块、SSE 事件不同。
- **Gemini**（`generateContent`）：`contents[].parts[]`、functionCall/Response、safetySettings。
- **判据**：LiteLLM 已翻译这两者 → 采用即可；但 **streaming / tool-calling / 多模态 / thinking** 四项保真度需实测（见 01 §2.2 Spike 矩阵）。

## 三、能力③ 本地模型 —— 编排项目 + 模型选型

### 3.1 编排/serving 项目

| 项目 | 定位 | 与"常驻/临时"的关系 | 采用建议 |
|---|---|---|---|
| **[llama-swap](https://github.com/mostlygeek/llama-swap)** | OpenAI-compat 代理，前置多后端，按需热加载/卸载，per-model **TTL** | **直接实现常驻(长TTL)/临时(短TTL)** | **首选采用**（本地模型编排核心）|
| **MLX / [mlx-lm](https://github.com/ml-explore/mlx-lm)** | Apple 原生统一内存推理+微调+serving | 核心常驻模型的 Apple Silicon 后端 | **采用**（与 oMLX 一脉）|
| Ollama | 易用本地模型管理 | 单后端、适合快速起步 | 备选/起步 |
| vLLM | 高吞吐 GPU serving | 有独显时的高性能后端 | Mac 外/社区端采用 |
| llama.cpp (server/router) | GGUF 通用后端 | llama-swap 的默认后端 | 采用 |

**推荐全栈**：`iDoris Router → LiteLLM(外部) → llama-swap(本地编排) → {mlx-lm / llama.cpp / vLLM / whisper.cpp}`，全链 OpenAI-compat。

### 3.2 模型清单（HF 现役最优，按能力/规模档）

> 用户给的规模（0.1B 语音 / 2B ASR / 4B 视觉 / 14B coding）与现役最优模型高度吻合，下表给"推荐默认 + 规模档 + 判据"。

| 业务能力 | 推荐默认（HF）| 规模 | 内存(4bit 约) | 常驻/临时 | 备注 |
|---|---|---|---|---|---|
| **核心推理（常驻）** | **Ornith-1.0-9B**（9B打35B，Mac mini 60t/s，MIT）；备选 Qwen3-8B/14B | 9B | ~6–7GB | **常驻** | 推理/脚手架为核心；"以小打大"横向扩展路线，M4 24GB 首选。**M4 24GB 决策见 [05 §5](./05-集成与技术栈协调规划.md)** |
| **核心推理（大模型,32GB+）** | **Ornith-1.0-35B MoE**（打397B）/ **Agents-A1-35B MoE**（追平万亿模型）| 35B MoE | ~19GB(Q4) | 32GB+ | ⚠️ **24GB 撑不住**（Q4≈19GB 吃满内存+需驱逐+短上下文）；32GB+ 才实用。详见 [07 §4](./07-模型量化内存评估与动态推荐.md) |
| **核心多模态（常驻可选）** | **Qwen2.5-VL-7B**（超 Llama3.2-11B-Vision）/ Qwen3-VL | 7B | ~6GB | 常驻/临时 | 若核心要多模态，用 VL 版当常驻 |
| **视觉/视频识别** | **Qwen2.5-VL-3B**（轻）/ 7B | 3–7B | 2–6GB | 临时 | 对应"4B 视频识别"；banner/图理解 |
| **ASR（语音转文字）** | **faster-whisper large-v3-turbo**（≈809M，6GB）/ **Qwen3-ASR**（52 语言）| 0.8–2B | 1–3GB | 临时 | 对应"2B ASR"；whisper.cpp 走 llama-swap |
| **TTS（文字转语音）** | **Kokoro-82M**（CPU 可跑，2–3GB，自然）| 0.08B | <3GB | 临时/常驻 | 对应"0.1B 语音"；极轻可常驻 |
| **Coding** | **Qwen2.5-Coder-14B**（16GB）/ 7B（8GB）/ Qwen3-Coder | 7–14B | 6–16GB | 临时 | 对应"14B coding"；或走能力①订阅中转 |
| **小语言模型（轻业务）** | **Qwen3-4B / Qwen2.5-3B** | 3–4B | 2–3GB | 临时 | 对应"blog 调 2B 小模型"；润色/摘要/分类 |

**选型判据**：
1. **常驻核心 = 推理优先**，多模态可选（按机器内存决定用 8B/14B/30B-MoE，用户可换）。
2. **同族优先（Qwen 系）**：统一 tokenizer/风格/微调工具链，降低 LoRA 与联邦的 base 对齐成本（见文档 03——所有节点须同 base checkpoint）。
3. **量化优先**：4bit(QLoRA 兼容) 是 Mac 统一内存下的甜点；MLX 自动 QLoRA。
4. **可换机制**：核心模型经配置项切换（`IDORIS_MODEL`），不同 Mac 不同默认。

## 四、联邦学习 / 本地训练 —— 项目 landscape（详见文档 03）

| 项目 | 定位 | 采用建议 |
|---|---|---|
| **[Flower (flwr)](https://github.com/adap/flower)** | Python 原生联邦学习，集成 HF Transformers，支持 **LoRA 联邦微调**，gRPC | **首选**（个人↔社区↔城市联邦）|
| **[OpenFedLLM](https://github.com/rui-ye/OpenFedLLM)** | LLM 联邦微调框架（instruction tuning + value alignment）| 参考/借鉴基线 |
| NVIDIA FLARE / OpenFL | 企业级联邦 | 城市/机构级备选 |
| **mlx-lm LoRA** / [MLX-LoRA-Studio](https://github.com/Goekdeniz-Guelmez/MLX-LoRA-Studio) | Mac 本地 LoRA/QLoRA 训练 | **采用**（个人端本地自训练）|
| PEFT (HF) | LoRA/DoRA 参数高效微调 | 与 Flower 组合 |
| DP-FedLoRA / 差分隐私 | 端侧联邦 + 差分隐私 | 隐私阶段采用 |

**关键机制**：所有节点约定**同一个 base checkpoint**（从公共 registry 取），联邦时**只共享 LoRA adapter**（几十 MB，相对 base 极小）——这是"隐私 + 低通信 + 可组合"三赢的技术根基。

## 五、调研小结（一页纸结论）

1. **三种能力全部有成熟开源支撑**，iDoris 不需重造网关：能力①=agent-cli-to-api 范式；能力②=LiteLLM；能力③=llama-swap + MLX。
2. **"常驻/临时"= llama-swap TTL**，天然落地；核心模型推理优先、Qwen 系、量化、可换。
3. **异构外部 API 可统一**（LiteLLM 已翻译 Anthropic/Gemini），但需 Spike 验证四项保真度。
4. **本地自训练 + 联邦**有 MLX-LoRA（个人）+ Flower/OpenFedLLM（联邦）两级现成工具，"只传 LoRA、同 base"是核心机制。
5. **iDoris 的真正自研价值**集中在最上层薄编排（意图路由 + 订阅中转门禁 + 隐私标签 + 业务能力组合 + 自增长/联邦编排），以及与 Agent24 审批/记忆/隐私的缝合——**不是重写基础设施**。
