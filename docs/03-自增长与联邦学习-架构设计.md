# iDoris 自增长与联邦学习 —— 架构设计

> 文档类型：架构设计（数据流 + 自训练 + 联邦学习）
> 日期：2026-07-30 ｜ 维护者：iDoris.ai / @jhfnetboy
> 前置：[`01-统一模型服务-架构设计.md`](./01-统一模型服务-架构设计.md)、[`02-模型与项目选型-调研.md`](./02-模型与项目选型-调研.md)
>
> **本文回答**：当 iDoris 对外是"一个统一服务"时，数据如何在其内部**完整流转并驱动自我进化**（个人层）；两个 iDoris（个人↔社区↔城市）如何在**保护隐私的前提下联合训练**（联邦层）；这套"自增长"逻辑是否成立、怎么分阶段落地。

---

## 1. 核心命题：iDoris 是一个"自增长系统"

> 因为对外统一、对内三能力，且服务与数据同处一台机（个人 Mac / 家庭 Mac mini），**数据可以在模型体系内完整闭环流转**：使用产生数据 → 数据沉淀 → 沉淀驱动 agent/skill/模型迭代 → 迭代提升下一次使用。这就是"越用越懂你"的自增长（对应 AuraAI 护城河 3）。

自增长有**三个可迭代对象**（都在本地）：
1. **Agent 迭代**：调用轨迹/成功失败 → 优化 prompt/persona/工作流（无需训练模型）。
2. **Skill 迭代**：使用统计 → 新增/改进技能模块（Agent24 模块生态）。
3. **模型迭代（LoRA）**：脱敏后的个人语料 → 本地 LoRA 微调核心模型（MLX-LoRA）。

## 2. 第一层：个人本地自增长闭环

### 2.1 数据流架构（单机内闭环）

```
        使用（chat / banner / blog / 微信 / agent runs）
                       │  产生
                       ▼
   ┌───────────────────────────────────────────────┐
   │  个人数据湖（本地，分级存储，永不默认出设备）    │
   │  • 会话/记忆   (Agent24 D1 CanonicalSession)    │
   │  • 调用轨迹    (runs / tool_calls / 审批 audit) │
   │  • 业务产物    (banner/blog/文件…)              │
   │  • 反馈信号    (采纳/修改/点赞/重试)            │
   └───────┬───────────────────────┬────────────────┘
           │ 提炼(1)                │ 提炼(3)
           ▼                        ▼
   ┌───────────────┐        ┌───────────────────────┐
   │ Agent/Skill   │        │ 训练语料(脱敏)         │
   │ 优化(无训练)  │        │ → 本地 LoRA 微调(MLX)  │
   └───────┬───────┘        └──────────┬────────────┘
           │                           │ 产出
           │                    ┌──────▼──────┐
           └───────────────────▶│ 核心模型 +   │──▶ 下次使用更懂你
                                │ 个人 LoRA    │    (热挂载,不改 base)
                                └─────────────┘
```

### 2.2 关键机制
- **base 冻结 + LoRA 外挂**：核心模型权重不动，个人化只体现在几十 MB 的 LoRA adapter，可热切换、可加密迁移（换机不丢"懂你"）。技术栈：`mlx-lm.lora`（Mac 上 7–8B QLoRA 约 7–8GB 内存、<30min 可出一个 adapter）。
- **闲时训练**：仿 Prism Tier2——Mac mini 24h 常驻，闲时自动跑增量 LoRA，不影响在线推理。
- **⚠️ LoRA 晋升门（codex-rescue R1 / S2）**：自动微调不能悄悄替换常驻模型（否则会静默退化）。**新 LoRA 走 `候选(candidate) → holdout 评测 → 晋升(promoted) → 可回滚`**：只有在本地保留集上不劣于当前 adapter 才晋升为默认；adapter 版本化，随时回滚；灾难性遗忘由多 adapter 组合 + 回放缓解。**此门只对"模型/LoRA 晋升"生效，不约束 prompt/persona/工作流的日常微调**（那些无需门，避免过度设计）。
- **分级存储对齐隐私**（产品隐私分级 0–3）：级别 0（生物特征/位置/家人）永不参与任何外传训练；只有脱敏语义摘要可进入联邦（见 §3）。
- **数据即副产品**：用户为"好用"而使用（记账/写博客/聊天），数据是真实的生命足迹，非"为训练而造"——冷启动与真实性同时解决（Prism 洞见）。

### 2.3 与 Agent24 的接点（复用，不重造）
- 数据湖 = Agent24 store（sessions/runs/tool_calls/audit）+ D1 记忆 + 业务产物目录。
- 训练触发 = H5 self-wake（闲时定时）+ scheduler。
- 危险动作（写模型/导数据）经 C4/D3 审批门。

## 3. 第二层：个人 ↔ 社区 iDoris 联邦

### 3.1 拓扑（"外部 API 指向社区"即联邦入口）
个人 iDoris 把能力②的"外部 API"之一**指向社区 iDoris**（社区端配置更强：多 GPU、更大模型）。因为两端都是 iDoris，这条连接不仅能"借算力/借大模型"，还能**跑联邦学习**：

```
   个人 iDoris(A)          个人 iDoris(B)          个人 iDoris(C)
   base + LoRA_A           base + LoRA_B           base + LoRA_C
        │  只上传 LoRA(脱敏)     │                      │
        └──────────┬───────────┴──────────┬───────────┘
                   ▼                       ▼
            ┌──────────────────────────────────┐
            │        社区 iDoris (聚合方)        │  ← 更强算力
            │  • 收各端 LoRA adapter(非原始数据) │
            │  • FedAvg/FedIT 聚合 → LoRA_community│
            │  • 反哺：LoRA_community 下发给每端  │
            └──────────────────────────────────┘
```

### 3.2 为什么这样能"隐私 + 有效 + 低成本"三赢
- **只传 LoRA，不传原始数据**：各端约定**同一个 base checkpoint**（公共 registry 取），联邦时只交换 adapter（几十 MB）。原始个人数据不直接出设备。
  > ⚠️ **重要修正（codex-rescue R1 / S1）**：**"只传 LoRA" ≠ 隐私保证。** adapter/梯度可被反推出训练数据（membership/inversion 攻击，见 [04 T5](./04-联邦学习挑战-技术伦理法律基础设施.md)）。正确表述：**"只传 LoRA 降低了原始数据暴露面，但在 DP 加噪 + 安全聚合 + 梯度裁剪 + 同意门就位前，不算隐私安全"**。因此 F0 只用合成/脱敏数据跑链路，真实数据必须等 F1 隐私层（这与"只传 adapter 就安全"是两码事）。
- **成熟框架**：[Flower (flwr)](https://github.com/adap/flower)（Python 原生、集成 HF Transformers、支持 LoRA 联邦、gRPC 传输，NumPyClient + Strategy 范式）；参考基线 [OpenFedLLM](https://github.com/rui-ye/OpenFedLLM)（instruction tuning + value alignment）。
- **联合模型 = 更大范围经验**：单人语料有限，社区聚合出"通用经验插件"（community LoRA）反哺每个人——个体用极低成本拿到"群体智慧"，核心隐私仍留本地（AuraAI 社区端双角色：技术托管 + 集体进化）。

### 3.3 隐私强化（阶段二再上，见 §5）
- **差分隐私联邦 LoRA**（[DP-FedLoRA](https://arxiv.org/abs/2509.09097)）：上传的 adapter 加噪，抵御从 adapter 反推数据。
- **安全聚合**：聚合方只见聚合结果，不见单端 adapter。
- **贡献授权**：用户签署脱敏训练协议后才参与（对齐隐私级别 2"可选同步，明确授权"）。

## 4. 第三层：社区 → 城市（层级联邦 / 分形）

同一机制向上再套一层——**iDoris 节点是分形的**：一个节点既是"个人核心"，也能当"别人的上游"。

```
个人_i ──LoRA──▶ 社区_j ──社区LoRA──▶ 城市_k ──城市LoRA──▶（公共物品，反哺各社区/个人）
```
- **个人→社区**：邻里/兴趣共识（AuraAI 在地社区 + 精神社区），聚合出社区特性模型。
- **社区→城市**：多社区脱敏贡献 → 城市级公共模型/服务（如城市级危机预警、公共服务匹配）。属 Mycelium "数字公共物品"（Park 协议）。
- **层级联邦**（hierarchical FL，Flower/FLARE 支持）：城市只聚合社区级 adapter，个人数据在两层脱敏之后，隐私边界更强。

> **⚠️ 分形 ≠ 重复 FedAvg（codex-rescue R1 / E1）**：每一层都需要一个**控制面**，光有聚合算法撑不起"个人→社区→城市"。落一个**最小联邦会话契约**（Federation Session Contract）即可，**不现在设计城市级治理**（那才是过度设计）：
> ```yaml
> federation_session:
>   participants: [did:...]          # 谁参与(AirAccount DID 身份)
>   base_model_digest: sha256:...    # 统一 base(见 06 §10.4)
>   consent_proof: [...]             # 每方同意凭证(opt-in)
>   aggregation: fedavg|fedit|robust # 聚合策略
>   round_id: <n>                    # 轮次
>   audit_hash: sha256:...           # 审计链(Agent24 audit)
>   rollback_target: <round_id>      # 坏聚合可回滚
> ```
> 有了这七个字段，分形扩展才真正成立；发现/信任/激励等更重的治理留 F2（见 [04 §五](./04-联邦学习挑战-技术伦理法律基础设施.md)）。

> **这解答了"能否支撑个人/社区/城市"**：能。同一套"base 冻结 + 只传 LoRA + 分层聚合"机制，天然按行政/社会结构分形复用，无需为每级另设架构。

## 5. 分阶段落地（严格按用户给的顺序：先跑通 → 隐私 → 效率）

| 阶段 | 目标 | 内容 | ⚠️ 边界 |
|---|---|---|---|
| **F0 链路跑通** | 证明数据能在体系内完整流转 | 个人端：使用→数据湖→提炼→MLX-LoRA→热挂载，闭环跑通；个人↔社区：Flower 起最小联邦（同 base、传 LoRA、FedAvg 反哺）| **必须用合成/脱敏样例数据**，不得用真实个人隐私跑无隐私联邦 |
| **F1 隐私安全** | 让联邦可用真实数据 | DP-FedLoRA 加噪 + 安全聚合 + 授权协议 + 隐私级别 0 硬隔离 + 审计 | 真实个人数据从此阶段起才准入联邦 |
| **F2 效率** | 规模化 | 通信压缩、客户端择优参与、闲时调度、增量聚合、非-IID 缓解 | — |

> **对"先不管隐私安全"的诚实提醒**：链路层面可以先不含隐私（F0 用假数据验证机制），这是合理的原型策略；但**联邦的价值前提就是隐私**——一旦接入真实个人数据，隐私层（F1）必须先就位，否则"联邦"退化成"上传数据"，违背整个体系的初衷与 Mycelium 使命。这条要写死进设计门禁。

## 6. 论证：自增长逻辑成立吗？

### 6.1 成立的技术根据
- **本地自训练可行**：MLX 让 Mac 上 LoRA 微调是分钟级、$0 云成本的日常操作（实测 7B QLoRA <30min）。自增长不是画饼。
- **联邦可行且成熟**：Flower/OpenFedLLM/PEFT 已是 LLM 联邦的标准工具；"同 base + 只传 LoRA"是被反复验证的低成本高隐私路径。
- **分形可扩展**：个人/社区/城市复用同一机制，架构不膨胀——符合菌丝网络"指数传播、共生互利"范式。

### 6.2 诚实的挑战（不回避，需在 F1/F2 解决）
| 挑战 | 说明 | 应对 |
|---|---|---|
| **non-IID 数据** | 各人数据分布差异大，naive FedAvg 可能"聚合出平庸" | 个性化联邦（保留个人 LoRA + 只联邦共性层）、聚类联邦 |
| **base 版本一致性** | 所有节点必须同一 base checkpoint 才能聚合 adapter | 统一模型 registry + 版本协商（同 §Qwen 系选型判据）|
| **激励对齐** | 凭什么贡献数据/算力 | 信用体系（AuraAI 护城河 5 / Mycelium GToken），非金钱亦可 |
| **通信/算力成本** | 联邦轮次通信、社区端聚合算力 | 只传 LoRA(几十 MB)、择优参与、闲时聚合 |
| **投毒/女巫攻击** | 恶意端上传坏 adapter | 鲁棒聚合(中位数/裁剪)、身份(AirAccount DID)、信任分层 |
| **隐私反推** | 从 adapter 反推训练数据 | DP-FedLoRA + 安全聚合（F1）|

### 6.3 结论
> **逻辑成立**：个人层"使用即进化"有 MLX-LoRA 兜底；联邦层"个人↔社区↔城市"有 Flower + LoRA-only 机制兜底；分形结构与 Mycelium 使命同构。**核心价值不在单个模型多强，而在"数据在体系内自增长 + 隐私前提下的集体进化"这套闭环**——这正是纯商业 API 给不了、且难以复制的护城河（关系图谱/个人化模型/网络效应属于用户与社区）。落地按 F0→F1→F2 推进，隐私是接入真实数据的硬门槛。
