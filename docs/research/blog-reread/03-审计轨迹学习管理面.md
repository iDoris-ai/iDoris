### 2.1 ATIF / 轨迹格式 / 轨迹驱动学习

**[Cua: Computer-Use 2.0](https://blog.mushroom.cv/blog/cua-computer-use-2-0-desktop-agent-benchmark-trajectory-cua-s1/)**
核心观点：GUI 操控应降格为 Agent 的一次工具调用而非独占循环；配套的 Cua Bench 三段式评测（setup→execution→evaluation）支持导出轨迹数据供训练；CUA-S1-Forms（70万参数/2.8MB）单次前向读 logprob 决策，真实表单 100% 准确但样本仅 196 个决策。
对 iDoris 的启示：验证了"决策模型先行"路线（tiny model 读 logprob）的可行性，但也提醒**小样本验证的自信心要打折扣**——iDoris 的决策模型晋升门禁应要求最低真实验证样本量，不能只看合成测试集分数。

**[别浪费失败！斯坦福失败轨迹驱动改进](https://blog.mushroom.cv/blog/learning-from-failure-inference-time-gui-agent-improvement-stanford/)**
核心观点：Failure-Case Loop——收集失败轨迹→LLM 诊断四类失败模式（定位错误/能力缺口/知识不足/冗余循环）→生成推理时补丁（prompt 增强/代码模块，不改模型权重）→轻量人工验证（97%直接采纳）→注入→循环。零训练成本，OSWorld 42.3%→48.9%，且补丁可跨基准迁移。
对 iDoris 的启示：这是**比 LoRA-SFT 更便宜的一级学习路线**，现有设计 §4.8 的学习层顺序（①决策模型→②OPD→③编译型学习→④偏好→⑤RL）里缺了这一级——应在"决策模型先行"之前或并列插入"**失败轨迹→推理时补丁**"这一档：不改权重，只改路由/隐私判定器的 prompt 或规则，用决策账本里的误判轨迹驱动，成本几乎为零。四类失败模式（grounding/competency/knowledge/redundant loop）也可以补充进 §5.5 的 `failure_mode` 分类体系。

**[HarnessX：脚手架即进化对象](https://blog.mushroom.cv/blog/harnessx-agent-scaffold-evolvable-darwin-team-xiaomi-engineering-guide/)**
核心观点：把 prompt/工具/记忆/控制流当作可搜索设计空间，用执行轨迹驱动迭代；9B 模型 ALFWorld 从 53%→97%，全部改动在脚手架层面（不训练模型）。
对 iDoris 的启示：这属于 Agent24 Evolver 的范畴（改 Skill/Prompt 不改权重），但其"轨迹分析→定位失败模式→生成脚手架变体→评估→选择"闭环和现有设计 §2 不变式 #6"策略是数据，写入走提议→diff→批准→版本化"高度一致，可作为该流程的一个可复用实现参考（尤其是失败模式自动分类的做法）。

**[GEPA：让 LLM 阅读自己的执行轨迹进化 Prompt](https://blog.mushroom.cv/blog/gepa-reflective-prompt-evolution-vs-reinforcement-learning/)**
核心观点：读轨迹做自然语言反思 + 合并经验 + Pareto 候选选择，比 GRPO 平均高 10%（最高 20%），且只需 GRPO 3% 以下的 rollout 数（HotpotQA 上 32x-303x 更省）。不改模型权重。ICLR 2026 Oral。
对 iDoris 的启示：**这是本轮最值得单独拎出的发现**。iDoris §4.8 的学习层从"决策模型 SFT"直接跳到"OPD/RL"，没有覆盖"用决策账本轨迹做 prompt/规则级反思进化"这一档——而 GEPA 证明了这一档在**样本效率**上碾压 RL。iDoris 的路由判定器（intent/privacy/complexity）目前设想走"规则→embedding→本地 logit→决策头训练"的路径，可以在"决策头训练"之前先加一级：用决策账本的误判轨迹跑 GEPA 式的 Pareto 反思循环，改判定器的 prompt/规则集，而不是一上来就训练模型。这与 §2 不变式 #10"模型只提议，代码判决"是同构的——GEPA 的"进化"产物依然是可审查的文本（prompt），不是黑盒权重。

**[SkillPyramid：技能三层金字塔](https://blog.mushroom.cv/blog/skillpyramid-hierarchical-skill-consolidation-self-evolving-agents/)**
核心观点：原子层（跨任务最小操作）→功能层（任务级技能）→抽象层（跨功能模式），关系分析器做"向下原子抽取+向上抽象归纳"；比 ReAct 多 38% 奖励，少 28% 步骤；且对 150K 个互联网挖掘的噪声技能过滤后仍有效（56%→62.7%）。
对 iDoris 的启示：技能层归 Agent24 管，但其"层级化组织比平铺技能库更抗噪声"的结论，可以类比应用到 iDoris 自己的**决策规则集**上——现有设计的 `route.intent`/`route.privacy`/`route.complexity` 等决策点如果规则越堆越多，也应该做原子规则抽取+抽象归纳，而不是让规则集平铺膨胀。

**[SkillClaw：阿里集体技能进化](https://blog.mushroom.cv/blog/beyond-static-skill-libraries--alibaba/)**
核心观点：Agentic Evolver 自动聚合脱敏用户交互轨迹，"精炼"或"新建"技能同步回共享库；6轮进化后 Creative Synthesis 任务提升 88.41%；论文本身提到与 iDoris 联邦 LoRA 路线的对照——**SkillClaw 聚焦技能层（云端共享库），iDoris 聚焦模型权重层（DP-SGD+联邦LoRA），两者正交并存**。
对 iDoris 的启示：这篇文章的作者视角本身就在替 iDoris 做定位——确认了"Agent 的技能由 SkillClaw 类机制集体进化，决策模型由 iDoris 类机制持续学你"是两条互补路径，值得写进现有设计 §1 或 §8"对上游的服务目录"里，明确 iDoris 不做技能层进化（那是 Agent24 Evolver 的事）。

**[美团图灵 Agent 评测两年实践](https://blog.mushroom.cv/blog/meituan-agent-evaluation-trajectory-rubric-harness-practice/)**
核心观点：评测是"精密量具"而非答题；Rubric 二元化（把"是否口语化"拆成"是否用您/是否有语气词"等 yes/no 判据）把人人一致率从 62%提升到 92%；数据飞轮起点要低，从 20 个指标的冷启动一年扩到近 200 个，靠 Bad Case 喂养而非白板设计；四层评测（结果/过程/效率/风险）多数团队只做第一层。
对 iDoris 的启示：现有设计 §5.5 的分类体系已经有质量层 L0-L3，可以补充"**Rubric 二元化**"这个具体技巧到 §4.7 的"结构化 reason"设计中——把"这次路由是否合理"这类主观判断拆成可复现的 yes/no 断言，比 0-10 打分更适合作为决策账本的训练/评测信号。

**[WikiSkill：三层持久知识架构](https://blog.mushroom.cv/blog/wikiskill-agent-experience-persistent-wiki-skill-evolution/)**
核心观点：Skills（可回滚）/ Wiki（永不回滚，跨迭代复利积累）/ Raw（不可变一次写入）三层；Inference Agent 执行期间不能读 Wiki（否则会抄答案，消融实验证明会让效果变差 63.7%→60.9%）；Skill 更新失败会回滚但 Wiki 记录本身永久保留，成为下次提案的参考。
对 iDoris 的启示：与现有设计 §5.4"原件不可变"高度一致，但补充了一个现有设计没有明确写的细节——**"生成候选方案的 Agent 不能预先看到过去所有失败教训的全文，否则会抄"**。iDoris 的决策模型训练（尤其是 GEPA 式反思循环）如果让"改进 prompt 的元 LLM"看到过多历史成功案例，也可能出现类似的"抄答案"而非"真学习"的风险，值得在设计元 LLM 的输入时留意做训练/验证分离。

**[S1-DeepResearch：图谱驱动轨迹构造范式](https://blog.mushroom.cv/blog/s1-deepresearch-long-horizon-research-agent/)**
核心观点：三步范式——知识图谱出题（先裸答一遍过滤掉靠记忆能答的题，只留最难的30%）→Agent 跑轨迹→五维验证过滤；仅用 SFT（不用 RL）就让 32B 模型逼近百亿级旗舰；15K 高质量轨迹全部开源。
对 iDoris 的启示：其"先裸答一遍过滤题目难度"的做法，可以用于 iDoris 决策模型训练数据的质量筛选——判断一条历史请求是否值得进训练集，可以先看"不给上下文/规则时基座模型能否猜对"，猜对的说明不需要训练，只有猜不对的才是有信息量的样本。

**[Agentic Harness Engineering (AHE)](https://blog.mushroom.cv/blog/agentic-harness-engineering-observability-self-evolution-coding-agent/)**
核心观点：三层可观测性——组件可观测（7类文件级组件+git跟踪）、经验可观测（10M token trace蒸馏成分层报告）、决策可观测（每次修改必须声明可证伪预测，下轮自动验证）；跨模型迁移测试证明"结构性 harness 知识可迁移，文字策略指令不行"。
对 iDoris 的启示：**"每次修改都要声明可证伪预测，下轮自动验证"**这一条已被现有设计 §4.7 采纳（"变更记录带预测"）。AHE 额外提供了一个现有设计没写的细节：**消融实验显示增益主要来自工具/中间件/长期记忆，而非系统提示词**——这提示 iDoris 的策略 diff 审批 UI 应该优先展示"工具定义/路由规则"层面的改动，而不是过度关注 prompt 措辞级别的微调，后者投入产出比更低。

**[Meituan / BrainTrust 六代 eval](https://blog.mushroom.cv/blog/brainstrust-agent-eval-six-generations-guide/)**
核心观点：eval 对象跟着架构复杂度扩大（Prompt→Chain→ReAct→Workflow Graph→Modern Loop→AI Harness）；"正确但太贵不算成功"；生产失败要回流成 eval case（production-to-eval 飞轮）。
对 iDoris 的启示：iDoris 处于"第六代 AI Harness"阶段（有 memory/sandbox/permissions/durable state），文章列出的分层 eval 方法（smoke tests→offline evals→simulations→replays→shadow runs→online scoring）与现有设计 §6.2"回放模拟器"+"shadow 对比"完全对应，可以直接把这六层作为 iDoris 学习层门禁的具体检查清单写进 §4.8"晋升门禁"。

### 2.2 观测性 / 日志即运行时

**[Maka：日志即运行时](https://blog.mushroom.cv/blog/maka-agent-runtime-host-event-log-desktop-tui-eval/)**
核心观点："Log is the Runtime"——会话视图/UI/发给模型的上下文/崩溃恢复全部是对 Runtime Event Log 的投影，而非各自维护状态；"**上下文不等于历史**"（context is not history）：剪枝压缩只影响模型看到的内容，日志本身永远保留完整证据链；Desktop/TUI/Eval 三个入口共用同一个 Runtime Host，保证"测的就是用户实际用的执行逻辑"。
对 iDoris 的启示：这是现有设计 §2 不变式 #9"日志即运行时"的**直接来源**，已被采纳。补充细节：Maka"上下文不等于历史"的措辞比现有设计更精确，可以直接用于文档措辞——iDoris 的 `<think>` 内容分离、上下文剪枝，都应遵守"给模型看的可以精简，Event Log 永远完整"这条边界。

**[Retrace：回放+分叉调试](https://blog.mushroom.cv/blog/retrace-ai-agent-debug-observability-tool/)**
核心观点：记录每次 LLM 调用/工具调用/错误，支持从任意历史节点 **fork**（分叉）——"如果在这一步做了不同决策，后续会怎样"，而不只是重放。
对 iDoris 的启示：现有设计 §6.2"路由"页只有"回放模拟器"（新 policy 在过去流量上跑一遍），**没有"fork"能力**——即从一次具体请求的某个决策点分叉，手动改一个判定结果（比如把 route.intent 从 A 改成 B），看后续路由/预算/隐私链路会怎样。这是一个现有设计目前缺失但很有价值的管理界面功能，建议加入 §6.2"请求"详情页。

**[AgentSight：eBPF 系统边界追踪](https://blog.mushroom.cv/blog/agentsight-ebpf-boundary-tracing-ai-agent-observability/)**
核心观点：在 SSL/TLS 调用点截明文 + eBPF 抓内核事件，agent 自己改不掉这层观测；CPU 开销<3%；但 macOS/Windows 只能读 agent 自己的本地会话文件，没有 eBPF 捕获——**Mac 用户拿不到这套方案最核心的能力**。
对 iDoris 的启示：已被现有设计引用。补充提醒：iDoris 的目标硬件是 Mac（个人层），AgentSight 这类"agent 无法篡改的系统级观测"在 Mac 上做不到内核级捕获，说明 iDoris 自己的 Event Log（应用层，可被自己代码控制）**不能依赖外部工具兜底防篡改**，"日志即运行时"的完整性保证只能靠自身实现（例如追加式写入+签名），不能寄望于系统层旁路方案。

**[Semantica：决策溯源图谱](https://blog.mushroom.cv/blog/semantica-graph-native-ai-provenance-enterprise-knowledge-graph/)**
核心观点：每个 AI 决策记为图节点+因果链（`record_decision`/`add_causal_relationship`/`trace_decision_chain`），冲突检测标记而不静默覆盖，W3C PROV-O 标准溯源可直接导出给监管方。
对 iDoris 的启示：现有设计 §4.7"决策账本"记录 `{decision_point, judge, model_revision, prompt_hash, scores, latency}`，但**没有显式的因果链接口**（比如"这次隐私脱敏决定导致了后续哪次路由降级"）。可以借鉴 Semantica 的 `trace_decision_chain` 模式，给决策账本加一个"causal_ref"字段，把同一请求内相互影响的决策点串成链，方便审计时回答"为什么"而不仅是"是什么"。

**[Dense-Mem：受治理的 AI 记忆](https://blog.mushroom.cv/blog/dense-mem-governed-ai-memory-mcp-evidence-provenance/)**
核心观点："模型输出是一份提案，能否变成持久状态由服务端确定性策略决定"；证据只增不删，生命周期变更只改变有效状态，不抹除溯源链；关系只有在证据"合格"时才成为活跃图边。
对 iDoris 的启示：这是现有设计 §2 不变式 #10"模型只提议，代码判决"在记忆系统上的**几乎逐字对应实现**，强烈验证了这条不变式的正确性。但它的"证据只增不删"与现有设计 §5.6"删除/撤回授权→墓碑→硬删除"存在张力：Dense-Mem 从不硬删除原始证据，只改变其"有效性"标记；iDoris 目前设计是行使删除权时**硬删除+留墓碑**。这是一个值得在 §5.6 明确记录的设计取舍（见第4节）。

**[Memory Harness：六层可追溯记忆](https://blog.mushroom.cv/blog/memory-harness-local-first-programmable-auditable-long-term-memory/)**
核心观点：Evidence（不可变）→Knowledge Unit→Episode→Memory→Living Knowledge→Agent Asset 六层，每层保留来源链接；混合 RAG 完全本地无云依赖；多 AI 协作但草稿彼此隔离，需人工确认才共享。
对 iDoris 的启示：现有设计 §5.6 的血缘表是"轨迹→数据集版本→adapter→部署"四层，Memory Harness 提供了更细粒度的六层参考。不需要照搬全部六层，但"多 AI 协作、草稿彼此隔离、仅显式提交才共享"这条对 iDoris 的多租户/多 key 场景有直接参考价值——不同调用方（key）产生的轨迹在进入共享训练集之前应有类似的"草稿隔离+显式提交"机制，而不是自动混入。

**[Belief Context Graph (BCG)](https://blog.mushroom.cv/blog/belief-context-graph-bcg-agent-memory-confidence-provenance-deterministic-reasoning/)**
核心观点：把记忆从"检索"升级为"信念"——确定性置信度（三分量计算，非模糊 LLM 打分）+精确证据溯源（来自哪轮对话哪个偏移量）+冲突检测；候选/假设默认不进召回。
对 iDoris 的启示：现有设计的决策账本记录 `scores`，但没有说明 score 的计算是否确定性可复算。BCG 的"确定性置信度公式（可追溯每条证据贡献的权重）"是一个好的补充标准——iDoris 路由判定器输出的校准概率，应该在决策账本里存"贡献了多少权重的证据/规则"，而不只是最终分数，方便审计员理解"为什么判定为 S2 敏感度"而不只是"判定为 S2"。

### 2.3 元数据与内容分离

**[Agent Skills 标准：渐进式披露](https://blog.mushroom.cv/blog/agent-skills-open-standard-progressive-disclosure-anthropic/)**
核心观点：三阶段披露——发现阶段只加载 name+description，激活阶段任务匹配才读全文，执行阶段才按需跑脚本/加载引用文件；让 Agent 同时挂载大量技能不撑爆上下文。
对 iDoris 的启示：这是"元数据与内容分离"在 Skill 领域的标准实践，与 iDoris 的 ATIF 设计中"规范层存 messages，`extra.idoris` 命名空间存治理字段"是同一个思路的不同应用场景——**元数据要小、要总在场；内容要大、要按需加载**。可以作为一条通用设计原则写进现有设计的不变式，而不只是体现在某一处具体实现。

**[awesome-agent-skills 四条质量判据](https://blog.mushroom.cv/blog/awesome-agent-skills-cross-vendor-paths-quality-criteria-anti-slop/)**
核心观点：顶层元数据压到 ~100 token 以内、正文控制在 500 行以内、不许硬编码绝对路径、不许申请全量工具权限（`"tools": ["*"]`）。
对 iDoris 的启示：这四条给了"元数据/内容分离"一个**可执行的数字化标准**。iDoris 的组件卡（catalog）、策略 diff 摘要、决策账本的 reason 字段，都可以套用类似的体量上限（比如响应头/reason_code 的元数据要控制在几十 token 内，避免把内容误当元数据传递）；"不许申请全量工具权限"直接对应 iDoris 的虚拟 key 权限最小化设计。

**[watermarks-remover：AI 内容溯源三层解剖](https://blog.mushroom.cv/blog/watermarks-remover-ai-provenance-c2pa-synthid-statistical-open-source/)**
核心观点：Unicode 编辑水印（可验证去除）、统计采样水印（改写可降低但无公开通用检测器验证）、C2PA 文件元数据（可清除或有远程绑定）；核心教训——"这个工具无法认证官方检测器会失败"，可验证的和"尽力而为"的要分开报告。
对 iDoris 的启示：如果 iDoris 未来要给自己生成的内容加溯源标记（比如标注"这是本地小模型生成的"或用于合规），应该学习这篇的诚实分级——**明确区分"可验证证明"（如 Unicode 计数）和"尽力而为的猜测"（如统计信号），不要把两者混在一个置信度里汇报**，这也呼应了 BCG 的"候选/假设不进召回"设计。

### 2.4 训练数据的授权、删除与溯源

**[OpenThoughts-Agent：100+ 消融实验的 SFT 数据配方](https://blog.mushroom.cv/blog/openthoughts-agent-sft-data-recipe-agentic-models/)**
核心观点：六阶段流水线逐项消融——①任务来源选择可造成 30pp 精度差距（最重要环节）；②Top-4~8 混合最优，Top-16 反而下降；③LLM 改写任务描述**没有**提升；④LLM 任务过滤器+3pp；⑤**更强的模型不一定是更好的教师**（GLM-4.7 比 GPT-5.3-Codex 教得更好）；⑥过滤掉少于5轮的轨迹提升最大；扩规模时"多采样同任务"会平台化，只有"合成扩展任务描述多样性"能突破平台。
对 iDoris 的启示：这些是**直接可操作的数据策展经验**，应该补充进现有设计 §5.6 策展流程：
- iDoris 训练数据策展时，"教师模型选择"不应默认选"本机最强的档位"（现有设计②本地教师蒸馏 OPD 假设"deep 档教 fast 档"），而应该像本文一样做小规模 A/B，验证哪个本地档位实际教得更好，不能想当然。
- "LLM 改写任务描述没有提升"提醒 iDoris 不要在数据增强环节过度依赖"让模型改写请求再学"，应优先保留原始请求措辞。
- "少于5轮的轨迹过滤掉，长轨迹质量更高"可以作为 iDoris 决策训练数据的一个具体过滤规则。

**[Pentest Harness 拆穿：换皮+删除授权边界](https://blog.mushroom.cv/blog/pentest-harness-deepseek-harness-rebrand-authorization-teardown/)**
核心观点：MIT 协议下换皮合规，但把"仅限授权测试"降级为纯粹用户自我声明，没有 scope 文件/白名单/审计日志；代码深处埋了一段"Authorization: FULL，无范围限制、不警告合法性"的兜底人格（虽非默认触发，但是 fork 作者主动写入的）。
对 iDoris 的启示：已被现有设计 §2 不变式 #12"调用方的自我声明永远不能放宽授权；只接白名单 provider"直接引用，是一个很扎实的反面案例来源，本次核实确认引用准确。

**[Claude for Financial Advisors](https://blog.mushroom.cv/blog/claude-financial-advisors-connector-skill-approval-pattern/)**
核心观点："Connector（权限继承+只读+范围限定）+ Skill（工作流技能）+ 审批（投资建议/合规判断必须人工批准）+ 审计（Enterprise 版审计日志）"打包模式；Addepar 集成初期刻意只做四类分析检索，不做写操作；作者判断"垂直 AI 的护城河不在训练专用模型，而在谁能把审批和审计做成产品默认设置"。
对 iDoris 的启示：与 iDoris §4.6 预算"超额审批队列"、§6.3"提议→diff→二次确认→版本化"高度一致。补充启示：**"初期只做读、不做写"是审批系统的一个稳妥落地顺序**，iDoris 的 Admin API 分期（M4 只读→M5 隐私/预算/审批→M6-M7 轨迹/学习）本身已经遵循这一顺序，本文可作为该分期策略的行业验证案例。

**[织影 Video Production Buddy：分阶段审批门](https://blog.mushroom.cv/blog/video-production-buddy-zhiying-ai-pipeline-guide/)**
核心观点：把生产流程拆成策划→脚本→场景规划→素材生成→审查五个阶段，**每个阶段结束后暂停等待人工批准**才继续；Backlot 实时看板显示当前阶段/花费/每次调用的提供商决策；完成后支持 Replay 模式按时间轴逐帧重放。
对 iDoris 的启示：这是"策略提议→diff→批准→版本化"在 UI 层面的一个具体可视化范式，直接可以套用到现有设计 §6.2"轨迹与学习"页——训练任务的每个阶段（策展→数据集卡→训练→评测门禁→晋升）都可以做成 Backlot 式的实时看板+逐阶段审批门，而不是一个"提交后等结果"的黑盒任务。这比现有设计目前描述的"回放模拟器"更进一步，建议补充进 §6.2 的具体交互设计。

### 2.5 本地训练在常规机器上是否可行

**[KTransformers v0.7.1：CPU+GPU 异构 LoRA](https://blog.mushroom.cv/blog/ktransformers-v071-moe-lora-finetune-qwen-vlm-kimi-rawint4/)**
核心观点：路由专家权重放 CPU 主存，GPU 只跑注意力和共享专家，允许用大内存 CPU+少量 GPU 微调本来进不了 GPU 的超大 MoE；新增 RAWINT4 LoRA（不需要先反量化成 BF16，训练显存和推理一致）。
对 iDoris 的启示：这是 NVIDIA+Linux 生态的方案，不直接适用于 Mac，但验证了一个通用原则——"训练内存需求应该等于推理内存需求"（RAWINT4 LoRA 的核心卖点），这对 iDoris 未来若考虑非 Mac 硬件（Windows+独显路径已在 llama.cpp GGUF 里提及）有参考价值。

**[Unsloth Desktop](https://blog.mushroom.cv/blog/unsloth-desktop-local-run-train-ai-claude-code-mcp-finetuning/)**（仅摘要判断，未逐句精读全文细节）
核心观点：一个 App 集成本地运行/训练/部署，直连 Claude Code 和 MCP。
对 iDoris 的启示：验证"本地训练+推理一体化 App"这个产品形态在 2026 年已经成熟到有商业化桌面产品，为 iDoris 自己的极简控制台（§6.1）的模型/训练页提供竞品参考。

**[H2O LLM Studio 实战指南](https://blog.mushroom.cv/blog/h2o-llmstudio-finetune-guide/)**
核心观点：具体硬件表——RTX 3090/4090（24GB）：7B bf16 约85分钟/epoch，13B 需 QLoRA(nf4) 约2.7小时/epoch，70B 无法运行；A100 80GB：70B QLoRA 约4.4小时/epoch；DPO 训练需要 chosen/rejected 对格式。
对 iDoris 的启示：这组数字可以直接补充进现有设计 §5.8 的硬件表（该表目前的数据来源是 kev/arle/idoris立项文，加入 H2O 的独立实测数字可以交叉验证 24-32GB 档"9B QLoRA 偏紧"的判断——H2O 数据显示 24GB 卡上 13B 已经要用 nf4 且要 2.7 小时，佐证了现有设计的保守估计是合理的。

**[Adapta：本地知识库诚实上手指南](https://blog.mushroom.cv/blog/adapta-self-hosted-local-knowledge-base-guide/)**
核心观点："事实归 RAG，行为归微调"的清晰区分；**评测门禁**——训练出的 LoRA 适配器必须在留出样本上考试，绝对分数≥0.6 或明显打赢原始模型才允许创建为可服务的 endpoint，否则不给上线机会；作者诚实标注"2 个 star、单人原型、认证代码未经审查"。
对 iDoris 的启示：Adapta 的"训练完的适配器必须先考试才能上线"与现有设计 §4.8"晋升门禁"（场景评测+贪心逐token比对+安全回归+位置偏差测试）在思路上完全一致，是一个很好的独立验证案例，可以在文档里引用其"≥0.6 分或跑赢基线"这类具体阈值设定方式（而非只写"通过评测"这种模糊描述）。

**[在 Mac 上训练角色 LoRA（FLUX）](https://blog.mushroom.cv/blog/train-character-lora-local-flux-mac/)**
核心观点：M1 Max 64GB，rank-16 LoRA，60 epoch×6图=360次迭代，约3-4小时；**第一轮训练"翻车"**（过拟合+训练数据混入无关框线元素导致模型学到"杂物"）；第二轮修复方案——数据整洁度优先于数量、减少 epoch（60→25）+存档多个 checkpoint 挑最佳而非用最后一轮、caption 强调"isolated, no text"。
对 iDoris 的启示：这是一个非常具体的**本地 LoRA 训练失败→修复案例**，两条经验可以直接写进现有设计 §4.8"晋升门禁"或训练操作手册：①**训练数据的"脏"（包含无关噪声/框线/未剥离的元数据）比数量不足更致命**，策展阶段的去重/质量过滤应该包含"内容纯净度检查"，不能只看数量够不够；②**不要默认用最后一轮 checkpoint**，应该像该文一样在训练过程中多存几个 checkpoint 并用评测门禁挑最佳一个，而不是训练完直接晋升最终轮次。

**[stoa (Pluralis Research)：14 台 Mac 异步 RL](https://blog.mushroom.cv/blog/stoa-pluralis-research-mac-rl-fleet-distributed-training/)**
核心观点：把 RL 的"生成经验"（rollout，用 MLX 在 Mac 上跑，占计算量大头）和"从经验学习"（梯度更新，集中在一张 B200）彻底解耦，只通过 Cloudflare R2 bucket 交换；PULSE 稀疏无损权重 delta（只传 anchor 之间的稀疏差分）；DPPO Gate 对陈旧 rollout 做重要性采样矫正，过滤过期数据；任何一台 Mac 掉线不影响 trainer 继续学习。
对 iDoris 的启示：这篇文章的核心价值不在"14台Mac比GPU便宜"，而在于证明**"RL 训练里最耗资源的 rollout 生成不需要 GPU，Mac 用 MLX 做推理就够"**。这对 iDoris 未来 M8"组织版与联邦"阶段有直接参考价值：如果 community/city 层需要做 RL（现有设计 §4.8 明确写"RL 建议 GPU，走 P-6 离机训练"），可以考虑借鉴 stoa 的解耦架构——多台个人 Mac（community 内成员）异步生成 rollout 上传，只有梯度更新集中在少数算力节点，而不是要求每个参与者都有 GPU；PULSE 的"稀疏 delta 而非全量传输"思路也可以用于联邦 LoRA 场景下的 adapter 增量分发。

### 2.6 策略"提议→diff→批准→版本化"的实践

**[Pipelock 出站防火墙实测](https://blog.mushroom.cv/blog/agent-egress-firewall-pipelock-rate-limit-kill-switch/)**
核心观点：四层 Agent 防线模型——提示注入防护/工具权限系统/**出站防火墙**（管跨时间累积行为，如"一小时200次请求"）/OS沙箱；出站防火墙必须站在 Agent 进程外面（写在 prompt 里的"每分钟不超过5次"是请求不是约束）；实测 kill switch、域名白名单、限速全部有效，但"没开 TLS 拦截时看不到请求体"、"macOS 不走代理的程序可以直接出网"是明确局限。
对 iDoris 的启示：已被现有设计大量引用（不变式 #8 不静默、kill switch、边界声明"Router 只管 LLM 流量"）。核实确认这条边界声明的措辞（"pipelock（macOS 上不走代理的 socket 直连出网）"）与 pipelock 实测结论完全一致，是准确的引用。

**[Trinity：每 Agent 一容器审计](https://blog.mushroom.cv/blog/trinity-abilityai-sovereign-agent-platform-per-agent-docker-audit/)**
核心观点：四层 RBAC；只追加的平台审计日志（管理员只读）；Operator Queue 人在环审批队列；`max_turns` 硬限制+护栏是运行时硬约束而非提示词软约束；通过第三方渗透测试（UnderDefense Grade A）。
对 iDoris 的启示：已被现有设计引用。补充细节：Trinity 的"数据库选择非黏性、非破坏性"（SQLite↔Postgres 切换靠环境变量，注释掉配置就自动回退）是一个很好的工程实践参考，iDoris 的 personal/tenant 存储切换（现有设计 §5.7）可以参考这种设计——本地部署默认走轻量存储，升级到租户模式时平滑迁移且可回滚。

**[Archestra 企业级网关](https://blog.mushroom.cv/blog/archestra-enterprise-ai-platform-mcp-gateway-guardrails-llm-proxy-k8s/)**
核心观点：Dual-LLM 验证 + Lethal Trifecta 防护（高权限目标+不可逆操作组合触发拦截）；MCP 工具"以当前用户身份运行"（On-Behalf-Of），而非共享服务账号，工具调用可精确追踪到发起者。
对 iDoris 的启示：已被现有设计引用。补充启示：iDoris 的虚拟 key 设计已经做到了"调用方身份=key"，但 Archestra 的 On-Behalf-Of 模式提醒——**如果未来 iDoris 的 MCP 代理能力扩展到工具调用层（目前边界声明只管 LLM 流量），也应该延续"工具以当前用户身份运行"这条原则**，而不是共享一个后端凭据。

**[LoopX：本地状态内核](https://blog.mushroom.cv/blog/loopx-loop-engineering-state-kernel-long-running-agents/)**
核心观点：五个原语（quota should-run/todo claim/todo update/refresh-state/quota spend-slot）把"控制状态"从对话上下文里剥离；配额感知调度——安静跳过/预检失败/dry-run 预览不消耗配额，只有验证过的回写才 spend-slot。
对 iDoris 的启示：已被现有设计引用。"**dry-run 预览不消耗配额，只有验证通过的回写才真正计费**"这条对 iDoris 的预算设计（§4.6 reserve→settle 两阶段）是一个有价值的补充——目前设计里"reserve"发生在请求前，但 LoopX 的做法提示：**如果策略变更的"回放模拟"本身要调用真实模型来验证效果，这类模拟调用也不应计入正式预算**，需要在预算维度里明确区分"生产调用"和"策略验证调用"。

**[HugAgentOS：本体作为控制平面](https://blog.mushroom.cv/blog/hugagentos-zju-enterprise-agentos-ontology-trustworthy/)**
核心观点：本体在构建时/启动时/运行时/执后四个阶段都发挥治理作用；违规返回"规则+证据+修复指导"而非静默失败；执后审计记录变成版本化本体提案，需人工审查可回滚。
对 iDoris 的启示：已被现有设计引用（不静默原则、统一错误体 `{type, rule_id, reason_code, evidence, remediation}` 与本文的"规则+证据+修复指导"完全对应）。核实确认引用准确。

**[claude-reflect-system：纠错一次永不再犯](https://blog.mushroom.cv/blog/claude-reflect-system-continual-learning-skill-correction-persistent/)**
核心观点：把对话里的纠错信号按置信度分级（HIGH明确纠正/MEDIUM正向确认/LOW建议），只有 HIGH 才写入"Critical Corrections"强制执行；每次更新前先做时间戳备份+YAML 语法验证，写入即 git commit，格式错误自动回滚。
对 iDoris 的启示：这是"策略提议→diff→批准→版本化"最具体的一个工程实现范例，可以直接补充进现有设计 §6.3 的交互原则——现有设计只写了"提议→diff→二次确认→版本化→可撤销"的抽象流程，claude-reflect 给出了三个可以照搬的具体机制：①**按置信度分级处理反馈**（不是所有👍👎/用户纠正都同等对待）；②**写入前自动语法/schema 校验，失败自动回滚**；③**每次学习对应一个带描述的 git commit**（`policy version` 的具体载体可以直接用 git，而不必自研版本化格式）。

## 3. 按议题汇总的结论（每条注明来源）

### 3.1 ATIF / 轨迹格式
- 轨迹驱动的学习分三个成本层级，现有设计只覆盖了后两层：**①（近乎零成本）失败轨迹→推理时补丁/规则修改，不改权重**〔learning-from-failure、GEPA、HarnessX〕；②（低成本）本地小模型 SFT/OPD/KTO/DPO〔现有设计已覆盖〕；③（高成本）RL〔现有设计已覆盖〕。建议在 §4.8 学习层顺序里明确补上第①层。
- 轨迹质量筛选的两个可操作规则：过滤掉短轨迹（<5轮）〔OpenThoughts-Agent〕、先裸答一遍过滤掉靠模型记忆就能答对的样本〔S1-DeepResearch〕。
- 用于训练/改进的 Agent 不应能提前读到全部历史成败案例的全文，否则会"抄答案"而非真学习〔WikiSkill 消融实验〕。

### 3.2 元数据与内容分离
- 渐进式披露（发现阶段仅名字+描述，激活阶段才读全文，执行阶段才跑代码/加载引用）是行业公认的标准做法〔Agent Skills 标准〕，可数字化为"元数据 ≤100 token、正文 ≤500 行"的硬指标〔awesome-agent-skills〕。
- 内容溯源（水印/C2PA）要严格区分"可验证证明"和"尽力而为的猜测"，绝不能混在一个置信度分数里〔watermarks-remover〕。
- 决策账本目前只记 `scores`，应补充"贡献权重的具体证据"，做到确定性可复算而非黑盒打分〔Belief Context Graph〕。

### 3.3 训练数据的授权与删除
- "模型只提议，代码判决"+"证据只增不删、生命周期变更只改状态不删数据"是可落地的成熟范式，已有独立产品验证〔Dense-Mem〕。这与现有设计的"硬删除+墓碑"存在张力，见第4节。
- 数据策展的反直觉发现：更强的模型不一定是更好的教师〔OpenThoughts-Agent〕；LLM 改写任务描述通常不提升质量，应保留原始措辞〔同上〕；数据"干净"比数据"多"更重要，混入的噪声/框线元素会被当作特征学进去〔train-character-lora-flux-mac〕。
- 垂直 AI 产品的合规做法：初期只做读/分析，写操作和高风险判断（投资建议/合规判定）必须留给人工批准，且权限继承自底层系统而非重新授予〔Claude for Financial Advisors〕。
- 自我声明的授权/合法性检查没有约束力，必须有 scope 文件/白名单/审计日志才算数〔Pentest Harness〕。

### 3.4 本地训练在常规机器上是否可行——有哪些实测
- Mac（Apple Silicon）本地 LoRA 训练实测：M1 Max 64GB，9B QLoRA 舒适（约14GB），角色 LoRA（FLUX）60轮×6图约3-4小时〔iDoris立项文、train-character-lora-flux-mac〕。
- 独立第三方实测（非 Mac，NVIDIA）：RTX 4090 24GB，7B bf16 约85分钟/epoch，13B 需 QLoRA 约2.7小时/epoch，70B 跑不动；A100 80GB 70B QLoRA 约4.4小时/epoch〔H2O LLM Studio〕。这组数字与现有设计 §5.8 的量级估算（16GB≤2B、24-32GB约4B、64GB约9B）互相印证。
- 更大规模 MoE（30B+）的本地训练需要 CPU+GPU 异构（路由专家权重放CPU主存），且量化格式训练时不应反量化到 BF16（RAWINT4 LoRA），否则显存优势尽失〔KTransformers〕——这条路径只适用于 NVIDIA/Linux，Mac 上没有直接对应方案。
- RL 训练的"生成经验"环节（rollout）不需要 GPU，Mac 用 MLX 推理即可承担，只有梯度更新需要集中的算力节点，可异步解耦、任意 Mac 掉线不影响训练〔stoa/Pluralis Research〕——这为 iDoris 未来 community/city 层的联邦式 RL 提供了一个不要求每个参与者都有 GPU 的架构选项。
- LoRA 训练失败的常见原因是"过拟合+数据脏"而非算力不够：应减少 epoch、存多个 checkpoint 挑最佳、caption 精确排除无关内容〔train-character-lora-flux-mac〕；上线前必须过 eval gate（≥0.6分或跑赢基线），未达标就拒绝上线〔Adapta〕。
- 数据量不是瓶颈：几千条高质量样本即可见效（Agent Lightning 用 6K、JevEmbed 用 7.9万条把准确率从30%拉到84%，两者均已被现有设计引用）。

### 3.5 策略"提议→diff→批准→版本化"的实践
- 完整可复用的工程实现范式：写入前时间戳备份+schema 校验，失败自动回滚，每次学习对应一个 git commit〔claude-reflect-system〕。
- 反馈应按置信度分级处理（明确纠正/正向确认/建议），不能把所有输入都当同等权重的指令〔claude-reflect-system〕。
- 分阶段审批门+实时看板+完成后逐帧 Replay 是审批工作流 UI 的一个成熟范式，可套用到训练/学习流程的每个阶段〔织影 Video Production Buddy〕。
- Dry-run/模拟调用不应消耗正式预算或触发正式副作用，只有验证通过的回写才计费〔LoopX〕。
- 自我改进系统的提案通过率可能很低（AIDE2 实验中 90% 被拒），严格拒绝率是健康信号，不是流程缺陷的证明〔realtime-rl-agent-research-2026〕。

### 3.6 日志即运行时
- "日志即运行时"的关键补充措辞："上下文不等于历史"——给模型看的内容可以剪枝压缩，但 Event Log 必须保留完整证据链，永远可回溯〔Maka〕。这句话建议直接补进现有设计 §2 不变式 #9 的说明文字。
- 系统级、Agent 无法篡改的观测（eBPF）在 Mac 上做不到内核级捕获，iDoris 的 Event Log 完整性只能靠自身实现（追加式写入、内部一致性校验），不能寄望外部旁路工具兜底〔AgentSight〕。
- 决策账本应支持因果链查询（这次决策是因为哪次上游决策），而不只是记录孤立的决策点快照〔Semantica〕。
- 回放之外还应支持"分叉"（fork）——从历史某个决策点手动改判定结果，看后续链路如何变化，这是现有设计"回放模拟器"目前缺失的能力〔Retrace〕。

### 3.7 数据飞轮的失败案例
- 高比例的自动提案会被拒绝（AIDE2：90% 拒绝率），这是正常现象〔realtime-rl-agent-research-2026〕。
- 纯结果奖励对真实世界 Agent 不够，需要对违反约束的中间动作（如反复重试、跳过授权流程）额外施加路径惩罚，即使最终任务完成〔RLVP，realtime-rl-agent-research-2026〕。现有设计 §4.8"⑤RL"目前没有这条。
- 不能把 Agent 自我生成的"我学到了什么"叙述当作学习效果的证据，这类文本是模板化的角色扮演输出，不是可验证的认知状态，晋升门禁必须基于确定性评测〔bitterbot-desktop〕。
- "本地优先"的宣传如果不逐条列出实际出站点，容易与真实行为产生落差；egress 透明度清单是必要的信任建设手段，不是可选项〔bitterbot-desktop 反例 vs. 现有设计已有的"UI 显示云端实际收到的字节"〕。

## 4. 与现有设计冲突或需要修改之处（逐条列出依据）

1. **学习层顺序缺失"零训练成本的失败轨迹补丁"这一档**
   现有设计 §4.8 的学习路线是 ①决策模型SFT→②本地教师蒸馏OPD→③编译型学习→④反馈偏好→⑤RL，五档全部涉及改权重或至少改专用小模型。但 GEPA〔35x更省rollout，比GRPO赢10-20%〕和 learning-from-failure〔零训练，OSWorld+15.6%〕两篇独立文章证明：**用决策账本里的误判轨迹做"自然语言反思→改 prompt/规则"的循环，往往比训练模型更省成本、效果相当甚至更好**，且完全符合"模型只提议，代码判决"（不变式#10）——产物是可审查的文本 diff，不是黑盒权重。建议在①之前插入"⓪ 轨迹反思修正判定器 prompt/规则（GEPA式）"这一档，作为决策模型训练之前的低成本尝试。

2. **RL 奖励设计缺"路径惩罚"**
   现有设计 §4.8"⑤RL"只写"奖励不给中间过程加分，不知道优于幻觉，同时计入成本"，未提及对违反约束的中间动作（如反复越权重试、跳过隐私脱敏）要额外扣分。依据：RLVP 论文的核心发现——纯结果奖励下，模型会为了完成任务而做出违反规则但不影响最终结果的坏动作，必须"惩罚路径，奖励结果"两者并重。建议在 §4.8 补充一条：RL 奖励函数除任务成功率外，需对确定性可检测的坏动作（超预算尝试、绕过隐私闸的重试、多次触碰授权边界）施加负奖励。

3. **"证据只增不删"与"硬删除+墓碑"的张力**
   现有设计 §5.6 对删除权的处理是"删除/撤回授权→墓碑→血缘表查出受影响数据集与adapter→标记撤回/需重建"，隐含对原始轨迹做硬删除。而 Dense-Mem 的成熟实践是"证据精确、持久、只增不删；生命周期变更只改变有效状态，从不抹除溯源链"。这不是简单的孰优孰劣问题，而是**法律义务（用户行使删除权/被遗忘权时必须真正删除数据）与审计完整性（保留证明"曾经发生过什么"的能力）之间的真实冲突**。建议在 §5.6 明确写清楚这个取舍的边界：对于合规意义上的"删除请求"（用户主动行使权利），保留现有的硬删除+墓碑；但对于非合规触发的"标记失效"（如训练效果不佳、被人工判定错误、adapter 被回滚），应该像 Dense-Mem 一样只改状态、不删证据，因为这类"失效"记录本身是宝贵的训练/审计数据（呼应 WikiSkill"Wiki 永不回滚"的设计）。目前的措辞把两种情况混在一起容易导致工程实现时过度删除。

4. **决策账本缺少因果链字段**
   现有设计 §4.7"决策账本"记录 `{decision_point, judge, model_revision, prompt_hash, scores, latency}`，是孤立的决策点快照，没有显式的"这个决策导致了后续哪个决策"的链接。依据：Semantica 的 `record_decision`+`add_causal_relationship`+`trace_decision_chain` 三件套证明企业级审计场景下，"能否回答为什么"取决于因果链是否可查询，而不仅是能否查到每个决策点本身。建议在决策账本 schema 里加一个可选的 `causal_ref: [decision_id]` 字段，串联同一请求内相互影响的判定。

5. **管理界面缺少"分叉"（fork）能力**
   现有设计 §6.2"路由"页只有"回放模拟器"（新policy在历史流量上整体重跑）。依据：Retrace 的核心差异化功能是允许从任意历史节点分叉，手动改一个决策再看后续影响，这在调试单个误判案例时比"整体重放"更精确、更快。建议在 §6.2"请求"详情页补充：查看某次请求的决策链后，可以在某个决策点手动改判定结果，触发一次"假设性重放"（只读，不产生真实副作用），辅助排查具体误判原因。

6. **多 key/多租户轨迹汇入训练集前缺"草稿隔离"环节**
   现有设计 §5.6 的策展流程是"采集→自动分类→资格筛选→策展（含人工批准队列）→数据集卡→导出"，人工批准队列是在策展阶段，但没有明确不同调用方（key）产生的轨迹在进入这个批准队列之前是否互相隔离。依据：Memory Harness"多AI协作但草稿彼此隔离，只有主动提交的内容才共享"的设计，提醒 iDoris 在多租户场景下，一个 key/成员产生的轨迹在未经批准前不应默认与其他 key 的轨迹混合排队，否则批准环节的粒度会失真（批准了一批混合来源的数据，实际上可能有些来源不该进）。建议在 §5.6 策展流程里显式加一步"按来源（key/tenant）隔离候选池"，批准时逐来源确认。

7. **决策账本的"scores"应记录证据权重分解，而非只记最终分数**
   现有设计目前只记 `scores` 这个字段（校准概率或分类分数），没有说明其可复算性。依据：Belief Context Graph 的确定性置信度设计——posterior_confidence 由 initial_confidence/evidence_confidence/factor_confidence 三分量确定性算出，任何一条置信度都能追溯到具体证据的权重贡献。建议在决策账本 schema 里，对可解释的判定器（规则/embedding相似度），额外记录贡献权重最高的 1-3 条依据（例如命中了哪条规则、哪个embedding最相似），而不只是一个最终分数，便于人工审计"为什么判成 S2"而不只是"判成了 S2"。

8. **"元数据/内容分离"目前只是零散实践，应提升为通用不变式**
   现有设计里"字段兑现矩阵"（§4.1）、`extra.idoris` 命名空间（§5.4）都体现了元数据/内容分离的思路，但没有作为一条独立的通用设计原则出现在 §2 不变式列表里。依据：Agent Skills 标准的三阶段渐进式披露（发现→激活→执行）和 awesome-agent-skills 的数字化标准（100 token/500行）证明这是整个 Agent 生态公认的核心设计模式，值得从"体现在具体字段设计里"提升为"写进不变式清单的一条通用原则"：**元数据必须小、必须总在场（用于路由和判定）；内容必须大、必须按需加载（只在真正需要时进入上下文/存储访问）**。

以上 8 条均基于本轮精读的一手文章原文，不改变现有设计的整体架构，均是在现有不变式和分层设计基础上的补充或措辞精确化建议，供后续讨论时参考取舍。
