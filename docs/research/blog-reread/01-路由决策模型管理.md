## 2. 逐篇笔记（仅限相关文章）

> 按主题分组排列；每条含 URL、核心观点、对 iDoris 的具体启示。已被既往「blog-调研记录」精读过、本次只做核对未重新展开分析的 5 篇，仅列一行摘要，不重复展开。

### 2.1 Jev / System-1 决策模型家族

**[typesafe-ai-jev-system-one-model-rlcd-decision-ai-enterprise](https://blog.mushroom.cv/blog/typesafe-ai-jev-system-one-model-rlcd-decision-ai-enterprise/)**
TypeSafe AI 发布 Jev，RLCD（非 RLHF/RLVR）训练目标是"校准概率"而非"生成对错"。三种问题原语：Judgment（是非）、Selection（≤255 候选选择）、Scoring（打分）。关键坑：**Noul（是非题）类型不带置信度**，这是后续多篇复刻都验证过的不对称设计缺陷。定价 $0.042/M input、output 免费。官方自曝准确率 67.8% vs 对比模型 74.1%——速度快不等于准。
**对 iDoris 的启示**：`/v1/systemone` 的三种问题类型（Choice/Score/Noul）设计已经和 iDoris 现有 `route.intent`/`route.privacy`/`route.complexity` 决策点命名对齐；但要注意 Noul 型判断（纯 yes/no）**必须显式返回置信度**，不能因为"简单"就省略——这是 Jev 生态里被反复踩的坑（KaLM-Jev、kev 等复刻都验证了）。

**[agentjev-0-6b-system-one-decision-model-qwen3](https://blog.mushroom.cv/blog/agentjev-0-6b-system-one-decision-model-qwen3/)**
Qwen3-0.6B + 置换等变决策头，Typed Decisions 基准 79.25% 超过 Laya。**Shared Prefix KV Cache**：64 候选时骨干 token 从 33,547 降到 2,551（-92.4%）。零输出 token 解码，~50ms 一次前向。完整概率分布输出，可直接做阈值门控。
**对 iDoris 的启示**：这是"多候选共享前缀、只在尾部分叉"这一优化模式的又一个独立验证（SemIf、LLM2Jev、Kev 也都用同一套思路）——iDoris 的入口判定层（§4.4 T2.4→T3 方向的"本地 logit 读取型 System-1"）如果要支持"一次请求多个决策点"（比如同时判断 intent + privacy + complexity），**应该原生支持共享前缀 KV cache 的多分支并行**，而不是三次独立调用。

**[jev-skill-agent-decision-9-skills-90-scenarios-openrouter](https://blog.mushroom.cv/blog/jev-skill-agent-decision-9-skills-90-scenarios-openrouter/)** ⭐ 本次重读最重要的一篇
9 个 Jev Skill 覆盖分诊/路由/代码审查等场景。**核心规则**：若 `OPENROUTER_API_KEY` 缺失，Agent **禁止静默降级**。只有两条合法路径——(A) 提示用户去拿 key，等到了再调真实 Jev；(B) 用宿主 Agent 模拟决策，但**必须在输出中显式标注 `mode: agent_simulation` 和 `jev_called: false`**。"悄悄用 GPT 代替 Jev 然后假装是 Jev 的结果"被明确禁止。
**对 iDoris 的启示**：这直接回答了任务里问的"判定器失败时的语义"——目前 iDoris 规划里 `/v1/systemone` 只写了"判定引擎可选 Jev 类模型：外部 API 或本地开源实现"，**没有规定判定引擎不可用/加载失败时的响应契约**。应该照抄这条规则：判定器不可用时，**要么显式拒绝（返回错误 + reason_code，让调用方决定 fallback），要么明确标注"这是宿主模型模拟的判断，不是校准过的 Jev 类判断"**，绝不能静默把 `/v1/systemone` 的响应换成未校准的 LLM 猜测却不告知调用方。详见 §4 冲突清单 C-1。

**[jevembed-embedding-decision-framework-choice-score-noul](https://blog.mushroom.cv/blog/jevembed-embedding-decision-framework-choice-score-noul/)**
用 Embedding 模型（KaLM/Qwen3-Embedding/E5）做决策，成本远低于 LLM logit 路线（CPU 可跑）。LoRA 微调效果显著：KaLM 30%→77%，Qwen3-0.6B 31%→84%。支持 >255 候选（原版 Jev 格式上限 255）。
**对 iDoris 的启示**：这是比"本地 logit 型 System-1"更轻量的第四条判定器路线（embedding 相似度），适合超大候选集（比如未来 catalog.yaml 模型/角色候选很多时的路由）。可以作为 `route.intent` 判定器级联链（`rules → embedding → local-logit → remote`）里 embedding 那一环的具体实现参考。

**[semif-semantic-if-local-jev-decision-engine](https://blog.mushroom.cv/blog/semif-semantic-if-local-jev-decision-engine/)**
目前最成熟的开源 Jev 复刻（3,700+ star，MIT）。四后端（CUDA/MLX/llama.cpp/WebGPU）全覆盖，**每条输出带 `model_revision`（HF commit hash）+ `prompt_hash`，天然可审计可复现**。状态复用（同一 state 多个判断标准共享 KV）吞吐 20 decisions/sec。ECE（校准误差）经校准后从 0.068 降到 0.038（人工数据集）。
**对 iDoris 的启示**：`model_revision + prompt_hash` 这个可审计字段设计，iDoris 决策账本（§4.7）里的 `{decision_point, judge, model_revision, prompt_hash, scores, latency}` 已经完全对齐——本文是这条设计的一手依据，值得在决策账本 schema 注释里直接引用这篇作为来源。

**[kev-jaredpalmer-local-decision-model-jev-open-source-qwen-lora](https://blog.mushroom.cv/blog/kev-jaredpalmer-local-decision-model-jev-open-source-qwen-lora/)**
块因果掩码（block-causal masking）把文档和所有问题打包进一条序列，文档编码一次、多问题并发出结果。**关键训练发现**：学习率必须是 5e-5，用默认 2e-4 会导致知识任务回归 4.7pp——这类"错误默认值毁掉训练"的坑值得记录进 iDoris 自己训练决策模型时的操作手册。**7.4% 选项顺序敏感**：同一问题换个选项排列顺序，argmax 答案有 7.4% 概率改变。
**对 iDoris 的启示**：iDoris §4.4 已经写了"置换一致性测试"（引用 kev `/permute`），本文确认了这个测试点的真实必要性——选项顺序敏感不是理论风险，是实测 7.4% 的真实故障率。

**[kalm-jev-local-judgment-engine-hardware-deploy](https://blog.mushroom.cv/blog/kalm-jev-local-judgment-engine-hardware-deploy/)**
Nano(0.27B)/Small(1B)/Large(4B) 三档硬件selection建议：日均判断量 <10万次用 Nano+消费级 GPU；10万-100万次用 Small；高精度场景用 Large。LRU 缓存默认 256MiB，复用相同文档编码。
**对 iDoris 的启示**：给 iDoris catalog.yaml 的判定引擎选型提供了具体的"日请求量 → 模型档位"经验值，可以直接搬进 iDoris 的 recommender 文档。

**[llm2jev-local-jev-api-prefill-only-binary-inference](https://blog.mushroom.cv/blog/llm2jev-local-jev-api-prefill-only-binary-inference/)**
任意 HuggingFace 因果 LLM 转 Jev 兼容判定引擎，零训练。**staged 模式**利用 SGLang Radix Cache，共享前缀只算一次：长上下文+多候选场景加速 4.9×；但短输入或缓存已热时 `all`（打包批量发送）反而比 `staged` 快 1.7-2.0×。
**对 iDoris 的启示**：这是一个重要的性能反直觉点——**KV 前缀复用优化不是无脑开启就好，短请求/热缓存场景下反而更慢**。iDoris 的判定引擎实现应该做这个自适应判断（候选数/上下文长度过阈值才走 staged 路径），而不是把 staged 模式当默认硬编码。

**[jev-chat-jarvis-android-chat-copilot-accessibility](https://blog.mushroom.cv/blog/jev-chat-jarvis-android-chat-copilot-accessibility/)**
Jev 判断模型接入 Android 无障碍服务做聊天助手，v1.0 release notes 原话："Jev 判断模型主要用英文训练，中文对话判断质量还需用真实数据校准"。
**对 iDoris 的启示**：直接印证了 iDoris §4.4 已经标注的"⚠️ 需核查：T2.4 用的 embedding 模型和阈值是在什么模型上标定的，中文请求配英文嵌入模型会静默失效"——这不是 iDoris 自己的猜测风险，是 Jev 生态里被多个独立项目验证过的真实坑，中文场景的判定器**必须**单独用中文/多语种数据标定阈值，不能沿用英文默认值。

**[jev-awesome-list-gold-rush-fact-check](https://blog.mushroom.cv/blog/jev-awesome-list-gold-rush-fact-check/)**
对"Jev 生态一天冒出 800+ 项目"的核查报道：真实情况是聚合而非当天新增，21% 的收录项目没有许可证，10% 被证实根本没调用 Jev API。
**对 iDoris 的启示**：非架构性启示，但提醒引用 Jev 生态项目时要素核（本次重读已经交叉验证过官方发布博客与多个独立复刻项目的关键数字一致，可信度较高）。

**[browser-use-jev-ultrafast-dom-web-agent](https://blog.mushroom.cv/blog/browser-use-jev-ultrafast-dom-web-agent/)** / **[jev-browser-use-jev-clicks-codex-thinks-browser-automation-skill](https://blog.mushroom.cv/blog/jev-browser-use-jev-clicks-codex-thinks-browser-automation-skill/)**
两篇独立报道同一模式：**投机扇出（speculative fan-out）**——同一次观察状态下，多个决策头（operation + target）并行推理，一次网络往返出两个决策，用不到的分支直接丢弃。浏览器协议调用从 1092 次降到 101 次（-91%）。第二篇进一步明确"decision 层用 Jev 做点击/导航/滚动，reasoning 层用 Codex 做输入文字/验收判断"的两级分工，成本差 238 倍（$0.0042 vs $1.00 / 10万token）。
**对 iDoris 的启示**：投机扇出是 mu 判断核（已被 iDoris 引用）之外的又一个可迁移微优化——**iDoris 的入口判定层在同时判断 intent/privacy/complexity 三个决策点时，可以用同样的"共享前缀 + 多头并行推理，未命中分支丢弃"模式**，而不是三次串行调用同一个判定模型。这是 §4.4 判定点级联设计的一个具体实现建议，值得写进 R2（请求处理核心）的实现细节。

**[bespoke-nimble-9b-open-decision-model-logprob-jev-rival](https://blog.mushroom.cv/blog/bespoke-nimble-9b-open-decision-model-logprob-jev-rival/)**
用一天时间复刻 Jev 的 logprob 读取式决策模型。**Mac 上比 GPU 快**（MLX 共享 context 一次处理），CUDA 版每个字段独立跑完整 forward pass 无法共享 KV cache——这是 Mac 本地部署反而在多字段场景下比云端 GPU 有结构性优势的一个反直觉证据。
**对 iDoris 的启示**：支持了 iDoris "本地优先"路线在多字段决策场景下的性能合理性，不只是隐私考量，Mac 统一内存架构在这类工作负载上确实有工程优势。

### 2.2 路由框架 / 网关架构

**[semantic-router-ai-agent-entry-point-guide](https://blog.mushroom.cv/blog/semantic-router-ai-agent-entry-point-guide/)**
五类开源路由方案实测对比：**路径路由**（该走 agent/搜索/邮件/模型/链路哪一条）和**模型选择**（强模型还是弱模型）是两层，混为一谈会导致预算先剔除远程、意图再从剩余候选里选——这正是一次"静默降级"。结论首选 aurelio-labs/semantic-router（嵌入相似度，~0.1B，零 LLM 调用，可换底层嵌入模型）。
**对 iDoris 的启示**：iDoris §4.4 已完整采纳"路径路由 vs 模型选择分两层"的结论，且 iDoris 不变式 #1（2026-09-27 由 jason 修订为"隐私→意图→预算"而非"隐私→预算→意图"）**正是这篇文章"不能在意图之前做全局预算闸"论点的直接应用**——本次重读确认这个修订方向与本文结论完全一致。

**[opensquilla-multi-model-routing-guide](https://blog.mushroom.cv/blog/opensquilla-multi-model-routing-guide/)** / **[opensquilla-token-efficient-ai-agent-open-source](https://blog.mushroom.cv/blog/opensquilla-token-efficient-ai-agent-open-source/)** / **[opensquilla-token-efficient-ai-agent-squilla-router](https://blog.mushroom.cv/blog/opensquilla-token-efficient-ai-agent-squilla-router/)**

**对 iDoris 的启示**：这为"入口判定层必须本地化，不能默认调远程 API"这条设计原则提供了量化依据（延迟预算），可以作为 R2 阶段判定器选型的硬性约束写进设计文档：**默认判定器的 p99 延迟目标应该 <5ms（本地 logit 型），<1ms（embedding/规则型）**。

**[google-skills-137-agent-skills-negative-routing-vs-anthropic](https://blog.mushroom.cv/blog/google-skills-137-agent-skills-negative-routing-vs-anthropic/)**

**[openclaw-gateway-unattended-multi-agent-orchestration](https://blog.mushroom.cv/blog/openclaw-gateway-unattended-multi-agent-orchestration/)**

### 2.3 本地模型管理 / MLX / oMLX 实测坑

**[m1-max-64gb-local-ai-model-selection-memory-guide](https://blog.mushroom.cv/blog/m1-max-64gb-local-ai-model-selection-memory-guide/)**

**[krill-mac-mlx-llm-runtime-coding-agent](https://blog.mushroom.cv/blog/krill-mac-mlx-llm-runtime-coding-agent/)**

**对 iDoris 的启示**：两条直接可用的教训——① **iDoris 任何自带的投机解码/推理加速特性，如果有内部一致性测试，必须把测试结果（通过/失败次数）暴露在某个可查的地方**，不能像 Krill 一样测试连续失败却照常发布默认开启；这应该写进 iDoris §4.3"真模型 live 测试层"的验收标准——不仅要有测试，测试失败时**默认应该关闭该特性**，而不是保持现状。② **工具名约束采样**是给本地小模型接工具调用的一个通用技巧，如果 iDoris 未来的本地判定引擎需要输出结构化 Choice（从固定候选里选），可以采用同样的"生成阶段就把非法 token 概率清零"而不是"生成后再解析校验"。

**[llm-dock-docker-compose-local-llm-dashboard](https://blog.mushroom.cv/blog/llm-dock-docker-compose-local-llm-dashboard/)**

KV-cache 从不清空的极端会话亲和实现：每轮对话只追加新 token，输入成本 O(新增) 而非 O(全部历史)。三种模式对比（持久/标准/前缀匹配缓存）；作者自己承认这是 2 星冷门项目，性能数字未经第三方复现。

**[orion-core-rust-agent-harness-local-llm-teardown](https://blog.mushroom.cv/blog/orion-core-rust-agent-harness-local-llm-teardown/)**

### 2.5 决策模型训练 / 编译型学习

**[cmu-better-harnesses-smaller-models-slm-agent-cost-reduction-engineering](https://blog.mushroom.cv/blog/cmu-better-harnesses-smaller-models-slm-agent-cost-reduction-engineering/)** ⭐ 本次重读第二重要发现
CMU 论文：SLM+定制 harness 可以用 4% 成本恢复 89.7% 的 LLM 性能，但**每个模型的最优 harness 不能跨模型复用**（qwen3-coder 调好的 harness 对 ministral-3-8b 无效，各家失败模式不同）。任务多样性用 Levenshtein 距离量化，决定是否值得投入 harness 适配（距离 <0.3 值得，>0.6 收益差）。5 类失败模式（指令跟随/知识缺口/工具使用/长上下文/规划推理）→3 类适配策略（上下文/工具/循环）。
**对 iDoris 的启示**：这篇填补了 iDoris §4.3"升级/切换流程"的一个盲区。iDoris 目前的模型升级门禁（§4.3）关注的是**权重层面**的一致性（贪心逐 token 比对 + 场景评测），**完全没有提到 harness/prompt 配置本身也需要跟着模型版本重新验证**。本文明确证明：不同底座模型即使能力相近，最优的系统提示词/工具封装方式也可能完全不同。**建议修改**：iDoris 模型升级流程应该在"计划冻结"阶段同时冻结/版本化该模型对应的 harness 配置（系统提示词模板、工具描述格式），升级候选模型时不能只做权重对比，还要评估现有 harness 配置是否仍然适配新模型（如果新模型的最优 harness 明显不同，晋升决策应该同时给出"要不要连带更新 harness 配置"的建议，而不是默认沿用旧配置）。详见 §4 冲突清单 C-2。

**[program-as-weights-paw-fuzzy-functions-guide](https://blog.mushroom.cv/blog/program-as-weights-paw-fuzzy-functions-guide/)**
"模糊函数编程"：4B 编译器把自然语言描述编译成 LoRA 适配器（一次性，~23MB），0.6B 冻结解释器本地永久运行。0.6B+PAW 在 FuzzyBench 上超过 Qwen3-32B 直接调用（73.78% vs 68.70%），内存只用 1/50。多模态场景下**解释器不变、只换编译器**（文本编译器→VL 编译器）。
**对 iDoris 的启示**：这是 iDoris §4.8 学习层路线③"编译型学习"（compile-by-training/castform 已引用）的一个更具体、更通用的实现范式——**编译器（教师模型）→LoRA 程序（可换）→冻结小解释器（常驻）**这个三段式架构，比"高频请求在编译期请教强模型生成标注"描述得更精确。可以考虑在 §4.8 里补充这个具体架构模式作为路线③的实现参考：iDoris 的判定引擎本身（AgentJev/Kev 类）某种意义上就是这个模式的一个特例（决策头相当于"编译好的程序"）。

**[needle-26m-function-calling-edge-ai-cactus](https://blog.mushroom.cv/blog/needle-26m-function-calling-edge-ai-cactus/)**
26M 参数、**去掉 FFN 层**（通常占 Transformer 2/3 参数）只留纯注意力，理由是工具调用本质是"检索+对齐+拼装 JSON"，不需要 FFN 提供的逐位置特征变换。6000 tokens/s prefill，单轮工具调用优于 10 倍体量的竞品。
**对 iDoris 的启示**：属于研究性参考，非当前可落地项——如果 iDoris 未来需要一个比 AgentJev(0.6B)/Kev(0.5B) 更极端轻量的判定头（比如嵌入到手机/手表端的 iDoris-Mobile 层做本地意图初筛），Needle 的"去 FFN 纯注意力"架构思路值得关注，但目前 iDoris 的 catalog 最小档位是 2B（Qwen3.5-2B），暂无这个需求。

**[neohorse-1-recursive-self-improvement-agentic-post-training](https://blog.mushroom.cv/blog/neohorse-1-recursive-self-improvement-agentic-post-training/)**
Routing Harness：模型在异构模型池里执行任务的轨迹和失败模式被 harness 捕获，直接转化为下一轮训练信号（不是人工标注，是模型自己暴露的能力边界）。Agent 类基准提升最明显（VitaBench +10.5~11.0pp）。
**对 iDoris 的启示**：与 iDoris §4.8"决策模型先行"（决策账本直接当训练数据）+ opensquilla"数据飞轮"是同一思路的另一个独立验证；本文的增量信息是**"路由能力缺口"本身可以作为专门的训练信号维度**（不只是对错，还有"这类请求该走哪条路由但没走对"），iDoris 未来训练自己的决策模型时，可以把"路由决策与实际最优路径的偏差"作为单独的奖励/损失项，而不只是端到端正确率。

### 2.6 大厂案例（架构决策参考）

**[anthropic-commerce-agents-30pct-cart-technical-architecture-deep-dive](https://blog.mushroom.cv/blog/anthropic-commerce-agents-30pct-cart-technical-architecture-deep-dive/)** ⭐ 本次重读第三重要发现
六个架构决策：①单 Agent+Skills 而非多子代理（电商对话高度耦合需要共享上下文，Skills 是动态加载到主 Agent 上下文的指令，不是独立进程）；②UI 组件用结构化工具调用而非 XML 标签（schema 验证 + provenance 追踪 + 无上下文膨胀）；③**prompt 缓存三层分段**（全局层-系统提示词+skills，几乎不变，命中率~100%；会话层-用户偏好/购物车状态，高命中；易变层-当前消息，不缓存），最容易破坏缓存的错误是把时间戳/请求ID放进系统提示词；④安全强制在 harness 层不在 prompt 层（购物车写入只接受本次会话 catalog 工具返回的 ID 白名单验证，数量上限 harness 层强制 clamp，支付方法在后端接口层根本不存在，模型物理调不到）；⑤异步记忆提取（不阻塞主对话路径，只读文字内容不读工具结果防止工具输出被误存为偏好）；⑥快照测试优于多轮模拟（直接构造目标 SessionState，10 倍快 100 倍稳定，且必须覆盖负向用例）。
**对 iDoris 的启示**：这篇提供了三个可以直接落地到 iDoris 设计的具体技术：
1. **prompt 缓存三层分段**是 iDoris §4.3"会话亲和"之外一个更细粒度的技术——iDoris 目前的会话亲和只讨论"路由到同一实例保住 KV 缓存"，没有讨论"请求内部的字段应该按变化频率分层排列以最大化缓存命中"。这应该写进 R2（请求处理核心）的实现细节：iDoris 组装发给后端的最终 prompt/messages 时，应该把**全局不变部分（系统提示词、policy 规则）放最前面，会话级信息其次，当前请求内容放最后**，且时间戳/request-id 类易变字段绝不能混进前缀。
2. **"安全约束在物理接口层杜绝而非靠 prompt 拦截"**（支付方法根本不在后端接口里）比 iDoris 目前"闸一/闸二"的判断型拦截更彻底——对于 iDoris 明确禁止的操作类型（比如 tenant 模式下绝对不允许的某些 provider），应该优先考虑"物理上不提供这个接口/凭据"而不是"判定器拦截"，判定型拦截应该留给无法物理杜绝、需要语义判断的场景（内容脱敏）。
3. **快照测试方法**直接对应 iDoris FU-8"测试不承重"的解法——iDoris 的判定器/路由测试应该优先用"直接构造 SessionState/请求上下文"的快照测试，而不是多轮模拟对话，这样测试才能稳定覆盖边缘情况（如"预算不足+隐私要求冲突"这类组合状态）。

**[claude-financial-advisors-connector-skill-approval-pattern](https://blog.mushroom.cv/blog/claude-financial-advisors-connector-skill-approval-pattern/)**（见 2.2 已展开）

## 3. 按设计议题汇总的结论

### 3.1 请求处理顺序（隐私 / 意图 / 预算 / 容量）

- **有文章明确讨论过这个顺序问题**：`semantic-router-ai-agent-entry-point-guide` 明确论证"不能在意图之前做全局预算闸，否则会把预算先剔除远程、意图再在剩余候选里选，变成一次静默降级"；`vitalik-ai-survival-guide-cn` 论证隐私应该放在最前且只能收紧不能放宽。iDoris 不变式 #1 在 2026-09-27 由 jason 修订为"隐私→意图→预算→admission→选择/降级"，**这个修订方向和上述两篇文章的结论完全一致**，本次重读没有发现任何文章支持"预算应该先于意图"的反例。
- **补充发现**：`anthropic-commerce-agents` 的"安全强制在 harness/接口层而非 prompt 层"进一步支持"隐私判断必须在最前面且是结构性的，不能是语义判断可以被绕过的"这条设计取向。

### 3.2 意图与工具链、路径映射

- `google-skills-137-agent-skills-negative-routing-vs-anthropic`：工具/Skill 数量过百时正向 description 会产生路由歧义，负向路由（"别用我，改用X"）成为主要手段。
- `mu-coding-agent-judgment-kernel-35-decision-points-hive`：意图判断应该拆解成命名化的决策点（而非单一大黑盒判断），每个决策点独立配置判定器、可级联、可 shadow 测试。
- `minimax-h3-context-ir-prompt-orchestration-multimodal-video`（既往研究已覆盖）：意图到结构化中间表示（Context-IR）的翻译层设计，把自然语言意图转成下游可执行的结构化上下文，是"意图→工具链"映射的一个具体范式。
- `what-is-agent-skill-autonomy-vs-workflow` / `danielmiessler-lifeos`：意图应作为独立于具体提示词的一等公民概念，但 iDoris 的意图判定范围应严格限定在"路由到哪条路径"，不涉及用户长期目标建模（那是 Agent24/MemPalace 的范围）。

### 3.3 路由应放在本地还是远程，延迟要求

- 一致结论：**路由/入口判定必须本地化**。`clawrouter` 给出量化依据：Agent 高频调用 LLM，路由延迟 50-100ms 会在多步任务里累积成秒级延迟；`opensquilla` 系列、`semantic-router` 都强调"prompt 不出机做路由决策"。
- 具体延迟数量级参考：ClawRouter <1ms（15维本地评分）；SquillaRouter LightGBM+ONNX 本地推理；AgentJev/SemIf 类 System-1 判定 ~50ms 单次前向；jev-ultrafast 投机扇出单次网络往返完成两个决策。
- **建议为 iDoris 判定器设定延迟预算分级**：规则/embedding 类判定器 <1ms；本地 logit 型 System-1 判定器 <100ms（p99）；需要升级到远程 Jev 类 API 的判定 <500ms。

### 3.4 判定器失败时的语义 ⭐ 本次重读最大补充

- `jev-skill-agent-decision-9-skills-90-scenarios-openrouter` 提供了目前全网最明确的规范：判定器不可用时**禁止静默降级**，只有两条合法路径——显式告知用户/调用方并等待恢复，或者用宿主模型模拟但**必须在响应中标注 `mode: agent_simulation` / `jev_called: false`**。
- `rapid-mlx-apple-silicon-local-ai-inference` 的历史 bug（云端路由静默失败无日志）是这条规则重要性的反面案例。
- `exxperts` 的"上下文窗口探测不到导致预算硬编码 128000 可能静默截断"是同一类问题在另一个维度的体现。
- **iDoris 现状**：不变式 #8 已经写了"不静默"的一般原则（"不支持的请求参数要么真实兑现，要么显式 400"），但 §4.4 判定层设计和 §8"对上游的服务目录"里的 `/v1/systemone` 端点**没有专门规定判定引擎本身失败/降级时的响应契约**。这是本次重读发现的最明确的设计空白，见 §4。

### 3.5 模型热切换与驱逐

- `m1-max-64gb-local-ai-model-selection-memory-guide`：oMLX 单模型驻留+自动卸载+切换延迟 10-30 秒的实测经验，是 iDoris 全局内存账本设计的直接依据。
- `superlinked-sie-inference-engine-agent`：100+ 模型 LRU 驱逐是集群级别（跨角色：chat/embed/rerank/guard）的统一策略，与 iDoris 目前"每个后端独立驱逐互斥锁"的设计粒度不同——**多角色模型共享内存池时需要统一驱逐优先级，避免关键角色（如 guard/隐私判定模型）被普通 chat 模型挤掉**。
- `krill-mac-mlx-llm-runtime-coding-agent`：内部一致性测试连续失败但特性仍默认开启，是"模型/加速特性升级门禁"必须严格执行、失败即回退默认值的反面教材。

### 3.6 MLX、oMLX 实测坑

- 投机解码/加速特性的正确性回归测试不能只是"有测试"，测试失败必须有强制的默认行为回退（krill 反例）。
- KV 前缀复用类优化（staged 模式）在短请求/热缓存场景下反而更慢，需要自适应而非硬编码开启（llm2jev 实测数据：staged 在长上下文+多候选下快 4.9x，但短输入下 all 模式反而快 1.7-2.0x）。
- 中文 token 估算：字符数÷4 的通用公式对中文严重失准（实测差 2.0-2.4 倍），orion-core 与 T2.4 的"⚠️ 需核查"呼应。
- 会话亲和（KV 缓存复用）要求脱敏必须是确定性的（同一实体同一占位符），否则前缀复用直接失效。

### 3.7 小模型做决策（Jev、SemIf、AgentJev 等）如何接进网关

- iDoris §4.4 已经确立四级判定器级联：规则/显式 header（永远优先）→ embedding 相似度 → 本地 logit 型 System-1（AgentJev/SemIf/Kev/LLM2Jev 类）→ 远程升级（TypeSafe Jev，仅限 privacy 允许出本机的请求）。本次重读确认这个级联顺序与全网实践完全一致，没有发现反例。
- 新增的具体实现建议：
  - **多决策点应支持共享前缀并行推理**（投机扇出模式），而非串行逐个调用（browser-use-jev/jev-browser-use 的 speculative fan-out）。
  - **决策头的 IIA（无关选项独立性）在不同实现路线间表现不同**：真实 Jev 有约 -0.28 log-odds 的跨选项依赖效应，LLM2Jev 这类"逐候选独立 prompt"设计无法复现这个特性——如果 iDoris 未来对比不同判定器实现的一致性，不能假设它们在候选集之间的行为完全等价。
  - **置换一致性测试是硬性要求**：kev 实测选项顺序变化导致 7.4% 的 argmax 结果改变，iDoris §4.4 已列入此项测试，本次重读确认其必要性有量化数据支撑。
  - Noul（纯 yes/no）类型的判定必须带置信度输出，不能因为是二元判断就省略校准概率（typesafe-ai-jev 原始设计的已知局限）。

## 4. 与现有设计的冲突或需要修改之处

> 逐条列出：现在怎么写、应改成什么、依据是哪篇文章。以下均基于 `/Users/jason/Dev/auraai/iDoris-plan/docs/iDoris-总体规划.md` v1.0（2026-09-27）通读后的比对，**没有发现颠覆性冲突**——本次重读的 74 篇相关文章里，绝大多数结论已经被 v1.0 规划吸收（说明既往那份"blog-调研记录"106 篇精读的覆盖质量确实很高）。以下是真正意义上的"现有设计没写清楚/有明确空白"的条目，不是"设计错了"。

### C-1（新增空白，优先级高）：`/v1/systemone` 判定引擎失败/降级时的响应契约未定义

- **现在怎么写**：iDoris 规划 §4.4「P-2 已拍板」只写了"判定引擎可选 Jev 类模型：外部 API（TypeSafe Jev）或本地开源实现（SemIf/LLM2Jev/Kev/AgentJev 类，local_only 请求只能用本地）"，§8 服务目录里 `/v1/systemone` 只列了端点和消费者，**没有规定该端点在判定引擎不可用/加载失败/超时时应该返回什么**。
- **应改成什么**：比照 `jev-skill` 的规则，明确 `/v1/systemone` 在判定引擎不可用时的行为契约：
  1. 默认行为是**拒绝**（返回结构化错误 + `reason_code: judge_unavailable`），把 fallback 决策权交给调用方；
  2. 只有调用方显式声明愿意接受"宿主模型模拟判断"时，才允许降级，且响应体必须显式包含类似 `judge_mode: simulated` / `calibrated: false` 的字段，让调用方（Agent24/业务模块）知道这不是校准过的概率，不能和真实 Jev 类输出同等对待；
  3. 这条规则应该写入 iDoris 不变式（可以作为不变式 #8"不静默"的一个具体展开条款）以及 §4.7 决策账本 schema（`extra.idoris.route.decisions[].judge` 字段应该能区分 `local-logit` / `remote-jev` / `simulated-fallback` 三种来源，而不只是记录 judge 名称）。
- **依据**：`jev-skill-agent-decision-9-skills-90-scenarios-openrouter`（明确规则原文）；`rapid-mlx-apple-silicon-local-ai-inference`（静默失败反例）；iDoris 自身不变式 #8"不静默"的精神延伸。

### C-2（新增细化，优先级中）：模型升级/切换门禁未考虑 harness/prompt 配置的模型特异性

- **现在怎么写**：iDoris §4.3"升级/切换流程"目前是"候选→预检→基线→计划冻结→维护窗口→实验→Selector 判决→同端口晋升→在线复验→提交或回滚"，门禁包含"贪心输出逐 token 比对和场景评测"——这套流程假设的是**同一套 harness/prompt 配置在新旧模型上都适用**，只需要对比模型输出本身。
- **应改成什么**：在"计划冻结"阶段，除了冻结模型 pin，还应该把该模型对应的 harness 配置（系统提示词模板、工具描述格式、判定引擎的 prompt 模板）一并纳入"配置 bundle 时间旅行"（§4.3 已有此设计但未提及 harness 层）版本化范围。晋升评测除了贪心逐 token 比对，还应该有一个"harness 适配度"检查——如果新模型在沿用旧 harness 配置下的失败模式明显不同于旧模型（比如新模型更容易在长上下文丢失约束，需要不同的上下文管理策略），Selector 判决报告应该同时给出"是否需要连带调整 harness 配置"的建议，而不是默认沿用。
- **依据**：`cmu-better-harnesses-smaller-models-slm-agent-cost-reduction-engineering`（"harness 不能跨模型复用"是论文的核心负面发现之一，qwen3-coder 调好的 harness 对 ministral-3-8b 完全无效）。

### C-3（新增具体技术，优先级中）：R2 请求处理核心缺少 prompt 缓存的三层分段设计细节

- **现在怎么写**：iDoris §4.3"会话亲和"只讨论了"同一会话路由到同一已加载实例，保住 prefix/KV 缓存"，是路由层面的会话粘性，没有讨论**单次请求内部的字段排列顺序**如何影响缓存命中率。
- **应改成什么**：在 R2（请求处理核心）阶段实现细节里，明确组装最终 prompt/messages 时按"全局层（系统提示词+policy规则，几乎不变）→ 会话层（用户偏好/历史摘要，会话内稳定）→ 易变层（当前请求内容）"的顺序排列，并且**明确规定 request-id、timestamp、trace-id 等易变元数据不得混入前两层**（现有设计里 `X-iDoris-*` 系列都是走 header 不进 prompt body，这条其实已经规避了这个风险，但没有显式写出这条设计原则，建议补一句话说明原因）。
- **依据**：`anthropic-commerce-agents-30pct-cart-technical-architecture-deep-dive`（"最容易破坏缓存的错误是把时间戳/请求ID放进系统prompt"，实测命中率 90-99%）。

### C-4（前瞻建议，优先级低，M7+）：capabilities/catalog 字段预留负向路由

- **现在怎么写**：iDoris `/capabilities` 端点和 catalog.yaml 目前的角色分类是 `fast/core/deep/temp` 四档，规模较小，靠正向描述足够区分。
- **应改成什么**：当 M7-M8 之后 adapter 晋升积累、tenant 定制模型和角色种类增多，capabilities 描述字段应该预留 `avoid_for` / `prefer_over` 之类的负向路由字段，避免届时重蹈 google/skills 137 个 skill 里 67% 靠"别用我"兜底的覆辙。**非当前 M4-M6 阻塞项**，建议记入 §7 M7-M8 任务清单的技术债备忘。
- **依据**：`google-skills-137-agent-skills-negative-routing-vs-anthropic`（实测 67% 负向路由率，437 字符平均 description 长度）。

### C-5（边界澄清建议，优先级中）：Lethal Trifecta 类"组合风险检测"归属需要在 iDoris×Agent24 分工规范里明确写出

- **现在怎么写**：iDoris §4.5"边界声明"写的是"Router 只管 LLM 流量，上游 agent 自己的其他出网归 Agent24/OS 层管"，闸一/闸二是**单请求级别**的隐私/预算判断。
- **应改成什么**：`archestra` 的 Dual-LLM 验证 + Lethal Trifecta 防护（多个中风险信号组合=高风险，需要独立验证器拦截）是一种**跨请求/跨动作的组合风险检测**，目前不属于 iDoris 单请求判断的范畴。建议在 §12"与 Agent24 的分工边界与接口数据规范"起草时，**明确写一条"组合风险检测由 Agent24 负责，iDoris 只提供单请求级别的隐私/预算/意图判断原语（`/v1/systemone`、`/v1/inspect`），Agent24 可以调用这些原语多次组合出更高层的风险判断，但组合逻辑本身不下沉到 iDoris"**，避免协商时两边都假设对方会做这件事而都不做。
- **依据**：`archestra-enterprise-ai-platform-mcp-gateway-guardrails-llm-proxy-k8s`（Dual-LLM 验证 + Lethal Trifecta 概念）；iDoris 现有 §4.5 边界声明、§12 分工边界规范起草计划。
