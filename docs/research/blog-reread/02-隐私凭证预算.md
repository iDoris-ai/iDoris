### 1.2 判定为噪声的典型模式（N，未逐条列出，代表性说明）

- **正则误命中"隐私"标签**：大量文章标签里带有"隐私""本地优先"，但内容其实是模型量化/推理引擎评测（如 goinfer、ferrum-infer-rs、gsq-rco 量化、Qwen 系列 GGUF 发布）、TTS/图像/视频生成工具（LuxTTS、YuE2、FLUX.3、Mage-VL）、知识库/RAG 工具（Adapta、LEANN、pageindex）——这些文章的"隐私"只是"数据不上云"的营销词，没有讨论检测机制、误报/漏报、脱敏、出站控制等设计细节，与本报告主题无实质交集。
- **正则误命中"key"标签**：多数是"无需 API Key 即可使用"的功能性描述（browsentic、google-search-trends-mcp、免费 MCP 工具），并非凭证管理/代理设计。
- **正则误命中"budget/成本"标签**：不少是模型训练成本报道（VibeThinker $7800 训练成本、Castform RL 微调成本）、区域性硬件选型比较（Mac Studio vs AMD vs 云 GPU）、与业务模式相关的定价分析（DeepSeek V4 对 Vibe Coding 市场冲击、AhaCreator 抽成对比）——这些讨论的是"训练/硬件/市场"成本，不是 iDoris 关心的"请求级 LLM 调用预算控制"。
- **区块链/Web3 基建噪声**：AirAccount、SuperPaymaster 相关文章命中"密钥/凭据/预算"关键词是因为讲的是链上私钥/Gas 代付，与 LLM 网关的凭证代理、token 预算是完全不同的技术领域（虽然 iDoris 未来会消费 SuperPaymaster 的 gasless 能力，但这批文章不解释 LLM 网关内部设计，故不纳入本报告）。
- **安全/渗透测试类**：cloudflare-security-audit-skill、reverse-skill、Shannon、Strix、AI-Infra-Guard 等文章命中"安全/权限"标签，但主题是渗透测试工具本身；其中 Shannon/Strix 的"结构化 scope"设计已通过 pentest-harness 一文的对比引用间接纳入本报告，不再单独展开。

## 2. 逐篇笔记

> 为控制篇幅，本节按主题分组，每篇给出：URL、核心观点（含关键数字）、对 iDoris 的具体启示。全部 39 篇（含权重较低的 sphere-sdk）均已读全文。

### 2.1 隐私检测与脱敏（误报/漏报、本地优先的真假）

**① Osaurus** — https://blog.mushroom.cv/blog/osaurus-native-macos-ai-harness-swift-cryptographic-identity/
核心观点：发云端前用本地 `openai/privacy-filter`（1.5B 参数 MoE）扫 PII，命中实体替换为稳定占位符 `[PERSON_1]`，流式回复本地实时还原；**脱敏后再扫一遍，仍有遗漏就阻止发送**（fail-closed）；UI 有"Insights 面板显示云端实际收到的字节"。每个 Agent/设备一把 secp256k1 密钥对，Agent 间通信 X25519+ChaCha20-Poly1305 端到端加密，Relay 是盲管道。
对 iDoris 启示：这是闸一 REDACT 三件套（稳定占位符+流式还原+二次扫描 fail-closed）设计doc 已引用 osaurus 的最直接原型，代码级细节可直接参照；"出站字节可视化"UI 设计也可直接借鉴。

**② OpenMinis + 本地模型 + Tailscale** — https://blog.mushroom.cv/blog/openminis-private-personal-ai-tailscale-local-model-complete-guide/
核心观点：OpenMinis 默认把健康/日历/照片全量喂给云端 LLM 造成"隐私悖论"（越好用泄露越多）；修复方案是本地 Ollama + Tailscale 组网，作者强调"API Key 是字符串`ollama`，Ollama 不做认证——没有密钥泄露的风险"。
对 iDoris 启示：本地推理场景下"没有真实凭据"本身就是一种隐私优势（不存在闸二凭证泄露风险），但也说明**闸二的必要性只在能力②外部 API 时才成立**——纯本地路径根本不需要凭证代理这层防线。这是支持"预算/凭证闸应晚于路由判断"的旁证。

**③ jarvis-py 拆解** — https://blog.mushroom.cv/blog/jarvis-py-local-voice-assistant-privacy-teardown/
核心观点：项目自称"Offline"，实测**默认在线时把整段录音以 FLAC 明文 HTTP 发给 Google**（`http://` 而非 `https://`），断网才退回本地 Vosk；唤醒词阈值 0.3（低于官方建议 0.5）导致 **18 条近音干扰句中 11 条误唤醒**（FP）；文档 RAG 相似度阈值 0.6（从 0.45 上调以避免瞎编）导致 **6 个真问题里 5 个的正确答案完全没有被注入提示词**（FN）——门槛调紧治好了一个问题（幻觉）却制造了另一个问题（漏答）。
对 iDoris 启示：直接证明"隐私检测/内容过滤门槛"存在 FP↔FN 的硬trade-off，不能只调一个方向；且验证了"local-first"标签必须逐行代码核实（"local-first"和"offline"是两件事），这对应设计文档 §2 不变式 8"不静默"的精神。

**④ garmin-mcp-local 拆解** — https://blog.mushroom.cv/blog/garmin-mcp-local-sqlite-cache-health-data-teardown/
核心观点：项目缓存 Garmin 健康数据到本机 SQLite，服务器本身无出网套接字，**但"全本地"只对存储成立，对推理不成立**——工具返回的睡眠/心率数据会作为对话内容交给你接入的任何模型（云端就是发给云端）；Garmin 账号密码明文存在 `.env`，未用 Keychain；"只读"SQL 工具用 `WITH x AS (SELECT 1) DELETE ...` 可绕过前缀检查真正删除数据。
对 iDoris 启示：**"数据在本机"≠"推理在本机"**是本次调研反复出现的核心区分（exxperts、garmin-mcp、vitalik 都独立得出），iDoris 的隐私分级必须显式区分"存储位置"和"推理/出站位置"两个维度，不能混为一谈。凭证应强制走 Keychain，绝不允许明文 `.env`。

**⑤ Hindsight** — https://blog.mushroom.cv/blog/hindsight-agent-memory-retain-recall-reflect/
核心观点：v0.10.1 发布日志明确记录修复了"把技术数字（端口号、哈希值）误判为信用卡号码并脱敏"的 bug。
对 iDoris 启示：这是设计文档已引用的"端口号被误判为信用卡"citation 的原始出处，证实 L0 正则规则若不带校验和（如 Luhn）极易产生 FP，验证了 iDoris §4.5 "L0 机械规则...带 Luhn 等校验和防误报"设计的必要性。

**⑥ KaLM-Jev** — https://blog.mushroom.cv/blog/kalm-jev-local-judgment-engine-hardware-deploy/
核心观点：Noul 任务类型示例直接是"包含个人身份信息（姓名+电话/身份证）""包含攻击性或侮辱性语言""包含商业机密关键词"三条独立 yes/no 判断，本地 0.27B–4B 模型跑，硬件门槛最低（4–16GB）。
对 iDoris 启示：这正是 iDoris L1 System-1 Noul 判定的具体可落地实现模板——批量隐私类别判断可以用极小的本地判别模型（非生成式）完成，成本几乎为零，支持"隐私判定应尽量靠前、廉价、常驻"的架构假设。

**⑦ "$200/月 AI 干掉后勤部"读后** — https://blog.mushroom.cv/blog/ai-native-company-200-dollar-logistics-local-privacy-qwen3-analysis/
核心观点：原文架构把全部数据发给公有云 LLM；读后感建议按敏感度三层分流（敏感→本地 Qwen3-8B、中性→云端、公开→随意），本地方案在已有 Apple Silicon 硬件上边际成本≈$0。
对 iDoris 启示：三层敏感度分流与 iDoris 隐私分级（0–3 级）思路一致，进一步佐证"隐私分级"应该是路由决策的输入而非独立并列的一道闸。

**⑧ Vitalik 的 AI 生存指南** — https://blog.mushroom.cv/blog/vitalik-ai-survival-guide-cn/
核心观点：**本地模型是能力陷阱**（Qwen3.5:35B 写代码"远远不够"，DGX Spark 比游戏本还慢）；真正的隐私不是"不用云"而是"用云但云不知道你是谁"——需要 ZK-API（证明权限不暴露身份）+ 混合网络（打乱 IP 关联）+ TEE（硬件级"只有解密→推理→加密输出"的密码学证明）+ bubblewrap 沙箱 + **人机双因素确认**（"人是一个因素，AI 是另一个因素"，2-of-2 才能执行风险操作）。
对 iDoris 启示：这是对 iDoris"本地优先"假设最有力的外部挑战——本地不等于隐私，隐私的关键是**出站去关联**而非"是否本地"。iDoris 的"出站去关联：远程请求剥离 tenant/user/key 标识，每个请求用新的上游 request-id"设计方向正确，但 Vitalik 的标准更高（ZK-API 级不可关联），iDoris 现阶段至少要做到"不可从流量模式反推调用方身份"这条底线。人机双因素确认思路可用于高风险操作（放宽隐私、关闭 kill switch）的二次确认设计。

**⑨ tare 上下文压缩** — https://blog.mushroom.cv/blog/tare-lossless-context-compression-cache-correct-output-aware/
核心观点：无损优先（有损手段需显式开启）；**cache-correct**——先检测 provider 前缀缓存断点，只压缩断点后的动态后缀，前缀原样不动，因为改一个字节就作废约 10 倍缓存折扣；output-aware——压过头会导致模型用更啰嗦的输出补偿，总成本反升，需要监测输出 token 尖峰自动回退压缩力度；MCP 模式下代理会转发客户端携带的任意凭证（包括 Claude Pro/Max 订阅 OAuth token）。
对 iDoris 启示：cache-correct 的"断点检测、只动态修改断点后内容"正是 iDoris"隐私脱敏必须确定性（同一实体用同一占位符），否则会破坏缓存"citation 的技术原型；output-aware 的教训提醒 iDoris 的预算/token 优化不能只看输入侧，要监控输出侧补偿效应。

**⑩ DSH Remote** — https://blog.mushroom.cv/blog/dsh-remote-deepseek-harness-mobile-tailscale-pwa-mac/
核心观点：Remote API 白名单制，读取/修改 DeepSeek API 凭据**在代码层面没有远程调用入口**（不是文档承诺，是没写这个函数）；身份验证从可信本机代理连接解析真实 Tailscale 对端身份，**不信任浏览器提交的身份 Header**（可伪造）；设备私钥存 macOS Keychain 不放项目目录；白名单脚本拒绝删除最后一个允许设备防止误操作扩大访问范围。
对 iDoris 启示：这是"凭据不下发上层"的最佳工程实践范本——用**代码层面完全不提供读取接口**而非"权限检查"来保证凭证边界，比"检查了才放行"更彻底。"不信任调用方自称身份头，只信任传输层可信对端"的原则可直接用于 iDoris 虚拟 key 校验设计。

**⑪ Pipelock 出站防火墙实测** — https://blog.mushroom.cv/blog/agent-egress-firewall-pipelock-rate-limit-kill-switch/
核心观点：提出**四层 Agent 防线模型**：提示注入防护（看内容）→ 工具权限系统（看单次动作）→ **出站防火墙**（看跨时间累积行为，站在网络出口）→ OS 沙箱（保证前三层不可绕过）；实测域名白名单/每域名限速（5次/分钟，第6次429，60秒滑动窗口，被拒请求不计入配额）/ kill switch（sentinel 文件 + 独立端口 API，同一 API 打到数据面主端口返回 404）均有效；**HTTPS 请求体是盲区**——不开 TLS 拦截时白名单域名内的 POST body 携带 API key 照样放行；macOS 上不遵守 `HTTPS_PROXY` 的程序（原始 socket）可以直接绕过代理出网；免费版限速最低只能设到每小时 60 次，按小时/按天的预算属付费功能，无 license 时该配置段直接被禁用。
对 iDoris 启示：**四层模型**是审视 iDoris 防线完整性的现成框架——iDoris 目前主要覆盖"工具权限系统"（虚拟 key/policy）和部分"出站防火墙"（白名单 provider），OS 沙箱层完全没有覆盖（iDoris 是网关不是执行环境，这个边界已在 §4.5"边界声明"写明，合理）。**"macOS 上不走代理的 socket 直连出网"**是已经引用的 pipelock 反例，本文提供了具体机制（原始 socket 绕过 env var 代理）。**"被拒请求不计入配额"**这条设计可直接吸收进 iDoris 预算/限速设计。

**⑫ Pentest Harness 拆穿** — https://blog.mushroom.cv/blog/pentest-harness-deepseek-harness-rebrand-authorization-teardown/
核心观点：项目自称"仅限授权测试"，但授权全靠用户口头声明——没有 scope 文件、目标白名单、授权凭证、审计日志，且系统提示词里塞了"授权：完全、无范围限制、不警告合法性"的兜底人格；对照 Shannon/Strix 等正经渗透工具，后者把 `rules_of_engagement`/`scope`/`avoid`/`focus` 写进结构化配置，要求书面授权。
对 iDoris 启示：直接验证 iDoris 不变式 #12"授权结构化：调用方的自我声明永远不能放宽授权"——这里给出了一个具体的反面案例可以写进测试用例："隐私声明只能靠 header/policy，不能靠 prompt 里模型自己说'我有授权'"。

**⑬ exxperts 拆解** — https://blog.mushroom.cv/blog/exxperts-local-first-ai-agent-approval-gated-memory-teardown/
核心观点：记忆写入三步走：Remember（一次性无工具无网络的 worker 进程生成摘要预览）→ 你批准 → 系统写入，工作进程本身永远不写文件；每次保存先归档旧文件（copy-on-write）+ 写一条带 SHA-256 指纹的事件记录，可撤销、可"时间旅行"查看任意历史版本；服务端边界实测：只监听 127.0.0.1，无 token 返回 401，伪造 Host/代理头返回 403；README 口号"nothing leaves your machine"实际是"**no vendor cloud, but a model cloud**"——存储不出机，但接云端模型时对话与记忆内容照样作为 prompt 发给模型商。
对 iDoris 启示："no vendor cloud but a model cloud"是本次调研中对"本地优先"最精确的一句话总结，建议直接写入 iDoris 的隐私文档作为对用户的诚实声明模板。"提议→批准→写入，worker 无工具无网络"的三段式与 iDoris §2 不变式 #6"策略是数据...提议→diff→人批准→版本化→可撤销"完全同构，可以直接引用其"归档+SHA-256指纹事件"的具体实现方式。

**⑭ Lethal Trifecta** — https://blog.mushroom.cv/blog/simon-willison-lethal-trifecta-ai-agent-security/
核心观点：Simon Willison（Django 联合创始人，"prompt injection"术语提出者）2025年6月提出：**私有数据 + 不可信内容 + 对外通信能力**三者同时具备即进入高危区间；LLM 结构性地无法区分指令来源重要性（系统提示、用户输入、工具读取内容最终都拼成同一串 token）；GitHub MCP、Supabase MCP（`service_role` 绕过行级安全）、微软 365 Copilot EchoLeak（CVE-2025-32711，零点击，绕过官方提示注入分类器）三个真实攻破案例；"提示乞求"和 AI 检测分类器均**明确无效**——"95-99% 准确率的提示注入分类器不够好，应用安全领域 1% 的 SQL 注入失败率早就摧毁金融系统了"；**推荐防御顺序：优先破坏第三条腿（限制对外通信），其次破坏第一条腿（最小权限访问私有数据），最后是过滤不可信内容来源**；域名白名单严禁通配符（`*.yourdomain.com` 可能有开放重定向）。
对 iDoris 启示：**这是本次调研中理论权重最高的一篇**，直接为 iDoris 的隐私/出站设计提供第一性原理：(a) 验证 iDoris"隐私检测只判定不改写"+"L0 机械规则 fail-closed"的必要性——不能指望分类器达到 99%+ 准确率就够用；(b) **明确支持"出站去关联/白名单"应作为最优先的防御手段**——这与 iDoris §4.5 的出站去关联设计方向一致，但本文把它论证为"应该优先于"隐私内容分类"的第一道防线，因为分类必然有漏网；(c) 对通配符域名白名单的警告应写入 iDoris 的白名单 provider 实现规范。

**⑮ Omni 权限感知** — https://blog.mushroom.cv/blog/omni-open-source-company-ai-agent-permission-aware/
核心观点："权限跟着数据走"——索引信息的可见范围严格继承自源系统权限，**索引这个动作本身不改变谁能看到什么**；代码执行沙箱四层叠加（隔离网络无内外网访问 + Landlock + 只读根文件系统 + 资源限额）。
对 iDoris 启示：如果 iDoris 未来涉及跨租户/跨用户的嵌入索引（用于语义路由或 RAG），"索引不能越权"是硬约束，直接支持 iDoris 不变式 #2"隐私只能收紧不能放宽"在数据管道层面的具体化。

### 2.2 凭证代理 / API Key 管理 / 身份与租户

**⑯ OneCLI** — https://blog.mushroom.cv/blog/onecli-ai-agent-credential-gateway-secret-vault-rust/
核心观点：MITM 网关架构：Agent 拿占位符 `FAKE_KEY_GITHUB` 发请求，Rust 网关按 host/path 规则匹配、实时解密注入真实 key，Agent 全程不接触真实凭证；真实凭据 AES-256-GCM 静态加密存储；Bitwarden 集成后**密钥根本不存在 OneCLI 服务器上**，按需从 Bitwarden 取用注入；HN 评论一针见血："Vault 保护静态存储的 key，但 agent 在运行时仍然拿到明文；代理方案让 key 完全对 agent 不可见"。
对 iDoris 启示：这是 iDoris 闸二凭证代理设计的最直接参照对象——"MITM+占位符+运行时注入"三段式可以直接映射到 iDoris 的 `secret://` 引用设计（§3 执行层"闸二凭证注入点（只见 secret:// 引用）"）。Bitwarden 集成模式（密钥不落盘、按需取）可作为 iDoris Keychain 集成的进阶选项。

**⑰ treg** — https://blog.mushroom.cv/blog/treg-openrouter-agent-tools-unified-api-credential-proxy/
核心观点：4 种凭证注入器（env / secret_file / oauth 自动刷新 / cli_auth 从 keychain 提取）；调用优先级明确排序：自己团队注册的工具+key > 团队存的 secret（虚拟工具转发）> 平台自己的 key（计费到团队余额）；**余额耗尽返回 HTTP 402，携带 `balance_micro`、`estimated_cost_micro`、`topup_url` 结构化字段，Agent 可直接解析无需读错误文案**；代理只做"注入认证、剥离控制头、流式转发"三件事，其余原样透传。
对 iDoris 启示：**HTTP 402 结构化预算耗尽响应**是一个值得直接采纳的具体接口设计，比"返回 429/403 + 自由文本 reason"更适合机器可读的降级处理；"自有凭证优先于平台凭证"的顺序对 iDoris tenant 分层授权（下层可以有自己的 key 覆盖上层默认路由）有参考价值。

**⑱ OpenConnector** — https://blog.mushroom.cv/blog/open-connector-saas-auth-gateway-ai-agents/
核心观点：认证网关把 1000+ SaaS 抽成"Action"（带 schema 的可调用操作），Agent 只拿到"是否有权限执行"和执行结果，**永远拿不到原始凭据**；Action allow/block policy + 完整 run log（支持 redaction）。
对 iDoris 启示：与 onecli/treg 同类思路的另一个实现，进一步验证"凭据边界"是这类项目的收敛设计共识，不是孤例。

**⑱-b open-connector 部署实操篇**（同项目姊妹文，补充一条独立于⑱的细节）— https://blog.mushroom.cv/blog/open-connector-mcp-agent-integration-guide/
核心观点：MCP 侧只暴露 `list_apps`/`search_actions`/`get_action_guide`/`execute_action` 四个元工具；**Key 明确分两级**——Admin Token 管控制台、权限最大，Runtime Token 在控制台单独创建、可限定 allow/block 哪些 Action，官方建议给 Claude Code 这类 agent 只发 Runtime Token；知乎无官方 API，只能用有有效期的 Cookie 作为一种非标准、易过期凭证。
对 iDoris 启示：Admin/Runtime 两级令牌与 iDoris "数据面 :PORT 用虚拟 key、管理面 :ADMIN_PORT 用会话令牌"的划分精确对应，且证明"执行面令牌天然带 allow/block 白名单"是可落地的具体机制，不只是设计意图；同时提醒闸二凭证代理要支持易过期、非结构化凭证（Cookie 类）的刷新生命周期，这是 onecli/treg 等文章没有覆盖的一种凭证类型。

**⑲ tnk 零信任沙箱** — https://blog.mushroom.cv/blog/tnk-zero-trust-sandbox-local-llm-agent/
核心观点：每个项目起一个独立 Lima VM，只挂载该项目工作区目录，宿主机密钥/SSH/其他项目文件默认不可见；推理仍在宿主机跑，沙箱只通过环境变量拿端点地址——**明确"管的是执行环境隔离，不是推理引擎选择"**，与本地推理正交；作者自己标注 experimental，3 star 0 fork，安全类工具"威胁模型只有作者自己验证过"的风险。
对 iDoris 启示：这一层是 iDoris 明确声明"不管"的范围（Router 只管 LLM 流量，不管上游 agent 执行环境），但值得在文档中显式引用作为"互补但外部"的防线，提醒使用方 iDoris 的隐私/凭证边界不能替代执行沙箱。

**⑳ OpenClaw 网关拆解** — https://blog.mushroom.cv/blog/openclaw-gateway-unattended-multi-agent-orchestration/
核心观点："可信网关，不可信执行，确定性策略"；**拒绝是结构性的不是请求模型自觉**——"审批链路走不通，默认结果是拒绝不是放行"；云端 worker 凭证**按次派发、10分钟 TTL、落盘哈希存储**；审批门槛绑定 `canonical command + cwd + environment hash + content-hashed file operands`，环境或文件一变哈希对不上自动重新要求审批，防止"复用一次批准的操作去偷换成另一次危险操作"；执行环境默认 Docker/Podman 容器（read-only root、drop 所有 capabilities、非 root 用户）；崩溃循环断路器"压住自动重启但保持控制面可访问"；**关键警示：沙箱和审批默认是关闭的，硬化是显式配置，不做无人值守就用默认配置几乎等于裸奔**。
对 iDoris 启示：这是 iDoris §2 不变式 #7"可信网关/不可信执行/确定性策略"citation 的原始出处，本文提供了三个可直接落地的具体机制：(a) **一次性短期凭证（按次铸造+TTL+哈希落盘）**应作为 iDoris 闸二凭证代理的标准实现，而非静态长期凭证；(b) **审批绑定内容哈希**（不是"批准过这个命令"而是"批准过这个命令+这个环境+这个文件内容的组合"）可用于 iDoris 敏感操作确认令牌设计；(c) **"安全默认关闭，需要显式开启"是一个反面警示**——iDoris 的 fail-closed 原则必须体现在默认配置本身，不能依赖运维人员记得去开某个开关。

**㉑ Wemux** — https://blog.mushroom.cv/blog/wemux-self-hosted-agent-orchestration-worker-first/
核心观点：控制面（规划/路由/评审）与 worker 执行分离，控制面**从不执行你的代码**，BYOK 模型密钥只留在 worker 端；遥测默认每日一次匿名聚合上报，字段白名单**提交进源码可审计**（`packages/shared/src/types/community-usage.ts`），一个环境变量关闭；作者自评"能把白名单提交进源码让人查，这个做法应该成为默认，可惜现在还不是"。
对 iDoris 启示：控制面/执行分离原则与 iDoris 数据面/管理面分离设计一致；"遥测字段白名单提交进源码"是 iDoris 自身审计/轨迹系统可以直接采纳的透明度实践，比"文档承诺不采集敏感数据"更可信。

**㉒ Proma** — https://blog.mushroom.cv/blog/proma-local-first-ai-desktop-agent-workspace/
核心观点：`~/.proma/` 下所有数据是明文 JSON/JSONL，**唯一加密字段是 API Key**（Electron `safeStorage`），其余会话内容、用户画像、附件全部明文可读。
对 iDoris 启示：这是设计文档 §5.7 已引用的反例原始出处，确认"只加密 key 不加密内容"是常见但不充分的做法——iDoris 的 SQLCipher 全库加密设计（personal 模式）优于这种局部加密方案，应坚持。

**㉓ Archestra** — https://blog.mushroom.cv/blog/archestra-enterprise-ai-platform-mcp-gateway-guardrails-llm-proxy-k8s/
核心观点：虚拟 API Key 给每个客户端工具（Claude Code/Codex/Cursor）单独发一个 token，按团队/用户追踪费用；**费用限额可按团队、按环境、按 Provider 设硬上限**；MCP 网关用 OAuth + **On-Behalf-Of**——工具以当前登录用户身份运行而非共享服务账号，审计可精确追踪到发起者；护栏两层且都是确定性的（不依赖单一 LLM 判断）：Dual-LLM 独立验证 + Lethal-Trifecta 式的"高权限目标+不可逆操作"组合拦截。
对 iDoris 启示：**"虚拟 Key = 调用方身份"**与"按团队/环境/供应商三维度设预算硬上限"两条均是 iDoris §4.2、§4.6 已有设计的直接原型，可以放心按此思路细化实现；On-Behalf-Of 模式提醒 iDoris 未来若支持多用户共享同一租户下的不同调用方身份时，应考虑透传真实调用者身份而非折叠成租户级别。

**㉔ authentik 2026.8** — https://blog.mushroom.cv/blog/authentik-2026-8-oidc-certified-rust-rewrite-pam/
核心观点：通过 OpenID Foundation 官方认证（8 个 profile）；PAM（特权访问管理）支持用户申请访问、指定审批人/最少审批人数/**请求与授权到期限制**/通知/自定义流程，每个操作记入事件日志；**策略/群组/用户绑定支持到期时间，过期后自动不再授予访问，无需人工删除**。
对 iDoris 启示："策略绑定到期"是 §4.2"临时授权：policy 绑定可以带到期时间...到期自动失效"citation 的精确原始出处，PAM 的"最少审批人数+到期+通知"整套流程可直接作为 iDoris §4.6 超额审批队列的实现参照。

**㉕ Platypus** — https://blog.mushroom.cv/blog/platypus-self-hosted-multi-tenant-ai-agent-platform/
核心观点：Blueprints——组织级共享配置（标准工具集/默认 Skill/Sandbox 配置），应用到 Workspace 时"**additive（不覆盖已有自定义）、idempotent（重复应用不出错不叠加）、a snapshot（应用当下那个版本，后续 Blueprint 更新不自动同步除非重新应用）**"；两层租户隔离 Organization → Workspace。
对 iDoris 启示：这是 §4.2 Blueprint citation 的精确原始出处，"增量/幂等/快照"三性质的具体定义可以直接写进 iDoris 的 Blueprint 实现规范，不需要重新设计语义。

**㉖ Sphere SDK**（权重较低）— https://blog.mushroom.cv/blog/sphere-sdk-autonomous-agent-economy-infrastructure/
核心观点：给 Agent 发密码学身份 + Bearer Token 钱包，Token 是自包含密码学对象（携带完整历史和证明）直接 P2P 流转，链上只留承诺哈希；发票即 Token，OPEN→COVERED→CLOSED 生命周期状态机绑定支付状态。
对 iDoris 启示：与 LLM 网关的预算控制场景不直接相关（这是 Agent 间支付结算基础设施），但"发票状态和支付状态绑定在同一个密码学对象上，不存在不一致"的思路对 iDoris reserve/settle 两阶段记账的"状态机不允许中间态不一致"设计有旁证价值，权重不高，仅作为补充记录。

### 2.3 路由顺序理论（核心：回应 jason 的质疑）

**㉗ 入口路由怎么选（semantic-router 等 5 类方案对比）** — https://blog.mushroom.cv/blog/semantic-router-ai-agent-entry-point-guide/
核心观点：**明确区分"路径路由"（决定这一步该怎么处理：走 agent/搜索/邮件/模型/链路）和"模型选择"（RouteLLM 式：简单问题用弱模型、难问题用强模型）是两层决策**，前者更早、更基础，"把它们混为一谈会导致要么在入口就烧了一次不必要的 LLM 调用，要么路由逻辑写死无法扩展"；推荐方案 `aurelio-labs/semantic-router`——**~0.1B 级、零 LLM 调用、嵌入相似度匹配**，几毫秒出结果，"入口是每次请求都要过的关卡，必须快、确定、便宜；调一次 LLM 做路由判断本身就违背了'入口要轻'的设计初衷"；RouteLLM 被明确定位为"该发生在路径已经确定要调用某个模型之后，而不是入口第一步"，"把它塞进入口路由,会导致'该不该调模型''调哪个模型'这两层决策被压扁成一层"。
对 iDoris 启示：**这是回应 jason 质疑最直接、最有力的一篇文章**，详见第 4 节专题讨论。

**㉘ ClawRouter** — https://blog.mushroom.cv/blog/clawrouter-llm-router-agent-native-multi-model-cost-optimization/
核心观点：路由引擎对每个请求做 **15 维度本地评分（不调用任何外部 API），不到 1ms 出结果**，"没有中间服务器知道你在用什么模型、问了什么问题"；四级复杂度（SIMPLE/MEDIUM/COMPLEX/REASONING）× 三种成本策略（ECO/AUTO/PREMIUM）矩阵；钱包签名代替账号注册，USDC 微支付（x402 协议）代替信用卡，8 个永久免费模型无需任何余额。
对 iDoris 启示：复杂度×成本档位矩阵已被 §4.4 引用，本文额外提供的关键证据是**路由决策本身"不到 1ms、零外部依赖"，即分类/路由这一步骤天然可以在预算判断之前完成而不产生额外成本或延迟**——这进一步支持"先路由再判预算"而非"先判预算再路由"的顺序。

**㉙ OpenSquilla** — https://blog.mushroom.cv/blog/opensquilla-token-efficient-ai-agent-squilla-router/
核心观点：SquillaRouter 是设备上运行的 **LightGBM+ONNX 分类器**（不是 LLM），**"分类在设备上运行，prompt 从不离开本机做路由决策"**，评分维度含 turn 长度/语言/是否含代码/关键词/语义 embedding；PinchBench 实测：同等质量（0.9251 vs 0.9255）下成本从 $6.23 降到 $0.69（降 89%），token 消耗减少 44%。
对 iDoris 启示：与 semantic-router、clawrouter 共同构成"复杂度/意图路由应该用极小的本地判别模型、零 token 成本、在决定是否需要外部付费模型之前完成"的一致证据链。

**㉚ Virtual AI Infra Team** — https://blog.mushroom.cv/blog/virtual-ai-infra-team-local-llm-self-upgrade-dflash2-mac/
核心观点："模型只提议、代码判决"——Planner（LLM）只能输出一份 JSON 计划（一句假设+2-3个候选ID+验收阈值），**"You cannot run shell commands"**；Policy 层把计划当不可信输入，白名单外 ID 直接拒绝，**模型给的阈值只能被夹紧收严不能放松**（内存取最小值、加速门槛取最大值，"模型只能把门槛调高，不能调低"）；Selector 判决规则写在纯代码里，"The model never declares its own success"；**没有候选合格时保留基线，这被明确定义为正常结果，不是失败**。作者自己的实测数据也显示"18.14→37.52 tok/s +106.84%"的头条数字只是代码题的中位数，散文题只有 +50.6%，均值 +89%——诚实标注了局限。
对 iDoris 启示：这是 §2 不变式 #10"模型只提议，代码判决...没有合格候选时保留现状，这算正常结果"citation 的精确出处，"模型给出的阈值只能收紧不能放松"这条具体机制可以直接套用到 iDoris 隐私/预算判定层——例如意图/隐私分类器给出的置信度阈值应该只能让判定更保守，不能被模型自己放宽。

**㉛ Maka** — https://blog.mushroom.cv/blog/maka-agent-runtime-host-event-log-desktop-tui-eval/
核心观点："Log is the Runtime"——模型消息/工具调用/工具结果/终止事实全部作为不可变事实写入 Runtime Event Log，会话/UI/发给模型的上下文/崩溃恢复都是对同一份日志的"投影"；**"Context is not history"**——发给模型看的上下文可以剪枝压缩，但完整证据链永远保留，随时可倒回去看"当时到底发生了什么"；Desktop/TUI/Eval 三种入口共用同一个 Runtime Host，执行语义完全一致（测试环境和生产环境走同一条代码路径）。
对 iDoris 启示：这是 §2 不变式 #9"日志即运行时...审计、用量、UI、轨迹、回放都是这条流的投影"citation 的精确出处。"Context is not history"这条细分原则可以直接用来澄清 iDoris §5"轨迹与审计物理分离"的边界：**发给下游模型的上下文可以被隐私脱敏/裁剪，但审计事件流永远记录未裁剪前的完整决策证据**（当然仍然只存元数据，内容归轨迹模块管）。

### 2.4 预算与成本核算

**㉜ hermes-local-rig-accounting** — https://blog.mushroom.cv/blog/hermes-local-rig-accounting-real-cost-per-token/
核心观点：本地推理不是免费的，插件把硬件折旧（按**实际推理小时**摊销而非自然日历）+电费折算成 $/M tokens，示例配置算出 **$0.62/M tokens**（折旧$0.057/hr + 电费$0.054/hr，二者几乎各占一半）；只统计本地 provider，云端调用直接忽略，两边账不混；作者承认"opportunity cost"写在开场白但公式里没有体现，是宣传语与实现的小落差；成本数据全部留在本地，无遥测。
对 iDoris 启示：这是 §4.6"本地影子价格：折旧+电费，按实测 TPS 折算；只进报表和组织内部分摊，不拦截请求"citation 的精确来源与公式模板，可以直接套用其"按实际推理小时摊销而非自然日历"的会计选择（对 iDoris 更有利，但要在文档中注明这是"对本地更友好"的口径选择，避免夸大本地经济性）。

**㉝ TokenTracker** — https://blog.mushroom.cv/blog/tokentracker-local-first-token-cost-accounting-dedup/
核心观点：基于 `reqId` 的传统去重（如 ccusage）对**不返回 request ID 的 provider（DeepSeek/Kimi/MiniMax/Claude 子 agent）会超算 1.6–3.7 倍**；TokenTracker 改用复合键去重，声称总数能与各家账单对上；36 个集成里绝大多数是被动读取型，只读工具自己写的日志文件，从不读 prompt 或响应正文；**价格未公布的模型（如腾讯 hy3-preview）token 照常统计但成本显示 $0，等厂商公布费率**；遥测（每日一次匿名心跳+匿名面板浏览事件）默认开启但一个环境变量可关，明确排除 token 数/模型名/prompt/路径。
对 iDoris 启示：这是 §4.6"自己生成 request_id...上游 usage 缺失（订阅 CLI）时标 usage.source=estimated；tokentracker（reqId 去重超算 1.6-3.7 倍）"citation 的精确数据来源，验证了 iDoris"网关计量是权威口径，不存在重复计数"的必要性。**需要特别指出的冲突点**：TokenTracker 对价格未知模型的处理是"显示 $0，等厂商公布"，这与 iDoris 不变式 #3"价格未知≠免费：远程模型价格未知时，要么拒绝，要么按保守上限估算"**直接相反**——TokenTracker 是一个只读统计工具（不介入调用链，错了也不影响功能），而 iDoris 是准入网关（错了会导致免费放行昂贵调用），两者的应用场景不同，iDoris 的 fail-closed 立场应该保留，但这提醒我们**必须在文档里说明为什么 iDoris 的选择比"更宽松"的同类工具更严格**（因为 iDoris 站在准入路径上，后果是资金损失而非仅仅统计误差）。

**㉞ orion-core 实测** — https://blog.mushroom.cv/blog/orion-core-rust-agent-harness-local-llm-teardown/
核心观点：HTTP 后端按"字符数÷4"估算 token，实测中文样本低估 2.0–2.4 倍；一次 6 轮中文对话中，第5轮真实 prompt token 已达 4887（超过默认 4096 预算），估算值只有 2090（不到一半），**一条消息都没有被裁剪**——若服务端上下文窗口较小会直接导致请求出错或被静默截断。
对 iDoris 启示：这是 §4.4"⚠️ 需核查：T2.4 用的 embedding 模型和阈值...中文请求配英文嵌入模型会静默失效"以及 §4.6 token 估算 citation 的**第二组独立数据来源**（与 tare 一文的 chars/4 误差实测互相印证，两篇文章的量级高度一致：tare 报告中文段落误差 2.04–2.37 倍，orion-core 报告 2.0–2.4 倍），构成了非常扎实的证据，强烈支持 iDoris 必须为中文场景使用真实 tokenizer 而非字符数近似。

**㉟ OpenSquilla / ClawRouter / Virtual AI Infra Team / Maka** — 见 2.3 节（同时属于路由与预算两个主题，不重复摘录）。

**㊱ Trinity** — https://blog.mushroom.cv/blog/trinity-abilityai-sovereign-agent-platform-per-agent-docker-audit/
核心观点：每 Agent 独占 Docker 容器 + 四层 RBAC（user<operator<creator<admin）+ **只追加的平台审计日志**（明确设计为"事后可查、不可篡改"）+ **Operator Queue 人在环审批**（Agent 可把审批/提问升级到操作员队列）+ OpenTelemetry 成本/token 追踪；`max_turns` 限制执行深度防失控；数据库默认 SQLite 零配置，生产推荐 Postgres，**切换非黏性非破坏性**（起并行容器复制校验数据、短暂停机切换，原 SQLite 文件全程不被写，回滚只需注释掉一行配置）；通过 UnderDefense 独立渗透测试 Grade A。
对 iDoris 启示："非破坏性迁移"是 §4.3"配置 bundle 时间旅行...可以快照、diff、回滚到 known-good"citation（cohesity/exxperts）之外的又一个具体实现范本，其"起并行实例、复制校验、短暂切换、原文件不被写"的四步法可直接用于 iDoris 未来 SQLite→Postgres（personal→tenant 迁移）的实现设计。Operator Queue 的"人在环"具体交互（UI 或 MCP 回答/批准/拒绝）可用于 iDoris 超额审批队列的接口设计。

**㊲ Claude for Financial Advisors** — https://blog.mushroom.cv/blog/claude-financial-advisors-connector-skill-approval-pattern/
核心观点：Anthropic 官方发布，打包 18 个连接器+8 个工作流技能，**未训练金融专用模型，用的还是通用 Claude**；"投资建议、客户沟通、合规判断仍必须人工审阅批准"，管理性动作（CRM 更新）先"暂存"等待批准；Addepar 集成的"Governed Connector"具体约束是：权限继承（用户在源系统的权限原样延续）、只读、范围限定在四个技能，初版明确不做交易执行/不改数据；作者判断"垂直 AI 的护城河不在训练专用模型，而在谁能把审批和审计做成产品的默认设置"。
对 iDoris 启示：进一步印证"connector+skill+人工审批+审计"是 2026 年生产级 Agent 平台的共识范式（Trinity、Archestra、Claude for Financial Advisors 三个不同层级的产品独立收敛到相似结构），支持 iDoris 把"提议→diff→人批准→版本化→可撤销"（不变式 #6）和超额审批队列作为核心而非可选功能来投入。

**㊳ LoopX** — https://blog.mushroom.cv/blog/loopx-loop-engineering-state-kernel-long-running-agents/
核心观点：长任务状态内核管五件事：目标（objective）/门控（gates）/待办（todos）/证据（evidence）/**配额（quota）**；五个核心原语中 `quota should-run`（该不该行动）和 `quota spend-slot`（为验证过的切片计费）是配对的准入-结算模式；**"安静跳过、预检失败、dry-run 预览不消耗配额；自动轮次必须先检查配额，只有在验证过的回写之后才 spend-slot"**。
对 iDoris 启示：这条"预检/跳过/dry-run 不计费，只有验证通过后才结算"的设计与 iDoris §4.6"被拒、失败、缓存命中都不计费"原则**完全一致**，是又一个独立来源的印证，可以增强该不变式的证据基础。同时提示 iDoris 的 reserve/settle 设计里，"预算检查（should-run）"和"预算消耗（spend-slot）"应该是两个显式分离的调用点，而不是隐式耦合在一次调用里——这个 API 形状值得借鉴。

**㊴ OmniRoute** — https://blog.mushroom.cv/blog/omniroute-free-ai-gateway-290-providers-never-stop-coding/
核心观点：4 层自动 fallback 降级级联：订阅账号（最贵最快）→ API Key（付费但便宜）→ 廉价模型 → 免费模型，触发条件是"配额用完"或"预算触碰"；**三层独立弹性机制**——Layer 1 Provider 断路器（仅 408/5xx 触发，OAuth 3次/API key 5次/本地 2次阈值，60s/30s/15s 后 HALF-OPEN 探测）、Layer 2 Connection 冷却（429 时遵守 `Retry-After`，指数退避，同池其他 key 继续服务）、Layer 3 Model 锁定（一个模型 429/404 只锁定这个模型不影响同 provider 其他模型）；对 Agent/工具透明——始终是同一端点 `localhost:20128/v1`，模型名 `auto`。
对 iDoris 启示：这是 §4.4"三粒度弹性 provider 断路器（HALF-OPEN 探测）/ connection 冷却（遵守 Retry-After）/单模型锁定"citation 的**精确原始出处**，三个粒度的具体阈值和恢复策略可以直接作为 iDoris 断路器实现参数的起点；4 层降级级联（订阅→API Key→廉价→免费）也是 iDoris 预算降级链设计（"降级候选还会二次复核 privacy_class 和 allowed_egress"）可以参照的顺序结构。

**㊵ Krill 拆解** — https://blog.mushroom.cv/blog/krill-mac-mlx-llm-runtime-coding-agent/
核心观点：项目自称"比 Ollama 快 1.57 倍"，但作者自己的基准文档承认单流解码实际打平（0.95倍），真正优势在并发（约2倍）和冷启动（2.9倍）；更关键的是**默认开启的 n-gram 投机解码功能，在项目自己每周跑的真模型一致性测试里连续 6 周（8月2日上线以来全部6次）失败**，而普通 CI（不跑真模型）一直是绿的。
对 iDoris 启示：这是 §4.3"真模型 live 测试层...krill（日常 CI 绿、真模型测试连续 6 周失败）"citation 的精确原始出处，直接支持 iDoris §4.3"真模型 live 测试层"设计的必要性——mock 测试绿不代表真实行为正确，必须有定期真模型回归测试。

## 3. 按议题汇总结论

### 3.1 请求处理顺序（隐私→意图→预算→容量，重点议题）

**结论**：本次调研找到**直接、具体、可操作的证据支持 jason 的质疑**——预算判断不应该无条件排在意图/路径判断之前，至少不应该排在"决定是否需要走外部付费模型"这一步之前。证据链如下：

1. **semantic-router 一文明确把"路径路由"和"模型选择"定义为两层，且要求路径路由必须在最前面、零 LLM 调用、几毫秒完成**：「入口是每一次请求都要过的关卡，必须快、确定、便宜；调一次 LLM 做路由判断本身就违背了"入口要轻"的设计初衷」。它把 RouteLLM（成本相关的模型选择）明确划归"路径已经确定要调用某个模型之后"的第二阶段决策，"把它塞进入口路由会导致'该不该调模型''调哪个模型'这两层决策被压扁成一层，扩展性会很差"。
2. **ClawRouter 和 OpenSquilla 两个独立项目都用本地小模型/规则做复杂度判定，且都强调"不到 1ms/零 token 成本/prompt 从不离开本机做这个决策"**——说明"判断这一步该走本地还是远程"这件事本身可以做到几乎零成本、零延迟，完全不需要经过一次真实的预算判定流程。
3. **Virtual AI Infra Team、OmniRoute 等文章展示的实际生产系统里，"降级/fallback 链条"的触发条件是"配额用完"或"429"，即预算约束是在已经决定要调用某个外部 provider 之后才生效的运行时约束**，而不是在决定"要不要调用外部 provider"之前就先算一遍预算。
4. **openminis 一文指出：纯本地推理场景下"API Key 是字符串 ollama，没有真实凭据，没有泄露风险"**——这从侧面说明，如果一个请求最终判定为可以（或必须）走本地，那么"预算""凭证代理"这两个概念在该请求的生命周期里根本不适用，提前对它们做判断是无意义的开销。
5. **treg 一文给出了一条独立于路由/意图讨论、但结论一致的证据链**：它的凭证解析顺序明确分三级——① 团队自己注册了该 provider 的工具，用团队自己的 key；② 团队存过该 provider 的 secret，注入后转发；③ 前两者都没有，才用 treg 自己的 key，费用记到团队余额，**只有落到第③级才会去检查余额、才可能返回 402**。也就是说，即使不谈"本地 vs 远程"，单纯在"该用谁的凭证/该走哪条 provider 路径"这一层内部，"预算检查"也被放在最后一步，而不是最先做的事。这为"预算是路径确定之后的收尾检查，而非路径选择之前的前置闸门"提供了第五个独立来源。

**具体建议**：iDoris 的准入顺序可以拆分成两个阶段而非一条扁平的四步链：

```
阶段 A（本地、近零成本、必须先做）：
  隐私分级（决定 local_only 还是 any）→ 路径/意图路由（决定走本地哪个角色 or 是否需要外部能力）
       │
       ├─ 本地模型可满足 → 直接进 admission/容量判断，跳过预算闸门
       │
       └─ 判定需要外部 API（能力②）或订阅 CLI（能力①）
                │
阶段 B（只在阶段 A 判定"需要出本机"时才触发）：
  预算闸门（reserve）→ 该外部路径的 admission → 执行
```

这与现有设计文档 §10 P-2 已经拍板的"意图判定层作为能力对外提供...自身兜底推断是 policy 开关"精神是兼容的，**真正需要修改的是 §2 不变式 #1"顺序即语义：隐私→预算→意图→admission→降级"这一句的字面表述**，建议改为："隐私→（本地优先的路径/意图路由）→［若判定需要出本机］预算→［该路径的］admission→降级"。隐私判断仍然必须最先做（因为它决定路由候选集合本身，且必须 fail-closed 收紧），但"预算"不应该是对所有请求（包括纯本地请求）都要过的一道闸，而应该是"进入外部路径分支之后"才触发的闸门。

**反方证据（也如实记录）**：本次调研没有找到任何文章明确论证"预算判断必须在所有路由决策之前"这个立场——OmniRoute、ClawRouter、Archestra 等展示"预算硬上限"的文章，全部是在描述**已经决定要调用某个 provider 之后**的限速/断路器/降级机制，没有一篇把预算判断放在意图判断之前作为通用架构原则。因此可以确定：现有设计文档里"预算排在意图之前"的顺序，**没有本次调研范围内的任何文章作为直接依据**，反而所有相关证据都指向相反方向。唯一需要谨慎的地方是：如果"意图路由"本身的判定成本不可忽略（例如需要调用一个不便宜的分类模型），则先做一个"轻量级预算熔断检查"（比如"账户余额是否为负/是否触发全局 kill switch"这种 O(1) 检查，而非完整的 reserve 流程）作为最外层兜底是合理的——这类似 OmniRoute/Pipelock 里"kill switch 优先级最高、独立于其他决策"的设计。

### 3.2 本地/远程分流

- 判据应该是**隐私分级 + 意图/能力路由**的组合，而非单独的"成本"信号（clawrouter/opensquilla 均以复杂度/语义特征而非价格作为路由主因）。
- "本地"这个词必须拆成"存储位置"和"推理/出站位置"两个独立维度（garmin-mcp-local、exxperts、vitalik 三篇独立得出同一结论）："no vendor cloud, but a model cloud"——数据存本地不等于处理过程不出本机。
- 本地能力①（订阅 CLI）和能力②（外部 API）在"是否需要预算判断"上性质不同：订阅 CLI 通常是包月定额（类似 OmniRoute Tier 1），实际约束是"配额"而非"每次调用的边际成本"，更接近 LoopX 的 quota 模型而非 iDoris 现有的 reserve/settle 逐次记账模型——iDoris 现有设计里"上游 usage 缺失（订阅 CLI）时标 usage.source=estimated"已经注意到这点，建议进一步明确：**订阅 CLI 路径的"预算闸"本质是配额检查（quota should-run），不是逐次金额 reserve**。

### 3.3 隐私检测的误报（FP）与漏报（FN）

- **FP 案例**：Hindsight（端口号/哈希被误判为信用卡）、jarvis-py（唤醒词阈值 0.3 导致 18 条近音词 11 条误触发）。
- **FN 案例**：jarvis-py（RAG 阈值从 0.45 调到 0.6 后，6 个真问题 5 个答案完全没被注入）——这是一个**FP→FN 此消彼长**的典型案例：为了压制"胡编"这一类 FP（低阈值下不相关文档片段被当作依据），把阈值调紧到导致大量真实答案被漏检的 FN。
- **核心结论**：Lethal Trifecta 一文明确指出"95-99% 准确率的分类器不够好"，这意味着 iDoris 的 L1 System-1 隐私分类**永远不能作为唯一防线**，必须叠加 L0 确定性规则（带校验和，如 Luhn，减少 FP）和"脱敏后二次扫描 fail-closed"（减少 FN 造成的实际泄露）。这与 iDoris §4.5 现有设计一致，本次调研为其必要性提供了扎实的实证支持。

### 3.4 脱敏与还原

- 稳定占位符（osaurus 的 `[PERSON_1]`）+ 流式实时还原是业界共识实现。
- **脱敏必须与前缀缓存兼容**——tare 一文的"cache-correct"机制（只压缩/改写缓存断点之后的动态部分，前缀原样不动）直接对应 iDoris"隐私脱敏必须确定性，否则会破坏缓存"citation，建议 iDoris 实现闸一脱敏时也采用同样的"断点检测"思路：同一实体在同一会话前缀部分必须使用完全相同的占位符字节序列，只有新增的后缀部分才允许重新脱敏。

### 3.5 出站审计

- Pipelock 实测给出了具体的"审计能证明什么、不能证明什么"边界："这份证据证明经过代理的流量是什么，不证明 Agent 没法绕过代理"——iDoris 的出站审计设计也应该明确声明这个边界（审计证明的是"网关看到并放行/拦截了什么"，不能证明"调用方没有绕过网关"，绕过网关是 OS 沙箱层的责任，iDoris 边界声明已经写明这一点，本次调研进一步验证其必要性）。
- **HTTPS 请求体是审计盲区**（Pipelock 实测：不开 TLS 拦截时白名单域名内的 POST body 可以携带任意内容包括密钥外泄，出站防火墙完全看不见）——如果 iDoris 未来考虑做内容级出站审计（而不仅是元数据级），必须意识到这个技术边界，代价是需要 TLS 拦截+装 CA，这是相当高的运维成本，可能超出 iDoris 作为"网关"的合理范围（iDoris 本身就是 provider 调用的直接发起方，不存在"看不到自己发出去的 HTTPS body"的问题，这一条主要是给上游 Agent 自己的其他出网提个醒，与 iDoris §4.5"边界声明：Router 只管 LLM 流量"一致）。

### 3.6 凭证代理（Keychain、MITM）

- **onecli 的三段式（占位符→网关匹配→实时解密注入）**、**openclaw-gateway 的按次派发+10分钟TTL+哈希落盘**、**dsh-remote 的"代码层面没有远程读取接口"**，三者共同构成了闸二凭证代理的最佳实践组合：不是"检查权限后放行"，而是"从代码结构上让上层永远没有机会拿到明文"。
- **反面案例**（proma、garmin-mcp-local）都是"只加密/保护部分数据（API Key），其余明文"——iDoris 现有的 SQLCipher 全库加密 + Keychain 主密钥包裹设计（§5.7）优于这两个反例，应坚持不降级。
- Bitwarden/OneCLI 的"密钥不落盘、按需从外部密钥管理器取"模式，可以作为 iDoris personal 模式下 macOS Keychain 集成的进阶选项（如果用户已有企业级密钥管理系统）。

### 3.7 预算（reserve/settle、token 估算、价格未知、订阅额度）

- **reserve/settle 与"检查/结算"分离已是共识**：LoopX 的 `quota should-run` / `quota spend-slot` 明确分离检查和结算两个调用点，"预检失败/dry-run 不消耗配额，只有验证通过后才结算"与 iDoris"被拒、失败、缓存命中都不计费"完全一致，是独立的第三方印证。
- **中文 token 低估问题现在有两组独立的量化数据**：tare（chars/4 对中文低估 2.04–2.37 倍）与 orion-core（同样 chars/4 方法，中文低估 2.0–2.4 倍，含具体逐轮对话数据：真实 5801 vs 估算 2523）。两组数据高度吻合，强烈支持 iDoris 不能用字符数近似，必须用真实 tokenizer（或至少对中文场景应用 2–2.5 倍的保守系数，作为 orion-core 建议的临时缓解方案）。
- **价格未知的处理存在真实的行业分歧**：TokenTracker（只读统计工具）选择"显示 $0 直到厂商公布价格"；iDoris 不变式 #3 选择"拒绝或按保守上限估算"。这不是矛盾而是场景不同——TokenTracker 错了只是数字不准，iDoris 错了是真金白银的资金风险。**建议在 iDoris 文档里明确写出这个对比和理由**，避免未来有人以"TokenTracker 都是这么做的"为由要求放松 fail-closed 立场。
- **三粒度弹性（provider 断路器/connection 冷却/model 锁定）的具体参数**现在有 OmniRoute 的精确数值可参考（OAuth 3次/API Key 5次/本地 2次触发阈值，60s/30s/15s HALF-OPEN 探测间隔）。
- **本地影子价格公式**（hermes-local-rig-accounting：折旧按实际推理小时摊销 + 电费，示例 $0.62/M tokens）已有现成可用的公式模板，可直接移植。

## 4. 与现有设计的冲突或需要修改之处（逐条列依据）

### 4.1【建议修改】§2 不变式 #1"隐私→预算→意图→admission→降级"的顺序表述

**现状**：文档写"顺序即语义：隐私→预算→意图→admission→降级。顺序反了就是漏洞，必须有测试。"

**依据**：
- semantic-router 一文明确论证路径/意图路由应在最前面且零成本零延迟完成，模型选择（预算相关）应在"路径已确定要调用某个模型"之后。
- ClawRouter、OpenSquilla 均把复杂度/路由判定实现为本地零 token 成本操作，与预算判断无关联、无先后依赖。
- 本次调研范围内的全部预算相关文章（OmniRoute、Archestra、Pipelock、Virtual AI Infra Team 等），预算/限速机制描述的都是"已确定调用某 provider 之后"的运行时约束，没有一篇支持"预算判断应先于路径判断"。
- openminis 一文指出纯本地路径根本不涉及真实凭据/预算概念，提前判断无意义。

**建议**：把不变式改写为两阶段表述——"隐私分级（fail-closed，决定候选路由集合）→ 路径/意图路由（本地判定，零成本，决定是否需要出本机）→［若判定需要出本机］预算闸门 → 该外部路径的 admission → 降级"。隐私仍然最优先（因为它约束路由候选集合本身），但预算不再是对所有请求（含纯本地请求）都强制经过的一道闸。保留一个例外：全局 kill switch / 账户余额熔断这类 O(1) 检查可以作为最外层兜底，与 Pipelock/OmniRoute 里"kill switch 优先级最高"一致。

### 4.2【建议补充】"价格未知"的例外说明

**现状**：不变式 #3"价格未知≠免费：远程模型价格未知时，要么拒绝，要么按保守上限估算"。

**依据**：TokenTracker（同类型工具里较主流的一个，1522 stars）选择相反做法："价格未知时统计 token 但成本显示 $0，直到厂商公布费率"。

**建议**：不需要改变 iDoris 的立场（因为 iDoris 是准入网关而非只读统计工具，后果不同），但建议在设计文档里显式补一句对比说明，防止未来被质疑"为什么不像 TokenTracker 一样宽松"时缺乏现成依据。

### 4.3【建议采纳的具体机制，非冲突，是补强】

1. **HTTP 402 结构化预算耗尽响应**（treg）：建议 iDoris 的预算拒绝响应体标准化为包含 `balance_minor`、`estimated_cost_minor`、`topup_hint` 等机器可解析字段，而不仅是文字 reason_code。
2. **审批绑定内容哈希**（openclaw-gateway）：iDoris 未来的敏感操作确认令牌（开启内容记录、开启训练、放宽隐私）应绑定"操作+上下文哈希"的组合，而不是一次性令牌对应任意后续操作。
3. **凭证按次派发+短 TTL+落盘哈希**（openclaw-gateway）：iDoris 闸二凭证代理如果涉及需要缓存的场景，应优先选择短期动态凭证而非长期静态凭证，参照 10 分钟 TTL 的量级。
4. **quota should-run / spend-slot 显式分离**（LoopX）：iDoris 的 reserve/settle API 设计上应该像 LoopX 一样把"是否可以发起（准入检查）"和"扣费结算（settle）"做成两个显式可单独调用、单独测试的接口，而不是隐式耦合。
5. **三粒度断路器的具体参数**（OmniRoute）：可作为 iDoris 断路器实现的默认参数起点（OAuth 3次/API Key 5次/本地 2次阈值；60s/30s/15s 恢复窗口）。
6. **"模型给出的阈值只能收紧不能放松"**（virtual-ai-infra-team）：建议把这条具体机制写入 iDoris 意图/隐私判定层的实现规范——不仅"策略层"不能被模型放宽，连"模型自己建议的置信度阈值"这种更细粒度的输入也要做"只能更严格"的 clamp。
7. **"Context is not history"**（Maka）：建议用这句话精确表述 iDoris 轨迹/审计分离原则中"发给模型的上下文可裁剪、但完整决策证据链不可丢弃"这一容易被误解的细节。
8. **非破坏性数据库迁移四步法**（Trinity）：起并行实例→复制校验→短暂切换→原文件不写，可直接作为 iDoris personal→tenant（SQLite→Postgres）迁移方案的实现模板。

### 4.4 未发现冲突、但证据显著加强的既有设计

- 隐私只能收紧不能放宽（不变式 #2）——omni-open-source-company"权限跟着数据走"、virtual-ai-infra-team"阈值只能收紧"、pentest-harness"自我声明不能放宽授权"三篇独立文章从不同角度印证。
- 可信网关/不可信执行/确定性策略（不变式 #7）——openclaw-gateway 是该 citation 的原始出处，本次调研额外发现其"默认不开启硬化"的重要警示，应在 iDoris 实现时特别注意 fail-closed 必须是默认值而非需要手动开启的选项。
- 不静默（不变式 #8）——jarvis-py"offline 标签下默认联网"反例、krill"CI 绿但真模型测试连续 6 周红"反例，均强化了"配置写了但不会生效就拒绝启动""降级必须在响应头回传"的必要性。
- 日志即运行时（不变式 #9）——maka 是精确原始出处，新增"Context is not history"细化澄清。
- 模型只提议代码判决（不变式 #10）——virtual-ai-infra-team 是精确原始出处，新增"阈值只能收紧"具体机制。
