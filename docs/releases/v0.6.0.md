# v0.6.0 发布说明

>
> 发布资产、tag 提交与 sha256 见 [GitHub Release v0.6.0](https://github.com/iDoris-ai/iDoris/releases/tag/v0.6.0)。

v0.6.0 是 **IDORIS-CORE** 版本（Agent24 [#1937](https://github.com/iDoris-ai/Agent24/pull/1937)）：iDoris 成为 Agent24 的必选核心。launcher 经发现文件找到动态端口，iDoris 向 agent24d 登记并报心跳，由 iDoris 自己探测、拉起并监管本地 oMLX，`/health` 说明「进程活着」与「模型可用」两级状态，并支持 embeddings 与按卡识别 oMLX key。wire 契约升到 **`1.3.0`**，只增不改。

## 版本与范围

- Rust crate（除 `idoris-compute-contracts` 外）和 `/health.version` 是 `0.6.0`；`idoris-compute-contracts` 仍是内部契约 crate，版本 `0.1.0`。
- wire 契约升到 **`1.3.0`**（`/health.contract_version`、发现文件里的 `contract_version`、`GET /admin/api/v1/status` 同值）。1.2.x 的调用方不受影响。
- 范围是 v0.5.0（`01484547`）之后合入 `main` 的所有变更。
- 对应接口规范修订 1.6 与 1.7（[iDoris × Agent24 边界与接口规范](../interfaces/iDoris-Agent24-边界与接口规范.md)）与设计稿 [`idoris-core-design.md`](../design/idoris-core-design.md)。**以规范为准**；规范文件头的勘误一至八记录了实现落地时回填的口径，修订 1.7 记录了与 Agent24 商定的 chat 放行口径。

## 新功能

### 动态端口与发现文件（S1）

- 托管路径下，`IDORIS_PORT=0`、`IDORIS_ADMIN_PORT=0` 被放行，由内核分配端口，iDoris 以绑定之后的实际地址为准；两个监听器仍只绑 loopback。固定端口路径与 v0.5.0 相同。
- launcher 在启动帧里给 `discovery_path`，iDoris 写 0600 的发现文件（实例 id、`instance_nonce`、pid、两个端口、版本、`contract_version`），基于目录 fd 原子写；发现文件被删或改坏时会自愈重写，退出时只删自己写的那一份。
- `instance_nonce` 由 iDoris 每次启动用 CSPRNG 生成，只存在于进程内存和发现文件，不进 `/health`、Admin、日志、argv、环境变量。

### `--launcher-stdin` 启动帧（S1）

- `idoris serve --launcher-stdin`：stdin 读一行 UTF-8 JSON（≤ 4096 字节，LF 结尾，10 秒内读完），帧内 `v` 为 1。它是旧 65 字节 `--admin-token-stdin` 帧之外的第二种帧；**旧 flag 和旧帧完全不变**，两者互斥，同时给出是用法错误（退出码 1）。
- 字段：`admin_token`、`discovery_path`、`register_socket`、`orphan_timeout_s`、`instance_nonce`（仅供确定性测试）、`engine`（`executables`、`stop_on_exit`）。解析严格，未知字段一律拒绝；错误只输出固定文案与原因码，绝不回显字段值。

### 登记、心跳与孤儿退出码 4（S2）

- 帧里给了 `register_socket` 时，iDoris 经 Unix domain socket 向 agent24d 登记（登记协议 v1：HMAC 证明、心跳、会话内可替换 Admin token、`bye`）。
- 帧里给了非 0 的 `orphan_timeout_s` 时，没有已 `ack` 的登记会话超过该时间，iDoris 优雅停止并以 **退出码 4** 退出（Agent24 取 900 秒）。已有另一个健康实例（`instance_conflict`）时退出码为 **3**。
- `bye` 只在优雅停止（信号或退出码 5）且存在已 `ack` 的会话时发送。

### `idoris setup omlx`（S4、S7）

- `--auto`：在本机探测 oMLX（含采纳已在运行的外部 oMLX），生成 oMLX 卡。
- `--managed`：在卡上写 `extensions.idoris_managed`，声明引擎由 iDoris 托管。
- `--no-probe`：不探测，直接写卡。
- `--bind embed=<模型>`：同时生成 **embeddings 伴生卡** `omlx-embed.yaml`（resident 卡，与主卡共用同一个 endpoint）；不给 `embed` 就不生成。主卡保持 `on_demand`，chat 的生命周期内存管理不受影响。`--force` 在这次没给 `embed` 时会把上次生成的伴生卡一并删掉。
- `--auto` 与 `--api-key-stdin` 的互斥已放宽：候选需要鉴权时，先校验监听端口的属主，通过才发 key（见下「安全」）。
- 托管引擎的模型目录取 iDoris 运行用户的 `~/.omlx/models` 并显式传 `--model-dir`。
- **`--force` 保留别的卡**（[#626](https://github.com/iDoris-ai/iDoris/issues/626)，[#633](https://github.com/iDoris-ai/iDoris/pull/633)）：只替换 `omlx.yaml`、伴生卡 `omlx-embed.yaml` 与 `subscription.yaml`，目录里别的卡（例如 `setup upstream` 生成的）原样保留，所以 `setup omlx` 与 `setup upstream` 不再有先后顺序要求。保留的卡与新卡放进暂存目录、用 `serve` 同一个加载器整体校验（`provider.id` 冲突、保留的卡加载不了、默认卡超过一张都报 `validation_failed`，目录一个字节不变）；落盘是事务，同一目录上的并发运行用独占锁排队。
- 输出新增 `next.key_note`：说明 oMLX 的 key 是可选的及取值顺序；`next.needs_env` 的形状不变。
- `GET /v1/models`：指向同一个端点的多张 HTTP 卡（主卡与伴生卡）列出的同一个模型 id 只出现一次，主卡胜出。

### `idoris setup upstream`（S4、S7）

- 为 loopback 的 OpenAI 兼容上游（如 LM Studio）生成一张 resident 卡：`--out-dir`、`--id`、`--force`、`--default`、`--bind`。
- 加载卡时 `serve` 现在会核对 `extensions.idoris_upstream.flavor`（[#626](https://github.com/iDoris-ai/iDoris/issues/626)）：必须存在、格式合法并与 `version_pin` 的产品名一致，否则卡校验失败、`serve` 退出码非 0，说明里带卡文件名与原因码 `upstream_flavor_invalid` / `upstream_flavor_mismatch`。不带 `idoris_upstream` 的卡行为不变。
- `--bind` 接受 chat 角色，也接受 **`embed`**：生成的卡能力为 `[chat, embedding]`，与 Agent24 在 v0.5.0 上手写并实测过的 LM Studio 卡一致；至少要有一个 chat 角色，`rerank`、`vision` 仍拒绝，`embed` 的模型必须在 `/v1/models` 里。

### 引擎管理器（S5，[#632](https://github.com/iDoris-ai/iDoris/pull/632)）

iDoris 自己探测、拉起并监管本地 oMLX，不再要求「先起 oMLX 再起 iDoris」。**只有卡里带 `extensions.idoris_managed` 才生效；没有托管卡时，启动与服务路径与 v0.5.0 一致。**

- **先接管后拉起**：端口上已有外部引擎时只探测，**永不发信号、永不重启、退出时也不停它**；没有时按声明拉起。`kill -9` 之后重启 iDoris，会接管仍在跑的自有引擎，沿用记录里的私有 key，已加载的模型留在内存里。
- **托管拉起**：引擎私有 key 由 CSPRNG 生成，经环境变量传给引擎子进程，不进 argv；每次拉起都传 `--model-dir` 与内存护栏（有额度传 `--memory-guard-gb`，没有额度传 `--memory-guard balanced`），引擎使用 iDoris 自己的私有 base 目录。额度不足 1 GiB 时不拉起（`budget_zero`）。
- **熔断**：失败后按 1、2、4 秒起翻倍、封顶 30 秒（±20% 抖动）退避重启；5 分钟内失败超过 5 次进入 `failed` + `crash_loop`，之后每 60 秒半开重试一次。
- **启动门控**：数据面与 Admin 最先绑定，`/health` 与 Admin `status` 立即回答；门控放行之前，数据面其余路径一律 503 `idoris_starting`（带 `Retry-After: 2`）。所有托管引擎「落定」（就绪，或不会自己好的终局）后才换上完整服务体，在途请求在旧体上跑完。
- **等待有上限与降级放行**：管理器启动后一个启动超时（oMLX 缺省 90 秒）仍没落定的引擎，到点算落定：停掉半拉起的引擎，记 `failed` + `startup_timeout`，门控放行。放行后，没就绪的托管卡不建 Supervisor，路由到它的请求**不发给引擎**，直接 503 `local_only_unavailable`，`error.reason_code` 是该上游在 `/health` 里的 `reason`（`engine_not_found`、`budget_zero`、`crash_loop`、`startup_timeout` 等，不新增错误码）；别的健康卡（resident 卡、`setup upstream` 的自定义上游）照常服务。
- **退出码 5**：门控放行之后，自有引擎进程退出 → iDoris 优雅停止，退出码 5，发 `bye`，一律停自有引擎，由 agent24d 重启。存活判据是进程：引擎活着但暂时不答只报 `unavailable`，不触发退出码 5。外部引擎失效永远只报 `unavailable`。
- **停止**：收到信号后并行 `bye`、停自有引擎（SIGTERM 进程组，8 秒宽限后 SIGKILL）与 HTTP 排空，总预算仍在原 17 秒内。

### embeddings（S7）

- 请求写 `model:"idoris/embed"`，数据 key 的 `allowed_roles` 含 `embed`；通过伴生 resident 卡服务，默认安装下不再是 503。写具体模型名会被当作无角色请求，要求 key 具备全部角色，否则 403 `role_forbidden`。
- 默认 `local_only`：只有可信本地卡（loopback）有资格，响应带 `X-iDoris-Served-Locality: loopback`。
- embeddings 路径的上游响应头超时放宽到 30 秒（聊天、rerank、messages 仍是 10 秒），冷加载 embedding 模型时更宽松。

### 按卡识别 oMLX key（S7）

oMLX 上游 key 的注入由「`provider.id` 等于 `omlx`」改为按卡的引擎种类识别：loopback 的、`engine_kind` 为 `omlx` 的卡才会带 key。自有引擎的端点只用私有 key；外部引擎的端点，环境变量 key 照旧，`~/.omlx/settings.json` 里的 key 只在监听端口的属主校验通过后才给。

### `/health` 新字段（S1、S5）

`status` 仍恒为 `"ok"`（语义是「进程活着」），原有字段不变。新增：

| 字段 | 说明 |
|---|---|
| `phase` | `starting`（门控未完成且仍在进行）、`ready`（门控完成且至少一个 upstream 为 `ready`，且没有托管上游处于终态）、`degraded`（进程正常，但没有就绪的模型服务，或有托管引擎处于终态） |
| `ready` | 等于 `phase == "ready"` |
| `started_at_ms` | 同发现文件 |
| `registered` | 当前是否有已 `ack` 的登记会话；没有 launcher 时恒为 false |
| `upstreams[]` | 每项有 `id`、`engine_kind`、`state`（`ready`、`starting`、`unavailable`、`restarting`、`failed`、`stopped`、`absent`）、`managed`、`owned`，不是 `ready` 时可有稳定的 `reason` |

`/health` 不做任何上游 I/O，响应状态来自后台探测与引擎管理器写入的快照。**任何 `phase` 下 `/health` 都返回 200。**

### 预热 `POST /v1/models/warmup`（S8，[#634](https://github.com/iDoris-ai/iDoris/pull/634)）

数据面、数据 key（不是 Admin）。让一个模型进入「可用」状态，之后第一次真正的请求不用再等加载；不生成任何 token。规范 §2.11.2 与勘误八。

- **请求**：`{"model":"idoris/daily","timeout_ms":120000}`。`model` 必填；`timeout_ms` 可选，整数，1000 到 300000，缺省 120000。多余字段、缺 `model`、`timeout_ms` 不合法一律 400 `unsupported_field`（`reason_code`：`unsupported_parameter`、`unsupported_model`、`invalid_timeout_ms`）；不是 JSON 是 400 `invalid_json`，不是对象是 400 `invalid_body`。
- **选卡**同聊天（角色绑定、隐私、熔断的就绪快照），另有三条：订阅中转卡不参与；请求的能力由角色定（`idoris/embed` 是 embedding，`idoris/rerank` 是 rerank，其余是 chat）；单价非零的卡一律 503 `paid_proxy_unavailable`（预热只服务本地免费卡）。key 的范围与隐私规则与 embeddings 同一个入口，无权是 403，不会加载任何东西。
- **生命周期卡（oMLX）**：与聊天的按需加载共用一段代码（读 catalog、拒绝 catalog 里没有的模型、带余量确认的幂等 load），加载完成即返回；并发的预热与首个聊天请求合并成一次加载。**resident 卡**：发一个最小的真实请求（chat `max_tokens:1`，embedding 输入 `"warmup"`），走与聊天同一个代理，响应头期限是它自己的 180 秒；`idoris/rerank` 选中 resident 卡时 400 `unsupported_field` / `unsupported_model`，什么也不发。
- **200** 返回 `{"model","provider_id","state":"ready","already_loaded","load_ms"}`，带 `X-iDoris-Record-Id` 与 `X-iDoris-Served-Locality`。`already_loaded` 是调用时 Supervisor 账本里它已就绪（尽力而为，不是原子读；resident 卡恒为 `false`）。
- **错误**：400、401、403、404 `model_not_found`、503 `headroom_confirmation_required`、503 `local_only_unavailable`（含 `supervisor_busy`、`load_unconfirmed` 等）、503 `idoris_starting`（门控未放行）、**504 `warmup_timeout`**。降级放行之后路由到没就绪的托管卡直接 503 `local_only_unavailable` 加该上游的 `reason`，别的健康卡照常预热。
- **`timeout_ms` 到点只是放弃等待**：返回 504 `warmup_timeout`，不取消、不缩短任何东西；客户端断开同理。预热自己的超时与客户端断开不留 `load.pending` 围栏；引擎侧的超时或 panic 保持既有的「结果未知」保护（围栏保留，503 `load_unconfirmed`），与聊天一致。resident 的最小请求在自己的任务里跑完，占代理的一个并发许可，504 按既有规则计入提供方熔断。
- **独立的加载超时**：oMLX 的 `load` 调用有自己的超时，缺省 180 秒，`IDORIS_LOAD_TIMEOUT_S` 可改（整数秒，1 到 3600，非法值启动失败并点名该变量）；其他管理调用的超时不变。这对聊天的按需加载同样生效：冷加载大模型不再被 10 秒与 30 秒截断。
- **副作用**：不写用量记录、不碰预算账本；审计写一条 `intent: warmup` 的 `audit.finalized`，完成、超时、客户端取消（`http_status` 499）各恰好一条。
- 首次启用向量召回前应先预热 embedding 模型（见「已知限制」）。

## 兼容性与升级说明

- **wire 1.3.0 只增不改**：1.2.x 的调用方照常使用；新增的是 `/health` 字段、发现文件、登记协议、`POST /v1/models/warmup`（以及 S6 合入后的 Admin `upstreams`，见上）。
- **全新安装**：本版没有升级迁移，也没有备份命令；由 launcher 托管时不支持自动升级，也不承诺回滚（M-IDL2 再做）。
- **没有托管卡的部署**：启动与服务路径与 v0.5.0 一致，不创建引擎管理器。
- **随 Agent24 自动安装**：iDoris 随 Agent24 自动安装、不弹同意（取代旧的 OD-2）；大文件下载仍须用户确认（下载接口本版仍未实现）。
- **与 Agent24 商定的 chat 放行口径**：
  - `phase:"starting"`：有界等待，不要立刻判失败；
  - `ready`、`degraded`：放行 chat 请求（`degraded` 时别的健康卡仍可服务，路由到没就绪托管卡的请求会得到 503 加 `reason_code`）；
  - 全部上游都是终局状态：立即 503，带 `reason`；
  - `/health` 在任何 `phase` 下都是 200；
  - **Agent24 的 30 秒启动窗口不得要求 `phase`**：门控等待最长可达一个启动超时（缺省 90 秒），启动窗口内只应判「`/health` 能答」，模型可用性另看 `phase`。
- **行为变化**：`IDORIS_PORT=0`、`IDORIS_ADMIN_PORT=0` 在托管路径下不再被拒；`/health` 响应多了上述字段；没设 `IDORIS_FORM` 时云相关路由仍不挂载。

## 安全

- **监听端口属主校验（[#619](https://github.com/iDoris-ai/iDoris/issues/619)）**：向引擎发 key 之前，先用 `lsof` 找到监听者，要求 uid 等于当前用户且 `codesign --verify` 通过、TeamIdentifier 为 oMLX 的发行团队；不符则不发 key、不接管，报 `port_in_use`。落地范围是**引擎管理器与 `setup`**，非托管卡的数据路径见「已知限制」。
- 自有引擎的私有 key 只在进程内存、引擎子进程环境和 0600 的所有权记录里，别的进程不带这个 key 访问该引擎得到 401。

## 依赖与 CI

- 没有依赖升级：v0.5.0 到本版 `Cargo.lock` 里只有 iDoris 自己的 crate 版本号变化，`deny.toml` 与 pnpm 锁文件也没有改动。
- `release.yml`：`cargo test` 用 `RUST_TEST_THREADS=2`（macos-latest runner 慢，满并行时短超时集成测试偶发失败）；build job 从已下线的 `macos-14` 改为 `macos-latest`，与 `ci.yml` 一致。
- `scripts/test_onboarding_smoke.py`：子进程用临时 `HOME`，不再读开发机真实的 `~/.omlx/settings.json`；版本钉到 0.6.0。
- **测试稳定性**：起真二进制的集成测试统一用 `ChildGuard`，测试失败时不再留下占着端口的孤儿进程（[#623](https://github.com/iDoris-ai/iDoris/issues/623)、[#629](https://github.com/iDoris-ai/iDoris/pull/629)）；对墙钟时间敏感的测试放宽阈值或改按事件而非固定时间校验：自愈日志节流（[#628](https://github.com/iDoris-ai/iDoris/pull/628)）、发现文件 `codesign` 探测遇 `ETXTBSY` 有界重试（[#627](https://github.com/iDoris-ai/iDoris/pull/627)）、登记 UDS 断线用例接受 `write_failed` 与 `disconnected` 两种合法观察（[#636](https://github.com/iDoris-ai/iDoris/pull/636)）、warmup 与进程内测试在负载翻倍时也站得住。这些不改变运行行为（#627 的重试只作用于探测）。

## 真机验证

在开发机（Apple Silicon，真实 oMLX）上验证了托管路径：

- **托管冷启动约 8 秒**：从 `idoris serve` 启动到托管的 oMLX 就绪、`/health.phase` 为 `ready`，约 8 秒（远低于缺省 90 秒的启动超时）。
- **`kill -9` 之后接管约 2 秒**：杀掉 iDoris 后重启，接管仍在运行的自有引擎、沿用记录里的私有 key，约 2 秒回到 `ready`，已加载的模型留在内存里。
- 单机一次结论，不是性能承诺；不同机器与模型大小会不同。D10（私有 key 优先）是否也在真实 oMLX 上验过，见「已知限制」第 6 条。

## 已知限制与后续跟进

1. **降级放行之后，坏引擎要重启 iDoris 才恢复**（v0.6.1 热恢复）：放行时没就绪的托管引擎冻结，不再半开重试，也不接受 `start`/`restart`；原因是 Supervisor 表在放行时整体创建，之后引擎好了也读不到。门控放行之后，自有引擎进程退出则以退出码 5 让 agent24d 重启 iDoris。冷启动超过启动超时（缺省 90 秒）的引擎不会再重试一次，要重启 iDoris。
2. **非托管卡的数据路径 [#619](https://github.com/iDoris-ai/iDoris/issues/619) 仍是 v0.5.0 的行为**（[#631](https://github.com/iDoris-ai/iDoris/issues/631) 跟踪）：`proxy.rs` 的 resident 代理、`OmlxAdapter`、`/v1/models` 对静态配置里 `settings.json` key 的使用，没有加端口属主校验。
3. [#626](https://github.com/iDoris-ai/iDoris/issues/626) 已由 [#633](https://github.com/iDoris-ai/iDoris/pull/633) 修复（见「`idoris setup omlx`」与「`idoris setup upstream`」）；`setup` 落盘用 `hard_link`，不支持硬链接的卷上以 `write_failed` 失败并回滚到原样。
4. **每种引擎只托管一个实例**：同种的两个实例会共用同一个私有 base，oMLX 会把命令行设置落盘互相覆盖；多实例与多引擎切换（`make_default`）是预留（规范 §2.12），本版只实现 oMLX。
5. 引擎活着但永远不答，不会被自动处理（不转成退出码 5）；要人去重启。
6. resident 的 embeddings 路径绕过 Supervisor，embedding 模型的内存不在 iDoris 的账本里，由 oMLX 自己的内存上限兜底（托管引擎有 `--memory-guard-gb`）；冷加载 embedding 模型可能较慢，首次启用向量召回前应先调用 `POST /v1/models/warmup` 预热。预热的 `already_loaded` 信任 Supervisor 的账本：引擎在 iDoris 不知情时换代（例如外部引擎被用户重启）之后会过期，这是降级放行后「不热恢复」同一个限制（v0.6.1）。
7. D10「私有 key 优先于 `OMLX_API_KEY` 环境变量与 `settings.json`」只用假引擎验证过，没有在真实 oMLX 上跑过。
8. 只提供 aarch64-apple-darwin 一个平台；没有升级迁移和备份命令。
9. 下载接口仍未实现（规范 §2.9 只冻结了归属）；[#609](https://github.com/iDoris-ai/iDoris/issues/609) 的跟进项仍在。
10. 沿用 v0.5.0：计算服务云形态没有可用上游，不能对外承诺 idoris.ai/api 可用；[#601](https://github.com/iDoris-ai/iDoris/issues/601) 仍待处理。
