# v0.5.0 发布说明

> 发布资产、tag 提交与 sha256 见 [GitHub Release v0.5.0](https://github.com/iDoris-ai/iDoris/releases/tag/v0.5.0)。

v0.5.0 带来两件事：一是 **idoris.ai/api 计算服务的第一版**（云、组织、个人三种形态共用一套代码）；二是 **wire 契约 1.2.0**，让 Agent24 能向 iDoris 询问「这台机器的 chat 用哪个模型」，并列出本机已有的模型。

**计算服务现在还不能对外提供服务**：云形态没有可用的上游，详见下文「上线前仍需人去做的事」。

## 版本与范围

- Rust crate（除 `idoris-compute-contracts` 外）和 `/health.version` 是 `0.5.0`。`idoris-compute-contracts` 是这一版新增的内部契约 crate，版本仍是 `0.1.0`，它不是对外发布的产物。
- wire 契约升到 **`1.2.0`**。这一版只做了加法，1.1.x 的调用方可以照常使用。
- 范围是 v0.4.0 之后合入 `main` 的所有变更。

## 计算服务 idoris.ai/api 第一版（[#600](https://github.com/iDoris-ai/iDoris/pull/600)）

三种形态共用同一套代码，用环境变量 `IDORIS_FORM` 切换：云（idoris.ai/api 对外）、组织（后端自己部署）、个人（本机）。

| 切片 | 内容 |
|---|---|
| S0 | 契约 crate `idoris-compute-contracts`：微单位金额、账户树、凭证、五项准入、7 状态 49 格的状态机、许可表 |
| S1 | 账户存储：主体、成员关系、付款账户委派树、凭证、额度 |
| S2 | 控制面 `/control/v1`、设备配对、`idoris control bootstrap` |
| S3 | 准入账本：沿祖先原子检查，预留、结算、释放、过期，只追加分录 |
| S4 | 云上游：按许可表选端点，多次尝试，结算按尝试记 |
| S5 | 云入口 `/api/v1`：凭证推导租户，`X-iDoris-Member`，三级限流 |
| S6 | 儿童安全管线：规则检查器 + LLM 检查器，输入输出双向拦截 |
| S7 | 本地和组织的云端档：本机服务不了时经显式同意回落到云端，`idoris cloud pair/status/unpair`，对账游标 |
| S8 | 调研与运维：端点核验、正式许可表、泰国合规调研、Litestream 运维与恢复演练、泰语 edu 评测集与本地基线报告 |

owner 拍板的几条口径（已写进代码与设计稿附录）：

- 已发送尝试的上游报 0 用量就收 0。
- 儿童租户默认必须配 LLM 检查器；`rules_only_acknowledgement`（原因、确认人、最长 90 天）可以显式放宽，到期后运行期也生效。
- 客户端发来的 assistant 历史：自伤表达交给输出规则和 LLM 检查器；索要方法、越狱指令仍按输入规则拦；跨句否定保持严格。
- 只靠授信的账户，新额度照常可花但不抵旧债（方案 C）。
- 控制面 `/control/v1` 只给后端，永远不发 CORS 头。

### 对存量部署的影响

不设 `IDORIS_FORM` 时，控制面、云入口、云端档都不挂载，HTTP 路由和响应不变；wire 1.1.0 的已有字段、launcher 契约、`/capabilities`、Admin v0、`deploy_mode`、`X-iDoris-Tenant` 都没改。但有**三处变化**，升级前请知道：

1. 启动时会拒绝含 `tenant_bootstrap` 行的数据库。
2. 新增的数据库迁移会建 `tenant_bootstrap` 表。
3. 预算记录改为记在真实的 key 和模型名下（原来记在 `default` 与 `model_id` 下）。

### 上线前仍需人去做的事

- **云形态目前没有可用的上游。** 许可表 17 条端点全部是 `dpa: unsigned`、`allowed_data_classes` 为空，所以连成人请求都没有可用上游，今天没有一个端点能合规承接 `child_edu`。需要有人去谈 DPA 和服务订单，见 `docs/design/compute-service-endpoint-verification.md` 第 8 节。**不能对外承诺 idoris.ai/api 可用。**
- 泰国 PDPA 第 20 条等结论需要泰国律师复核，见 `docs/design/compute-service-compliance-research.md`。
- 间接跑在 AWS 上的上游按禁止处理。
- 慢速攻击（极慢地发请求头）的超时由反向代理负责，上线时必须配好。
- 设计稿附录列出的其余「暂定理解」仍待 owner 逐条确认。

## wire 契约 1.2.0：本机 chat 模型推荐与本地模型列表（[#604](https://github.com/iDoris-ai/iDoris/pull/604)）

对应接口规范 §2.9（修订 1.4，[#602](https://github.com/iDoris-ai/iDoris/pull/602)，与 Agent24 双方确认）。只有新增。

| 接口 | 说明 |
|---|---|
| `GET /v1/recommendation?role=chat` | 按物理内存（GiB，左闭右开）分档推荐；推荐的模型放不下时按 35B → 27B → 8B 回落（`fallback_does_not_fit`），全放不下时 `model_id: null` 加 `insufficient_memory` |
| `GET /v1/models/local` | 只读扫描 `~/.omlx/models`，`kind` 按 catalog → `config.json` 推断 → `unknown` |
| `idoris recommend --role chat --json`、`idoris models local --json` | 与 HTTP 是同一个序列化结构；不开数据库、不取实例锁、不需要 serve 在跑、不读任何密钥 |

- 两条 HTTP 路由挂在全局鉴权之后，与 `/v1/models` 同级；只读，不加载、不下载、不改状态。云形态不挂。
- 档位：16 / 24 / 32 GiB 推荐 `Qwen3-8B-4bit`；48 GiB 及以上推荐 `Qwen3.8-27B-OptiQ-4bit`；64 GiB 及以上另可选 `Qwen3.6-35B-A3B-OptiQ-4bit`；不足 16 GiB 时，只有 8B 放得下才推荐。
- `role` 目前只支持 `chat`；缺省、重复、大小写不对都是 400 `unsupported_role`。
- 「放得下」按 iDoris 的内存公式算：权重 + 8k 上下文 KV 上界 + 1 GB，并且物理内存不低于 catalog 的 `min_ram_gb`。设置了 `IDORIS_ALLOCATED_BUDGET_BYTES` 时按该额度，否则按自探的可用 GPU 内存。
- 本地模型必须「完整」才会列出：`config.json` 可读、至少一个权重文件、分片齐全、没有下载残留。符号链接不跟随。
- CLI 的额度：`--allocated-budget-bytes` 优先，否则读 `IDORIS_ALLOCATED_BUDGET_BYTES`，格式错误退出码为 1。
- `config/catalog.yaml` 只给 `qwen3-8b`、`qwen3.6-35b-a3b`、`qwen3.8-27b` 加了 `omlx_id` 与 `kind`；现有的推荐与 `/capabilities` 不读这两个字段。
- **下载这一版没有做。** 规范里「下载归 iDoris、必须由用户确认」只冻结了归属，接口形状待另行修订。

## oMLX 密钥解析顺序（[#605](https://github.com/iDoris-ai/iDoris/pull/605)）

iDoris 连 oMLX 时，key 按下面的顺序取：`IDORIS_OMLX_API_KEY`（不变）→ `~/.omlx/settings.json` 的 `auth.api_key` → 无鉴权连接。

- **文件里的 key 只发给 loopback 的 oMLX**：base URL 不是 loopback 时视为没有这把 key。环境变量的 key 维持原行为。
- `settings.json` 必须是常规文件（符号链接、FIFO、设备都不算），key 取 trim 后的值；读不了、不是 JSON、值不是非空字符串、含内部空白或控制字符、超过 64 KiB 的，一律当作没有，不报错、不记日志。
- 每次调用重新读取，不缓存，改了文件不用重启。不打印、不写日志、不进 argv 或响应体。
- 生命周期适配器、常驻代理、模型列表三处都走这个统一入口。oMLX 回 401 / 403 时，常驻代理的 502 `upstream_auth_failed` 现在带 `remediation`（写明两处 key 来源，不重试）。
- `idoris setup omlx` **不变**：§2.7 冻结了「key 只从 stdin 读入、只用于探测」。
- **行为变化**：没设环境变量、但本机 `~/.omlx/settings.json` 里配了 `auth.api_key` 的用户，iDoris 现在会带上这把 key。以前是无鉴权连接，开了鉴权的 oMLX 会返回 401。

## 计算服务的评审后修复（issue [#603](https://github.com/iDoris-ai/iDoris/issues/603)）

#600 合入后，PR-Daemon 提出了 N1–N7 七条非阻塞发现，拆成三个 PR。这一版包含其中两个：

- **鉴权前限流按来源分份额**（[#607](https://github.com/iDoris-ai/iDoris/pull/607)，N3、N4）：
  - 配对失败限速原来是全局一个桶，一个来源每分钟发约 20 个垃圾码，所有租户的合法配对就都被拒。现在单来源每分钟最多 20 次「猜错」，另有全局总闸 600。
  - 未知前缀的认证预算原来是全局一个桶，一个来源刷随机 key 就能让冷的合法 key 全部 429。现在先扣来源份额（默认每分钟 120、突发 20，配置键 `abuse.per_source_auth_unknown`），再扣全局总闸；「已知 key」表从 FIFO 改为 LRU。
  - 来源的取法：云形态用控制面边缘按受信代理规则算出的客户端来源，组织形态只用 TCP 对端；客户端自己写的 `X-Forwarded-For` 等头不信；IPv6 取 /64。
  - 代价：共享出口（学校、公司）下，一个人刷垃圾请求会让同一出口上别人「冷」的凭证在份额用完后拿 429；认证成功过的凭证不受影响。
- **隐私取值、`extra_body` 白名单与 id 探测**（[#608](https://github.com/iDoris-ai/iDoris/pull/608)，N5、N6、N7）：
  - 请求体顶层 `privacy` 或 `metadata.privacy` 写了 `any` / `local_only` 以外的值，现在和请求头一样返回 400 `invalid_privacy`，不再被当作「没声明」而可上云。`metadata.privacy` 里调用方自己的标签也会因此被拒。
  - `extra_body` 从黑名单改为白名单：顶层只收 `provider`，里面只收布尔值的 `zdr`、`allow_fallbacks`，其余在加载时报错。正式许可表与示例配置里没有端点写 `extra_body`，不会拒掉现有配置。
  - 没有某项操作权限的调用者，对已存在和不存在的成员关系、额度、凭证 id 得到同一个答案，不能再靠错误码探测 id 是否存在。
  - 文字与注释更正：「还可用的设备随时有权离开自己的账号」；`executor.rs` 里过时的注释。迟到结算的用户份额标签行为没改，只加了测试锁住。

## 已知限制与后续跟进

- 只提供 aarch64-apple-darwin 一个平台。
- 没有升级迁移和备份命令；由 launcher 托管时不支持自动升级，也不承诺回滚（M-IDL2 再做）。
- 计算服务云形态没有可用上游（见上）。
- [#601](https://github.com/iDoris-ai/iDoris/issues/601)：充过值的账户也要按方案 C 记账。现在只靠授信的账户是对的；充过值的账户仍按 `min(余额, 额度剩余)`，余额被花成负数后新发的免费额度花不出去。另外，旧债未清时 `credit_used` 告警金额按净头寸算，对担保人是噪声。
- [#603](https://github.com/iDoris-ai/iDoris/issues/603) 里 N1（流式用量可信度，上线付费流式前必须修）、N2（儿童安全 assistant 历史，仅 rules-only 租户）尚未修复，修复在 [#606](https://github.com/iDoris-ai/iDoris/pull/606)，未随本版合入。
- [#609](https://github.com/iDoris-ai/iDoris/issues/609)：§2.9 推荐与 oMLX 密钥的跟进项，其中损坏的 `config.json` 仍报已安装、符号链接模型目录显示未安装、`fits` 设了额度时不扣 1 GB 余量，要在「下载」切片之前定下来；`settings.json` 检查与打开之间的 TOCTOU 也在其中。
