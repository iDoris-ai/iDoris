# v0.3.2 发布说明

> 发布资产、tag 提交与 sha256 见 [GitHub Release v0.3.2](https://github.com/iDoris-ai/iDoris/releases/tag/v0.3.2)。

安装与首次调用仍按 [v0.3.1 操作指南](../安装与首次调用-v0.3.1.md)，把文中的版本号换成 `0.3.2` 即可。v0.3.1 的完整变化见 [v0.3.1 说明](v0.3.1.md)。

## 版本与范围

Rust crate 和 `/health.version` 为 `0.3.2`，wire 契约仍是 `1.0.1`（`CONTRACT_VERSION` 不变）。这是只含一个修复的补丁版本，范围为 v0.3.1 之后合入 `main` 的变更。

## 修复

- **resident HTTP 卡带上 oMLX key**（[#583](https://github.com/iDoris-ai/iDoris/pull/583)，关闭 [#582](https://github.com/iDoris-ai/iDoris/issues/582)）：
  - provider id 为 `omlx` 的 resident 卡，转发到上游时会带上 `IDORIS_OMLX_API_KEY`（Bearer）。v0.3.1 里 oMLX 一开认证，这条路径就会返回 401。
  - 上游返回 401/403 时，统一映射为 `502 {"error":{"type":"upstream_auth_failed","reason_code":"upstream_auth_failed"}}`。iDoris 只看状态码就做出判断，丢弃上游的响应体，所以上游内容和 key 都不会透传给调用方。
  - 上游鉴权失败不计入 provider 熔断器的故障。key 配错时，熔断器不会打开、也不会挡住后续的正常请求；buffered 和 streaming 两条路径的行为一致。

## 对调用方的影响

- Agent24 等调用方应把 `502 upstream_auth_failed` 当作**终态**处理：不重试，不换 provider，提示用户检查 oMLX key。
- 默认打包的 on_demand 卡行为没有变化。

## 已知限制

和 v0.3.1 相同（`temperature` 被拒绝、没有 launcher、内存额度不限制外部 resident 服务、推荐器选项还没有经 HTTP 暴露），见 [v0.3.1 说明](v0.3.1.md#已知限制)。

## 与 Agent24

Agent24 [`v0.6.0-preview.20261028.1`](https://github.com/iDoris-ai/Agent24/releases/tag/v0.6.0-preview.20261028.1) 配对的是 v0.3.1。Agent24 会接入 `upstream_auth_failed` 终态处理，之后再把配对版本更新到 v0.3.2。在那之前，v0.3.1 和 v0.3.2 都满足它的 `contract_version == "1.0.1"` 检查。
