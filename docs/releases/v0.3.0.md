# v0.3.0 发布候选与迁移

本文件描述待审候选；发布状态以 GitHub Releases 为准。发版仍需独立批准、
合并 M4 尾栈及安全回移，并在实际 main 重跑验收后打 tag。

## 版本与能力

- Rust crate 版本统一为 `0.3.0`，发布包 `/health.version` 与 tag 对齐。
- M4 wire 契约为 `1.0.1`；`/v1/inspect` 的 `1.1.0` 升级属于后续 M5。
- M4 包含 Event Log 查询与审计投影、实际就绪模型选路、只读 Admin v0，
  以及 virtual key 的 tenant 绑定与可信审计归属。Admin v1 写接口仍待审。
- tenant 模式的监听范围仍为 loopback。

## Tenant key 升级

升级前停止 Router，并备份服务使用的 SQLite 数据库；显式配置时使用
`IDORIS_DB_PATH` 指定的文件。服务与发 key 命令必须使用同一数据库。

迁移 0002 为已有 key 增加可空的 `tenant_id`。旧 key 保留为未绑定；
不会从 `owner` 或 `budget_ref` 推断租户。tenant 模式拒绝未绑定 key，
因此需要按各调用方原有权限重新签发。例如，保存以下内容为本地 spec：

```json
{"owner":"agent24","tenant_id":"acme","allowed_privacy":["local_only"],"allowed_roles":["fast"]}
```

```bash
IDORIS_DB_PATH=/path/to/idoris.sqlite3 ./idoris key issue --spec-stdin < tenant-key.json
```

将输出中的 `secret` 配置给对应调用方；请求同时发送 `Authorization: Bearer …`
及唯一的 `X-iDoris-Tenant: acme`。tenant 必须与 key 的显式绑定一致。
发 key 的本地 JSON/命令输出不要提交到仓库。检查调用方后再启用新服务。

已撤销或过期的 key 返回 401；未绑定、跨租户或重复 tenant header 返回
403。成功缓存不会绕过新请求的鉴权。个人模式可以继续使用未绑定 key。
显式绑定到其他 tenant 的 key 不能用于个人模式；显式绑定 `personal` 的 key
可以用于个人模式，携带 tenant header 时必须唯一且同为 `personal`。

## 发布验收

执行仓库 Rust/TS 门禁、`bash scripts/conformance-rust.sh` 和发布 archive
smoke。包需包含二进制与四个运行配置文件；在仓库外、无 `IDORIS_*` 配置的
隔离测试用户目录验证 `/health.version == 0.3.0`。不得以候选分支验证代替
真实 main 的最终验收。
