# idoris.ai/api 设计稿 Codex 挑战评审记录

- 评审对象：`docs/design/compute-service-brainstorm.md`，分支 `feat/compute-service` @ `58462ce6`
- 评审方：Codex，经 Claude Code 的 codex 插件子代理调用。子代理没有报告具体用的哪个模型、跑了几轮。
- 日期：2026-11-05
- 方式：只读静态评审，对照了现有代码；没有跑负载测试
- 总体结论（原文）：**有条件满足**。「一套代码、三种形态」可以成立，账户树也可以作为额度委派结构。但共享代码不意味着共享密钥、共享身份、跨节点共享事务，也不意味着天然共享同一种计量单位。
- 作者核实：评审引用的 5 处代码事实已逐一核对，全部属实：
  - `router/budget.rs:50,202` 把 key 维度写死为 `"default"`；
  - `lib.rs:788,1023` 的 `paid_proxy_unavailable`；
  - `lib.rs:500` 在租户模式下强制要求 `X-iDoris-Tenant`；
  - `storage.rs:224` 的 `retain_tenants`；
  - `key_issue.rs:122` 拒绝非空 `admin_scopes`。

每条的处理结果见定稿 `compute-service-design.md` §14。

## Blocker
- **B1 开通流程没有可信身份链。** 学生的浏览器能复制出长期 `vk_` 密钥；安装实例重建后可能重复领取额度。建议：P0 由 eduai 后端代理，后端持有服务凭证并提交可信的假名成员 id；如果必须直连，改用后端签发的短期、限定用途的凭证；明确开通主体、稳定 id、发放幂等键和撤销流程；安装 id 只能辅助风控。
- **B2 真实密钥和模型还没接入预算。** `BudgetScope::new(tenant_id, DEFAULT_KEY_ID, provider_id, provider_id)` 中，`DEFAULT_KEY_ID == "default"`。建议 S1 打通从鉴权身份到预留、结算、审计的整条链；`account_id` 决定谁付费，key / provider / model 用于授权、细分限额和归因。
- **B3 付费流式和失败切换没有结算闭环。**
  - 现状：付费流式直接返回 503；remote 的流式抽象里没有 usage；执行结果不确定的请求会一直占着预留直到过期。
  - 风险：A 上游已经执行、再切到 B，会产生两笔成本；已经向客户端输出了部分内容，就不能再透明切换。
  - 建议：每次上游尝试单独记录；切换前按新候选重新准入；不确定的成本保留待核销；首字节输出之后禁止透明重放；如果暂时不做，就显式限定为非流式。
- **B4 overage 只是费用事实，不等于有担保的宽限。** 预留过期后的迟到结算可以突破宽限边界。建议把实际成本、用户可扣金额、担保责任分开记账；准入时原子占用所有祖先账户的额度、信用和速率；宽限资格单独设定。
- **B5 儿童输出过滤没有定义「什么时候算已发出」。** 流式输出是先转发再检查，等检测到问题时内容已经送达孩子。建议：P0 edu 先完整检查再发布；安全服务出错时一律拒绝放行；安全策略绑定租户属性，不能只依赖 `edu-*` 别名；安全调用本身计入成本。

## High
- **H1 一棵账户树扛不住身份、成员关系和付款三种关系。** 建议把主体、成员关系、付款账户、凭证拆开；每个请求只对应一个付款上下文；本地密钥、云凭证、Admin token 各自独立。
- **H2 组织作为一个云账户可行，但这样云端就做不到成员级隔离。** 建议：云端只认组织付款账户；组织按节点或用途分别发受限凭证；对账靠尝试 ID、不可变账目和幂等游标；P0 不允许离线节点自行增加云端额度。
- **H3 「钱只是配额来源」缺少单位系统。** 建议用带类型的金额 / 配额：单位、精度、用途、有效期、不可转让；cost 和 price 各自带币种；明确额度下发是「转移余额」还是「授权上限」。另外，按请求向上取整在小额调用上会明显失真。
- **H4 启动时的配置对账（`retain_tenants`）会删掉在线开出的租户。** 建议 S1 同时把数据库定为权威来源，并做好初始化迁移；验收覆盖「在线开户 → 重启 → 仍可用」。
- **H5 `admin_scopes` 目前只是一个字段，签发时会被拒绝；组织局域网也不能默认互信。** 建议按「操作 × 资源范围」做授权，下发权限不得超过授权者本人；Admin v0 保持只读、只在 loopback 上监听。
- **H6 假名 id 加一个「已同意」标记，执行不了儿童数据的生命周期。** 孩子仍可能在 prompt 里写进个人信息；撤回同意后凭证要立即失效。建议由 eduai 提供处理资格和撤销状态；财务担保人和同意主体分开。（法律条款未核实。）
- **H7 ZDR 不能只是一个布尔标签。** OpenRouter 区分 ZDR 和 Safety Retention；DeepInfra 官网说明基础设施在美国。建议维护端点级许可表（区域、留存、DPA、允许的数据类型、核验时间）；兜底也必须满足全部约束，没有合规候选就拒绝。
- **H8 「不记录正文」要覆盖缓存和运维链路。** 现有代理缓存里存着完整响应 body。建议写清内存处理、缓存时限、禁止落盘和清除机制，并扫描整条链路。
- **H9 SQLite 可以作为 P0 候选，但「持续备份 + 高可用」没有具体含义。** 现状是单连接 Mutex 加实例独占锁。建议明确单活动写节点、持久卷、恢复流程和 RPO/RTO；不要把备份叫作高可用。
- **H10 免费额度缺平台总支出硬上限。** 学校共享出口时，按 IP 限速会误伤。建议平台、租户、担保人、成员、凭证各有日 / 月上限和在途上限；补贴池原子扣减。

## Medium
- **M1 普通 OpenAI 客户端只配地址和密钥会报 400**，因为租户模式要求 `X-iDoris-Tenant`。建议云入口从密钥推导租户，本地契约保持不变。
- **M2 remote / oMLX / subscription 只是可复用的部件。** remote 转换会丢 tools 和 usage；subscription 走的是 CLI，不能进云端。建议按能力矩阵补齐云供应商契约，云端显式排除 subscription。
- **M3 S1–S8 顺序要调整。** 单位语义要先于配额和授信定下来；失败切换放在 P0 还是 P1，前后写得自相矛盾；S8 评测应该从第一天开始。
- **M4 「本地优先」拓扑有两种画法**：一种是云调用用户 Mac，一种是本地调用云。建议只保留「本地 / 组织主动调用云」；`local_only` 必须失败即关闭；写清 P0 Agent24 怎么消费云端。
- **M5 经济性方向合理，但数据不够支撑确定性结论。** 「3–10 倍」推不出来；50 人每月 $20 没算安全检查和重试；671B 需要 8 张 H200 这一点未核实。建议按「同模型、同质量、同服务目标」比较，用首个班级的真实数据验证。

## Low
- **L1** §2.4 仍把 DeepSeek 官方列为主力，和儿童数据限制冲突。建议用一份权威路由矩阵取代。
- **L2** 降级响应头目前是尽力而为，还不是契约。建议预算降级、容量降级、上游故障各用稳定的原因码，并定义浏览器可读的响应头。

## 评审方列出的必写架构要点
部署拓扑、控制面独立、身份与付款边界、账本边界、计量语义、请求状态机、儿童数据的信任边界、上游许可、运维边界、上线验收。全部已写入定稿 §2–§13。
