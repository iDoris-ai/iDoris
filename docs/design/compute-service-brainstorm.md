# idoris.ai/api 综合 AI 计算服务：脑暴与架构草案

> 状态：脑暴稿（2026-11-05），分支 `feat/compute-service`。§8 的产品决策已经由 owner 拍板（2026-11-05）；§9–§11 是在这些决策之后补的。还不是规范，也没有排期。
> 定位：给 **eduai**（教育）和 **Agent24**（办公 agent）供应 token 的「迷你 OpenRouter」。对外接口兼容 OpenAI，调用方只拿三样东西：**接口地址 `https://idoris.ai/api/v1`、密钥、模型名**。算力来自别人的硬件：token API、按需 GPU、租赁 GPU，再加上用户自己的 Mac。
> 价格数据大多来自第三方聚合站，只有 Modal、RunPod 来自官网。各家口径和日期不一致，下单前要逐家核对（见文末来源）。

---

## 0. 先说结论

1. **方向可行，但第一阶段不要租 GPU 自己部署模型。** 量小、峰谷明显时，自建的单位成本是 token API 的 3–10 倍。开源旗舰模型（DeepSeek V3.2 这一级，约 671B）至少要 8 卡 H200 才跑得起来，一小时 $30–40，iDoris 这点量根本跑不满。
2. **iDoris 的价值不在聚合模型。** OpenRouter 已经把广度做到头了。我们的价值在于：**场景别名 + 账户层级 + 预算与信用 + 本地优先**。所以 OpenRouter 应该当我们的一个兜底上游，而不是竞争对手。
3. **最佳供应商组合（按阶段）**
   - P0（泰国首发）：开源模型 token API 为主。DeepInfra 为主力，OpenRouter 的零数据留存（ZDR）路由兜底；Agent24 的成人用户还可以直连 DeepSeek 官方。未成年人数据不发往 DeepSeek 官方 API，见 §9。另加用户本机 Mac 或组织 Mac（oMLX，iDoris 已经支持）。硅基流动留到国内上线时再用。
   - P1：自定义小模型（内容安全、ASR/TTS、微调过的 edu 模型）放到 **Modal**。它能缩到 0，按秒计费，每月送 $30。
   - P2：等某个模型的持续用量超过盈亏线（见 §2.3），再按单个模型租 **RunPod** 的 pod 跑基线。
   - **Vast.ai** 只跑离线批处理、而且是不敏感的数据，**绝不碰未成年人数据**。
4. **「负值 / 部分信用」可以做，但必须有上限、有人担保、有速率闸门。** 否则 agent 一次失控循环，几分钟就能把信用额度打穿。体验上的正解是「**余额不够先降级，不直接拒绝**」，而不是「允许欠钱」。
5. **最大的风险不在技术**。泰国首发时主要有三件事：
   - PDPA 对未成年人数据的要求（监护人同意、数据最小化、跨境处理）。
   - 泰国 AI 法草案的走向。
   - 免费额度被薅。
   详见 §9。国内上线时还要再加备案和预付卡两件事。
6. **个人、组织、云三种形态能用同一套代码。** 账户和预算讲的是「配额」，钱只是配额的一种来源；账户树可以嵌套（§10）。

## 1. 定位：我们到底是什么

| | OpenRouter | iDoris 计算服务 |
|---|---|---|
| 服务谁 | 所有开发者 | 我们自己的两个场景：eduai、Agent24。之后可能开给社区 |
| 卖什么 | 模型广度 + 统一账单 | **场景化别名**（如 `edu-tutor`、`agent-coder`）背后的路由策略、账户层级、预算、信用 |
| 模型名 | 具体模型 | 场景别名为主，具体模型为辅 |
| 硬件 | 别人的 | 别人的 + 用户自己的 Mac（本地优先） |
| 账户 | 一个账户一个余额 | 组织 → 家长或老师 → 学生或 agent 实例，额度可以下发 |

**对调用方只承诺三样东西**：
- `base_url`：`https://idoris.ai/api/v1`
- `vk_` 开头的虚拟密钥
- 模型名，推荐用别名

模型名背后接哪个供应商、出故障时换到谁，都是 iDoris 的事，调用方不用管。这正是 iDoris 现在 role 别名（`fast` / `daily`）的延伸。

### 2.2 Token API 价格（开源模型，每百万 token，输入 / 输出）

| 模型 | 价位 | 说明 |
|---|---|---|
| DeepSeek V3.2（官方 / 硅基流动 / DeepInfra） | ~$0.21–0.28 / $0.32–0.42 | 中文好，支持工具调用，上下文 164K。各来源数字不一致 |
| Qwen3 32B | ~$0.10 / $0.44 | |
| Qwen3.6-35B-A3B | ~$0.15 / $1.00 | 新一代 MoE 小模型 |
| DeepSeek V3（Together） | $0.60 / $1.70 | Together 普遍偏贵。有一项对比覆盖 27 个模型，DeepInfra 有 24 个更便宜 |

硅基流动有若干限速免费的模型（例如 Qwen3-8B），可以拿来做免费档。

### 2.3 自建 vs API：盈亏线

公式：`每百万输出 token 成本 = GPU 小时价 ÷ 3600 ÷ 总吞吐(tok/s) × 1e6`。

- 单张 H100（$2.69/h，RunPod Community）跑 30B 级 MoE 或 32B dense，满载总吞吐按 1000–2000 tok/s 算，每百万输出 token 成本是 **$0.37–0.75**。
- 实际利用率：教育场景集中在上课和作业时段，按 15–25% 算，成本就变成 **$1.5–5 / M**。同级模型的 API 价是 $0.4–1.0。**API 便宜 3–10 倍。**
- 盈亏线：一张 H100 每天约 $65。按 API 价 $0.42/M 输出折算，要每天约 **1.5 亿输出 token**（24 小时平均约 1,800 tok/s）才打平。eduai 和 Agent24 早期离这个量差两到三个数量级。
- **结论：值得自建的只有三种情况**
  - (a) API 上没有的模型：微调过的 edu 模型、内容安全分类器、特定的 TTS 音色。
  - (b) 合规要求数据只能落在指定位置。注意：租来的 GPU 也是第三方机器，并不比 API 更「私有」。
  - (c) 单个模型的持续量超过盈亏线。

## 3. 场景、方案与模型建议

> 模型迭代很快，下面是「候选清单」，不是定稿。每个别名上线前都要用自己的评测集跑一遍，再决定用哪个。

### 3.1 eduai（面向儿童的课程）

| 场景 | 别名 | 候选模型 | 估算 |
|---|---|---|---|
| 答疑 / 陪练（中文） | `edu-tutor` | DeepSeek V3.2 非思考版；省钱档 Qwen3.6-35B-A3B | 每个活跃学生每天 20 轮 × (1.5K 入 + 0.4K 出)，约 $0.012/天，**每月约 $0.4/人** |
| 数学 / 逻辑推理 | `edu-reason` | DeepSeek V3.2 思考版 | 输出长，单价约为 tutor 的 3–5 倍，按需开 |
| 编程课助手 | `edu-coder` | Qwen3-Coder 小 MoE | — |
| 朗读 / 口语 | `edu-asr`、`edu-tts` | ASR：SenseVoice / Whisper-turbo；TTS：CosyVoice / Kokoro | Modal L4 缩到 0，或者跑在本机 Mac |
| 课程检索 | `edu-embed` | bge-m3 / Qwen3-Embedding | 很便宜 |
| **内容安全（必须）** | 网关内置，不暴露成别名 | Qwen3Guard / Llama Guard 类，输入输出双向过滤 | 每轮多一次小模型调用 |

### 3.2 Agent24（办公 agent）

| 场景 | 别名 | 候选模型 | 说明 |
|---|---|---|---|
| 主 agent（工具调用、规划） | `agent-main` | DeepSeek V3.2、Kimi K2 系、GLM-4.x、Qwen3.5 大 MoE | agent 很费 token：每天几百万输入 token 很常见，**上下文缓存命中率决定成本** |

## 4. 计费、账户与信用

### 4.1 账户层级

```
组织 Org（学校 / 公司 / 社区）        ← 签约方，可以后付费，有授信额度
 └─ 担保人 Sponsor（老师 / 家长 / 团队负责人） ← 预付费，给下级分额度
     └─ 使用者 Member（学生 / Agent24 实例）    ← 只持有 vk_ 密钥和额度，看不到钱
         └─ 密钥 Key（每个产品或设备一把）       ← iDoris 现有的 BudgetScope.key_id
```

现有基础：
- `BudgetLedger` 已经有：先预留（reserve）、再结算（settle）；最小货币单位用 i64；价格未知不按免费处理；超支事件留审计。
- `BudgetScope` 已经是 (tenant, key, provider, model) 四元组。

缺的是：**父子账户、额度下发、信用额度、价目表**。

### 4.2 「负值 / 部分信用」：我的挑战与改法

你的出发点是用户体验：不要在对话中途给用户一个 402。这个目标对，但「允许负余额」不是最好的手段。

| 你的想法 | 问题 | 我建议的做法 |
|---|---|---|
| 允许余额为负 | 谁来兜坏账？个人用户欠了钱，几乎追不回来 | **只有担保过的负值**：负额度来自上级（家长 / 组织）的授信，有硬下限，比如上级每月额度的 10% |
| 部分信用 | agent 一次失控循环，几分钟就打穿信用额度 | 信用额度加**花费速率闸门**（每分钟、每小时上限），超速就冻结这把密钥并通知担保人 |
| 流式输出中途钱不够 | 已经开始输出，没法停 | 请求前按 `max_tokens × 输出单价` **预留**（现有机制）。余额不够时，**按可用额度自动压低 max_tokens，或者降级到更便宜的模型**，不直接拒绝 |
| — | 一次请求的实际花费超过预留 | 现有 `settle` 已经「按实际扣费，超出部分记 overage」，这本身就是「最后一单宽限」 |

**体验分级**（从好到坏，逐级往下走）：
1. 正常：按别名的首选模型。
2. 额度紧：自动降级到同场景的省钱模型，响应头里带 `X-iDoris-Degraded`（已有）。
3. 额度用尽：宽限当前这一轮对话（不超过一次请求的预留），同时通知担保人「一键续额」。
4. 宽限用完：返回 402，附结构化原因（已有 `Budget402Body`），给孩子看的是「今天的能量用完了」，不是「余额不足」。

### 4.3 价目表与定价

- **内部记账单位**：沿用 i64 最小货币单位，按币种分别记账（人民币、美元各一本），不发明「点数」。点数一旦能转让，就踩到 PGL「不发可交易代币」的红线。
- 每次请求记下**两个数**：上游成本价 `cost`，和对用户的价 `price`。这样才能算每个别名、每个供应商的毛利。
- 定价公式（初稿）：`price = 上游官方价 × (1 + 加价率)`。
  - 加价率要覆盖：支付通道费（3–6%）、失败重试、免费档补贴、内容安全的额外调用。
  - 建议：付费档加价 20–30%；免费档按配额给，不按价格给。
- **透明定价**：公开「上游价 + 我们的加价」，符合数字公共物品的透明原则，也比 OpenRouter 更容易解释。
- 别名单价取它背后候选模型里**最贵的那个**。降级时实际扣费更低，用户只会得到「比报价便宜」的惊喜。

## 5. 挑战你的思路：哪里不行、为什么

### 5.1 「租外部 GPU 部署多种模型」：先别做
理由见 §2.3。还有两点：
- 多模型自建意味着要自己做容量规划、冷启动、版本升级、故障切换，一个人运维不过来。
- 好模型太大，单卡跑不了；单卡能跑的小模型，API 也最便宜。

**什么时候做**：等某个别名的持续量过了盈亏线，或者有 API 上没有的模型时，针对**那一个模型**做，而不是建一个「GPU 平台」。

### 5.2 不要把本地 iDoris 改成 SaaS
本地 iDoris 的默认行为和 Agent24 契约保持不变：只监听 loopback，Admin 只读。SaaS 只是同一套代码的「云形态」，详见 §10。

### 5.3 「商业收入 40% 回流」的口径
owner 决定：这件事从 iDorisAI 整体来看，**不在本服务的定价里考虑**。本服务的价目表只需要覆盖上游成本、支付费用和免费档补贴。

### 5.4 合规可能是最长的那根杆
首发地区是泰国，详见 §9。国内上线是以后的事，到时要另做一遍，下面几条先留着：
- 国内面向未成年人提供生成式 AI，通常需要大模型备案、算法备案和未成年人模式。
- 国内用户的数据只走国内上游。这要做成路由的硬约束。
- 充值余额可能被认定为单用途预付卡。
- 适用于所有地区：转售 API 要逐家确认服务条款允许；闭源前沿模型的订阅账号绝不能拿来转卖。

### 5.5 薄毛利生意的现实
开源模型的 token 单价还在下降，加价空间会持续被压缩。可持续的收入应该来自**服务层**：组织账户、学校套餐、合规的未成年人安全层、本地加云端的混合体验，而不是 token 差价。

## 6. 架构草案

```
           eduai 前端 / Agent24 桌面 / 第三方工具
                     │  OpenAI 兼容：https://idoris.ai/api/v1 + vk_ 密钥 + 模型名(别名)
                     ▼
 ┌────────── idoris.ai/api 云网关 ─────────────────────┐
 │ ① 接入：鉴权(vk_) · 限速 · 地域标记 · 请求规范化       │
 │ ② 内容安全：输入过滤（edu 租户强制）                  │
 │ ③ 路由：别名 → 候选(供应商×模型) → 过滤：              │
 │      地域/合规硬约束 → 隐私等级 → 预算状态 → 健康度      │
 │      → 排序：价格 / 延迟 / 缓存亲和 → 失败切换          │
 │ ④ 计费：预留(reserve) → 调用 → 结算(settle)           │
 │      账户层级额度下发 · 授信下限 · 速率闸门 · 降级        │
 │ ⑤ 内容安全：输出过滤                                  │
 │ ⑥ 记账：cost / price / 毛利 · 审计事件 · 账单          │
 └──────┬──────────┬──────────┬───────────┬──────────┘
        ▼          ▼          ▼           ▼
   token API   Modal 自定义   RunPod 基线   (用户本机 iDoris
 DeepSeek/硅基/  安全/ASR/TTS  (P2,按模型)    通过 Agent24 托管，
 DeepInfra/OR   (P1)                       本地优先)
```

能复用 iDoris 现有能力的地方：
- OpenAI 兼容的数据面
- 虚拟密钥（vk_）、租户
- `BudgetLedger` 的预留和结算
- role 别名
- 隐私等级（local_only）
- 结构化错误体、402 结构体、降级响应头
- 事件日志
- 上游模块里的 remote 适配器

要新建的：
- 账户层级和额度下发
- 授信与速率闸门
- 价目表（cost / price 分离）
- 多上游健康度与失败切换
- 地域硬约束
- 内容安全层
- 云端部署形态
- 支付和账单

## 9. 泰国首发的影响

- **个人数据（PDPA）**
  - 10 岁及以下儿童的数据，必须由家长等监护人同意；10–20 岁的未成年人在部分情况下也要家长同意。
  - 跟未成年人沟通要用易懂的语言，要做年龄核验和监护人核验，并留存记录。
  - 2026 年有修订草案，以 PDPC 现行文本为准。
- **职责划分**
  - 身份、同意、年龄核验由 **eduai** 负责。
  - iDoris 只拿到**假名化的成员 id**，不存孩子的姓名、年龄这些个人信息。iDoris 的账户树里有「担保人」节点，对应家长或老师，但只是一个 id，加一个「已取得同意」的标记。
- **数据最小化**
  - edu 租户默认不记录 prompt 和回复正文，只记 token 数和费用。
  - 上游只选支持零数据留存（ZDR）、能签数据处理协议（DPA）的供应商，比如 DeepInfra，或者 OpenRouter 的 ZDR 路由。
  - **未成年人数据不发往 DeepSeek 官方 API**：它的数据存储在境外，隐私条款不适合儿童数据。要用 DeepSeek 模型，就通过 ZDR 的托管方调用。
  - 跨境处理要写进隐私声明，列出境外处理方，并取得同意。
- **AI 法**
  - 泰国 2026 年 7 月发布了新的 AI 法草案：按风险分级，对外国提供方也适用，对 AI 生成内容有透明度要求，部分外国提供方可能要在泰国指定代表。
  - 目前没有生效。
  - P0 先做到：eduai 界面标明「AI 生成」，并按 ETDA 的生成式 AI 治理指南（自愿性）执行。
- **部署位置**：云形态部署在**新加坡**区域，离泰国近、延迟低，主要上游也都有亚太节点。
- **泰语模型**
  - 泰语能力是这次选模型的第一约束。
  - 候选：DeepSeek V3.2、Qwen3.x、Gemma 系列，以及 SCB 10X 的 Typhoon。Typhoon 2 是开源权重；某个托管方已在 2026-05 下架它的 70B 版本，所以托管可用性要现查。
  - 上线前要先建 **泰语 edu 评测集**（课程问答、儿童用语、安全题），并参考 SEA-HELM、ThaiExam，再定各别名背后的模型。没有评测之前，§3 的模型表只是候选。
- **免费额度**
  - 发放：每个成员按月发配额，记作平台补贴账户转入成员账户（复式记账），这样免费档每月花了多少一眼可见。
  - 范围：只覆盖省钱档的别名。
  - 防薅：账户必须由 eduai（学校或家长）或 Agent24（安装实例）发起开通，不开放匿名注册；另加按 IP 和按设备的限速。

## 10. 一套代码，三种形态：个人、组织、云

你的问题是：普通组织用一台 Mac Ultra 自己运营 AI，给成员发 API 密钥；我们自己运营在线的 idoris.ai/api。这两件事逻辑上自洽吗？能用同一套代码吗？

**结论：自洽，能用同一套代码。** 前提是守住两条原则：
1. **账户和预算讲的是「配额」，钱只是配额的一种来源。** 组织 Mac 上记的是配额，用来公平分配本机算力；云端记的是泰铢或美元，以及免费配额。预留、结算、授信、速率闸门、降级是同一套代码，只有价目表和记账单位不同。支付只是一个往账本里记入的适配器，不放进核心。
2. **账户树可以嵌套。** 组织节点在云端只是**一个账户**：它的成员云端看不见（正好满足 PDPA 的数据最小化），组织节点自己给成员计量；组织节点调用云端档时，由云端向这个组织账户计费。个人形态就是只有一个成员的组织节点。

```
idoris.ai/api（云）的账户树                组织 Mac（组织节点）的账户树
平台
 ├─ 泰国学校 A（组织账户） ◀── 云端档 ──── 学校 A
 │                                        ├─ 老师甲（担保人）
 │                                        │   └─ 学生 1、2…（成员 + 密钥）
 │                                        └─ 办公室 Agent24 实例
 ├─ 家长乙（担保人）
 │   └─ 孩子（成员 + 密钥）
 └─ Agent24 个人用户（成员 + 密钥）  ◀── 云端档 ──── 用户本机 iDoris（个人形态）
```

### 10.1 三种形态的差异

| | 个人（现状） | 组织（新） | 云 idoris.ai/api（新） |
|---|---|---|---|
| 跑在哪 | 用户的 Mac，由 Agent24 托管 | 组织的 Mac Studio Ultra | 我们的服务器（新加坡） |
| 入口 | 只监听 loopback | 局域网，需要 TLS 和密钥 | 公网：TLS、防滥用、开通流程 |
| 账户 | 一个租户 | 组织树 | 平台树（组织节点也是其中一个账户） |
| 记账单位 | 不计费 | 配额（不是钱） | 泰铢 / 美元 + 免费配额 |
| 信用 | 无 | 组织内互借配额 | 有担保的负值（§4.2） |
| 上游 | 本机模型（+ 云端档） | 本机模型 + 云端档 | 各家 token API + Modal（+ P2 租卡） |
| 支付 | 无 | 无（组织向云端付账） | P2 接入 |
| 存储 | SQLite | SQLite | P0 用 SQLite，单区域加持续备份；扛不住了再换 |
| 运维要求 | 尽力而为 | 尽力而为 | 高可用、监控、值班 |
| 合规角色 | 用户自己 | 组织是数据控制者，我们只提供软件 | 我们是数据处理者 |

在现有代码里，`DeployMode` 已经分了 `Personal` 和租户模式。三种形态就是在这个基础上把「租户模式」拆成组织和云两种配置，**不是三份代码**。

### 10.2 哪里不一致，要单独处理
1. **写操作的管理接口**：组织和云都需要建成员、发密钥、分额度。现在 Admin v0 是只读的，而且是 Agent24 契约的一部分，**不能改**。新的账户管理接口要另起：独立的监听地址，或者用独立的权限范围（`VirtualKeyScope.admin_scopes` 已经有这个字段）。
2. **租户来源**：现在租户来自一份可信配置文件，只有额度上限和时区，没有层级。账户树要改成存在数据库里、可以在线管理。配置文件保留，用于初始化。
3. **信任模型**：组织局域网里，成员和管理员彼此信任；公网上要防薅免费额度、防盗用密钥、防滥用。这些都放在云形态的入口模块里，组织形态不加载。
4. **容量**：Mac Ultra 内存大，能跑大 MoE，但并发低。组织节点必须会排队，本机放不下时落到云端档。现有的内存额度、驱逐和降级二选一、1GB 余量这些逻辑正好可以直接用。

### 10.3 idoris.ai/api 是 SaaS 吗？加上本地 iDoris 能达成目标吗？
- **是 SaaS**：我们运营的、多租户的云形态。本地 iDoris 不变成 SaaS，指的是本地形态的默认行为和契约不变。SaaS 才需要的能力（公网入口、开通、支付）只在云形态里启用。
- **能达成目标**：用户（或组织）只拿一把密钥、一个接口地址。请求先走本机或组织的 Mac，放不下或者要更强的模型时走 idoris.ai/api，两边记在同一个账户体系里。

### 10.4 云端将来跑什么，和组织节点一致吗
| 阶段 | 云端跑的 | 组织节点跑的 | 一致的部分 |
|---|---|---|---|
| P0 | 网关：账户、密钥、配额、路由、计量；上游适配器（ZDR token API）；edu 内容安全；免费额度发放 | 同一个网关核心 + 本机模型运行时 | API、别名、账户语义、预算和信用的规则 |
| P1 | + Modal 上的自定义模型（泰语语音、安全分类）+ 多上游失败切换 + 给组织节点和个人节点用的云端档 | + 云端档适配器 | 同上；组织节点看到的云端就是一个上游 |
| P2 | + 支付 + 组织后付费 + 按模型租的 GPU 基线 | 不变 | 同上 |

**两边不一致的只有上游和入口这两层。** 成员看到的接口、模型名、额度规则完全一样。
