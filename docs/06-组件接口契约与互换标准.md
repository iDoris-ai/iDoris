# iDoris 组件接口契约与互换标准

> 文档类型：接口契约（Interface Contract）+ 组件治理标准
> 日期：2026-07-30 ｜ 维护者：iDoris.ai / @jhfnetboy
> 关联：[`05-集成与技术栈协调规划.md`](./05-集成与技术栈协调规划.md)
>
> **核心原则（用户定调）**：**接口 + 数据标准 + 业务能力对接的定义，才是最核心的资产；所有组件（含 router、核心模型、网关）都可替换。** 选错了就换——只要接口不变，换组件零伤筋动骨。本文把"组件之间是什么关系、怎么通信、怎么替换"讲清，并梳理当下标准。

---

## 1. 三条铁律

1. **接口是资产，组件是耗材**：iDoris 拥有的是**契约**（能力定义 + 通信协议 + 数据标准），不是任何具体实现。任何组件都可被同契约的另一个实现替换。
2. **进程边界通信，不 import 跨仓库**：组件间只经 **网络/进程边界**（HTTP/Nostr/stdio）通信；不把某语言的 SDK 当跨组件契约（同 Agent24 SPEC-001 §10）。
3. **一个能力，一份契约**：每类能力（chat/embedding/asr/tts/vision/tool/comms/credential/train）有唯一契约；实现它的组件即插即换。

---

## 2. 通信的四个层级（讲清"怎么通信"）

用户点出"通信可能有几个层级"——正是。任一组件对接，都要在这四层各说清：

| 层级 | 回答什么 | iDoris 标准 |
|---|---|---|
| **L1 传输（Transport）** | 字节怎么过去？ | 首选 **HTTP/REST**；去中心通信 **Nostr**；本地子进程 **stdio/argv**；联邦训练 **gRPC** |
| **L2 数据标准（Data Schema）** | 载荷长什么样？ | 首选 **OpenAI-compat**（chat/embeddings/audio/images）；工具 **MCP**；原生直通 **Anthropic Messages / Gemini**；通信 **Nostr 事件(NIP-44/33)** |
| **L3 能力语义（Capability）** | 这是什么能力？ | 枚举：`chat / reasoning / embedding / asr / tts / vision / tool / comms / credential / train`；每个能力有输入输出契约 |
| **L4 生命周期（Lifecycle）** | 怎么起停/健康/取消？ | 健康探针 + 优雅关闭 + CancellationToken + 版本 pin（复用 Agent24 ModelRouter health/cooldown）|

> **一次完整对接 = L1×L2×L3×L4 都定义清楚。** 例：llama-swap = L1 HTTP + L2 OpenAI-compat + L3 chat/vision/asr + L4 常驻进程带 TTL。

## 3. 组件形态的排列组合（用户要的"各种情况"）

组件按 **[L1 传输] × [生命周期]** 组合，落成 6 种标准形态。每种给：怎么通信、生命周期、何时用、代表、如何换。

### 形态 A：常驻 HTTP 服务（Long-running HTTP Service）
- **通信**：L1 HTTP + L2 OpenAI-compat，固定端口。
- **生命周期**：iDoris 启动时拉起（或已在跑），健康探针，崩溃重启。
- **何时用**：高频、需常驻的推理/路由/编排。
- **代表**：llama-swap、LiteLLM、ClawRouter、OmniRoute、MLX server。
- **如何换**：换一个同样暴露 OpenAI-compat 的进程，改 `*_URL` 指向即可，上层零改。

### 形态 B：子进程 CLI（Spawn-on-call CLI, stdio/argv）
- **通信**：L1 stdio/argv（进程边界），iDoris spawn 后读 stdout；可再由薄封装转 HTTP。
- **生命周期**：按需拉起、用完退出（或短驻）；CancellationToken=kill。
- **何时用**：订阅态工具、无 HTTP 接口的 CLI、法律上要"包二进制不 vendor 源"的上游。
- **代表**：claude/codex CLI（能力①）、agent-speaker(Go)、whisper.cpp、nak。
- **如何换**：换等价 CLI，改 spawn 命令 + 参数映射；封装层吸收差异。

### 形态 C：捆绑二进制（Bundled Binary）
- **通信**：随发行版打包的可执行文件，经 HTTP 或 stdio 调。
- **生命周期**：随 app 分发（electron-builder extraResources 模式，同 Agent24 C8）。
- **何时用**：推理引擎、需随产品分发的本地组件。
- **代表**：llama.cpp server、agent24d 二进制。
- **如何换**：替换二进制文件 + 版本 pin，接口不变。

### 形态 D：去中心节点（Nostr Node, async）
- **通信**：L1 Nostr + L2 NIP-44 加密事件 / NIP-33 可替换事件；异步、去中心。
- **生命周期**：长驻 daemon 或按需；经 relay 收发。
- **何时用**：跨节点发现、agent↔agent 通信、联邦握手、社区/城市互联。
- **代表**：agent-speaker（Agent24 nostr-bridge 已 subprocess 驱动它）。
- **如何换**：换等价 Nostr 客户端 CLI；事件 schema（NIP）是契约，实现可换。

### 形态 E：透明网关 / MITM（Transparent Proxy）
- **通信**：L1 HTTP，agent 带占位符发出 → 网关注入真凭证 → 转发真实 API。
- **生命周期**：常驻代理进程，性能敏感路径。
- **何时用**：出站外部 API 的凭证保护（key 不进 agent 上下文）。
- **代表**：onecli 模式（Rust MITM）。
- **如何换**：换等价注入代理，agent 侧仍只见占位符，零改。

### 形态 F：离线批处理进程（Batch / On-demand Job）
- **通信**：L1 gRPC/HTTP/文件，按需拉起，产出落盘（如 LoRA adapter）。
- **生命周期**：非常驻；由 scheduler/self-wake 触发；跑完退出。
- **何时用**：训练、联邦、重导出——不该常占内存的重活。
- **代表**：Flower + PEFT + mlx-lm（联邦/本地训练）。
- **如何换**：换等价训练框架，产出 adapter 格式（契约）不变即可挂载。

### 形态速查表

| 形态 | L1 传输 | 生命周期 | 内存占用 | 代表 | 典型能力 |
|---|---|---|---|---|---|
| A 常驻 HTTP | HTTP | 常驻 | 中-高 | llama-swap/LiteLLM/ClawRouter | 推理/路由 |
| B 子进程 CLI | stdio/argv | 按需 | 低-中 | claude/codex, whisper.cpp | 订阅/ASR |
| C 捆绑二进制 | HTTP/stdio | 随产品 | 中 | llama.cpp, agent24d | 引擎 |
| D Nostr 节点 | Nostr | 长驻/按需 | 低 | agent-speaker | 通信/发现 |
| E MITM 网关 | HTTP | 常驻 | 低 | onecli | 凭证 |
| F 离线批处理 | gRPC/文件 | 按需 | 高(短时) | Flower+mlx-lm | 训练/联邦 |

## 4. 组件关系图（谁调谁）

```
                       ┌──────────────── iDoris Router (编排核心, 自研薄层) ─────────────────┐
                       │  持有全部契约; 意图路由/隐私标签/订阅门禁/业务组合/健康/审批          │
                       └─┬────────────┬──────────────┬──────────────┬───────────────┬───────┘
              HTTP(A)    │   HTTP(A)  │   spawn(B)    │   Nostr(D)    │   spawn(F)    │ HTTP(E)
                 ▼       ▼            ▼               ▼               ▼               ▼
          能力②路由   能力③编排    能力①订阅       跨节点通信       联邦训练        凭证网关
        ClawRouter/  llama-swap    claude/codex    agent-speaker   Flower+mlx-lm    onecli
        OmniRoute/     │  (A/C)      CLI              (D)            (F)             (E,出站)
        LiteLLM(A)     ▼
                    MLX/llama.cpp/vLLM/whisper.cpp/kokoro (C/B, OpenAI-compat 后端)

   消费方(都经 iDoris 统一 URL, OpenAI-compat):

```

**关键**：所有箭头都是"进程边界 + 标准协议"；任一节点可替换为同契约实现。

## 5. 组件契约模板（每个组件接入必须填）

每引入一个组件，写一份 **组件卡（Component Card）**，声明这 8 项——这就是"如何跟它通信 + 如何更换"的标准答案：

```yaml
component: llama-swap                 # 名称
capability: [chat, vision, asr]      # L3 提供哪些能力
form: A-long-running-http            # 形态（A-F）
transport: http                      # L1
data_schema: openai-compat/v1        # L2 (+ 版本)
endpoint: http://127.0.0.1:9292/v1   # 地址（或 spawn 命令）
lifecycle:                           # L4
  start: "llama-swap --config ..."   #   如何拉起
  health: "GET /health"              #   健康探针
  shutdown: "SIGTERM, 5s grace"      #   优雅关闭
  cancel: "HTTP abort / kill"        #   取消
version_pin: "v201"                  # 版本锁
config_env: [OMLX_URL, ...]          # 依赖的环境/配置
replace_with:                        # 如何替换 ←★
  compatible: [Ollama, LiteLLM(local)]   # 同契约备选
  swap_steps: "改 endpoint 指向; 迁移 config; 跑契约测试"
license: MIT                         # 许可（cargo-deny 式门禁）
distribution: binary                 # exe/binary/container/submodule
```

> 全部组件卡集中放 `iDoris/components/*.yaml`（或内核注册表），构成"组件登记册"——一眼看全体系有哪些能力、由谁提供、怎么换。

## 6. 更换组件的标准流程（Swap Procedure）

因为"所有组件可替换"是硬要求，替换要有标准动作：

1. **确认契约一致**：新组件提供相同 `capability` + `data_schema`（L2/L3 对齐）；差异由封装层吸收。
2. **过契约测试**：对新组件跑该能力的**契约测试套件**（正/错例、streaming、tool-call、取消）——即 Agent24 `contract-tests` 的 iDoris 版。全绿才算合格。
3. **改配置，不改上层**：只改组件卡的 `endpoint`/`start`/`version_pin`；iDoris Router 与所有消费方零改。
4. **灰度 + 回滚**：health/cooldown 下先并存灰度，异常自动 fallback 回旧组件（复用 Agent24 ModelRouter）。
5. **登记**：更新组件卡 + 登记册 + 版本 pin。

> 这套流程让"router 选错了再换"成为一个**低成本、可回滚**的常规操作，而非重构。

## 7. 当下标准梳理（Current Standards）

| 维度 | 采用标准 | 说明 | 备选/直通 |
|---|---|---|---|
| **模型调用（L2）** | **OpenAI-compat** `/v1/chat/completions`、`/v1/embeddings`、`/v1/audio/*`、`/v1/images` | 全生态普通话；chat+vision+asr+tts+embed 都能覆盖 | Anthropic Messages / Gemini **native 直通**（高级特性保真时）|
| **工具（L2）** | **MCP**（Model Context Protocol） | Agent24 已双向支持（E1 client + E4 server）；工具即插 | — |
| **去中心通信（L1/L2）** | **Nostr** + NIP-44(加密)/NIP-33(可替换事件) | agent-speaker 已实现；节点发现/联邦握手 | — |
| **子进程（L1）** | **stdio/argv** + JSON | 订阅 CLI、agent-speaker、whisper.cpp | — |
| **联邦（L1）** | **gRPC**（Flower）+ adapter 文件格式 | LoRA adapter 是聚合契约 | HTTP |
| **身份（L3）** | **AirAccount DID** + 模块签名（Agent24 M5）| 联邦/社区互认信任根 | — |
| **凭证** | 占位符 + **MITM 注入**（onecli 模式）| key 不进 agent 上下文 | env/vault |
| **分发** | **二进制/CLI/容器**，版本 pin，不 vendor 源码 | SPEC-001 §10；许可门 cargo-deny 式 | 需 patch 的协议层用 submodule 固定 commit |

## 8. 接口版本化与兼容

- **加法优先**：契约演进走加法（新增可选字段），老实现不因此失败（同 Agent24 H1 `risk_class` 加法迁移经验）。
- **版本号进 data_schema**：`openai-compat/v1`、`nostr/nip-44`、`mcp/2025-06` 等显式版本。
- **零漂移门**：契约与实现之间加 drift-check（同 Agent24 `pnpm gen:api` 零漂移 CI），防止实现悄悄偏离契约。
- **能力发现**：iDoris Router 暴露 `GET /capabilities`，列出当前每个能力由哪个组件提供、什么版本——供消费方运行时自省。

---

## 9. 小结

> iDoris 的架构本质是**一套契约 + 一个编排器 + 一堆可替换组件**。契约锁定在"四层通信 × 能力枚举 × 数据标准"上，组件用六种标准形态接入，每个组件有组件卡声明"怎么通信 + 怎么换"，替换走五步标准流程。**router、核心模型、网关、训练框架——全部是可拔插耗材，选错即换，接口不动。** 这既满足你"接口是最核心资产、组件皆可替换"的定调，也让整个 Mycelium 多语言生态（Rust/Go/TS/Python）在 REST+Nostr+DID 三条普通话上自然互通。

## 10. 契约补全（codex-rescue 评审 R1，2026-07-30）

> 评审指出："06 命名了协议，却没定义足够的真契约，可拔插是空头支票"。本节把最关键的契约补成**可执行骨架**（planning 高度：给强制字段与语义，不写全套实现 schema）。**完整 per-capability I/O schema + 黄金一致性测试 = U0/U1 交付物**（现在写全属过度设计，故明确列为后续里程碑，而非现在）。

### 10.1 canonical ProviderDescriptor（统一三套词汇 · 修 G3）
provider 家族(`idoris|claude|openai|local`)、tier(`Local|Remote|Lora`)、capability 枚举此前各说各话。统一到一个描述符：
```yaml
provider_descriptor:
  id: ornith-local
  family: idoris|claude|openai|local|other   # 来源家族
  tier: local|remote|lora                     # 路由层(隐私判据)
  capabilities: [chat, reasoning, vision]     # L3 能力
  privacy_class: local_only|any               # ★ 隐私类（见 10.2）
  cost: {input_per_m: 0, output_per_m: 0}     # 计费(本地=0)
  locality: loopback|lan|remote               # 物理位置(决定 tier 是否可信 local)
```
> 路由/隐私/fallback/计费/发现从此读同一个描述符，不再互相矛盾。

### 10.2 组件卡强制策略字段（修 G4 · Critical）
组件"协议兼容"不等于"路由安全"。组件卡（§5）**新增强制字段**：
```yaml
privacy_class: local_only|any    # 该组件可承载的最高隐私级
allowed_egress: [none|loopback|lan|internet]  # 允许的出站范围
fallback_policy: fail_closed|next_in_chain    # 失败时行为
fail_closed: true                # LocalOnly 任务无本地可用→报错，绝不外泄
```
缺这些字段的组件卡**不合格、不注册**（同 Agent24 H10 清单严格校验）。

### 10.3 抽象 LoadPolicy / ModelLease（修 P3 · 引擎无关）
"常驻/临时"是抽象语义，不该绑定任一引擎的实现细节。抽象成：
```yaml
load_policy:
  mode: resident|on_demand|evict_to_load   # 抽象语义
  keepalive: { pinned: bool | idle_ttl_s: <n> } # 常驻=pinned；临时=idle 超时/压力驱逐
  admission: coexist|requires_eviction      # 能否与常驻共存
```
**参考实现 = oMLX（U0 实测，v0.4.3）**，抽象语义 → oMLX 具体 knob：
| LoadPolicy 抽象 | oMLX 实现 |
|---|---|
| `mode: resident` | `model_settings.is_pinned=true`（不被驱逐）|
| `mode: on_demand` | unpinned + 首次请求加载 |
| `evict_to_load` | ProcessMemoryEnforcer 压力驱逐（ok/soft/hard/ceiling，实测）|
| 显式控制 | `POST /v1/models/{id}/load` `/unload` |
| admission 查询 | `GET /api/status`（`model_memory_max`/loaded）|
| 内存预算 | `--memory-guard {safe|balanced|aggressive}` + `--memory-guard-gb`（可模拟目标机）|
> llama-swap TTL = 同契约的**另一种**实现（仅当需混非-MLX 引擎时）。Ollama/vLLM 亦可。**契约不变，实现可换。**

**⚠️ 跨平台硬约束（不可写死 oMLX）**：Agent24 = Electron 前端 + Rust 后端，分发到 **Windows / Linux / macOS**；而 **oMLX 属 MLX 生态，仅 Apple Silicon**。故 capability③ 的实现**按平台选**，都在 LoadPolicy 契约之后：
| 平台 | capability③ 实现 |
|---|---|
| **macOS (Apple Silicon)** | **oMLX**（首选，原生最优）/ MLX / Ollama |
| **Windows / Linux (有 NVIDIA)** | **vLLM** / llama.cpp / Ollama |
| **Windows / Linux (无独显/CPU)** | llama.cpp(GGUF CPU) / Ollama |
> iDoris/Agent24 只认 **LoadPolicy + OpenAI-compat 契约**；启动时按 OS/硬件**探测并选后端**（动态推荐模块 07 一并负责）。oMLX 是"macOS 的默认实现"，**不是 iDoris 的固定依赖**。

### 10.4 AdapterManifest + base 一致性（修 P4/E2 · Critical · 解训练框架锁定）
"adapter 格式不变即可挂载"不够——LoRA 因框架/rank/target/base/量化而不同。联邦聚合与热挂载的**真契约**：
```yaml
adapter_manifest:
  base_model_digest: sha256:...     # ★ 聚合前必须匹配(修 E2 base一致性)
  tokenizer_digest: sha256:...
  framework: mlx|peft|unsloth       # 产出方(可换,manifest 不变)
  tensor_format: safetensors
  rank: 16
  target_modules: [q_proj, v_proj, ...]
  quantization: none|q4|q8
  license: apache-2.0|mit|...        # 许可门(cargo-deny 式)
  privacy_treatment: raw|dp_noised|secure_agg   # ★ 修 S1
  aggregation_compat: fedavg|fedit|flora
```
`base_model_digest`/`tokenizer_digest` 不匹配→**拒绝聚合/挂载**（防"一次静默升级毁掉整批 LoRA"）。

### 10.5 控制面：task profile 不走 prompt（修 S4 · 统一 URL 不够用）
OpenAI `/v1/chat/completions` 载不动 router 需要的意图/隐私/复杂度/能力要求。**加控制面**（二选一，优先 header）：
```
# 方式A: iDoris 扩展 header（对 OpenAI-compat 透明）
X-iDoris-Privacy: local_only
X-iDoris-Intent: banner|blog|reasoning|coding
X-iDoris-Complexity: simple|complex
X-iDoris-Capabilities: vision
X-iDoris-Fallback: fail_closed
# 方式B: 侧端点 POST /idoris/route (返回选定 provider) 再调 /v1
```
> 消费方**声明式**表达策略，不再把意图塞进 prompt / model 名（Agent24 `TaskProfile` 即映射到这些）。

### 10.6 路由策略 = 声明式配置（修 P5 · router 真可换）
iDoris Router 若把意图/隐私/fallback 逻辑硬编码，换 router 就要移植隐藏策略。**策略是数据不是代码**：
```yaml
routing_policy:            # 版本化、可导出导入、有契约测试
  version: 1
  rules:
    - if: {privacy: local_only}          then: {tiers: [local, lora], fail_closed: true}
    - if: {intent: banner}               then: {capability: vision, load: on_demand}
    - if: {complexity: complex}          then: {tiers: [remote, local]}
```
换 router = 换执行引擎，**策略配置照搬**；引擎只要能解释这份 policy 即合格。

### 10.7 native 特性收进 extensions（修 G2/P2 · 防 provider 锁定）
OpenAI-compat 表达不了的 provider 原生特性（Anthropic prompt-cache、Gemini grounding）**不得裸用**：
```yaml
extensions:
  provider.anthropic.prompt_cache: {...}   # 命名空间隔离
  _degradation: "换 provider 时此特性降级为无缓存，行为已声明"
```
消费方用了 extension 就要接受"换 provider 时按声明降级"。**完整 extension schema 等真实消费者出现再写**（先有消费者再有提供者）。

### 10.8 /capabilities 加容量字段（修 E3 · 24GB 紧,容量是接口）
```
GET /capabilities → 每个能力附:
  resident: bool
  estimated_memory_gb / ctx_limit / queue_depth
  admission_status: ready|requires_eviction|blocked
```
业务(blog/banner/coding)据此知道"能否共存/要不要驱逐/会不会超延迟"。与 07 动态推荐模块同源。

### 10.9 战略平台依赖 vs 可替换组件（回应 P6 · 划清边界）
**不是所有东西都要抽象成可替换**——过度抽象即过度设计。明确两类：
| 类别 | 成员 | 处理 |
|---|---|---|
| **战略平台依赖**（生态地基，如同"用 HTTP"）| **Nostr**（去中心通信）、**AirAccount DID**（身份信任根）| 直接依赖，不套抽象层。它们是 Mycelium 的既定赌注 |
| **可替换组件** | router / 核心模型 / 本地编排 / 训练框架 / **凭证**(CredentialProvider 抽象) / 外部API | 走组件卡 + §6 五步替换 |
> 凭证保留 `CredentialProvider` 接口（onecli 是默认实现，可换）；Nostr/DID 不抽象——把它们当"可换组件"反而增加无谓复杂度。

### 10.10 契约成熟度分级（回应 P1 · 不过度设计）
承认 06 当前是**契约框架**，各能力契约成熟度不一，明确"现在到哪、后续补什么"：
| 成熟度 | 含义 | 现状 |
|---|---|---|
| L0 命名 | 只有能力名 | tts/train 等 |
| L1 骨架 | 有强制字段 + 语义（本节）| chat/adapter/load-policy/routing |
| L2 完整 schema | 全 I/O + streaming + error + cancel + 幂等 | **U0/U1 交付** |
| L3 黄金测试 | 一致性测试套件，过则可换 | **U1 交付** |
> 声明可替换性**只对达到 L2+L3 的能力成立**；未达的诚实标注，不假装。
