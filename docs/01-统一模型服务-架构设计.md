## 1. 一句话架构

> **iDoris = 一层"个人 AI 网关"**：对外一个本地统一 URL（OpenAI-compat），对内把 **①本地订阅中转 ②外部 API ③本地模型（常驻+临时）** 三类能力，按业务意图路由、组合、降级，成为业务层的统一基础能力。

```
                         ┌──────────── 对外：统一本地 URL ────────────┐
   业务/Agent/渠道 ─────▶│   http://127.0.0.1:PORT/v1  (OpenAI-compat) │
  (banner/blog/chat/     └───────────────────┬─────────────────────────┘
   微信/Nostr/Agent24)                        │
                                    ┌─────────▼─────────┐
                                    │   iDoris Router    │  ← 路由/组合/降级/用量/隐私标签
                                    │  (能力选择 + 策略)  │
                                    └──┬──────┬──────┬───┘
                     ┌─────────────────┘      │      └─────────────────┐
             ①本地订阅中转            ②外部 API              ③本地模型服务
        ┌──────────────────┐   ┌──────────────────┐   ┌──────────────────────────┐
        │ claude / codex   │   │ OpenRouter/OpenAI │   │ 常驻: iDoris 核心推理模型  │
        │ CLI (订阅登录)    │   │ Anthropic/DeepSeek│   │ 临时: 0.1B语音/2B ASR/    │
        │ →封 OpenAI-compat │   │ Kimi/Gemini ...   │   │      4B视觉/14B coding... │
        └──────────────────┘   └──────────────────┘   └──────────────────────────┘
                                                        (llama-swap 按 TTL 载入/卸载)
```

**部署形态**：以上整体可跑在个人电脑（测试期），或部署到 Mac mini 24h 常驻、经 Tailscale VPN 从任意地点访问同一个 URL。对外看永远是"一个模型服务"。

## 2. 三种能力 —— 逐层拆解

### 能力① 本地订阅中转（CC switch / CC proxy）

**目标**：让 iDoris 直接复用本地已登录的 **Claude Code / Codex 订阅**算力，不额外花 API 费。

**技术形态（推荐）**：subprocess 驱动本地 `claude` / `codex` CLI（订阅态），封装成 OpenAI-compat 端点。与 Agent24 既有 CLI-wrapper 策略（G3 / SPEC-001 §10：*进程边界=授权边界，包二进制不 vendor 源码*）完全一致，法律与架构清晰。

**现成参考项目**（GitHub，充分借鉴）：
| 项目 | 能力 | 借鉴点 |
|---|---|---|
| [agent-cli-to-api](https://github.com/leeguooooo/agent-cli-to-api) | 把 Codex/Cursor/Claude Code/Gemini CLI 暴露为 OpenAI-compat `/v1`，用前缀 `claude:`/`codex`/`gemini:` 选后端 | **最贴合本能力**——直接的多 CLI→统一 API 范式 |
| [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) | OpenAI/Gemini/Claude/Codex 兼容 API，走 OAuth | OAuth 订阅态接入 |
| [claudecodex](https://github.com/karem505/claudecodex) | 用 ChatGPT 订阅经本地 Codex proxy 驱动 Claude Code UI | 订阅复用范式 |
| claude-max-api-proxy / clovapi | Claude Max/Codex 订阅 → localhost OpenAI 端点 | 极简本地桥 |

**合规立场（2026-07-30 采纳用户判断，详见 [05 §7](./05-集成与技术栈协调规划.md)）**：个人把**自己的**订阅转成本地 API 供**自己**用，是对自有资产的正当使用（开源、非商业、不干预服务方、不转售）——**合理**；ToS 上属未明确禁止的灰区。据此：能力① **默认 loopback + 单用户**（尊重灰区的保守默认，也保护用户自己），可由用户自行放开到 Tailscale 私网多设备（属"个人自用"延伸）；但**社区端/城市端绝不转发个人订阅**——多租户转发超出自用范畴、会触碰服务方明确红线，社区/城市端用自己的 API（②）或本地模型（③）。

---

### 能力② 外部 API 接入（OpenRouter / OpenAI / Anthropic / DeepSeek / Kimi / Gemini …）

**目标**：统一封装各家云 API，业务只认一个 OpenAI-compat 接口。

**核心难点（用户已点破）**：不是所有接口都是 OpenAI chat-completion 规范。差异最大的两类：
- **Anthropic Messages API**：`/v1/messages`，`system` 独立字段、`content` 块数组、tool_use/tool_result 块、thinking 块、SSE 事件结构不同。
- **Google Gemini**：`generateContent`，`contents[].parts[]` 结构、`functionCall`/`functionResponse`、安全设置字段。
- 其余（DeepSeek、Kimi/Moonshot、OpenRouter、Groq、SiliconFlow…）**基本都是 OpenAI-compat**，差异小。

**结论：能统一封装，且不必自造轮子。** 业界成熟方案已解决这些翻译：

| 项目 | 规模 | 定位 | 许可 | 借鉴/采用建议 |
|---|---|---|---|---|
| [LiteLLM](https://github.com/BerriAI/litellm) | **140+ provider / 1892 模型** | Rust core + Python SDK；SDK 与独立 Proxy 两种形态；OpenAI 格式统一，含 cost tracking / fallback / load-balancing / guardrails | MIT | **首选采用**——外部 API 层直接站在它肩上，尤其它已处理 Anthropic/Gemini 的原生翻译 |
| [one-api](https://github.com/songquanpeng/one-api) / new-api | 20+ provider | 单二进制 Go 网关，OpenAI-compat | MIT | 轻量、单文件部署可参考；中文生态成熟 |
| OpenRouter | 云聚合器 | 一个 key 打多家 | 商业 | 作为"外部 API 的外部聚合器"直接当一个上游 |

**技术 Spike 计划（落地前必做，写进 backlog）**：
1. 用 LiteLLM 分别打通 Anthropic Messages / Gemini generateContent，验证 **streaming、tool-calling、多模态图片输入、thinking/reasoning 块** 四项在统一 OpenAI-compat 出口下的**语义保真度**。
2. 明确哪些高级特性 OpenAI-compat 表达不了（如 Anthropic 的 prompt caching、Gemini 的 grounding），决定"降级暴露"还是"透传原生"（LiteLLM 支持 `native` 直通）。
3. 产出：一张"provider × 特性 × 是否统一可用"矩阵，作为能力② 的验收基线。

---

### 能力③ 本地模型服务（常驻 + 临时加载）

**目标**：把一批不同规模/模态的本地模型，组织成"业务按需取用"的基础能力池。

**分类（用户规划）**：
- **常驻（resident）** = iDoris **核心模型**：**推理为核心能力**，可选多模态；一直在内存里、随叫随到。**可按机器配置更换**（不同 Mac 内存不同），给一个"推荐默认"。
- **临时加载（on-demand）** = 按业务意图临时载入的小模型：如 banner→视觉模型、blog→小语言模型、语音→TTS/ASR。用完按 TTL 卸载释放内存。

**核心机制发现（关键）**：这套"常驻 vs 临时"**正是 [llama-swap](https://github.com/mostlygeek/llama-swap) 的设计**——一个 OpenAI-compat 代理，前置于 llama.cpp/vLLM/Whisper 等后端，按需 **热加载/热卸载** 模型，每模型可配 **TTL**（空闲超时自动卸载释放显存/内存），并暴露**一个稳定 URL**。
- **常驻** = TTL 设为无限/长（核心模型不卸）。
- **临时** = TTL 短（用完即卸，给下一个业务腾内存）。

**业界标准全栈**（NVIDIA 开发者论坛实证的组合）：
```
业务/Agent  →  LiteLLM(能力②统一)  →  llama-swap(能力③编排)  →  {llama.cpp / vLLM / MLX / Whisper}
```
> 这正是 iDoris 三能力的天然实现骨架：**LiteLLM 管"外部+统一出口"，llama-swap 管"本地模型编排"，两者都是 OpenAI-compat，可级联。** iDoris Router 在最上层加"意图→能力选择 + 订阅中转 + 隐私标签"。

**Apple Silicon 落地**：MLX / mlx-lm 原生统一内存，OpenAI-compat serving；M5 实测 14B dense TTFT <10s、30B MoE <3s。与 Agent24 既有 oMLX（默认运行时，`~/.omlx/models/`）一脉相承。

**推荐模型选型**：见 [`02-模型与项目选型-调研.md`](./02-模型与项目选型-调研.md) §模型清单（核心推理 / 视觉 / ASR / TTS / coding 各给了 HF 现役最优 + 规模档）。

## 3. iDoris Router —— 三能力之上的编排层（我们要自己写的那一层）

LiteLLM + llama-swap 给了"统一出口 + 本地编排"，但**它们不懂 iDoris 的业务语义**。iDoris Router 是薄薄一层，负责下面这些"别人给不了的"：

| 职责 | 说明 |
|---|---|
| **意图→能力路由** | "做 banner"→视觉模型（临时）；"深推理"→核心常驻；"跑 coding agent"→订阅中转或 14B coding；隐私敏感→强制本地 |
| **订阅中转门禁** | 能力① 只对本机单用户开放，社区/城市端不转发个人订阅（合规红线落地点）|
| **隐私标签** | 复用 Agent24 `TaskProfile{privacy, complexity}`：`LocalOnly` 永不出设备（对齐产品隐私分级 0–3）|
| **降级链** | 核心模型忙/OOM → 外部 API → 订阅中转，按策略 fallback（复用 Agent24 `ModelRouter` health/cooldown）|
| **业务能力组合** | 把"原子模型能力"组合成"业务级基础能力"（如 blog = 大纲(推理)+配图(视觉)+润色(小模型)）|
| **用量/审计** | 统一用量统计、危险动作经 Agent24 审批门（C4/D3）|

> **复用而非重写**：iDoris Router **不重造** LiteLLM/llama-swap 的能力，而是 orchestrate 它们 + 接上 Agent24 已有的隐私路由/审批/记忆。这是"契约先行、先有消费者再有提供者"原则的延续。

---

## 4. 与 Agent24 内核的关系（落地路径）

Agent24 的 Rust `ModelRouter`（三层 Local/Remote/Lora + 隐私强制 + health/cooldown）**已经是 iDoris Router 的雏形**。落地不是另起炉灶，而是：

1. **iDoris 统一 URL = Agent24 的一个 provider**：把"iDoris 统一服务"作为 `IDORIS_URL` 接进 `ModelRouter::from_env()`（纯加法，见汇总文档 §9 I1）。
2. **或 Agent24 内核直接演进为 iDoris Router**：把能力①②③ 的编排（LiteLLM/llama-swap 客户端 + 订阅中转 subprocess）落进 Rust 内核的 provider 层。
3. 二者可并存：先用外部 LiteLLM/llama-swap 快速跑通（Python/Go 现成），验证后按需内化进 Rust。

## 5. 论证：这套逻辑成立吗？能撑起"个人/社区/城市"吗？

### 5.1 成立 —— 且是"站在巨人肩上"，非空想
- **三能力统一网关**是当下本地 AI 的**事实标准架构**（LiteLLM 140+ provider、llama-swap 3k★、"App→LiteLLM→llama-swap→backends"是被反复实证的全栈）。iDoris 的创新不在"重造网关"，而在**把订阅中转 + 隐私路由 + 业务意图 + 自增长/联邦**这几件别人没缝合的事缝进同一层。
- **常驻/临时** 有 llama-swap TTL 直接落地；**Apple Silicon** 有 MLX 成熟生态；**外部 API 异构** 有 LiteLLM 兜底。三条腿都有现成支撑。

### 5.2 对"个人 / 社区 / 城市"三级的支撑力
| 层级 | iDoris 如何支撑 | 关键能力 |
|---|---|---|
| **个人** | 一台机（或 Mac mini + Tailscale）跑统一服务，隐私数据不出设备，本地自增长（见文档 03）| 能力③ 常驻核心 + 订阅中转 + 本地 LoRA |
| **社区** | 社区 iDoris = 更强配置（多 GPU），个人把"外部 API"指向社区 iDoris；两个 iDoris 间跑联邦学习 | 能力② 指向社区 + 联邦（文档 03）|
| **城市** | 社区之上再聚合成层级联邦（个人→社区→城市），城市级模型/公共服务由多社区脱敏贡献训练 | 层级联邦 + 公共物品定位（Mycelium Park）|

> 结论：**逻辑成立**。它天然是"分形/菌丝式"的——同一个 iDoris 节点，既能当个人的核心，也能当别人的"外部 API 上游"，靠联邦把三级串成一张自增长的网。这与 Mycelium"数字公共物品 + 协作网络"的使命同构。

### 5.3 诚实的风险与前提（不回避）
| 风险 | 说明 | 缓解 |
|---|---|---|
| **订阅中转合规** | ToS 灰区，仅个人本地自用 | 硬编码 loopback+单用户；社区/城市端禁转发订阅 |
| **外部 API 语义保真** | Anthropic/Gemini 高级特性未必能 100% 统一 | 先做 Spike 矩阵（§2.2），必要时透传 native |
| **Mac 统一内存上限** | 常驻+临时模型总量受内存限制，不能无限并存 | 容量规划 + llama-swap TTL + 单会话 `maxConcurrency=1` |
| **联邦真实收益** | non-IID 数据、激励对齐、base 模型版本一致性是真问题 | 见文档 03 的分阶段（先跑通→隐私→效率）与诚实评估 |
| **"先跑通再隐私"的边界** | 链路可先不含隐私，但**不得用真实个人数据**跑无隐私联邦 | 原型用合成/脱敏数据；真实数据必须等隐私层就位 |

## 6. 落地里程碑（建议，供拍板；不越 Agent24 P4 门）

| 阶段 | 内容 | 风险/门 |
|---|---|---|
| **U0 Spike** | LiteLLM 打通 Anthropic/Gemini，产出"provider×特性"矩阵；llama-swap 跑通"常驻核心 + 临时小模型"最小组合 | 低（本地调研）|
| **U1 统一出口** | 起本地统一 URL：LiteLLM(外部) + llama-swap(本地) 级联，一个 `/v1` 对外 | 低 |
| **U2 订阅中转** | agent-cli-to-api 式 subprocess 封 claude/codex，接入统一 URL，loopback+单用户门禁 | ⚠️ 合规红线 |
| **U3 iDoris Router** | 在统一 URL 之上加意图路由 + 隐私标签 + 业务能力组合；接进 Agent24 `ModelRouter`（`IDORIS_URL`）| 中 |
| **U4 核心模型定选** | 定"推荐常驻核心模型"（推理为主，见文档 02），可换机制 | 低 |
| **U5 自增长/联邦** | 见文档 03（个人本地训练 → 社区联邦 → 城市层级）| ⚠️ 部分越 P4 门，需拍板 |
