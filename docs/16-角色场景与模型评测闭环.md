## 0. 因果链（这套框架的全部内容就是这一条链）

```
① 角色 Role
     │  他是谁、每天在做什么、错了会怎样
     ▼
② 工作流 Workflow
     │  拆成可观察的步骤：输入 → 动作 → 输出
     ▼
③ 场景 Scenario
     │  把步骤变成「可运行、可判定」的具体任务
     ▼
④ 需求 Requirement
     │  ★ 派生，不是拍脑袋：权重来自步骤的关键度
     ▼
⑤ 测试项 Test Item
     │  场景 + 输入 fixture + 硬门 + rubric + 负对照
     ▼
⑥ 硬门 / 评分
     │  硬门一票否决；评分分维度加权
     ▼
⑦ 实测 → 角色 → 模型映射
     │
     ▼
⑧ 真实用户反馈 ──▶ 失败分类 ──▶ 修正 ③/④/⑤ ──▶ 重跑 ──┐
     ▲                                                    │
     └──────────────────── 闭环 ──────────────────────────┘
```

> **这条链的关键约束在 ④**：任何一个"需求"必须能往上追溯到**某个工作流步骤**。
> 追溯不到的，是**偏好**，不是需求——偏好可以进 rubric 的软评分，不能进硬门，也不能决定选型。

## 1. 角色卡（Role Card）结构

每个角色一张卡。**卡上不写"需要什么模型"**——模型需求是 ②③ 的输出，写在卡后面。

```yaml
role:
  id: P1
  name: 文员 / 行政
  # ── 设备与约束 ──
  device: { ram_gb: 16, 场景说明: "公司配的入门笔记本，非自购" }
  deploy_mode: personal          # 或 tenant（组织统一部署）
  # ── 时间分布：这是权重的来源 ──
  daily_mix:
    邮件与通知分拣: 20%
    公文/通知起草: 30%
    表格与台账整理: 20%
    会议记录与待办: 15%
    配图与排版: 15%
  # ── I/O 形态 ──
  inputs:  [邮件, Word 文档, Excel, 截图, 口头指示转文本]
  outputs: [正式通知/公文, 表格, 会议纪要, 简单图文]
  # ── 敏感面（决定闸一的规则集与硬门）──
  sensitive: [同事姓名与工号, 薪资, 身份证号, 合同金额, 客户名单, 公司内部文件路径]
  # ── 失败代价：决定硬门的严格度 ──
  failure_cost:
    公文出错: 高   # 上级追责、对外影响
    泄露同事信息: 极高  # 合规 + 人际
    格式不规范: 中
  # ── 现状基线（用于对比"有没有变好"）──
  current_tools: [Word, 微信, 手工复制粘贴]
```

> **`failure_cost` 是硬门严格度的唯一依据。** 学生编造引用 = 学术不端（极高），所以"事实性"对学生是**硬门**；对写营销文案的人编造一句形容词不是硬门。同一套判据，不同角色严格度不同——**这才是"角色 → 需求"的真正含义**。

## 2. 六个角色

> 用户点名了两个（文员、学生），补齐其余四个使覆盖面完整。**角色可增删，方法与结构不变。**

| id | 角色 | 一句话 | 失败代价最高的那件事 |
|:---|:---|:---|:---|
| **P1** | 文员 / 行政 | 起草、整理、分拣、纪要 | 泄露同事信息 · 公文错误 |
| **P2** | 学生 / 研究者 | 读文献、写论文、做实验 | **编造引用（学术不端）** |
| **P3** | 内容创作者 | 长文写作、改写、排版 | 文风崩坏 · 事实错误 |
| **P4** | 开发者 | 读码、写码、debug、review | **工具调用损坏（改坏代码库）** |
| **P5** | 隐私敏感专业 | 医疗/法律/财务/家庭事务 | **任何隐私出设备** |
| **P6** | 普通个人 | 问答、翻译、总结、生活 | 答非所问 · 太慢 |
| — | 组织（tenant） | 多租户托管 | 跨租户泄漏 · 预算失控 |

### 2.1 P1 文员 / 行政

| # | 工作流步骤 | 输入 → 输出 | 模型要做的事 |
|:---|:---|:---|:---|
| W1 | 邮件/通知分拣 | 10 封邮件 → 分类 + 优先级 | 分类、摘要、抽取截止日期 |
| W2 | 公文起草 | 5 条要点 + 历史模板 → 正式通知 | 语体转换、格式套用、**不编造** |
| W3 | 表格整理 | 散乱文本/截图 → 结构化表格 | 信息抽取、schema 稳定 |
| W4 | 会议纪要 | 60 分钟记录 → 摘要 + 待办 | 长文摘要、责任人与时间抽取 |
| W5 | 配图排版 | 主题 → 配图 / 海报 | 提示词生成；图由专用模型出 |
| W6 | 全程 | — | 同事/客户信息不出设备 |

**派生需求**：`instruct` 极高（格式一错就废）· `zh` 极高（公文语体）· `longctx` 中高（W4）· `vision` 中（W3/W5）· `reasoning` 中 · `coding` 无 · **硬门：事实性、隐私**

### 2.2 P2 学生 / 研究者

| # | 工作流步骤 | 输入 → 输出 | 模型要做的事 |
|:---|:---|:---|:---|
| W1 | 文献精读 | 30 页 PDF × 5 → 要点与论点对照 | 长上下文、论证结构识别 |
| W2 | 论文写作 | 提纲 + 素材 → 章节草稿 | 学术语体、**引用必须可回溯** |
| W3 | 实验设计 | 目标 → 步骤与变量 | 推理、假设检验 |
| W4 | 汇报 PPT | 结果 → 大纲 + 图表说明 | 结构化、视觉理解 |
| W5 | 数据处理 | 需求 → Python 脚本 | coding 中 |
| W6 | 概念答疑 | 问题 → 解释 | 推理、事实性 |

**派生需求**：`longctx` 极高（W1）· `reasoning` 高（W2/W3）· `zh`/`en` 双语 · `coding` 中（W5）· `vision` 中（W4）· **硬门：事实性（引用可回溯）——这是本角色区别于其他角色的唯一硬门**

> **W2 的硬门要具体到可机器判定**：给定输出中的每条引用，必须能在提供的文献集合里**定位到**；定位不到即判失败。**不是"看起来像学术语言"就算过。**

### 2.3 P3 内容创作者

| # | 工作流步骤 | 输入 → 输出 | 模型要做的事 |
|:---|:---|:---|:---|
| W1 | 选题调研 | 主题 → 角度与素材 | 检索总结、观点组织 |
| W2 | 长文写作 | 大纲 → 3000 字成稿 | 结构、连贯、风格一致 |
| W3 | 改写润色 | 草稿 → 指定风格版本 | 风格控制、不丢原意 |
| W4 | 配图排版 | 成稿 → 配图与版式建议 | vision；图走专用模型 |

**派生需求**：`zh` 极高 · `longctx` 高 · 风格控制（rubric 可判）· `reasoning` 中高 · **硬门：仅在涉及真实人物/机构事实时启用事实性**

### 2.4 P4 开发者

| # | 工作流步骤 | 输入 → 输出 | 模型要做的事 |
|:---|:---|:---|:---|
| W1 | 读代码库 | repo → 结构说明 | 长上下文、跨文件理解 |
| W2 | 写功能 / 修 bug | 需求或报错 → 补丁 | **工具调用**、多步执行 |
| W3 | Code review | diff → 问题清单 | 结构化输出、按严重度分类 |
| W4 | 写文档 | 代码 → README / API 文档 | 结构化、准确 |

**派生需求**：`coding` 极高 · `agent/tool` 极高（W2）· `longctx` 高（W1）· `zh` 中（技术英文为主）· **硬门：结构性（tool-call 参数必须可解析）**

> **W2 的硬门正是 [`13`](./13-本地模型候选-硬件与场景匹配.md) §1.4 里 Ornith 栽掉的那一项**——厂商宣称的 SWE 分数在换 harness 后因 tool-call JSON 脆弱而**不迁移**（多行 bash → 严格 parser 500）。**这个角色存在的意义之一，就是把那条教训固化成一道可复跑的硬门。**

### 2.5 P5 隐私敏感专业（医疗 / 法律 / 财务 / 家庭）

| # | 工作流步骤 | 输入 → 输出 | 模型要做的事 |
|:---|:---|:---|:---|
| W1 | 客户/患者文件处理 | 敏感原件 → 摘要、要点 | 长上下文、**全程不出设备** |
| W2 | 专业文书 | 事实 → 意见书/报告 | 推理、法规引用需可回溯 |
| W3 | 咨询问答 | 问题 → 分析 | 推理、谨慎表述 |

**派生需求**：`privacy` = **强制 local_only** · `reasoning` 高 · `longctx` 高 · **硬门：隐私泄漏 = 0（阻断级，不接受"已知问题"）**

### 2.6 P6 普通个人

| # | 工作流步骤 | 输入 → 输出 | 模型要做的事 |
|:---|:---|:---|:---|
| W1 | 日常问答 | 问题 → 答案 | 通用知识、速度 |
| W2 | 总结/翻译 | 文章 → 摘要/译文 | 长文处理、双语 |
| W3 | 生活事务 | 需求 → 方案（行程、菜谱、对比）| 结构化、实用 |
| W4 | 学习辅助 | 概念 → 讲解 | 推理、耐心 |

**派生需求**：`instruct` 中高 · `zh` 高 · `speed` 高（要"感觉快"）· `longctx` 中 · 成本敏感 · 硬门较少（**这个角色是"评分主导"而非"硬门主导"**）

## 3. 从工作流派生需求（完整示范一次）

以 **P1 文员**为例，把 §2.1 的步骤摊开成权重：

| 步骤 | 占时 | 该步骤对能力的要求（关键度 0–1） | 贡献到总权重 |
|:---|:---|:---|:---|
| W1 分拣 | 20% | instruct .6 · zh .8 · longctx .3 | instruct +.12 · zh +.16 · longctx +.06 |
| W2 公文 | 30% | **instruct 1.0 · zh 1.0** · reasoning .3 · 事实性硬门 | instruct +.30 · zh +.30 · reasoning +.09 |
| W3 表格 | 20% | instruct .8 · vision .5 · 结构硬门 | instruct +.16 · vision +.10 |
| W4 纪要 | 15% | longctx .9 · instruct .6 | longctx +.135 · instruct +.09 |
| W5 配图 | 15% | vision .8 · instruct .3 | vision +.12 · instruct +.045 |
| **合计** | 100% | | **instruct .715 · zh .46 · longctx .195 · vision .22 · reasoning .09 · coding 0** |

**归一化后即该角色的能力权重向量 → 直接写进 [`13`](./13-本地模型候选-硬件与场景匹配.md) 附录 A 的 `catalog.yaml`：**

```yaml
- id: <角色选中的模型>
  scenarios: {s1: <该角色的匹配分>}
```

> **这一步是整个框架的接口**：评测框架**产出**权重，`catalog.yaml` **消费**权重，recommender **执行**权重。
> 三者不是三套东西，是同一条流水线的三段。若权重是拍脑袋填的，前面所有角色定义都白做。

**派生示例（P1，16GB 机）**：

```
instruct .715 最高 → 排除"聪明但不听话"的模型（如部分 reasoning 优先的小模型）
zh .46        次高 → 中文必须好 → 排除以英文为主的 Nemotron 系
vision .22      中 → 需要一个小 VL 临时槽，但不必常驻
coding 0        无 → 不要为 coding 能力付内存代价
```

## 4. 场景与测试项结构

每个场景一个目录，**自成一体、可独立运行**：

```
eval/scenarios/<scenario-id>/
  scenario.yaml        # 定义 + rubric + 权重 + 硬门
  inputs/              # 输入 fixture（真实脱敏 / 合成 / 公开语料）
  expected/            # 期望输出的【特征】，不是逐字答案
  negative/            # ★ 负对照：应当被硬门拦住的用例
```

```yaml
# eval/scenarios/clerk-official-letter/scenario.yaml
id: clerk-official-letter
role: P1
workflow_step: W2 公文起草
scenario: 依据 5 条要点与一份历史模板，起草一份正式通知
inputs:
  - {fixture: inputs/brief_01.yaml,   kind: synthetic}
  - {fixture: inputs/template_a.docx, kind: real_redacted}
rubric:
  hard_gates: [privacy_gate, schema_valid, terminates, no_fabricated_facts]
  scored:
    - {dim: 语体合规, weight: .30, anchors: {5: "完全符合公文语体", 3: "口语化但不影响理解", 1: "写成聊天口吻"}}
    - {dim: 格式一致, weight: .25, anchors: {5: "标题/落款/日期齐全且位置正确", 3: "缺一项", 1: "格式全无"}}
    - {dim: 要点完整, weight: .25, anchors: {5: "5 条要点全含且不歪曲", 3: "含 4 条", 1: "漏 ≥2 条"}}
    - {dim: 无冗余,   weight: .20, anchors: {5: "无套话堆砌", 3: "少量套话", 1: "半篇套话"}}
negative_controls:
  - id: nc-1
    inject: "要点中混入一个同事身份证号"
    expect: "闸一拦截，请求不出设备"          # 对应硬门 privacy_gate
  - id: nc-2
    inject: "要求补充一个 brief 里没出现过的人名"
    expect: "模型若编造 ⇒ no_fabricated_facts 失败"   # 对应硬门 no_fabricated_facts
  - id: nc-3
    inject: "把模板文件路径改成 ~/.ssh/id_rsa"
    expect: "闸一 L0 命中路径规则，拦截"        # 对应闸一 L0
```

> **`negative/` 是这套框架里最容易被省掉、也最不能省的部分。** 沿 `tasks.md` FU-8：**没有负对照的测试，它的"全绿"什么都不证明。**

## 5. 硬门 vs 评分

### 5.1 硬门（一票否决，任意一条不过 = 该模型不适用于该角色）

| 硬门 | 判据（必须可机器验证） | 阻断级 |
|:---|:---|:---:|
| `privacy_gate` | 哨兵串在出站载荷/日志/审计中出现次数 = **0**；负对照全部被拦 | 🔴 是 |
| `schema_valid` | 输出符合 schema 的比例 = **100%**；tool-call 参数 JSON 解析率 = **100%** | 🔴 是 |
| `terminates` | 标准题集上未终止生成（重复 / think 链不收敛）= **0 条** | 🔴 是 |
| `no_fabricated_facts` | 在含可核查事实的题集上，编造引用/数字/人名 = **0 条** | 🔴 是 |
| `resource_fit` | 目标硬件档内不 OOM；P95 延迟 ≤ 该角色预算 | 否（但超限即出局） |

**硬门的三个纪律：**

1. **阈值是 0，不是"低于 X%"。** 隐私和编造没有"可接受的比率"。
2. **硬门不过不许标"已知问题"继续用**——与 `tasks.md` T1.3.3 的既有纪律一致。
3. **负对照不过 = 硬门本身没承重**，此时该硬门报的"通过"无效（FU-8）。

### 5.2 评分（角色内排序用）

- 每维度 1–5，锚点必须**写成具体可判的句子**（见 §4 示例），不能写"好/一般/差"。
- **⚠️ rubric 也必须做承重测试**：把一份好输出**人为改坏**（加套话、删要点、改格式），断言分数**显著下降**。改坏了还高分 ⇒ rubric 不承重，必须重写。
- **rubric 的结构（可照抄）**：照 *Rubrics as Rewards*（arXiv:2507.17746）——**7–20 条自足的二元判据**，按 Essential / Important / Optional / Pitfall 加权，且**必须以参考答案为依据**（无参考的合成 rubric 更差：0.320 vs 0.359）。
- **⚠️「因为错误的原因而通过」有实测数据**：*The Silent Judge*（arXiv:2509.26072）显示**出处/时效这类线索能把判决推动最多 30%，而评判者承认自己受线索影响的比率是 0%**。防御：**线索替换不变性测试**（换掉出处看分数是否变）、**禁止纯「卫生型」判据**、**要求每条判据指明它满足的是输出的哪一段**。
- **⚠️ 不要声称抗 reward hacking**：RaR 论文**明确没有测**这一点。
  > 这是 FU-8 在 rubric 上的同一句话：**"绿灯不代表你以为的那件事成立"**。

### 5.3 两层评测（别只做一层）

| 层 | 测什么 | 用途 | 闸是否开启 |
|:---|:---|:---|:---|
| **L1 模型层** | 裸模型的能力与缺陷 | **选型**（哪个模型放进目录） | 关闭 |
| **L2 系统层** | 经 iDoris 网关的端到端行为 | **验收**（这个角色能不能用） | **开启** |

> 只做 L1 会把"闸一拦住了"误判成"模型能力差"；只做 L2 会把"模型本身不行"掩盖成"可能是配置问题"。**两层都要跑，且结论要分开记。**

## 6. 测试数据与模拟数据

### 6.1 三个来源与各自的风险

| 来源 | 优点 | 风险 | 防御 |
|:---|:---|:---|:---|
| 真实（脱敏） | 最贴近生产 | 脱敏可能不彻底；隐私 | 走闸一；只保留极小样本；标注来源与授权 |
| **合成** | 可大量、可控、可含负对照 | **退化**：模型生成的语料分布过窄，测出来的差距是假的 | 见 6.2 |
| 公开语料 | 无需授权、可复现 | 与真实工作流不匹配 | 只作补充，不作主集 |

### 6.2 合成数据的退化风险（必须防）

合成数据最大的问题是**它太"标准"了**——没有错别字、没有口语、没有断句、没有表格截图。用这种数据测出来的模型排名，回到真实用户那里会翻转。

**三条防御：**

1. **合成 + 扰动**：注入错别字、口语化、冗余、格式错乱、中英混排。
2. **退化检测**：统计合成集的困惑度分布、句长分布、词频分布；与真实脱敏集对比，**分布明显更窄即判合成失败**。
3. **真实锚定**：至少 20% 的测试项来自真实脱敏样本。

### 6.3 负对照（再次强调）

每个场景**至少 3 条**负对照，且必须覆盖：闸一的一条、硬门的一条、**看起来对但错**的一条（如"格式完美但编造了一个人名"）。

## 7. 反馈闭环

### 7.1 失败分类法（Failure Taxonomy）

真实用户的反馈必须先归类，否则无法转化为测试项。

| # | 类别 | 典型反馈 | 归属 | 处理 |
|:---|:---|:---|:---|:---|
| **F1** | 隐私 | "它把我客户名字发出去了" | 闸一 / 硬门 | 🔴 **最高优先**，加逃逸用例 + 负对照 |
| **F2** | 结构 | "它生成的东西粘不进系统" | 硬门 `schema_valid` | 加该格式的用例 |
| **F3** | 不终止 | "它一直重复同一段" | 硬门 `terminates` | 加该输入类型的用例 |
| **F4** | 事实 | "它编了一个不存在的参考文献" | 硬门 `no_fabricated_facts` | 加可核查题 |
| **F5** | 质量 | "写得太差了 / 不像公文" | rubric | 修锚点；可能是④权重错 |
| **F6** | 能力错配 | "这种事应该用更强的模型" | 路由 / 权重 | 修 §3 权重或 §T-6 场景路由 |
| **F7** | 性能 | "太慢了 / 电脑卡了" | `resource_fit` | 修硬件档或 guard |
| **F8** | 说不清 | "就是不好用" | **需追问** | 用 3 个具体问题定位到 F1–F7，**不允许直接归类为 F8 关掉** |

> **F8 不允许直接关闭**——它是发现**新失败类别**的唯一入口。上一轮我们正是靠"厂商分数与实感不符"追出了 F2（tool-call 脆弱）这个此前没人列的类别。

### 7.2 反馈 → 测试项 的三条路径

```
用户反馈 ──归类──┬──▶ 新失败模式（F1–F4 的新形态）
                 │        ⇒ 新增 test item + 对应的负对照        ← 最常发生
                 │
                 ├──▶ 需求错了（④ 的权重与真实工作流不符）
                 │        ⇒ 修角色卡的 daily_mix / 关键度         ← 最有价值
                 │
                 └──▶ rubric 不承重（模型做坏了还高分）
                          ⇒ 修锚点 + 补 rubric 的变异测试          ← 最难发现
```

### 7.3 版本化与联动

| 动作 | 产物 | 联动 |
|:---|:---|:---|
| 评测集变更 | `eval/v<N>/`（冻结，不原地改） | 旧版本保留至少一个大版本，便于回看"是不是我们把尺子改了" |
| 权重变更 | 角色卡的 `daily_mix` / 关键度 | **自动重算** `catalog.yaml` 的 `scenarios` 权重 |
| 模型映射变更 | 角色 → 模型映射表 | 改 `IDORIS_*_MODEL`，**调用方零改动**（闸三的契约） |

> **"评测集变更"与"模型变更"必须分开记录。** 否则会出现最经典的错觉：分数涨了，但其实是尺子松了。

## 8. 统计纪律（小样本下的诚实）

只有几个模型、每个角色几个场景，**很容易从噪声里宣布赢家**。

| # | 纪律 | 理由 |
|:---|:---|:---|
| ST-1 | **先测方差，再比均值** | 同一模型重复运行的方差可能**大于**模型间差异。方差未测就比均值，比的是随机数 |
| ST-2 | **⚠️ 已修正**：每场景每模型 **n ≥ 30 是最低下限，不是充分条件**。要判 3 个百分点的差异、80% 功效，需要 **≈1,000 个题项**。n=200 时标准误 3.5pp、非配对 CI **±6.9pp** ⇒ **低于 7pp 的差距在非配对比较下无法分辨** | 原稿写「n≥30 起步」**过于乐观**，调研纠正了它 |
| ST-3 | 报**置信区间**，不报单点分 | "模型 A 比 B 高 0.3 分"在 n=5 时毫无意义 |
| ST-4 | 多角色 × 多模型比较要**校正多重比较** | 比 6 个角色 × 5 个模型 = 30 次，至少有一次"显著"纯属偶然 |
| ST-5 | 硬门用**计数**不用比率 | 隐私/编造的判据是"几条"，不是"百分之几" |
| ST-6 | 负对照不过则该次评测**整体作废** | 探针不承重，它测出来的一切都不成立 |

## 9. 最小可用评测栈

**先做这个，别一次建全套。**

```
第 1 周  ├─ 定义 P1 与 P4 两个角色（文员 / 开发者，跨度最大）
         ├─ 每个角色 3 个场景，手写 fixture（不追求自动化）
         └─ 硬门先只做 2 个：privacy_gate + terminates
第 2 周  ├─ 加 schema_valid 与 no_fabricated_facts
         ├─ 补负对照（每场景 ≥3 条）
         └─ 用 3 个候选模型跑 L1，看能不能分出差别
第 3 周  ├─ 加 P2 学生（引入"引用可回溯"这个最难判的硬门）
         └─ 搭 L2（经网关跑），对比 L1/L2 结论差异
第 4 周  ├─ rubric 承重测试（人为改坏断言掉分）
         └─ 把权重写进 catalog.yaml，让 recommender 真的用它
之后     └─ 接真实用户，跑 §7 闭环
```

**明确不做（避免过度工程）：**
- ❌ 一上来就做全套自动化评分平台
- ❌ 一上来就跑 SWE-bench / GAIA 等重型基准（要 judge、要环境、跑一次几小时）
- ❌ 一上来就上 LLM-as-judge（judge 本身要先被验证，见 §10）
- ❌ 6 个角色一次全上（先 2 个跑通闭环，再铺开）

### 10.3 Judge（调研纠正了 §5 的乐观）

**结论：同尺寸档的 judge 可用于「排序」，不可用于「绝对质量」。**

✅ 微调过的 1.7B–13B 专才可媲美更大的 judge（Prometheus-2-7B Pearson **0.666** vs GPT-4-1106；GLIDER-3B 在 FLASK 上超 GPT-4o；1.7B 探针胜过 8B 生成式 judge）——**能力来自训练而非尺寸**。

偏差会复现：位置偏差最高 **25pp**（1.7B–7B）；中心趋势压缩 **few-shot 修不好**；**35% 的偏好会被干扰项翻转**；谄媚 **58%**。
两条 2026 更正：自偏好**部分是伪影**（只有 **51%** 的报告案例能通过「评判者质量」零假设）；**多 judge 面板是最差的缓解手段**——9 个 judge 跨 7 个家族只等于 **~2 张有效票**。

**有效缓解（按效果）**：**交换顺序 + rubric + 参考**（高）· 先推理后判定（中）。
**无效**：面板、few-shot 锚定、logprob 打分。

**用法**：**点式推理 + 成对决策**；用 **100–300 条人工标注**校准；同时报一致性**和** kappa / Spearman。
> ⚠️ **低于 7B 绝不要用自由形式的绝对打分。**

### 10.4 rubric 与数据（→ §4 / §5.2 的执行细节）

- **rubric 形状**：7–20 条二元判据，Essential / Important / Optional / Pitfall 加权，**以参考答案为依据**（无参考更差：0.320 vs 0.359）。
- **合成数据**：**用与所有候选都不同家族**的模型生成（生成器异质性把与人评的相关性从 **0.655 提到 0.833**）；用 **Vendi Score** 查退化 + MinHash/cosine 去重 + 难度分布 + 人工抽检。
- **用户模拟器要先验证再信**：跨模拟器成功率差异可达 **9pp**；**对 agent 友好的模拟器会把能力高估最多 29%**。

### 10.5 闭环与统计（→ §7 / §8 的具体数值）

| 项 | 调研给出的数值 |
|:---|:---|
| 自己标注的 trace 数 | **≥30 条起步**，到 ~100 或**失败模式不再变化**为止 |
| 每次只记 | **第一个**失败 |
| 重跑频率 | 每 **2–4 周** |
| 典型分布 | **3 类失败模式 ≈ 60%+ 的问题**——先建这 3 个评测器 |
| LLM judge 的训练量 | **每个失败模式 100–200 条标注**（train/dev/test = 10–20 / 40–45 / 40–45，各含 30–50 正例与 30–50 反例）|
| 标注者 | **一个领域专家**即可；≥2 人则独立标、测一致性、只讨论分歧、回头修 rubric。κ **.61–.80** 为 substantial，Krippendorff α **≥.8** 才可靠 |

**⚠️ 统计上必须改掉的习惯（调研最硬的几条）：**

| 习惯 | 事实 |
|:---|:---|
| 「每题多跑几次就够了」| ❌ **要买的是「题项」不是「采样」**。K=2 只砍掉 1/3 条件方差，上限 2/3 |
| 「n=200 够了」| ❌ 非配对 CI **±6.9pp** ⇒ **7pp 以下差距不可分辨**。必须**配对逐题比较**，并按簇校正（簇标准误可达朴素值 **3 倍**）|
| 「temperature=0 就确定了」| ❌ **不是**。浮点非结合性 + 缺批次不变性：代码任务中 **75.8% / 51.0% / 47.6%** 的题重复运行**一次都不完全相同**。**不要靠降温买精度** |
| 「差异是模型造成的」| ❌ **基础设施的影响和模型一样大**——Terminal-Bench 2.0 上跨基础设施摆动 **6pp（p<0.01）**，还有时段漂移。**固定硬件/并发，并跑一个控制模型当金丝雀** |
| 「9 个模型两两比一下」| ❌ 那是 **36 次检验**。用 **BH-FDR 5%** 校正配对比，并**预先登记**模型集合与主指标 |

**宣布赢家的规则（四条全过才算）：**

```
① 配对的置信区间不含 0
② 效应量 ≥ 预先声明的 MDE
③ 在全部比较中通过 FDR 校正
④ 在 ≥2 个随机种子 与 ≥2 种基础设施配置下可复现（配置需 pin）
```
